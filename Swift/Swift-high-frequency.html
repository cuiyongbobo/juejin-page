一、类型与可选值

1. 类、结构体、枚举有什么差别？赋值之后谁和谁共享状态？

口述版

类是引用类型，赋值复制的是引用，两个变量是同一个实例。结构体和枚举是值类型，赋值后各有一份，改副本不影响另一份，改自己要 mutating。值语义不是深拷贝，结构体里的类拷走的仍是引用。共享看的是值语义还是引用语义，值放在栈上还是堆上解释不了这题。

解析

赋值或传参之后，改其中一个名字，另一个名字还能不能看见，取决于复制的是引用还是值。

类复制的是引用。var a = b 之后，两个变量指向同一个实例，改一边的属性，另一边看得到，也可以用 === 判断是不是同一个对象。类可以继承，也可以在 deinit 里做销毁时的收尾。

结构体和枚举复制的是值。赋值之后两边各有一份，改其中一份的存储属性，另一份不会变。方法里要修改自己这份属性，必须标 mutating。枚举用来表示一组互斥状态，不能继承，也没有一套可继承的存储属性布局。

「各有一份」指的是这一层。结构体的属性如果是类，复制走的是那个引用，两个结构体仍然共享同一个对象。

class Room { var name = "A" }
struct Note { var title = "A"; var room: Room }

let a = Room()
let b = a
b.name = "B"            // a.name 也是 "B"

var n1 = Note(title: "A", room: Room())
var n2 = n1
n2.title = "B"          // n1.title 仍是 "A"
n2.room.name = "B"      // n1.room.name 也是 "B"

放在栈上还是堆上，不决定上面的共享关系。小结构体常常在栈上；一旦放进类、逃逸闭包或 any 容器，就可以到堆上。位置变了，该共享的还是共享，该分开的还是分开。

追问

  • 什么时候用类？要对象身份（===）、继承、deinit 里任意一样。都不要，用结构体。一组互斥状态用枚举。
  • let 有什么差别？let 结构体不能改属性。let 类只是不能换引用，对象里面的 var 还能改。
  • public 结构体的成员初始化器，模块外能调用吗？不能。没写 init 时生成的是 internal。自定义 init 写在类型本体里，这份自动生成的就没有了；写在扩展里，自动的还在。类不会按成员生成初始化器。没有父类、所有存储属性都有默认值、又没写任何 init 时，类才有无参 init()。
  • actor 呢？也是引用类型。它和类的差别是隔离，放到并发那一题。

2. 枚举的关联值和原始值有什么区别？

口述版

原始值和关联值是两套声明，同一个枚举不能同时用。原始值在声明时就定好，每个 case 对应一个同类型常量，Int 不写就从 0 递增，用 init?(rawValue:) 还原，对不上是 nil。关联值是创建这个值时才带上的数据，不同 case 的类型可以不同。

解析

原始值是 case 的常量，不是每个实例各自带的一份数据。所有 case 共用一种类型，声明时就定死。Int 原始值省略时从 0 开始递增，这是语言规则。还原必须走可失败初始化器，失败得到 nil，不会崩。

关联值到创建这个值时才放进去。不同 case 可以带不同的类型，运行时这个枚举值只处于其中一个 case。

enum Direction: Int {
    case north // 0
    case east  // 1
}
Direction(rawValue: 3) // nil，对不上不会崩

enum LoadState {
    case success(Data)
    case failure(Int)
}
let state = LoadState.success(Data())

同一个枚举不能一边写 : Int，一边又给 case 带关联值。原始值回答「这个 case 对应哪个固定编码」，关联值回答「这一次的值随身带了什么」。

追问

  • 既要和外部编码对应，又要带一份数据，怎么写？把编码放进关联值，或另写一个计算属性。语言不允许既声明原始值类型，又给 case 带关联值。
  • 为什么不用几个可选属性拼一种状态？可选属性可以同时有值，拼得出非法组合。互斥状态用带关联值的枚举，非法组合写不出来。
  • 枚举在内存里怎么压缩？那是 ABI，别背成语言规则。这题只讲两种声明的差别。

3. 可选值是什么？接口边界怎么处理，什么情况下 ! 是合理的？

口述版

可选值就是 Optional 这个枚举，some 是有值，none 是没有，nil 就是 none。缺值如果是正常情况，用 if let、guard let、可选链或 ??，让调用方看见这个空。感叹号只用于这段代码已经证明一定有值的地方，接口上传进来的数据不要用它赌。空了就说明前提已经破了，用 precondition 早点停，不要造一个假的默认值继续跑。

解析

Optional<Wrapped> 只有两格：.some 里装着值，.none 表示没有。nil 是 .none 的写法，不是「空指针」这个语言概念。引用类型的可选值底层常会借用空表示，结构体的可选值同样成立。

缺值是业务常态时，参数和返回值就该是可选值，调用方必须处理。guard let 失败必须离开当前作用域，所以后面的代码可以依赖绑定成功。某个分支已经证明有值、后面还有很长的代码，用 guard let 把可选值收掉，不要在后面反复 !。

struct Response { var name: String?; var title: String? }
func show(_ response: Response) {
    guard let name = response.name else { return }
    print(name)                         // 这里的 name 不是可选值
    print(response.title ?? "未命名")
}
let createdOutlet: String? = "ready"    // 创建流程已经保证有值
let outlet = createdOutlet!             // 只放在「如果是空，就是写错了」的位置

外部 JSON、网络字段、用户输入都不属于这个位置。「正常情况下都会有」不代表调用方永远不传空。最好的 ! 是让它不再出现。

追问

  • T! 是非可选吗？不是。隐式解包可选值仍然可能是 nil，只是访问时自动强制解包。
  • 缺值时返回 0、空字符串或空对象可以吗？那是另一个值，不是「没有值」。继续跑会产生更难查的错时，用 precondition 或 fatalError。
  • 编译器会不会证明这里不是 nil，然后把判断去掉？你写了 !，失败就会崩。这是运行时陷阱，不是可 catch 的 Error，也不能把优化说成语言保证。

4. is、as、as?、as! 分别做什么？

口述版

is 只得到 Bool，不拿出新类型。as 只用在编译器已经知道一定成功的时候，比如子类转父类。as? 是尝试转换，失败给 nil，外部数据走它。as! 是认定一定成功，失败就崩，所以只能放在前面已经证明过的地方。不确定就不要从 as? 升到 as!。

解析

这四者是一条阶梯：只问是不是，用 is；编译器已经能证明一定成功，用 as；失败是正常情况，用 as?；另有证明、失败就该崩，才用 as!。

class Animal {}
class Dog: Animal { func bark() {} }
let pet: Animal = Dog()

pet is Dog                 // true，原值不变
let dog = pet as? Dog      // Dog?，失败是 nil
let animal = dog! as Animal // 向上转，编译期知道一定成功
// pet as Dog              // 向下转编译器证明不了，不能写裸 as
let forced = pet as! Dog   // 失败就崩

is 不做转换。as 只接受编译期能证明的转换，包括子类转父类，以及语言规定一定成功的桥接，例如 String 到 NSString。向下转、转协议，失败是正常输入时用 as?，结果是可选值，不会抛 Error，也不会崩。

紧接着就要用那个类型时，直接 as? 绑定，少一次 is。JSON、协议容器和框架回调上的失败是数据问题，不是编程前提，不要用 as!。你写哪种，语义就是哪种，不要说成编译器有时会把 as? 变成 as。

追问

  • 先 is 再 as! 稳妥吗？同一处用 as? 一次做完。判断和取值之间如果值还能变，两次就对不上。
  • switch 里的 case let x as Dog 是哪一种？条件转换加绑定，和 as? 同一类，不是裸 as。
  • as! 失败会抛 Error 吗？不会。和强制解包一样，是运行时陷阱。

5. throws、try?、try!、Result 怎么选？defer 什么时候执行？typed throws 适合用在哪？

口述版

错误要交给直接调用方，用 throws。只需要有没有值、原因可以丢，用 try?。失败说明程序写错了，用 try!。成功和失败要存起来或交给回调，用 Result。defer 在作用域因 return、throw、break、continue 离开时执行，后写的先执行。fatalError 这种不展开栈的路径不会执行它。typed throws 适合模块内部和要把错误类型传下去的泛型；公开接口继续用普通 throws，否则以后多一种失败就可能破坏调用方的穷尽处理。

解析

先分两路。失败要顺着调用栈交给直接调用方，用 throws，签名里看得见失败，调用方必须 try。成功和失败要当成一个值保存、传给回调、稍后再打开，用 Result。它不自动往外抛，谁拿着谁打开。

普通 throws 的错误类型是 any Error。throws(MyError) 之后，catch 可以直接拿到这个具体类型。公开接口一旦写出具体错误类型，增加 case 或换类型都可能破坏调用方已经写死的穷尽处理。这是兼容性承诺。

func use() throws {
    defer { print("1") }
    defer { print("2") }   // 离开时先 2 再 1
    try work()             // return 和 throw 都会跑到 defer
}
let value = try? work()   // 失败变成 nil，错误对象没了
let forced = try! bundledResource() // 只有「失败代表程序写错」才这样写

defer 用来做必须成对的收尾：加锁解锁、开始结束、注册反注册。fatalError、precondition 失败和真正的崩溃不展开栈，defer 不会跑。它不是「进程怎么死都会执行」的保险。throws 底层怎么传递错误是 ABI，面试讲到调用方看不看得见失败即可。

追问

  • try? 之后还能拿到原始错误吗？不能。错误在这一步已经被丢掉，日志、恢复、区分错误种类都不要走它。
  • 循环里的 defer 什么时候跑？每一次迭代结束就执行，不是函数最后才执行。
  • 怎么从 Result 回到抛出？对它 try get()。try? 和 try! 都不会自动变成 Result。

二、属性、访问控制与泛型

6. 存储属性、计算属性、lazy、属性观察器有什么区别？扩展为什么不能加存储属性？

口述版

存储属性占实例的位置，计算属性只是 getter 和 setter，不占位置。lazy 仍是存储属性，第一次访问才创建，所以只能是 var，而且不保证多线程只创建一次。willSet 拿得到新值，didSet 拿得到旧值；本类型初始化器里的赋初值不触发观察器，子类在 super.init 之后改父类属性会触发。扩展不能加存储属性，因为那会改变已经确定的实例布局。

解析

这题按值存在哪、什么时候写入、写入时要不要通知来分。存储属性参与实例布局，下一次还能原样读到。计算属性没有自己的存储，读的时候现算，写的时候转交出去，不算实例大小。

struct Counter {
    var stored = 0
    var doubled: Int { stored * 2 }
    lazy var heavy = Array(repeating: 0, count: 1000)
    var observed = 0 {
        willSet { print("将变成", newValue) }
        didSet { print("原来是", oldValue) }
    }
    init() {
        observed = 1 // 本类型的初始化器赋初值，不触发观察器
    }
}

lazy 仍然占存储，只是第一次访问才创建，所以不能是 let。类型系统只保证它延迟初始化，不保证线程安全。多个线程可能同时第一次碰到它时，用锁、actor，或在外部显式初始化。

观察器是初始化完成之后的赋值通知。子类初始化器在 super.init 之后再给父类属性赋值，会调用父类的观察器。这是语言规则。

扩展可以加计算属性、方法、初始化器和协议遵循，不能加存储属性。存储属性会改变实例大小和偏移，已经编译出的布局对不上。

追问

  • 关联对象能证明扩展可以加存储属性吗？不能。objc_setAssociatedObject 是 Objective-C 运行时给对象挂的旁路表，不是实例布局里的字段，结构体也没有这条路。
  • lazy 第一次初始化走观察器吗？第一次按初始化写入，不走观察器；之后再赋值才走。多线程同时第一次访问，不保证只创建一次。
  • 观察器里可以再写回同一个属性吗？不要。容易递归。

7. static 和 class 修饰类型成员有什么区别？

口述版

static 和 class 的差别就是这个成员能不能被子类重写。static 四处都能用，用在类上等于 class final，子类不能重写。class 只能修饰类的类型方法和计算类型属性，子类可以 override；存储属性不行。static 只让这一个成员不能被重写，不是把整个类标成 final。别的模块也要重写，类和成员还得是 open。

解析

这题问的是类型成员能不能被子类换掉，不是整个类能不能被继承。想锁住整类，给类加 final。

class Node {
    static var count = 0
    static func make() -> Node { Node() }
    class func describe() -> String { "node" }
    class var title: String { "node" }
}
class Leaf: Node {
    override class func describe() -> String { "leaf" }
    // override static func make() 不行
    // class var count 也没有这种存储语法
}

static 可以修饰类、结构体、枚举和协议的类型成员。出现在类上时，这个成员不能被重写，语义就是 class final。class 只能用在类上，修饰类型方法或计算类型属性，子类写 override class。

追问

  • 类型上要存一份数据，写成 class var 行吗？不行。存储类型属性只能 static。class 没有存储属性这条语法。
  • 本模块里能重写，别的模块是不是也能？不是。跨模块重写要求类和这个成员都是 open。
  • static 方法怎么派发？不能重写，调用目标在编译期可以确定，走直接调用。会不会再内联，不保证。派发的完整规则在方法调用那一题。

8. 访问控制从宽到窄是什么？private 和 fileprivate 差在哪？

口述版

访问级别从宽到窄是 open、public、package、internal、fileprivate、private，不写就是 internal。open 才能在别的模块被继承和重写；public 是别的模块能用，但不能在别的模块继承，本模块里仍然可以。package 是同一个包，internal 是当前模块。fileprivate 是整个源文件，private 是当前声明，再加上同文件里这个类型自己的扩展。对外签名不能比它暴露出来的类型更宽，setter 可以单独收得更严。

解析

访问控制是编译器在检查谁能看见这个名字，不是运行时再拦一层，也不是编译器优化。package 从 Swift 5.9 起就是语言级别，对应同一个 package，不是同一个文件夹。

级别谁可以访问
open其他模块可以访问，也可以继承、重写
public其他模块可以访问；不能在其他模块继承或重写。本模块里仍然可以，除非另外标了 final
package同一个 Swift package
internal当前模块。不写就是它
fileprivate当前源文件里的所有类型
private当前声明，加上同一文件里这个类型自己的扩展
 
struct Account {
    private var pin = "1234"
    fileprivate var id = "a"
    private(set) var balance = 0
}
extension Account {
    func readPin() -> String { pin } // 同类型、同文件，private 看得见
}
struct Audit {
    func read(_ account: Account) -> String { account.id }
    // account.pin 看不见：private 不给同文件的其他类型
}

private 不是「只有这一对花括号」。public 也不是「任何地方都不能继承」，缺的主语是「其他模块」。

追问

  • open 能用在结构体上吗？不能。它只用于类和类的可重写成员。
  • 对外只读、对内可写怎么写？setter 单独收窄，例如 private(set) 或 fileprivate(set)。
  • 类型用到了更窄的类型，自己就不能更宽吗？内部实现可以用更窄的类型。不能更宽的是继承、属性、参数和返回值这些对外签名。public 方法不能暴露 internal 的参数或返回值。

9. 泛型解决什么问题？它和 Any 有什么差别？

口述版

泛型是把类型做成参数，同一套逻辑在调用点仍然做类型检查。T: P 是要遵循协议，T: AnyObject 是要类，T: SomeClass 是要这个类或子类。Any 什么都能装，用的时候原来的类型已经没了；AnyObject 只表示类实例。协议里的占位类型是关联类型，where 用来加更细的约束。编译器有时会按具体类型做特化，那是优化，语言不保证每次都发生；没特化也不等于变成了 Any。

解析

泛型解决的是复用一份实现，同时把类型关系留在编译期。每次调用的 T 是一个具体类型，返回值、参数之间可以保持同一个 T。写错约束会编译失败，不是运行时再碰运气。

func first<T: Equatable>(_ items: [T], equalTo target: T) -> T? {
    items.first { $0 == target }   // T 在这个调用点是具体类型，== 编译期就查得过
}
let box: [Any] = [1, "a"]
let text = box[1] as? String       // 拿出来已经不知道原来是什么

Any 和 AnyObject 都是类型擦除之后的结果。前者装任意类型，后者只表示类实例。T: AnyObject 是泛型约束，约束的是「这个类型参数必须是类」，它自己不是 Any。T: SomeClass 约束的是继承关系。

协议里要等遵循者来填的类型写成关联类型，例如集合的元素。它不是调用时随便换的参数。where 给泛型或扩展加附加约束。

追问

  • 元素其实都遵循同一个协议，为什么不要先装进 Any？擦掉之后，相等、下标和具体方法都要靠运行时转回来。能写成泛型或 some 时，不要先擦成 Any。异构、又没有共同操作，才用 Any。
  • 没被特化时调用协议方法，类型还安全吗？安全。泛型协议约束会带着见证表调用，仍然是泛型，不是退回 Any 或消息发送。特化在跨模块、又看不到函数体时不保证发生。
  • 数组什么时候才遵循某个协议？那是条件遵循，单独一题。这里只记：where 不满足，这个遵循在编译期就不存在。

三、内存、闭包与拷贝

10. ARC 是什么？strong、weak、unowned 怎么选？

口述版

ARC 是类和 actor 的自动引用计数，强引用到 0 就同步 deinit，不是垃圾回收，也拆不掉循环引用。属性默认 strong，会把对象留住。weak 不增加计数，对象没了会自动变 nil，所以必须是可选 var，而且这次置空不走属性观察器。unowned 也不增加计数，但不会变 nil，只有确定对方活得更久才能用，对象没了再访问会崩。谁先死不确定就用 weak。结构体和枚举没有引用计数，不能 weak。

解析

ARC 只管类、actor，以及限定为类的协议（: AnyObject）。编译器在引用赋值和失效时插入记账：强引用加一，最后一条强引用消失就减到 0，对象立刻进入 deinit。它不是过一会儿再来扫的垃圾回收。互相强引用时，环上的计数不会自己变成 0，环的那一条改成 weak，通常是不拥有对方的那一方。

class Owner {
    var child: Child?
    weak var delegate: OwnerDelegate?
    unowned let parent: Owner
    init(parent: Owner) { self.parent = parent }
}

需要把对象留住，用默认强引用。两边谁先销毁不确定，或者销毁之后访问应该变成「没有」，用 weak。它必须是可选的 var。运行时把 weak 清成 nil 时，直接写空，不调用 willSet / didSet。

unowned 的前提是被引用的对象一定活得更久，例如它拥有我、我不可能活过它。拿不准就用 weak。多一次可选绑定，比崩溃便宜。unowned 不是可选值，对象释放后继续使用会立刻陷阱。

追问

  • deinit 在哪个线程跑？纯 Swift 对象，最后一条强引用在哪个线程消失，就在那个线程同步跑。路过 Objective-C、进了自动释放池的对象，release 可能要等池子排空。不要把「计数到 0 就立刻 deinit」说成所有桥接对象的绝对时序。
  • unowned 和 unowned(unsafe) 呢？普通 unowned 仍会在使用时检查对象还在不在。unowned(unsafe) 连这个检查都没有，用错是未定义行为。面试说的 unowned 不是后者。
  • 优化会不会把「最后一条强引用消失才销毁」优化掉？不会。编译器可能省掉成对的 retain/release，不会改变这条规则。weak 靠运行时的旁路记录在对象死亡时置空，所以有额外开销。

11. 这段代码为什么循环引用？weak 和 unowned 怎么选？

口述版

这段代码成环，是因为 Owner 的属性强引用闭包，闭包又默认强引用 self，两边计数都到不了 0。捕获列表写在参数前面，用来改这次捕获的方式。谁先释放不确定，用 weak，self 先没就变成 nil。unowned 也不增加计数，但不会变 nil，只有闭包一定活不过对象才用，否则对象释放后再调用会崩。拿不准就 weak。写出 self 本身不是 weak。

解析

对象强引用闭包，闭包又强引用对象，两边的 deinit 都不会发生。捕获列表只决定这一次捕获是不是强引用。不写，抓到的就是强引用。逃逸闭包里要求你写出 self，只是让捕获看得见，不会把强弱改掉。

class Owner {
    var work: (() -> Void)?
    func start() {
        work = { self.doWork() }          // 属性强引用闭包，闭包强引用 self
    }
    func startSafely() {
        work = { [weak self] in self?.doWork() }
    }
    func doWork() {}
}

闭包存在属性、回调、定时器里，页面或对象可能先消失，用 [weak self]，里面用 self? 或 guard let self。闭包只被这个对象持有，而且不会被拷给更长寿的一方，对象释放前不可能再调用，才可以 [unowned self]。闭包一旦逃到对象外面，这个前提通常就不成立。

追问

  • 捕获列表写在哪？参数列表前面：{ [weak self] in ... }，有参数就是 { [weak self] value in ... }。写到参数后面就不是捕获列表。
  • 闭包存在 self 的属性里，就可以一律 unowned 吗？不行。只要这个闭包还能被赋值到别处，unowned 就会悬空。说不清还会不会被别人留住，用 weak。
  • 成环是因为闭包在堆上吗？不是。闭包作为引用类型放在堆上，是实现方式。成环的原因是两边都是强引用。编译器不会自动把存进属性的闭包改成 weak。

12. 闭包是引用类型吗？@escaping 改变了什么？为什么逃逸闭包不能捕获 inout？

口述版

闭包是引用类型，赋值复制的是引用，两个变量是同一个闭包。它默认捕获的是外面的变量绑定，不是当时的一份拷贝；捕获类实例时默认是强引用。要留下当时的值，就在捕获列表里写成 [n = n]。函数参数上的闭包默认不逃逸，返回后不能再调用；@escaping 才允许存起来稍后执行。inout 只在这次调用期间独占外面的变量，函数返回时这次访问就结束，所以逃逸闭包不能捕获它，不逃逸的可以。@escaping 不会把捕获改成 weak，它只要求把 self 显式写出来。

解析

这题有三层：闭包这个值是不是引用，它能不能活过这次函数调用，它捕获的是一份快照还是外面那个变量。复制闭包变量，得到的是同一个闭包，不是把闭包体再复印一份。

var saved: (() -> Void)?
func run(body: () -> Void) { body() }
func store(body: @escaping () -> Void) { saved = body }

var n = 1
let seeLater: () -> Int = { n }
n = 2
seeLater()                    // 2，双方看见的是同一个变量
let snap: () -> Int = { [n] in n } // 留下捕获当时的 1

func bump(_ value: inout Int, body: (inout Int) -> Void) {
    body(&value)              // 非逃逸，调用还在这次 inout 访问之内
}

函数参数的闭包默认非逃逸，例如 map 的变换，函数返回后不能再调用，所以可以捕获 inout。@escaping 允许闭包活过这次调用。inout 是临时把外面那个变量的独占使用权借给你，返回时必须写回并结束访问。带出函数的闭包不能夹走这次借用。

类实例默认按强引用捕获。可能成环，要在捕获列表写 [weak self]。只是把 self. 写出来，仍然是强捕获。

追问

  • 不捕获上下文的闭包一定在堆上吗？语言层面按引用类型理解闭包值。不捕获上下文时，编译器有时会当成全局函数，不一定分配闭包对象。这是优化。需要把上下文留到函数之外时，实现上会把捕获放到堆里，那也不是你要背的分配承诺。
  • 属性里的函数类型要标 @escaping 吗？属性里的函数类型本身就是逃逸的。参数要存进属性、交给别的对象、或在函数返回后才调用，才给参数标 @escaping。
  • 不能捕获 inout 是编译器没做优化吗？不是。非逃逸让编译器更容易把捕获放在栈上，那是优化。能不能捕获 inout 是访问期限：借用不能活过函数返回。

13. 为什么 Array、String、Dictionary、Set 是值类型？copy-on-write 怎么发生？自定义结构体为什么不会自动有？

口述版

Array、String、Dictionary、Set 做成值类型，是为了赋值之后各改各的，不共享可变状态。copy-on-write 不是语言给所有结构体的承诺，而是这几个类型的实现：变量里存的是一块内存的地址，赋值复制的是这个地址，元素还在同一块内存里。要改的时候，如果这个地址还有别人拿着，就新开一块内存，把元素复制过去再改；只剩自己拿着，就在原来那块上改。自己写的结构体只拷贝存储属性，不会自动做这套检查。

解析

语言保证的是值语义：赋值、传参之后，修改这一份，另一份观察不到。copy-on-write 是标准库为了让这份语义便宜，用在这四个类型上的实现。编译器不会看见结构体就自动插入唯一性检查。

变量里存的是内存地址，元素在这块内存里。赋值复制的是地址，两边地址相同，读和单纯赋值可以很便宜。要修改并且这个地址还有别人拿着，才新开一块内存，把元素复制过去，换成新地址再改。只剩自己拿着，就直接改。检查失败就必须复制，否则就破坏值语义。这不是「编译器也许会优化掉复制」。

自定义结构体赋值，拷贝的是它的各个存储属性，没有自动的「整份结构体唯一化」。要给自己的大块缓冲区做延迟复制，就用一个类握住数据，修改前看强引用是不是只剩这一份。

final class Storage {
    var items: [Int]
    init(_ items: [Int]) { self.items = items }
}
struct Queue {
    private var storage = Storage([])
    mutating func append(_ n: Int) {
        if !isKnownUniquelyReferenced(&storage) {
            storage = Storage(storage.items)
        }
        storage.items.append(n)
    }
}

追问

  • 结构体里放一个 Array，要不要自己再写一套？不用。结构体赋值拷走的是数组这个值，缓冲区仍由数组自己的 copy-on-write 管。属性若是类，拷走的是引用，值语义在这一层已经破了。
  • isKnownUniquelyReferenced 是锁吗？不是。它只看这一刻是不是只有一条强引用。两个线程同时通过检查，仍然会改到同一块存储。线程安全用 actor 或锁。
  • 标准库缓冲区里有哪些字段？面试讲清「赋值复制地址，要改并且还有别人拿着才复制」即可。某个版本的缓冲区字段不是语言规范。

四、协议

14. 为什么说 Swift 是面向协议编程的？

口述版

Swift 面向协议，是因为结构体和枚举也能遵循协议，复用能力不用先继承一个类。协议扩展可以给默认实现，旧类型也能事后补上能力。需要什么能力就组合什么协议。只有要区分是不是同一个对象、要继承，或者要在 deinit 里收尾，才用类。面向协议不是禁止用类。

解析

面向协议复用的是「有没有这套能力」，不是「在继承树上的哪一层」。谁能把协议要求做完，谁就能用这套 API，不管它是类、结构体还是枚举。协议扩展给大多数遵循者一份默认做法，后来的类型不用先认一个父类。

protocol Named { var name: String { get } }
extension Named {
    func greeting() -> String { "Hi, \(name)" }
}
struct User: Named { var name: String }
User(name: "Lin").greeting()

大部分类型的实现相同，就把默认实现写在扩展里，并且放进协议要求。不放进要求，具体类型的同名方法不一定会被调用。类仍然是引用类型，身份、继承和 deinit 都是它的语言能力。这题是设计规则：默认实现最终走直接调用还是见证表，由它是不是协议要求决定。

追问

  • 扩展里的默认同名方法，通过协议调用一定能找到类型自己的实现吗？不一定。没写进协议要求的方法不会进见证表。这是第 17 题。
  • 只是为了复用几行代码，要不要建一个类继承树？先看是不是真的需要身份、继承或 deinit。没有身份需求时，类继承是在主动共享可变状态。

15. Swift 协议和 OC 协议有什么区别？

口述版

Swift 原生协议让结构体和枚举也能遵循，可以有关联类型和默认实现，但不能写 optional，调用靠见证表按下标找实现。@objc 的 optional 要求协议和方法暴露给 Objective-C，遵循者必须是类，调用按方法名走 objc_msgSend，结构体和枚举进不来。Swift 里想要「可以不写」，通常是拆小协议，或在扩展里给默认实现。默认实现是一定有一份，optional 是可能没有。

解析

两套协议的差别，来自两套「按协议找实现」的机制。Swift 原生协议为每个「类型 + 协议」生成见证表：左边是协议要求，右边是这个类型的实现，调用时按下标取。Objective-C 协议没有这张卡，调用变成 objc_msgSend，拿着方法名（选择子）去类里按名字找。

protocol Drawable {
    func draw()
}
extension Drawable {
    func draw() {}          // 默认实现一定存在
}
@objc protocol Clickable: AnyObject {
    @objc optional func click() // 可以不实现，调用前要知道它可能没有
}
Swift 原生协议标了 @objc 的协议
谁能遵循类、结构体、枚举必须是类
要求怎么写可以有关联类型和默认实现，不能写 optional 要求可以写 optional，不能有关联类型
怎么找到实现见证表，按下标objc_msgSend，按方法名
缺这个方法时没有默认实现就不通过编译optional 方法可以不实现

必须跟现有 Objective-C 委托、可选回调兼容时，协议和方法标 @objc，遵循者用类，调用 optional 前按可选方法处理。不要用 OC 的 optional 来模拟「给一批遵循者一个默认做法」。

追问

  • 只加 @objc，Swift 里的调用就按方法名找了吗？没有。只加 @objc 是把声明暴露给 OC。从 Swift 直接调用一个类方法时，仍可能走虚表。要保证 Swift 调用也按方法名查找，需要 dynamic。这个差别在方法派发那一题展开。
  • 见证表的槽位顺序要背吗？不用。它是遵循关系生成的代码结构，不是可有可无的优化；具体怎么排槽位是 ABI。

16. some 和 any 差在哪？

口述版

some 背后是一个具体类型，any 是把具体类型擦掉之后的存在类型。返回 some P，底层是函数作者选定的一种类型，每条路径都必须相同，调用方看不见名字。参数上的 some P 就是泛型，类型由调用方决定。any P 里同一个值前后可以装不同的遵循者，调用时要查见证表。不需要把不同具体类型装进同一个值，就优先 some。some 不是「任意类型」，any 也不是父类。

解析

先问两件事：具体类型是谁定的，调用方能不能把不同的具体类型装进同一个值。类型固定而且不需要擦掉，用 some；每次可能是不同遵循者，又要放进同一个值，用 any。

protocol Greeter { func hello() -> String }
struct Pirate: Greeter { func hello() -> String { "Ahoy" } }
struct Robot: Greeter { func hello() -> String { "Beep" } }

func one() -> some Greeter { Pirate() }
// func mixed() -> some Greeter { Bool.random() ? Pirate() : Robot() } // 两条路径不是同一种类型

func greet<T: Greeter>(_ value: T) {}
func greetSome(_ value: some Greeter) {} // 参数上的 some 就是这种泛型简写

var crowd: [any Greeter] = [Pirate(), Robot()]

返回位置的 some P 是不透明类型：整个函数只有一个底层具体类型，调用方不能点名这个类型，也不需要先擦成 any 再返回。参数位置的 some P 由调用方在每次调用时决定。两次调用可以是两种类型，同一次调用里就是一个 T。

any P 是存在类型。同一个变量前后可以装不同的遵循者，这些类型之间不必有继承关系。调用协议要求时通过见证表。要 Pirate 和 Robot 放进同一个数组，就得用它。

追问

  • any 会不会总是在堆上？值放不进缓冲区时，常见实现会把值放到堆上。缓冲区多大是 ABI，不要背一个字节数，也不要说 any 永远在堆上。上不上堆不是改选 some 的唯一理由；不需要异构存储时，优先把具体类型留在编译期。
  • 盒子上调不了依赖 Self 或关联类型的方法，就改回继承吗？先不要。那是第 18 题：关联类型被擦掉之后，用到那个类型的方法停在盒子外面。
  • 底层类型已知时，调用还查存在容器吗？按这个具体类型派发，不必查存在容器里的见证表。会不会再把函数体内联进去，不保证。

17. 协议扩展里写了方法，为什么有时调用不到类型自己的实现？

口述版

先看这个方法有没有写进协议要求。写进去了，见证表就有这个方法的槽位，通过 any 或泛型调用也会找到类型自己的实现；类型没写，才落到扩展里的默认实现。只写在扩展里、协议没要求的方法没有这个槽位，编译器按静态类型直接调用。所以 g 是 any Greeter 时，hello 是 Pirate 的 Ahoy，bye 却是扩展里的 Bye。把 bye 补进协议要求，才会调到 Arr。

解析

调用时编译器手里有没有一个固定槽位，决定它会不会去查见证表。写进协议要求的方法有槽位，类型自己写了就填自己的，没写就填扩展里的默认实现。只写在扩展里的方法是按当时看见的静态类型直接调用的。

protocol Greeter {
    func hello() -> String
}
extension Greeter {
    func hello() -> String { "Hello" }
    func bye() -> String { "Bye" } // 不是协议要求
}
struct Pirate: Greeter {
    func hello() -> String { "Ahoy" }
    func bye() -> String { "Arr" }
}
let pirate = Pirate()
pirate.bye()                 // "Arr"，静态类型就是 Pirate
let g: any Greeter = Pirate()
g.hello()                    // "Ahoy"，要求在见证表里
g.bye()                      // "Bye"，按 any Greeter 直接调扩展

希望通过协议类型调用时仍然执行每个类型自己的版本，就把方法写进协议要求，默认实现可以放在扩展里。这个方法只是给某个具体类型用的便利函数，不需要被动态替换，才可以只写在扩展里。静态类型已经是具体类型时，编译器可以直接调用那个类型的方法；会不会再内联，是优化。

追问

  • 静态类型本来就是 Pirate 时，bye() 调谁？调 Pirate.bye()。意外只发生在静态类型只剩协议或未打开的泛型约束的时候。
  • 是不是「扩展里的方法都是静态派发」？不是。协议要求的默认实现仍然在见证表里，具体类型的实现会替换那一格。没写进要求的方法才没有槽位。
  • 这是子类 override 吗？不是。这里没有子类覆写，只有有没有协议要求。编译器也不会在你没把方法写进协议时，自动改去调用具体类型的同名方法。

18. 带关联类型的协议为什么往往不能直接写成 any？主关联类型解决了什么？

口述版

带关联类型的协议，以前常常连 any 都不能写，只能当泛型约束。Swift 5.7 之后可以写 any Collection，但元素类型已经被擦掉，所以 any RangeReplaceableCollection 不能直接 append，编译器不知道放进什么。主关联类型就是把最常用的那个类型写进尖括号，any Collection<String> 把元素定成 String，用到元素类型的方法才能用。方法如果要求必须是同一个具体 Self，any 上还是调不了，因为调用方不知道这个存在类型里面的具体类型，传不进一个对得上的值。

解析

这题要分成两句：现在能不能把这个协议写成 any，以及写成 any 之后还剩哪些方法可调用。Swift 5.7 之前，关联类型还没确定时，这类协议通常不能作为存在类型使用，只能当泛型约束，例如 T: Collection。现在能写，限制跑到了「哪些成员还能调用」。

关联类型是协议里的一个空格，遵循者才填写。盒子如果没把空格填上，调用方就不知道该拿什么类型的值去配这个方法。any Collection 把 Element 擦掉了，不依赖元素具体类型的操作还在；any RangeReplaceableCollection 不能直接 append，因为编译器不知道该放进什么。

func add(_ bag: inout any RangeReplaceableCollection) {
    // bag.append(...) 编译不过：元素类型已经被擦掉
}
func addString(_ bag: inout any RangeReplaceableCollection<String>) {
    bag.append("a") // 主关联类型把 Element 定成 String
}
func same(_ a: any Equatable, _ b: any Equatable) -> Bool {
    // a == b 编译不过：== 要求同一个具体 Self
    false
}

主关联类型把最常用的那个空格印回尖括号。any Collection<String> 表示元素已经确定是 String，参数或返回值只用到 Element 的方法就可以调用。它没有保留「和盒子里同一个具体类型」的另一个值，所以要求 Self 的方法仍然不可用。

追问

  • 加上 <String> 之后，要求 Self 的方法就能用了吗？不能。主关联类型补的是那个关联类型，不是盒子里的具体 Self。两个 any Equatable 仍然不能直接 ==，两边可能是不同的具体类型。
  • 调不了的时候怎么用？把盒子传进泛型函数，让函数打开这一次的具体类型，再在里面使用。这是语言规则里的打开方式，不是偶然优化。
  • 整个 API 都能确定一种具体集合呢？返回 some Collection<String>，不要先装进 any。主关联类型没有把协议变成一个新的运行时对象，会不会因此少一次堆分配，不要当成保证。

19. 什么是条件遵循？[String] 为什么可以是 Sendable？

口述版

条件遵循就是类型参数合格，外层类型才遵循协议。Array 只有在 Element 是 Sendable 时才是 Sendable。Sendable 表示这个值可以交给别的任务或 actor，不会因此数据竞争；值类型传过去的是副本。String 满足，所以 [String] 满足。元素若是普通可变类，类本身不行，数组也不行。这是编译期就决定的，不是运行时再扫一遍元素。

解析

条件遵循是编译期规则：where 里的约束满足，这个遵循才存在；不满足，就好像没有写过这个遵循。标准库的数组是 Element: Sendable 时才遵循 Sendable。

extension Array: Sendable where Element: Sendable {}
let titles: [String] = ["a"]   // String 满足，[String] 就满足
// let views: [UIView] = []    // 元素不是 Sendable，数组也不是

[String] 能跨任务传递，是因为 String 这个类型已经满足，传过去的是值的副本。不是运行时检查了每个元素再决定让不让传。约束满足时，这个具体数组类型的遵循关系就参与普通的见证表派发；不满足就编译失败。编译器不会在运行时临时补一张表。

Sendable 是标记协议，不是一把运行时的锁。它表示值跨越并发隔离域不会因此数据竞争。元素是普通可变类时，不要把数组标成可以传递；先把类收成不可变且满足条件，或者把共享状态关进 actor。

追问

  • 所有数组都是 Sendable 吗？不是。[UIView] 这种元素不是。外壳救不了里面共享的可变对象。
  • 自己的泛型类型想要同样的行为，怎么写？extension Box: Sendable where T: Sendable。不要无条件声明 Sendable。
  • Sendable 会不会顺便保证复制很便宜？不会。它管的是有没有数据竞争，不管复制成本，也不会把值类型变成加锁或者深拷贝工具。

五、方法调用与对象布局

20. Swift 方法调用是如何实现的？

口述版

方法调用就记一句：编译时能确定就跳，不能确定就查表，连固定槽位都没有就按名字找。结构体、枚举、final、private、static，以及协议扩展里多出来的方法，都是直接跳。类里可重写的方法走虚表，子类重写就是换掉一格。协议要求走见证表，泛型有时会被特化成直接调用，那只是优化，语言不保证。dynamic 和重写 OC 方法才走 objc_msgSend，按选择子查缓存和方法列表。只加 @objc，Swift 里的直接调用仍可能走虚表。内联同样只是优化。

解析

能在编译期确定唯一函数，就直接跳。不能确定、但有固定槽位，就查表。连槽位都没有、只能按方法名找，就走消息发送。

方式怎么找到函数用在哪
直接调用调用点已经知道唯一的函数结构体和枚举的方法；类里的 final、private、static；协议扩展里多出来、不是要求的方法
虚表对象的类指针加上下标类里可以重写的实例方法
见证表按协议要求的槽位取出这个类型的实现通过 any P，或还没特化的泛型约束调用协议要求
objc_msgSend按选择子查缓存、方法列表，再沿父类找标了 dynamic 的成员，以及重写了 Objective-C 方法的成员

结构体、枚举没有子类能替换方法，所以目标可以在编译期确定。final、static、private 的类成员不能被重写，语言规则允许直接绑定到唯一实现。类的可重写方法用虚表。协议要求用见证表，类型遵循协议时生成这张表，每个要求对应一个实现。

dynamic 强制这个成员走 Objective-C 消息发送。只加 @objc 是把声明暴露给 OC：OC 那边按名字发消息，Swift 这边的直接调用不因此自动改成 objc_msgSend。只是要让 OC 能调用这个 Swift 方法，@objc 就够了。要给 OC 运行时替换实现、做 KVO，或者这就是在重写 OC 方法，才需要 dynamic。消息发送会使用缓存，缓存不改变「按选择子查找，找不到再问父类」这个规则。

追问

  • 内联算第四种派发吗？不算。它是已经确定的函数体可能被嵌进调用点，也可以不嵌。不能说「直接派发就一定会内联」。
  • 没被特化的泛型是不是退回 Any 或消息发送？不是。仍然通过见证表调用，类型还是安全的。同一个模块里把虚表调用还原成直接调用，也是优化；跨模块、看不见唯一实现时，语言不保证。
  • 见证表就是类的虚表吗？不是。虚表跟着类的继承走，对象开头的类指针指向它，子类重写换掉其中一格。见证表跟着「哪个类型遵循哪个协议」走，不属于某一个对象。

21. Swift 协议的内部结构是什么？

口述版

协议自己不占对象内存，编译出来的是一份说明：名字、继承了谁、有哪些方法、属性和关联类型。某个类型一遵循，就另生成一张见证表，每个要求一格，指向这个类型的实现，没写就指向默认实现。所以调用协议方法不是在协议上找函数，而是拿这张表按下标跳。表属于「类型加协议」这份遵循，不是每个实例各藏一张。

解析

协议不是一个可实例化的基类，也不在每个遵循者对象头部占一份「协议字段」。它是一份要求清单。存储在遵循这个协议的类型自己的布局里，所以协议本身不让实例变大。

东西是什么什么时候出现
协议描述名字、继承的协议、要求列表编译这个协议时。不跟着每个实例复制
见证表每个协议要求一个槽，指向实际实现或默认实现每个「具体类型 + 协议」的遵循
调用拿到对应的见证表，按下标跳到函数通过存在类型，或泛型约束调用要求

类型没提供的要求，槽指向扩展里的默认实现，所以默认实现也能被调用。泛型函数调用协议要求时，对应的见证表会作为调用信息传进去。存在类型则把指向见证表的引用放在盒子里。对象或盒子里拿的是指向表的引用，不是每个对象自带一整张表。

追问

  • 同一个类型遵循两个协议，是一张表吗？不是。两套要求，两张见证表。
  • 方法没写进协议要求，能到这张表里找吗？不能。那是按静态类型直接调用，上一题已经分开了。
  • 槽位顺序和描述符的字段偏移要背吗？不用，那是 ABI。面试说清「一份要求清单 + 每份遵循一张表」即可。编译器看见具体类型时可以不经过表、直接调用，那是优化；通过 any P 调用时，语言模型仍然是查表。

22. 把协议当成类型（any P）时，运行时里面有什么？

口述版

any P 在运行时是一个存在容器，里面有三样：一块放值的空间、这个值的类型元数据、协议见证表。类型元数据带着值见证表，负责拷贝和销毁；协议见证表负责按要求找实现。值不大就放在容器里，太大就放到堆上，空间里只留指针。常见 ABI 的缓冲区大约三个指针宽，这是实现，不是语言承诺。编译器在 any P 这个静态类型上不知道具体类型，所以协议方法不能直接跳过去，得先查见证表。

解析

把协议当成类型，运行时拿到的不是那个具体值本身，而是一个存在容器。容器要同时回答三件事：值在哪、这是什么类型、协议方法找谁。编译器在这个静态类型上不知道具体遵循者，所以不能把协议要求直接绑定成一个函数。

容器里的东西干什么
值缓冲区固定的一小块空间。放得下就嵌在容器里；放不下，空间里改放一个指针，值放到堆上
类型元数据指向这个具体类型的运行时描述，其中有值见证表。复制、赋值和销毁盒子，必须按里面真实类型的规则来
协议见证表每个协议一张。调用 any P 上的协议要求

所以 any P 里面不是「只有一个指针」。小值还可以直接嵌在容器里。缓冲区的大小、多大就改为堆分配，是 Swift ABI 的实现。换工具链或架构时，不要用这个字节数写业务判断。常见 ABI 大约三个指针宽，用来回答「大概多大」，不用来写源码里的分支。

需要恢复具体类型再做依赖 Self 的操作时，把盒子传给泛型函数，在里面打开，而不是在盒子外强转。

追问

  • 值见证表和协议见证表是一张「方法表」吗？不是。值见证表在类型元数据里，负责这个不知道静态类型的值怎么拷贝、移动、销毁、占多大。协议见证表负责协议要求对应哪个实现。P & Q 就是两张协议表。
  • 装进 any 之后，结构体是不是变成了引用类型？不是。装箱不改变值语义。结构体放进 any P 再取出来，仍然按那个结构体的值语义复制；变的是运行时表示。
  • 签名写了 any P，能不能说一定不分配、一定不查表？不能。编译器如果能证明具体类型，可以避免装箱或改成直接调用。那是优化，不是这个静态类型的语言保证。

23. Swift 实例对象、类、元类的内部结构如何？

口述版

先分三层。实例在堆上，常见运行时布局是开头指向类，接着引用计数，后面才是存储属性；这是实现布局，不是语言里的属性。类的运行时说明记录父类、实例大小、属性偏移和方法表，另外还有编译时的类型描述。纯 Swift 类没有单独的元类，实例方法在虚表里，类型方法不靠 isa 再跳一层。只有 NSObject 这系才有元类：实例的 isa 找到类，类的 isa 找到元类，最顶上那个元类的 isa 指回自己，它的父类是 NSObject 这个类。实例方法在类上，类方法在元类上。

解析

实例是活着的对象，类是这个对象的运行时说明，元类是 Objective-C 给「类对象」再准备的那一层。对象头部长什么样，是运行时布局，不是 Swift 语法里能点出来的属性。引用计数也可能压缩在对象头里，它不是你在类里声明的一个字段。不要按偏移去读。

层里面有什么用在哪
实例常见布局是开头一个指向类的指针，接着引用计数，后面才是存储属性类的实例。这是 Apple 平台上的常见运行时布局，不是语言语法
类元数据父类、实例大小、属性偏移、实例方法的虚表纯 Swift 类和 OC 类都有自己的类说明。实例方法在这里
类型描述编译时生成的名字、属性、方法等描述运行时要名字和反射信息时来查。它不是虚表本身
元类类对象的类。实例的 isa 找到类，类的 isa 找到元类只有继承 NSObject、进入 Objective-C 运行时的类。类方法记在元类上

讲一个普通 Swift 类的实例方法怎么找到，画到「对象指向类，类上有虚表」就停。不要给所有 Swift 类都画「实例 → 类 → 元类 → 根元类」。类继承了 NSObject，或者要解释 OC 的类方法，再画 isa 链。类型描述、反射和调试信息是运行时和工具链的实现。会不会内联某个方法，跟对象头的布局不是同一题。

追问

  • 属性存在类对象上吗？存在实例里，类只记录偏移。
  • 根元类的父类是不是还是一个元类？不是。根元类的 isa 指向自己，父类是根类本身。对 NSObject 来说，元类的父类就是 NSObject 这个类。
  • 调试器里纯 Swift 类的指针也叫 isa，是不是就有元类塔？不是。叫法相同，不代表后面跟着 Objective-C 的元类。纯 Swift 类的类型方法由编译器按类型元数据直接找到。

六、并发

24. Swift async/await 和 GCD 有什么区别？await 会不会堵住当前线程？

口述版

await 挂起的是当前任务，不是让线程干等，所以线程可以转去跑别的任务。挂起只发生在 await 上，两个 await 之间的代码是同步的，会占着当前执行器；在主 actor 上，这段就会占主线程。GCD 是把闭包提交到队列，async 不阻塞提交者，sync、信号量和锁上的死等才会占住线程。不要在异步函数里用信号量把 await 改成死等。Swift 的合作线程池线程不多，都堵住时，别的任务没线程可跑，甚至会自己等自己。

解析

先分清挂起的是谁。await 只在挂起点挂起任务，不会让线程在那里空转等待。挂起之后，这个线程可以执行别的任务。没有遇到 await 的代码是同步的，占用当前执行器。主 actor 的执行器就是主线程，所以主 actor 上的同步重活会卡住界面。

func refresh() async {
    let data = await fetch()   // 挂起的是这个任务，线程可以去干别的
    decode(data)               // 这里没有 await，会一直占着当前执行器
    await updateUI(data)
}

GCD 是把闭包投进某个队列。异步提交不会阻塞提交线程；sync、信号量、Thread.sleep 和锁上的死等会占住线程。这些东西放进 Swift 并发的合作线程池里，会把线程占死，其他任务没有线程可跑，严重时还会自己等自己。想把老的回调包成 async，用 continuation，不要在异步函数里用信号量把等待改成死等。

看到卡顿，先看当前执行器上有没有一段没有 await 的重活，而不是先怪 await 本身。

追问

  • 写了 await 就是在后台线程吗？不是。它只表示这里可以挂起。挂起前后跑在哪个执行器上，看隔离是主 actor 还是别的 actor。
  • 函数标成 async 之后，后半段会自动并行吗？不会。没有新的子任务，就还是这段任务按挂起点往下走。编译器不会把两个 await 之间的重循环自动拆成挂起点，也不会因为函数是 async 就把整段代码搬到后台。
  • 为什么不能用 GCD 里「再阻塞一下也还能开线程」的经验？Swift 并发用的是合作式线程池，线程数量有限，这是运行时模型。一个任务不走到挂起点，池子就不能从它手里把线程拿走。GCD 全局队列的过载行为和它不一样。

25. actor 和类有什么差别？赋值之后谁和谁共享状态？

口述版

actor 和类一样是引用类型，赋值之后还是同一个 actor，两个变量看到同一份状态。差别是 actor 里面的可变数据有隔离，没遇到 await 时别的任务进不来。执行到 await，当前任务挂起并让出 actor，别的任务可以进来改同一份状态。隔离只覆盖没有挂起的那段，await 前后不是同一段临界区。类没有这层隔离，多个任务可以同时改。actor 自动是 Sendable，交出去的是引用，状态仍然只能在这个 actor 上改。

解析

这题的差别不在「会不会拷贝」。actor 和类赋值都是复制引用，共享同一个实例。类没有隔离，多个任务同时改同一个类的属性，是数据竞争。actor 的隔离状态同一时间只允许一个任务访问，这是语言保证，不是约定俗成的加锁风格。

actor Cache {
    private var items: [String: Data] = [:]
    func get(_ key: String) -> Data? { items[key] }
    func load(_ key: String) async -> Data {
        if let hit = items[key] { return hit }
        let data = await fetch(key) // 这里让出 actor，别的任务可以进来
        items[key] = data
        return data
    }
}

actor 不是「从函数入口锁到出口」。一到 await，当前任务挂起并让出，别的任务可以进入并修改同一份状态。隔离方法里只要写了 await，就不要假设前后中间没有别人改过状态。缓存、计数器和「先检查再写入」都按这个来设计，具体的写错方式在重入那一题。

actor 自动遵循 Sendable。别的任务可以持有这个引用，但不能绕过隔离直接改里面的状态。编译器不会把类自动改写成「整段方法持有锁」；让出是语义的一部分。

追问

  • 需要子类覆写，能用 actor 吗？不能。actor 不支持继承。需要继承或 OC 兼容，用类；共享了就要自己用锁，或改成 actor。
  • 外面怎么读它的隔离属性？从 actor 外面读隔离属性或调用隔离方法，要 await。明确不碰隔离状态的方法才标 nonisolated。
  • 标了 Sendable 就可以在外面直接改属性吗？不可以。传出去的是引用，修改仍要回到这个 actor 上。编译器在跨越隔离域时插入跳转，这是隔离规则，不是偶尔优化才隔离。

26. async let、TaskGroup、Task、Task.detached 分别是谁的子任务？

口述版

async let 和 TaskGroup 创建的是当前任务的子任务，父任务取消时它们会一起被取消。离开作用域如果还没等完，会先取消，再隐式等待它们结束，不是取消完就立刻返回。Task { } 不是子任务，它沿用当前 actor、优先级和 task local，所以在主 actor 上创建就会留在主 actor；外层取消不会自动取消它，要自己留着句柄调用 cancel()。Task.detached 也不是子任务，而且不沿用 actor、优先级和 task local。

解析

先问它是不是当前任务的子任务。是子任务，取消会顺着父子关系传下去，离开作用域还要把它等完。Task { } 和 Task.detached 都不是子任务，外层取消不会自动带到它们身上。编译器不会把一个普通的 Task { } 自动改成子任务，也不会在函数返回时替你 cancel()。

func fetch(_ id: String) async -> String { id }
func load() async {
    async let left = fetch("a")     // 子任务
    async let right = fetch("b")
    _ = await (left, right)         // 不 await 就离开：先取消，再等它们结束
}
func group() async {
    await withTaskGroup(of: String.self) { group in
        group.addTask { await fetch("a") } // 组里添加的都是子任务
    }
}
let handle = Task { await fetch("c") }    // 不是子任务，要自己 handle.cancel()
Task.detached { await fetch("d") }        // 也不继承 actor、优先级、task local

固定几件可以并行、并且必须跟着当前任务一起结束的事，用 async let。子任务数量要运行时才知道，用 withTaskGroup。要脱离当前作用域继续跑，例如界面发起一个之后还能自己取消的加载，用 Task { }，把返回的句柄存下来，离开时 cancel()。明确不要继承优先级、actor 和任务局部值，才用 Task.detached。

async let 和任务组会沿用优先级和任务局部值。子任务理会取消，就可以提前结束；父任务不是发完取消就立刻返回。

追问

  • 子任务不理会取消，父任务还能返回吗？不能立刻返回。作用域结束时先取消，再隐式 await 到它结束。一段不看取消标记的同步死循环会把父任务拖住。
  • async let 是不是语言保证两段同时在两个核上？不是。能不能占满多个 CPU，取决于它们会不会在同一个 actor 上排队，以及运行时有没有可用线程。同一个 actor 上的两个子任务可以交错，但 actor 一次仍然只进一个。
  • 在主 actor 上写 Task { }，里面的重活会自动丢到后台吗？不会。它沿用主 actor。要离开当前 actor，得让任务里的函数本身跑到别的执行器，或使用 Task.detached，并处理好 Sendable。Task.detached 不是更轻的 Task，它只是更少继承上下文，也不会因为页面没了而停。

27. 取消为什么是协作式的？页面已经消失，请求为什么还在跑？

口述版

取消是协作式的：cancel 只把任务标成已取消，不会中断正在执行的同步代码。任务要自己看 Task.isCancelled，或者走到会检查的地方，比如 Task.checkCancellation，才会停。一段不看标记的同步死循环会一直跑。页面里另起的 Task { } 不是子任务，页面消失不会自动取消它，必须在离开时拿着句柄调用 cancel。旧回调也不会因为外面取消了就自己停止。

解析

取消是一张贴上去的标签，不是一把把代码掐断的剪刀。cancel() 只设置状态，正在跑的同步代码会继续跑，直到它自己检查，或者走到一个会检查的挂起点。任务停不停，取决于它看不看这张标签；没有父子关系的任务，连标签都不会被页面替它贴上。

func walk(_ items: [Item]) async throws {
    for item in items {
        try Task.checkCancellation() // 不看这张标签，循环会一直跑
        try await handle(item)
    }
}

长循环或分片计算，每一段开始前看 Task.isCancelled，或者主动 checkCancellation()。等待本来就支持取消的 API，例如 Task.sleep 和合作的 URL 请求，直接 await 它，不要在外面再包一层死等。

页面里用 Task { } 单独拉起的请求，页面消失时用保存的句柄 cancel()。它不是视图的子任务，onDisappear 里什么都不做，请求还在。子任务希望跟着父任务停，用 async let 或任务组，而不是在里面再套一个无主的 Task { }。旧回调包出来的 continuation，取消时要自己注销底层请求，并决定怎样结束等待。

追问

  • Task.checkCancellation() 做了什么？已取消就抛出 CancellationError。它自己就是一个检查点。取消应当按错误结束这条任务时用它；循环里只想自己收尾，看 Task.isCancelled。
  • 取消会自动让 continuation 恢复吗？不会。没人 resume，等待的任务仍然挂着。包一层 await 也不会自动把底层请求停掉。
  • 运行时会不会帮我在循环里插入检查？不会。运行时不为了取消去抢占一条不挂起的同步循环。有些系统 API 会在取消时收尾，那是那些 API 的实现，不是所有闭包和回调的默认行为。

28. Sendable 保证什么？@unchecked Sendable 在承诺什么？

口述版

Sendable 保证的是这个值可以跨 actor、跨任务传，而不会因此数据竞争。它是编译期标记，不是运行时的锁。结构体和枚举只要属性都是 Sendable 就可以遵循，传过去的是副本。actor 自动遵循，传出去的仍是引用，状态只在 actor 上改。类一般要 final，而且属性是不可变的 Sendable。@unchecked Sendable 是你自己保证没有两处同时改，编译器不再检查；这个保证要靠锁或 actor 成立。保证不成立，数据竞争还在，运行时不会替你加锁。

解析

Sendable 是编译期的通行证。满足条件才能跨隔离域传递。它不会在运行时加锁，也不会把类变成值类型。值类型跨任务传递的是副本，所以成员都是 Sendable 时，结构体和枚举可以遵循。成员里藏着可变类，就不能随手盖章。

struct Point: Sendable { var x: Int; var y: Int }

final class Token: Sendable {
    let value: String
    init(_ value: String) { self.value = value }
}

final class Counter: @unchecked Sendable {
    private let lock = NSLock()
    private var value = 0
    func next() -> Int {
        lock.lock()
        defer { lock.unlock() }
        value += 1
        return value
    }
}

actor 隐式遵循 Sendable。能传的是引用，改仍然要进 actor。类要让编译器认可，通常必须是 final，存储属性不可变且为 Sendable。还有 var 又没有同步，编译器就不认。传的是引用，所以条件比值类型严。

@unchecked Sendable 关闭的是检查，不是关闭数据竞争。给一个到处都是 var 的类加上它，报错没了，同时修改还在。

追问

  • 只是想让编译器安静，可以加 @unchecked 吗？不要。先缩成值，或把状态搬进 actor。类里面有可变状态，但所有修改都进了同一把锁或同一个 actor，才用它，并把这个不变量写在类型旁边。
  • 闭包要跨隔离域执行呢？使用 @Sendable 闭包，不捕获可变的非 Sendable 状态。
  • 成员合格，public 类型就一定会自动公开这个遵循吗？不要这么背。跨模块时，public 类型往往需要显式写出 Sendable，编译器再检查成员。编译器也不会为了让一个非 Sendable 的类通过，而自动给它加锁或复制对象图。

29. @MainActor 保证的是什么？界面卡顿时先看什么？

口述版

@MainActor 保证代码在主 actor 上执行，主 actor 的执行器就是主线程。它不管这段代码有多重，也不会自动变成异步。界面卡的时候，先看主线程上有没有重计算和干等，再看有没有本来可以放到别的 actor 上的工作。两个 await 之间的同步代码会一直占着主线程。标了 @MainActor 之后，照样可以堵界面。

解析

@MainActor 是全局 actor。标在类型或函数上，表示这些代码隔离在主 actor，由主线程执行。这是隔离规则，不是「通常会这样」的优化。它不把重活改成并行，也不插入挂起点。编译器会在跨越主 actor 边界时安排切换，不会估算函数要跑多久，也不会自动把慢函数搬离主线程。

@MainActor
func show(_ items: [Item]) {
    view.items = items          // 碰界面，留在主 actor
}
func prepare(_ raw: Data) async -> [Item] {
    decode(raw)                 // 重活不要只靠加上 @MainActor
}

碰界面、UI 对象和主线程限定的 API，隔离到 @MainActor。函数体里有重计算，把重计算放到不会隔离在主 actor 上的函数里，算完再 await 回主 actor 更新界面。

卡顿时的顺序：先看主线程有没有长计算、同步 I/O，或者锁和信号量上的干等；再看解码、压缩、大列表加工有没有被标进主 actor；最后才看刷新频率这些表现层问题。同步部分不挂起，就一直占着主线程。

追问

  • 从别的 actor 调用主 actor 方法，函数体跑在哪？要 await，任务先切到主线程，切过去之后函数里的同步部分仍一次性占用主线程。
  • 类型整体标了 @MainActor，某个方法不碰界面呢？可以标 nonisolated，但要保证它真的不碰这些隔离状态。把整个视图模型都标上主 actor，又在里面做解码和排序，隔离只解决了跑在哪，没有解决工作量。
  • 在主 actor 上创建的 Task { } 呢？默认仍隔离在主 actor。这是隔离继承，不是调度器自由发挥。

30. actor 重入是什么？await 之后写缓存为什么会写错？

口述版

actor 只保证没停在 await 上的时候，只有一个任务在碰它的状态。一到 await 就让出，别的调用可以进来，这就是重入。所以先看见缓存没有、下载回来再无条件写入，中间可能已经有别人写好了，你这一写会盖掉；两个调用都看见没有，还会各下载一遍。这是逻辑竞态，不是数据竞争，因为两次写入仍然不会同时发生。修法是在让出之前把正在下载的 Task 登记进缓存，后来的调用发现已经在下，就等这一次的结果。

解析

隔离只覆盖「没停在 await 上」的那段执行。actor 保证的是互斥：没有挂起时，只有当前任务能碰这份隔离状态。它不保证整个函数是一个事务。await 会挂起并让出 actor，让出期间其他调用可以进入。「缓存里没有」这个判断，在 await 之后就过期了。

错的写法把检查和写入拆在挂起点两边。两个调用都看见没有，就会各下载一遍；后回来的那次写入，还会盖掉这段时间里已经放进去的结果。actor 仍然不让两次写入同时发生，破掉的是 await 前后的业务假设。

actor ImageCache {
    private var cache: [URL: Data] = [:]
    func image(for url: URL) async throws -> Data {
        if let cached = cache[url] { return cached }
        let data = try await download(url) // 停在这里时，其他调用可以进来
        cache[url] = data                   // 可能盖掉别人已经写好的结果
        return data
    }
}

修法是在让出之前，把正在进行的 Task 登记进去。后来的调用看见已经在下载，就等同一份 Task。

actor ImageCache {
    private var cache: [URL: Data] = [:]
    private var inflight: [URL: Task<Data, Error>] = [:]

    func image(for url: URL) async throws -> Data {
        if let cached = cache[url] { return cached }
        if let running = inflight[url] {
            return try await running.value
        }
        let task = Task<Data, Error> { try await download(url) }
        inflight[url] = task          // 这一步必须发生在 await 之前
        defer { inflight[url] = nil }
        let data = try await task.value
        cache[url] = data
        return data
    }
}

追问

  • 编译器会把跨 await 的读改写收成事务吗？不会，也不会发现缓存逻辑竞态后替你合并下载。只要中间有挂起点，就要按「别人可能进来过」来写。重入不是运行时偶尔发生的竞速。
  • 登记之前先 await 别的东西呢？登记晚了，两个调用都看不见对方。检查缓存、检查在途任务、登记，这三步必须落在同一次不挂起的执行里。
  • 下载函数能不能在还没让出 actor 时，反过来同步死等这个 actor？不能。外层必须 await 把 actor 让出去，里面的工作才跑得动。失败时清掉在途记录，成功时再写入数据缓存，后来的等待者要和发起者看同一份结果。

31. 怎么把 completion 或 delegate 桥成 async？调用方不再等待时怎么结束？

口述版

只回调一次，用 withCheckedContinuation；会失败就用 withCheckedThrowingContinuation。拿到结果后必须恰好 resume 一次：一次都不调，等待永远挂着；调两次，checked 运行时直接报错。会回调很多次就用 AsyncStream，取消或对象释放时 finish。调用方不再等，原来的回调不会自己停，要在 withTaskCancellationHandler 里注销，并且仍然得有人 resume 或 finish。取消不会自动把 continuation 结束掉。

解析

桥接的关键不是把回调写进 async 函数，而是把「等待」交给一个只能结束一次的凭证。回调来一次，用 continuation；回调来多次，用流。调用方不等了，凭证不会替你把底层请求取消掉，也不会自己结束等待。

func load() async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        request { result in
            continuation.resume(with: result) // 成功和失败都算这一次
        }
    }
}

0 次 resume，等的人永远站着。checked 版本调用两次，运行时直接报错。可能出错就用 throwing 版本，失败走 resume(throwing:)。进度、搜索结果、事件流会叫很多次，不能塞进一个 continuation，用 AsyncStream 或 AsyncThrowingStream，结束时必须 finish，否则消费者会一直等下一次。

调用方取消时，在 withTaskCancellationHandler 的 onCancel 里移除委托、停掉原来的请求。只注销底层、不结束凭证，await 仍不回来。要让等待返回，就在取消路径上 resume(throwing: CancellationError())，或把流 finish。回调和取消处理如果都会走到结束，两边合计只能放行一次。函数返回了，不代表等待自然结束。

追问

  • 回调里 resume 一次，取消处理里为了保险再 resume 一次呢？checked continuation 会因为第二次直接报错。两条路径都可能走到 resume 时，自己收口成只放行一次。
  • 什么时候用 withUnsafeContinuation？没有测过、也不能证明只会 resume 一次，就不要换。unsafe 去掉运行时检查换速度，用错是未定义行为。编译器不会帮你证明所有路径都恰好 resume 了一次。
  • continuation 必须回到原来的隔离域再 resume 吗？不用。它可以在回调所在的线程上 resume，本身可以跨隔离域传递。

32. Swift 6 语言模式把什么变成了编译错误？它和编译器版本是一回事吗？

口述版

Swift 6 语言模式把数据竞争从警告变成编译错误。一份能改的数据被不同 actor 或任务一起用，又没有 Sendable，也没有关在某个 actor 里，就编不过。编译器版本和语言模式不是一回事：Swift 6 编译器仍可以按 Swift 5 模式编译某个 target，这时同类问题多半还是警告。例外是隔离区域分析：就算没标 Sendable，只要编译器能证明交给别的任务之后当前代码不再使用，就允许把这个值转移过去。证明不了就报错，这不是运行时再检查。

解析

先把两个开关分开：编译器是哪一版，以及这个 target 用哪一种语言模式。同一把新工具，可以按旧规则只提醒，也可以按新规则直接不过。

Swift 6 语言模式做完整的并发检查，跨隔离域的数据竞争问题是错误。共享可变状态必须是 Sendable，或者留在某个 actor 的隔离里。Swift 5 语言模式下，同样的问题多半还是警告，可以再配合严格并发检查的等级。模式是按 target 打开的。

隔离区域分析沿着「这个值还会不会被这里使用」做证明。一个非 Sendable 的值只是把所有权交给新任务，当前作用域之后不再碰，编译器可以允许这次转移。证明不了就报错。不要先给类乱加 @unchecked Sendable。它不改变剩余代码的隔离规则，只允许一种所有权已经交出去的传递，也不是运行时再看一眼。

追问

  • 升级了 Xcode 是不是就已经打开 Swift 6 语言模式？不是。语言模式是这个 target 的构建设置，不是整个 Xcode 只有一个全局开关。还没改完时，可以让 Swift 6 编译器继续用 Swift 5 语言模式，把问题先当警告看。
  • 编译错误都用 @unchecked Sendable 消掉，算迁移完了吗？不算。那是关闭检查。分析证明不了后面没有使用，就改成值、改成 Sendable，或把状态放进 actor。
  • 没有 Sendable 的值是不是绝对不能交给另一个任务？不是。所有权能被证明已经转移、当前区域之后不再使用，就允许。这是 SE-0414 的隔离区域分析，结论由编译器给出。这条路径要么证明转移是安全的，要么拒绝，不是编译器偶尔放过，也不是性能优化。

33. Swift 6.2 之后，一个 nonisolated async 函数默认跑在哪？@concurrent 做什么？

口述版

这题先看开关，不看编译器版本号。没开 NonisolatedNonsendingByDefault 时，nonisolated async 还是跑到公共并发池，这是 6.2 之前的行为。打开之后，它默认留在调用方的执行器上：调用方在主 actor 就留在主线程，调用方本来就在并发池就留在并发池。Xcode 的 Approachable Concurrency 会打开这个开关。@concurrent 才是明确离开调用方、放到并发池里跑，因此参数和返回值必须能安全送出。以前靠 nonisolated async 离开主 actor 的代码，开了开关就要改成 @concurrent。

解析

不要先背「6.2 之后默认在哪」。同一段 nonisolated async 函数，开关开或不开，运行的执行器不同。这是语言规则在开关两侧的定义，不是同一份代码随机调度。

// 开关关闭：和 6.2 之前一样，切到公共并发池
// 开关打开：默认就是 nonisolated(nonsending)，留在调用方的执行器上
func load() async -> Data { Data() }

@concurrent
func crunch(_ input: [Int]) async -> Int {
    input.reduce(0, +) // 明确离开调用方。参数和返回值必须能安全送出
}
开关和标记跑在哪
没开 NonisolatedNonsendingByDefaultnonisolated async 跑到公共并发池。旧项目、还没开 Approachable Concurrency 的 target 仍是这样
打开这个开关默认留在调用方的执行器上。调用方在主 actor，函数就留在主 actor
@concurrent离开调用方，切到公共并发池。确实要并行、要离开主 actor 的 CPU 工作才标它

调用方可能是主 actor，而这件工作会卡住界面，就标 @concurrent，同时让参数和返回值满足可以安全送出调用方隔离域的要求。打开开关后仍用 nonisolated async 来保证离开主线程，这条假设已经失效，函数会留在主 actor 上。

追问

  • 它是不是总会留在某一个 actor 上？不是。调用方在某个 actor 上，就留在那个 actor；调用方没有 actor、本来就在并发池，就留在调用方的执行器，通常就是并发池。不是另外找一个 actor 钻进去。
  • 函数已经隔离在某个 actor 上，能再加 @concurrent 吗？不能。@concurrent 隐含 nonisolated，只能和 nonisolated 一起用，不能拿来修改一个已有的 actor 隔离。
  • 这个开关是性能优化吗？不是。它改变的是默认隔离语义：离开主 actor 从「默认发生」变成「要显式标记」。编译器也不会因为函数看起来很重，就在没写 @concurrent、也没开开关时自动把它挪到后台。真正起作用的是 nonisolated(nonsending) by default 这项设置，Approachable Concurrency 会连带打开它。
