1. struct、class、enum 有什么区别？什么时候用？

基础优先

回答总结

struct 和 enum 是值类型，class 是引用类型。值类型在赋值或传参后，修改一份值本身不会影响另一份；引用类型的多个引用可以指向同一实例并共享状态。值语义不等于深复制，值类型中保存的类引用仍可能指向同一对象。三者都支持属性、方法和协议，类还支持继承与实例身份比较。选择时，独立数据优先用 struct，需要共享状态、对象身份或继承时用 class，需要表达互斥状态及其附带数据时用 enum。

进一步理解

值类型赋值后，为什么修改一份不会影响另一份？

把姓名“小明”放进结构体，再执行 b = a，可以把它理解为得到两份独立的个人资料。随后把 b.name 改为“小红”，a.name 仍是“小明”。这里说的独立，是修改值本身时互不影响；Swift 可以在底层采用共享存储等优化，不要求赋值时立即复制每一个字节。

结构体里保存类对象，还会完全互不影响吗？

假设两份个人资料里都保存了同一个 Account 对象的引用。复制资料时，这个引用也被复制，但不会因此新建一个 Account。通过任一份资料修改账户余额，另一份都能看到变化。要分清“修改结构体自己的字段”和“修改字段所指对象的内部状态”，后者操作的是共享对象。

为什么修改结构体属性要写 mutating？

结构体方法默认不能改变自身的值。例如把姓名从“小明”改为“小红”，是在修改这份结构体，方法需要标记 mutating，让调用方知道它会改变值。重新赋值 self、切换枚举 case 也是同一道理。如果方法只是修改所引用的 Account 对象余额，结构体保存的引用没有变，就不因此要求 mutating。

枚举的关联值和原始值分别有什么用？

加载结果可以是 loading，也可以是 success("数据")；success 携带的内容随每次结果变化，这叫关联值。原始值则像固定编号，例如某个 case 对应字符串 "loading"，在声明时就确定。前者表达“本次状态附带什么数据”，后者表达“这个 case 对应什么固定值”。

代码示例（看注释与结果）

struct Profile { var name: String }
var a = Profile(name: "小明")
var b = a
b.name = "小红"
print(a.name) // 小明：修改 b 不影响 a

class Account { var balance = 0 }
let x = Account()
let y = x
// let 固定的是引用，仍可修改对象的 var 属性
y.balance = 100
print(x.balance) // 100：x 和 y 指向同一对象
print(x === y)   // true：比较是不是同一实例

enum State {
    case loading
    case success(String) // 关联值：本次成功附带的数据
    case failure(Int)
}
let state = State.success("加载成功")

2. Optional 是什么？if let、guard let、?? 和类型转换怎么用？

基础优先

回答总结

Optional 表达“有值或无值”；if let 在分支内解包使用，guard let 失败先退出、成功继续用。T? 是 Optional<T> 的简写，nil 表示无值。?? 在无值时提供默认值，?. 在有值时继续访问成员，无值时返回 nil。类型检查用 is，可能失败的转换用 as?，转换结果可以继续安全解包；编译期能够确认的转换用 as。强制解包 ! 和强制转换 as! 都要求开发者保证成功，否则会触发运行时错误。

进一步理解

为什么空字符串与 nil 不能混为一谈？

昵称为 ""，表示已经拿到一个字符串，只是里面没有字符；昵称为 nil，表示这里没有字符串。比如输入框允许用户清空昵称，就可能得到空字符串；接口没有提供昵称，则可能用 nil 表示。Optional 让你先区分“没有值”和“有值但内容为空”，再决定显示什么。

if let、guard let 和 ?? 应该怎么选？

只想在有昵称时显示一段欢迎语，用 if let，让解包后的名字只在分支里使用。如果整个后续流程都必须有名字，用 guard let，先在缺失时 return，后面的代码就能直接使用 String。若缺失时显示“游客”即可，用 nickname ?? "游客"；它提供替代值，不会把原来的 nickname 改成有值。

as? 为什么经常与 if let 一起出现？

假设 value 声明为 Any，里面可能装字符串，也可能装数字。is String 只回答“是不是字符串”；as? String 则尝试取出字符串，成功得到 String? 中的值，失败得到 nil，再用 if let 判断并使用。as 用于编译期能确认的转换；as! 和强制解包 ! 则把成功当作前提，前提不成立就触发运行时错误，不能用 do-catch 补救。

代码示例（看注释与结果）

let nickname: String? = nil
print(nickname ?? "游客")       // 游客
print(nickname?.count as Any) // nil：不会访问不存在的字符串

func greet(_ input: String?) {
    guard let name = input else {
        print("没有名字")
        return // guard 失败必须离开当前作用域
    }
    print(name) // name 已经是 String，可以直接使用
}
greet("小明")

let value: Any = "Swift"
if let text = value as? String { // 转换失败得到 nil
    print(text.count) // 5
}
print(value is String) // true，只检查类型
// nickname!          // 若执行会崩溃，do-catch 也救不了

3. 存储属性、计算属性、lazy、static 和 class 怎么区分？

基础优先

回答总结

存储属性直接保存值，计算属性通过 getter 返回结果，也可通过 setter 处理赋值，本身不额外保存计算结果。lazy 将实例存储属性的初始化推迟到首次访问，必须是 var，且不保证并发首次访问时只初始化一次。static 和 class 都用于声明类型成员：static 可声明存储属性、计算属性和方法，在类中可以继承但不能重写；class 用于允许子类重写的类型方法和计算类型属性，不能声明存储型类型属性。存储型类型属性保证延迟初始化且只初始化一次，后续共享可变状态的读写仍需同步。

进一步理解

存储属性与计算属性，读取时到底有什么不同？

在下面的 Meter 中，value 保存当前数值；doubled 不单独存一份结果，而是读取时执行 value * 2。所以 value 从 1 改成 3 后，读取 doubled 就得到 6。可读写计算属性的 setter 也不必保存传入值：把华氏温度设为 212，可以换算后写入 celsius，下次读取时再从摄氏温度算回来。

lazy 为什么必须是 var？什么时候适合用？

假设 history 的创建比较费时，而有些实例从来不会读取它。lazy 把创建推迟到第一次访问，避免一开始就付出成本。第一次读取会把“尚未初始化”变成“已经保存了结果”，所以实例 lazy 必须是 var。它不会随其他属性变化自动重新计算，也不保证多个线程同时首次访问时只创建一次。

willSet 和 didSet 各能看到什么？

执行 meter.value = 3 时，willSet 在真正写入前运行，此时 value 还是旧值，newValue 是 3；写入完成后 didSet 运行，此时 value 已是 3，oldValue 保存原值。它们适合在赋值前后做校验或刷新。初始化器直接给本类型定义的存储属性设置初值时不触发这些观察器，因此不要靠 didSet 完成必需的初始化工作。

static 和 class 为什么不通过实例访问？

“米”是 Meter 这个类型共用的单位，不必让每个 meter 都各存一份，因此写成 Meter.unit。类的 static 成员可以被子类继承，但不允许重写；如果需要让 Car 给出不同的类型方法结果，就用允许重写的 class func。class 还能声明计算类型属性，但不能声明存储型类型属性。

代码示例（看注释与结果）

struct Meter {
    var value = 1 {
        didSet { print("旧值", oldValue, "新值", value) }
    }
    var doubled: Int { value * 2 } // 计算属性，不单独保存结果
    lazy var history = [0, 1]      // 第一次访问才初始化，必须是 var
    static let unit = "米"         // 类型属性：Meter.unit
}
var meter = Meter()
meter.value = 3         // 旧值 1 新值 3
print(meter.doubled)    // 6
print(meter.history)    // [0, 1]
print(Meter.unit)       // 米

class Vehicle {
    static func category() -> String { "车辆" }
    class func name() -> String { "普通车" }
}
class Car: Vehicle {
    override class func name() -> String { "汽车" }
}
print(Car.name())       // 汽车
print(Car.category())   // 车辆：static 可以继承，但不能重写

struct Temperature {
    var celsius = 0.0 {

        didSet { print("原来是", oldValue) }
    }
    var fahrenheit: Double {
        get { celsius * 1.8 + 32 }
        set { celsius = (newValue - 32) / 1.8 } // 改的是 celsius
    }
}
var temperature = Temperature()
temperature.fahrenheit = 212 // 准备写入 100.0；原来是 0.0

进阶补充：扩展与类型存储属性的限制

扩展不能添加实例存储属性，但能添加计算属性和方法；在类型与泛型限制允许时，也能添加 static 存储属性。存储型类型属性延迟初始化并保证只初始化一次，但之后若保存共享可变状态，仍需同步。不要把这项保证套到实例 lazy 上。初始化期间也不是所有赋值都不触发观察器，应区分初始化器直接设置本类型存储属性初值与其他赋值路径。

4. Swift 初始化器有哪些？两阶段初始化是什么？

基础优先

回答总结

初始化器负责为存储属性建立合法初值；类的两阶段初始化先沿继承链完成各层属性的初始赋值，再进行实例定制。类的指定初始化器先初始化本类新增的存储属性，再调用父类的指定初始化器；便利初始化器通过 self.init 调用本类其他初始化器，最终到达指定初始化器。第一阶段结束前，不能调用实例方法、读取实例属性或把 self 作为完整实例传出。init? 用 nil 表示失败，throws 可以传递失败原因；required 要求子类也支持该初始化器，可按规则继承，无法继承时必须自行实现。

进一步理解

为什么要先初始化本类属性，再调用父类初始化器？

创建子类对象时，对象既有子类新增的字段，也有继承的字段。指定初始化器先给本类新增字段初值，再调用 super.init，让父类负责它自己的部分。整条继承链完成这一步之前，对象还没有完全建立，不能调用实例方法、读取实例属性或把 self 传出去；修改继承属性也要等父类初始化返回。这样可以避免方法读到尚未准备好的状态。

convenience 是多走一步，还是在复用代码？

下面 Vehicle.init() 没有重复设置 name，而是调用 self.init(name: "默认车")。可以把它理解为“少填参数的快捷入口”，最终仍由指定初始化器完成建立对象的工作。便利初始化器必须先委托本类的其他初始化器；不能直接跳过去调用父类的 super.init。

init?、throws、required 分别解决什么问题？

init? 表示“可能创建不出来”，失败返回 nil；throws 则能进一步说明失败原因，两者也可以组合。required 解决的是子类的接口约束：父类要求支持 init(name:)，子类也必须支持这一创建方式；能自动继承时无需重写，不能继承时必须实现并继续标 required。它不代表多调用一次初始化器。结构体没有类继承，不使用 convenience 和 required。

代码示例（看注释与结果）

class Vehicle {
    var name: String
    init(name: String) { self.name = name } // 指定初始化器
    convenience init() {
        self.init(name: "默认车") // 便利入口复用指定入口
    }
}
class Car: Vehicle {
    var seats: Int
    init(name: String, seats: Int) {
        self.seats = seats      // ① 本类属性先有初值
        super.init(name: name)  // ② 父类完成自己的初始化
        print(self.name)       // ③ 完整 self 现在可用于读取和调用
    }
}
let car = Car(name: "小车", seats: 4)

struct Age {
    let value: Int
    init?(_ value: Int) {
        guard value >= 0 else { return nil } // 合法失败
        self.value = value
    }
}
print(Age(-1) as Any) // nil

补充：required 从哪里来？它不是上面 Vehicle 示例中已有的内容，而是另一条初始化语法：开发者把 required 写在父类的 init 前面，就要求子类也提供相同参数的创建方式。这里的“初始化入口”就是“可以怎样传参来创建对象”。看下面两个子类，一个直接继承，一个自己实现。

class Device {
    let name: String
    required init(name: String) { // 父类规定：所有子类都要支持这个创建方式
        self.name = name
    }
}

// 情况一：没有新增存储属性，也没有自己定义初始化器，自动继承
class BasicDevice: Device {}
let basic = BasicDevice(name: "基础设备") // 不必再写一份 init(name:)

// 情况二：自己定义了指定初始化器，不能再自动继承父类指定初始化器
class Phone: Device {
    let storage: Int
    init(name: String, storage: Int) {
        self.storage = storage
        super.init(name: name)
    }
    required init(name: String) { // 必须补上父类要求的创建方式；这里不写 override
        self.storage = 128       // 子类决定该方式下自己的属性如何初始化
        super.init(name: name)
    }
}
let phone = Phone(name: "手机") // 使用 required init(name:)，容量为 128
print(phone.name, phone.storage) // 手机 128

“可按规则继承”在这里具体指：子类没有自己定义指定初始化器，且新增存储属性都有默认值（或没有新增存储属性）时，会自动继承父类指定初始化器。BasicDevice 满足这个条件；Phone 自己定义了指定初始化器，因此需要补写 required init(name:)。required 可以修饰指定初始化器，也可以修饰便利初始化器；它表达的是对子类的要求。

5. ARC 怎么工作？weak、unowned 和循环引用怎么处理？

基础优先

回答总结

ARC（自动引用计数）由编译器自动插入并优化 retain、release 等操作，由运行时执行这些操作来管理类实例的生命周期。获得一份强引用所有权时，retain 增加强引用计数；放弃这份所有权时，release 减少计数。计数归零时触发实例销毁，执行 deinit 并清理存储属性。强引用环会让环中实例的计数无法归零，ARC 不会自动拆环，需要根据所有权关系改用 weak、unowned，或主动断开强引用。两者都不增加强引用计数：对方可能先释放时用 weak，它必须声明为可选的 var，对象释放后自动变为 nil；只有能保证每次访问时对方仍存在，才考虑 unowned，它不会自动清零，访问已销毁的对象会触发运行时错误。

进一步理解

ARC 的“自动”体现在哪里？编译期与运行时各做什么？

编译器分析强引用的使用和所有权，在需要的位置自动插入保留、释放操作，并优化多余操作，开发者不需要手写 retain 和 release。程序运行时，这些操作实际增减对象的强引用计数；计数归零才进入实例销毁流程。因此不能把“自动插入代码”理解为“编译时就释放对象”，也不能把它理解为运行时定期扫描、回收所有用不到的对象。具体释放时机受引用的使用情况与编译器优化影响，不能简单断言局部变量一定等到右花括号处才释放对象。

为什么外面的变量清空了，对象还没有释放？

下面的 Page 保存 onTap 闭包，如果闭包又通过默认的强捕获保存 Page，就形成 Page → 闭包 → Page 的环。page = nil 只去掉外面的那条引用，环里的两条强引用还在互相保活。ARC 不会因为这组对象“外面已经用不到”就自动拆环，需要改为弱引用，或者在合适时机主动清空闭包。

为什么 [weak self] 能打断环，guard let self 又有什么作用？

[weak self] 让闭包能找到 Page，却不负责让它一直存活。Page 释放后 self 变成 nil，self?.refresh() 就不再执行。若一次操作中需要稳定使用对象，可先 guard let self，把当时仍存在的对象暂时强持有，避免使用期间消失。这会延长本次使用期间的生命周期；如果后面有长时间 await，也可能让对象跟着存活更久。

weak 与 unowned 应该怎么选？

先问“访问时，对方可能已经释放吗？”如果可能，比如页面关闭后回调才到达，weak 可以通过 nil 安全地跳过。unowned 则表达更强的承诺：每次访问时对方一定还活着，它不会自动变成 nil，承诺失效后访问会出错。代理通常用 weak；协议需继承 AnyObject，把遵循者限定为类，才能建立这种弱引用关系。

代码示例（看注释与结果）

final class Page {
    var onTap: (() -> Void)?
    func bind() {
        onTap = { [weak self] in // 闭包不再强持有 Page
            self?.refresh()     // Page 已释放就不调用
        }
        // onTap = { self.refresh() } // 若一直保存，会形成强引用环
    }
    func refresh() { print("刷新") }
    deinit { print("Page 释放") }
}
func demo() {
    var page: Page? = Page()
    weak var observer = page
    page?.bind()
    page?.onTap?() // 刷新
    page = nil    // 本例失去最后一条强引用，打印 Page 释放
    print(observer as Any) // nil：弱引用自动清空
}
demo()

6. 闭包如何捕获变量？@escaping、@autoclosure 有什么用？

基础优先

回答总结

闭包是可以传递和保存的代码，能够捕获定义作用域中的值和变量。默认捕获可变局部变量时，闭包与外部可访问同一变量；捕获列表可以保存创建闭包时的值，但捕获类引用不会深复制对象。涉及生命周期时，可通过 weak 或 unowned 调整捕获关系，避免不必要的强引用或循环引用。直接函数类型的参数默认非逃逸，@escaping 允许将其保存到函数返回后使用，但不代表异步执行，也不改变引用强弱。@autoclosure 自动把表达式包装成无参闭包以延迟求值，是否执行及执行几次由函数实现决定。

进一步理解

同一个 count，为什么一个闭包读到 2，另一个读到 1？

下面 readLive 默认捕获可变局部变量 count，外面把 count 改成 2，它读取的仍是同一个变量，所以结果是 2。readSnapshot 使用 [count]，在创建闭包时保存 count 当时的值 1；之后读取的是“捕获时保存的值”，外部 count 改成 2 不会影响它。如果捕获的是类引用，捕获列表保存的仍是对象引用，不会把对象内部数据深复制一份。

函数已经返回了，为什么闭包还能调用？

设想一个函数接收“下载完成后要做什么”，然后把闭包保存起来。函数本身先返回，下载完成后才调用闭包，闭包就活得比本次调用更久，这叫逃逸。直接函数类型的参数默认非逃逸，需要保存或允许返回后使用时标 @escaping。这个标记只允许更长的生命周期，既不保证晚执行，也不表示异步，更不会自动弱捕获对象。

@autoclosure 帮调用方省掉了什么？

普通闭包参数需要调用方写 { 表达式 }；@autoclosure 允许直接传表达式，由编译器包装成无参闭包。这样函数可以决定是否执行这段表达式，例如条件不满足就不计算日志内容。延迟求值不等于后台执行；函数若调用闭包两次，表达式也可能求值两次。

代码示例（看注释与结果）

func demoCapture() {
    var count = 1
    let readLive = { count }           // 捕获同一个可变局部变量
    let readSnapshot = { [count] in count } // 保存当前 Int 的值
    count = 2
    print(readLive())     // 2
    print(readSnapshot()) // 1
}
demoCapture()

func save(_ action: @escaping () -> Void) -> () -> Void {
    action // 允许返回，让调用者以后执行
}

}
log(false, String(1 + 2)) // 不调用 text，表达式不求值

    value += 1
}

    return { [value] in value } // 只带走当时的 Int 值

进阶补充：可选闭包参数与 inout 捕获

可选闭包参数不受直接函数类型参数默认非逃逸的同一限制，不额外标 @escaping。inout 表示函数调用期间临时获得修改调用方变量的权限；逃逸闭包可能在调用结束后仍存活，不能直接捕获这个临时权限。如果只需要当时的数据，可用捕获列表保存捕获时的值，而不是保存修改原变量的能力。

7. Array 是值类型，为什么复制不一定很贵？COW 是什么？

基础优先

回答总结

Array 是值类型，采用 COW（写时复制）在保持值语义的同时减少复制开销。赋值后可以先共享元素存储，修改时若存储仍被共享，才先复制存储再修改；独占存储时通常可直接修改，扩容等操作仍可能重新分配。因此，修改一份数组本身不会影响另一份。复制元素存储不会深复制其中的类对象，这些元素仍可能指向同一对象。COW 不提供线程同步能力，不能保证对同一个数组变量并发读写的安全。

进一步理解

数组赋值时，究竟复制了什么？

执行 b = a 后，从使用者角度看，a 和 b 是两份数组值；但底层可以暂时共用存放元素的那块存储。只读取时不必立即复制全部元素。随后执行 b.append(4)，如果存储仍被共享，b 就先取得自己的存储再修改，于是 a 保持 [1, 2, 3]，b 变成 [1, 2, 3, 4]。这就是“写时复制”：推迟复制成本，同时保持数组值的独立性。

复制数组后，为什么修改对象属性，两边都会变？

下面 first = [Item()] 创建数组和一个 Item 对象，second = first 不会再创建一个 Item。两个数组中的元素引用仍指向同一个对象。second[0].name = "新" 改的是对象属性，因此通过 first[0].name 也会看到“新”。如果改成替换 second[0]，改变的才是 second 自己的数组元素。COW 不等于把元素所指对象也深复制。

有了 COW，是否就能放心并发修改数组？

不能。COW 解决的是“两份值怎样减少复制开销”，并不负责安排两个任务的读写顺序。如果它们同时修改同一个数组变量，仍然需要 actor 等隔离或同步措施。只有一份值独占存储时，修改通常可以直接进行；需要扩容等情况仍可能重新分配，所以也不能理解成“只有共享时才会分配内存”。

代码示例（看注释与结果）

let a = [1, 2, 3]
var b = a       // 可以先共享底层元素存储
b.append(4)     // 修改 b，确保它有可独立修改的存储
print(a)        // [1, 2, 3]
print(b)        // [1, 2, 3, 4]

final class Item { var name = "旧" }
let first = [Item()]
let second = first
second[0].name = "新" // 改的是元素引用指向的对象
print(first[0].name) // 新：数组没有深复制类对象

别答错：值类型和 COW 都不允许多个线程无同步地修改同一个变量。

进阶补充：自定义 COW 不会凭空出现

自定义 struct 的每个属性遵循各自类型的复制规则，并不会自动把整个结构体变成共享存储。若自己用类封装存储，需要在修改入口检查是否独占；isKnownUniquelyReferenced 返回 Bool，能确认唯一强引用时可直接修改，否则先复制出自己的存储。这个检查不是线程同步工具。String 的短字符串还可能内联保存，不能把所有值类型都理解成只保存一个地址。

8. map、compactMap、flatMap 有什么区别？

基础优先

回答总结

对数组等序列，map 转换并保留全部结果，compactMap 转换后去掉 nil 并解包，flatMap 将每个元素产生的序列拼接为一层。Optional 也提供 map 和 flatMap，但它们只在有值时执行转换：map 会将转换结果再包装一层可选值，flatMap 用于衔接本身返回可选值的转换，避免额外嵌套。使用时先区分操作对象是序列还是可选值，不能把所有 flatMap 都理解为过滤 nil。

进一步理解

把字符串转成整数，为什么 map 会保留 nil？

对 ["1", "x", "3"] 逐项调用 Int，依次得到 1、nil、3。map 要为每个输入保留一个转换结果，所以输出仍有三项，类型是 [Int?]。如果业务只需要转换成功的数字，用 compactMap：它在转换后去掉 nil，并把剩余可选值解包，得到 [1, 3]。选择取决于“失败位置是否需要保留”。

flatMap 的“展开一层”是什么过程？

对 [[1, 2], [3]] 使用 flatMap { $0 }，闭包先返回每个子数组，再把它们顺次拼接成 [1, 2, 3]。它适合“每个输入产生一组输出”的场景，例如每个班级产生一组学生，再合成学生列表。$0 只是闭包第一个参数的简写，在这里就是当前子数组。

Optional 也有 flatMap，和拼数组是一回事吗？

不是同一种操作。下面 text: String? 有值 "x"，所以会执行 Int("x")，但转换结果是 nil。Optional.map 会把这个结果再包一层，得到 .some(nil)，类型是 Int??：外层表示原字符串存在，内层表示转整数失败。Optional.flatMap 直接衔接这次可选转换的结果，得到 Int? 的 nil。先看接收者是序列还是 Optional，才能正确理解同名方法。

代码示例（看注释与结果）

let input = ["1", "x", "3"]
let a = input.map { Int($0) }        // [Int?]
let b = input.compactMap { Int($0) } // [Int]
print(a) // [Optional(1), nil, Optional(3)]
print(b) // [1, 3]

let groups = [[1, 2], [3]]
print(groups.flatMap { $0 }) // [1, 2, 3]：拼接一层

let text: String? = "x"
let nested: Int?? = text.map { Int($0) } // some(nil)
let single: Int? = text.flatMap { Int($0) } // nil，无额外外层

别答错：不要把所有 flatMap 都解释为“过滤 nil”；序列这类用法现在应使用 compactMap。

9. throws、try?、try!、Result 和 defer 怎么用？

基础优先

回答总结

throws 声明函数可能抛错，throw 实际抛出错误，try 标记可能抛错的调用；调用方需用 do-catch 处理或继续向外抛出。try? 将失败转为 nil 并舍弃错误原因；try! 假定调用成功，实际抛错时触发运行时错误，不能通过 catch 恢复。Result 将成功值或失败原因包装成一个值，便于返回、存储和传递。defer 用于当前作用域退出时收尾，执行到声明处才注册，在正常结束、return 或 throw 离开时按注册逆序执行；程序崩溃时不能依赖它完成清理。

进一步理解

try、try?、Result，应该根据什么选择？

用户输入 "x"，parse 无法转成整数，这是程序应当处理的业务失败。需要提示具体原因，就用 try 配合 do-catch，或继续向外抛错；只关心“有没有转换成功”，可用 try? 把失败换成 nil。若要把成功值或失败原因保存下来、交给后续代码处理，就用 Result，再通过 switch 分别取出。try 只是标记可能抛错的调用，本身不会接住错误。

为什么把收尾代码写进 defer 更可靠？

假设函数打开资源后有多个 return，还可能 throw，每个出口都手写清理容易遗漏。执行到 defer 声明时先登记清理动作，之后离开当前作用域时统一执行。多个 defer 按登记的反方向执行，因此下面 finish() 先打印“先执行”，再打印“其次”，最后打印“最后”。如果在到达某个 defer 前就退出，那一个动作尚未登记，不会执行。

为什么 try! 的失败不能交给 catch？

try! 相当于开发者断言“这次调用不可能抛错”。如果实际抛错，程序触发运行时错误，而不是把错误继续交给外层 catch。强制解包失败和 fatalError 也不能用 do-catch 恢复；程序崩溃时也不能依赖 defer 做收尾。因此网络失败、输入无效等可预期情况，应使用正常错误处理。

代码示例（看注释与结果）

enum InputError: Error { case invalidNumber }
func parse(_ text: String) throws -> Int {
    guard let value = Int(text) else {
        throw InputError.invalidNumber
    }
    return value
}
do {
    let value = try parse("x")
    print(value)
} catch {
    print("输入错误", error) // 进入这里
}
print((try? parse("x")) as Any) // nil，舍弃错误原因
let result: Result<Int, InputError> = .failure(.invalidNumber)

func finish() {
    defer { print("最后") }
    defer { print("其次") }
    print("先执行")
}
finish() // 先执行 → 其次 → 最后

case .success(let value):
    print("成功", value)

    print("失败", error) // 失败 invalidNumber

    guard let value = Int(text) else { throw .invalidNumber }

throws(InputError) 表示这个函数只能抛出 InputError 类型的错误，让错误类型也成为接口约定。下面 parse 使用普通 throws，不限定具体错误类型；补充代码中的 parseTyped 则演示类型化 throws。两者都需要调用方处理可能的失败。

10. 泛型、Any、some、any 分别解决什么问题？

基础优先

回答总结

泛型通过类型参数让代码适用于多种类型，同时保留参数与返回值之间的类型关系，并可用协议约束能力。Any 可以保存任意类型的值，通常需要转换后才能使用具体类型的专有接口。any P 允许同一变量保存不同的协议遵循者，通过协议接口使用它们。返回位置的 some P 由实现决定具体类型，对外隐藏类型名称并保留其身份，普通非泛型函数的各返回路径必须使用同一底层类型；参数位置的 some P 则是泛型参数的简写，由调用方决定具体类型。

进一步理解

既然 Any 能装任何值，为什么还需要泛型？

设想 identity 收到什么就原样返回什么。若参数和结果都写 Any，传入整数后，调用方还要转换才能做加法；写成 identity<T>(_: T) -> T，编译器就能知道“输入与输出是同一种类型”。传入 3，返回值仍是 Int，可以直接加 1。泛型的价值不只是接受不同类型，还在于保留这些类型之间的关系；T: Equatable 则进一步要求它支持相等比较。

some Named 与 any Named，谁决定里面的具体类型？

下面 make() 返回 some Named，具体返回 User 由函数实现决定；调用方可以读取 name，但不需要知道它就是 User。对于这里的普通非泛型函数，不能某条分支返回 User、另一条返回 Book。any Named 则适合在同一变量或数组里存放不同遵循者，例如先装 User，再换成 Book；调用方统一通过 Named 提供的能力使用它们。

为什么隐藏类型后，不能直接使用所有专有成员？

假设 User 额外有 age，而 Named 只要求 name。拿到 any Named 时，调用方只凭这个接口无法确认里面一定是 User，所以不能直接读取 age；需要先尝试转换。同样，返回 some Named 是让调用方依赖声明的协议能力，不是公开 User 的所有接口。隐藏的是调用处可直接使用的具体类型信息，值在运行时仍然有自己的真实类型。

代码示例（看注释与结果）

func identity<T>(_ value: T) -> T { value }
let number = identity(3) // 返回仍是 Int，不需要 as?
print(number + 1)        // 4

protocol Named { var name: String { get } }
struct User: Named { var name: String }
struct Book: Named { var name: String }
func make() -> some Named {
    User(name: "小明") // 此普通函数底层始终返回 User
}
print(make().name)
var current: any Named = User(name: "小明")
current = Book(name: "Swift") // 同一变量可换成另一种遵循者
print(current.name)           // Swift

func same<T: Equatable>(_ a: T, _ b: T) -> Bool {
    a == b // 约束保证 T 支持相等比较
}
print(same(1, 1)) // true；不能传 1 和 "1"

11. 为什么说 Swift 支持面向协议编程（POP）？

重点理解

回答总结

Swift 的面向协议编程以协议描述能力，通过协议扩展提供默认实现，再通过泛型约束或协议类型组织调用，让代码依赖接口。类、结构体和枚举都能遵循协议，无需共同父类即可组合能力；遵循者可以复用默认实现，也可以提供自己的实现。协议要求规定必须提供的属性与方法，需要通过协议接口按具体类型选择实现的方法，必须写入协议声明。协议本身不保存实例数据，数据由遵循类型管理。这种方式有利于减少耦合、替换实现和编写测试，也可以与类继承配合使用。

进一步理解

面向协议编程，能减少哪一种重复？

假设页面既要显示用户，也要显示机器人。若显示函数直接依赖 User，就得为 Robot 再写一份。先用 Named 声明 name 和 greeting()，显示函数只依赖这两个能力，User 与 Robot 都能传进去。这样共享的是接口约定，不必为了复用显示逻辑而给两者安排一个共同父类，结构体和枚举也能参与。

默认实现到底替遵循者做了什么？

协议中的 func greeting() 是“必须具备这个能力”的要求；扩展里的函数体是“没有另写时，可以采用这一份代码”。所以 User 只提供 name，就能复用“你好，名字”；Robot 自己实现 greeting()，则输出“编号：名字”。协议不替实例保存 name 字段，具体数据仍由遵循类型负责。

为什么有些方法必须写进 protocol，而不能只放扩展？

show 的目标是“根据传入对象选用各自的 greeting()”。要表达这个可替换的接口，greeting() 必须出现在协议要求中。只放在扩展里的同名辅助方法，不会自动获得这种选择规则；通过协议接口调用时可能仍选扩展版本。第 12 题用 hello 与 bye 的结果对比说明这个差别。

代码示例（看注释与结果）

protocol Named {
    var name: String { get }
    func greeting() -> String // 放入协议要求，支持不同实现
}
extension Named {
    func greeting() -> String { "你好，\(name)" } // 默认实现
}
struct User: Named { var name: String }
struct Robot: Named {
    var name: String
    func greeting() -> String { "编号：\(name)" }
}
func show<T: Named>(_ value: T) {
    print(value.greeting()) // 依赖能力，不依赖 User 或 Robot
}
show(User(name: "小明"))  // 你好，小明
show(Robot(name: "R1")) // 编号：R1

图示说明

别答错：协议扩展不是给所有同名方法提供动态重写；需要多态调用的方法应列入协议要求，见下一题。

进阶补充：协议设计与实际调用方式

通用泛型实现可借助协议见证表选择方法；编译器针对具体类型优化后，也可能直接调用。因此面向协议编程是一种组织接口与复用行为的设计方式，不能等同于“所有调用都动态查表”。它也可以与类继承及其他编程方式结合。

12. 协议扩展的方法为什么有时调用不到自己的实现？

重点理解

回答总结

协议扩展方法如何选择实现，取决于它是否声明为协议要求。协议要求的对应实现在具体类型建立遵循关系时确定，通过协议类型或泛型约束调用时，能够按这份关系选择实现；扩展可以为要求提供默认实现。仅在扩展中新增的方法，则按调用处已知的类型和约束选择，不会再根据实际对象查找同名方法。因此，需要不同遵循者通过同一协议接口表现出不同行为时，应把方法加入协议声明。类继承还需注意：父类若采用扩展默认实现满足要求，子类新增同名方法不会自动替换这份遵循关系；需要支持重写时，应由父类先提供可重写实现，子类再重写。

进一步理解

同一个 Person，为什么换成协议变量后 bye() 变了？

person 的类型是 Person，编译器看得到 Person 自己的 bye()，所以直接调用时得到“自己的 bye”。value 的声明类型是 any Greeter，Greeter 并没有要求 bye()，编译器只根据这个接口选到扩展中的 bye()，不会再到实际对象里搜索同名方法。对象没有变，变化的是调用处知道哪些类型信息。

hello() 为什么又能调用 Person 的实现？

因为 hello() 明确写在 Greeter 的协议声明中。Person 建立协议遵循时，会记录“hello 这个要求由 Person.hello 满足”，这份实现对应关系称为协议见证。通过 any Greeter 调用 hello()，能沿这份关系找到 Person 的实现。因此需要不同遵循者提供各自行为时，应把方法列入协议要求，扩展仍可提供默认版本。

为什么泛型函数里的 bye() 也选扩展版本？

下面 sayBye<T: Greeter> 的通用实现，只知道 T 遵循 Greeter，不知道它一定是 Person。由于 bye 不属于协议要求，它按当前已知的协议约束选用扩展方法，不会因为这次实参恰好是 Person 就改成另一套语义。这也是“把方法写进协议要求”的实际意义，而不是代码书写位置上的偏好。

代码示例（看注释与结果）

protocol Greeter { func hello() -> String }
extension Greeter {
    func hello() -> String { "默认 hello" }
    func bye() -> String { "默认 bye" } // 不是协议要求
}
struct Person: Greeter {
    func hello() -> String { "自己的 hello" }
    func bye() -> String { "自己的 bye" }
}
let person = Person()
let value: any Greeter = person
print(person.bye())  // 自己的 bye：静态类型是 Person
print(value.hello()) // 自己的 hello：协议要求走遵循关系
print(value.bye())   // 默认 bye：仅扩展成员

func sayBye<T: Greeter>(_ value: T) -> String { value.bye() }
print(sayBye(person)) // 默认 bye：调用点只知道 Greeter 约束

}

13. Swift 协议和 Objective-C 协议有什么区别？

重点理解

回答总结

Swift 原生协议可由类、结构体和枚举遵循，支持关联类型、泛型约束及扩展默认实现；Objective-C 协议面向对象，支持必须实现和可选实现的要求。Swift 用 @objc 声明可与 Objective-C 互操作的协议，这类协议只能由类遵循，成员的类型和签名也必须能用 Objective-C 表达，不能直接使用关联类型等 Swift 原生能力。默认实现为要求提供可执行代码，可选要求则允许遵循者根本不实现该方法，因此调用前需检查方法是否存在。Swift 原生协议不能直接用 optional 修饰要求。

进一步理解

有默认实现，和允许不实现，区别在哪里？

下面 Dot 没写 draw()，但协议扩展提供了函数体，所以 Dot().draw() 有代码可以执行，会打印“默认绘制”。Button 没写 optional 的 click()，则可能根本没有这个方法，因此调用时写 button.click?()，先检查方法是否存在。前者是“有一份备用实现”，后者是“允许没有实现”。Swift 原生协议不能直接用 optional 修饰要求。

associatedtype 是给协议留了一个什么空位？

Source 规定“必须能 load 出某种数据”，但不同来源的数据类型可以不同，于是先用 associatedtype Item 留下一个类型名称。NumberSource 把 Item 确定为 Int，load() 就返回 Int。它不是枚举关联值：关联类型决定接口里使用哪种类型，枚举关联值则是某个枚举值随身携带的具体数据。

加上 @objc，为什么不能继续使用所有 Swift 协议能力？

@objc 是让 Objective-C 运行时也能理解这份接口，所以成员类型和签名必须能用 OC 表达，不能直接放入 associatedtype 等 Swift 原生能力。它也把遵循者限定为类，结构体和枚举不能遵循。示例继承 NSObject 是常见互操作写法，不代表所有 @objc 协议遵循者都必须直接继承 NSObject。

代码示例（看注释与结果）

import Foundation

protocol Drawable { func draw() }
extension Drawable {
    func draw() { print("默认绘制") } // 仍然是有实现的协议要求
}
struct Dot: Drawable {}
Dot().draw() // 默认绘制

@objc protocol Clickable: AnyObject {
    @objc optional func click() // 允许遵循者完全不提供方法
}
class Button: NSObject, Clickable {}
let button: any Clickable = Button()
button.click?() // 先检查方法是否存在；本例什么也不做

protocol Source {
    associatedtype Item // 协议声明一个待确定的类型名称
    func load() -> Item
}
struct NumberSource: Source {
    typealias Item = Int // typealias 给已有类型起别名，这里明确 Item 就是 Int
    func load() -> Int { 42 }
}
print(NumberSource().load()) // 42
// @objc 协议不能直接声明这样的 associatedtype

别答错：@objc 协议限制为类，不表示每个遵循者都必须直接继承 NSObject；示例继承 NSObject 是常用互操作写法。

进阶补充：required 与运行时调用的区别

OC 协议中的 required 表示必须实现要求，与 Swift 初始化器的 required 修饰符含义不同。Swift 的 @objc 协议未标 optional 的要求默认必须实现。Swift 原生协议要求的典型调用可经协议见证表，OC 协议方法则使用运行时消息查找；Swift 协议扩展也不能直接当作 OC 协议默认实现机制。

14. Codable 怎么把 JSON 转成模型？自动合成有什么坑？

基础优先

回答总结

Codable 是 Encodable 与 Decodable 的组合；JSONDecoder 将 JSON 数据解码为模型，JSONEncoder 将模型编码为 JSON 数据。符合合成规则、相关属性满足对应协议要求时，编译器可生成实现；CodingKeys 用于指定参与编解码的属性及对应字段名称。合成解码通常将可选字段缺失或 null 处理为 nil，类型不匹配仍会抛错。参与合成解码的可变属性，即使声明了初值，也不会在缺字段时自动回退；需要业务默认值或特殊转换时，应自行实现解码逻辑。子类继承父类的实现，也不会让新增字段自动参与编解码。

进一步理解

JSON 字段和 Swift 属性名不同，解码器怎么对应？

下面模型把属性命名为 name，接口却返回 display_name。CodingKeys 中的 case name = "display_name" 建立对应关系，解码器读取这个 JSON 键，再按 String 类型解码给 name。自动合成就是编译器依据这些属性和键生成常规编解码代码，不是任意 JSON 都能自动变成模型。Codable 同时包含编码与解码能力，也不限于 JSON 格式。

可选字段为什么还会解码失败？

nickname: String? 允许“没有昵称”，所以合成解码在缺少键或值为 null 时通常得到 nil。但如果服务器返回 nickname: 123，这个数字并不是期望的字符串，仍然会抛出类型不匹配错误。可选性解决的是“值可能不存在”，不是“任何类型的数据都接受”。

写了 var retries = 3，为什么缺字段时不自动用 3？

参与合成解码的 var 仍会按字段类型读取 JSON，声明处的初值并不是“读取失败后的备用值”。需要缺键或 null 时使用 3，就自己实现 init(from:)，用 decodeIfPresent 先读取，得到 nil 再通过 ?? 3 补默认值。下面 Settings 的第三组输入是字符串 "bad"，类型错误仍会抛出，而不会回退成 3。

代码示例（看注释与结果）

import Foundation
struct User: Codable {
    let id: Int
    let name: String
    let nickname: String?
    enum CodingKeys: String, CodingKey {
        case id, nickname
        case name = "display_name" // Swift 属性名 ↔ JSON 字段名
    }
}
let data = Data(#"{"id":1,"display_name":"小明"}"#.utf8)
do {
    let user = try JSONDecoder().decode(User.self, from: data)
    print(user.name) // 小明
    print(user.nickname as Any) // nil：可选字段缺失
    let encoded = try JSONEncoder().encode(user)
    print(String(decoding: encoded, as: UTF8.self))
} catch {
    print("编解码失败", error) // 类型不匹配等错误进入这里
}

补充示例：真正实现“缺字段或 null 时用默认值”，而不是只在属性上写初值。这个 Settings 只演示解码，所以使用 Decodable：

struct Settings: Decodable {
    var retries: Int
    enum CodingKeys: String, CodingKey { case retries }
    init(from decoder: any Decoder) throws {
        let container = try decoder.container(keyedBy: CodingKeys.self)
        retries = try container.decodeIfPresent(Int.self, forKey: .retries) ?? 3
    }
}
for json in [#"{}"#, #"{"retries":null}"#, #"{"retries":"bad"}"#] {
    do {
        let value = try JSONDecoder().decode(Settings.self, from: Data(json.utf8))
        print(value.retries) // 缺键、null：都输出 3
    } catch {
        print("类型不匹配，仍然失败") // 字符串 "bad" 不能解为 Int
    }
}

进阶补充：let 初值、CodingKeys 与继承的边界

已有初值的 let 不能被合成解码再次赋值，通常保留声明时的值；未列入 CodingKeys 且有默认值的属性也可保留默认值。这与参与合成解码的 var 不同，不能归纳成“有初值就会回退”。类继承父类的 Codable 实现，也不会让子类新增字段自动参与编解码，需要单独处理。

15. Swift 实例对象、类、元类的内部结构是什么？

进阶选学

回答总结

原生 Swift 类实例通常包含对象头和实例存储属性，对象头关联类型元数据及引用计数管理信息。同一具体类的实例共享类型元数据，用于描述大小、字段布局、继承关系及方法入口等，方法代码不会复制到每个实例。在 Apple 的 Objective-C 互操作环境下，类元数据兼容 OC 类对象，类对象通过 isa 关联 OC 元类，后者承载 OC 类方法相关信息。Swift 元类型用于表示类型本身，与 OC 运行时的元类是不同概念。对象头编码与具体布局受平台及运行时实现影响，不能把概念结构当作固定偏移；对类类型使用 MemoryLayout 测量的是引用表示大小，而非整个堆对象大小。

进一步理解

创建两个 Person，会把方法代码也复制两份吗？

不会。两个实例各自保存 age 等实例数据，也各有运行时管理所需的对象头；描述同一个具体类的信息则可以共享。对象头关联类元数据，让运行时知道“这是什么对象”，类元数据再提供字段布局、方法入口等信息。可以把它理解为每人各有资料，而同一类资料的格式说明共用一份；实际内存编码仍取决于平台与运行时。

Person.self 和 Person() 为什么不是同一种东西？

Person() 创建一个具体的人，里面有这个实例自己的 age。Person.self 表示 Person 这个类型本身，可保存在 Person.Type 的变量里，用于把“类型”作为值传递，并没有因此再创建一个人。Person.Type 也能保存其子类的类型值；这是 Swift 类型系统里的“元类型”。

OC 元类与 Swift 元类型，为什么都带一个“元”字？

在 Apple 的 OC 互操作环境中，还可以把类当作运行时对象来看：对实例调用 object_getClass 得到类，对类对象再调用一次得到 OC 元类。OC 元类承载 OC 类方法相关信息。它与 Person.Type 表达的 Swift 元类型概念不同，不能把两者混为同一种对象，也不能因此推断所有 Swift class func 都走 OC 消息派发。

代码示例（看注释与结果）

import Foundation
import ObjectiveC

class Person: NSObject {
    var age = 18
    @objc class func species() -> String { "Human" }
}
let person = Person()         // 创建实例，保存 age 等实例数据
let typeValue: Person.Type = Person.self // Swift 元类型值，不是新实例
print(type(of: person) == typeValue) // true

if let cls = object_getClass(person), // 运行时类
   let meta = object_getClass(cls) {  // 类对象的运行时类，即 OC 元类
    print(class_isMetaClass(cls))     // false
    print(class_isMetaClass(meta))    // true
}
print(Person.species()) // Human

16. Swift 方法调用如何实现？四种派发怎么区分？

重点理解

回答总结

方法派发是确定一次调用最终执行哪份实现的过程，常见方式有四种。静态派发在编译期确定目标；虚表派发按对象的实际类，从方法表对应位置选择重写实现；协议见证表派发按具体类型与协议的遵循关系查找协议要求的实现；Objective-C 消息派发在运行时根据接收者和方法标识查找实现（IMP）。判断时要结合方法声明、调用处类型信息及编译优化，不能仅按值类型或引用类型划分。@objc 表示暴露给 OC，并不单独保证所有 Swift 调用都走消息派发；在 OC 互操作环境下，@objc dynamic 要求保留运行时动态派发。

进一步理解

变量写成 Animal，为什么调用到了 Dog.sound()？

下面 animal 的声明类型是 Animal，实际指向 Dog。sound 允许子类重写，运行时需要根据实际类选实现；典型做法是在类的方法表中，为这个方法预留一个位置，Dog 的对应位置指向重写版本，所以输出 Woof。这叫虚表派发，不是每次都按方法名从子类向父类逐层搜索。

换成 any Speaker，运行时怎么知道该调用哪个 speak()？

Speaker 只声明能力，不指定唯一实现。Dog 遵循 Speaker 时建立“这个协议要求由 Dog.speak 满足”的记录。通过 speaker.speak() 调用时，可以借助这份协议见证表记录找到入口。虚表关心“实际类如何重写方法”，协议见证表关心“具体类型如何满足协议要求”，两者解决的问题不同。

静态派发与 OC 消息派发，分别怎么找目标？

若调用处已经能确定唯一实现，例如已知 Dog 的 final speak()，就可以直接调用，不必再选择重写版本。OC 消息派发则把接收者和方法标识 selector 交给运行时查找实现，通常先查缓存，必要时查方法列表、父类，或进入动态解析和转发。示例的 @objc dynamic run() 在 OC 互操作环境中采用后一种方式。

代码示例（看注释与结果）

import Foundation
protocol Speaker { func speak() -> String }
class Animal {
    func sound() -> String { "Animal" }
}
class Dog: Animal, Speaker {
    override func sound() -> String { "Woof" }
    final func speak() -> String { "Hello" }
}
class Demo: NSObject {
    @objc dynamic func run() { print("Running") }
}

print(animal.sound()) // Woof：典型虚表调用，找到 Dog 的重写
let speaker: any Speaker = dog
print(speaker.speak()) // 协议要求：典型见证表调用
Demo().run() // @objc dynamic：采用 Objective-C 动态派发

别答错：不能说“struct 永远静态、class 永远虚表”：struct 经协议接口可走见证表，class 的 final 方法可直接调用。

进阶补充：声明规则与优化后的机器代码

@objc 表示暴露给 Objective-C，单凭它或继承 NSObject，不能断言每次 Swift 调用都走消息派发。@objc dynamic 在这里要求使用运行时动态派发。对于虚表或见证表调用，优化器若能证明最终目标，也可能改成直接调用，这称为去虚化。因此既不能说“class 永远走虚表”，也不能把静态派发与 static 关键字画等号。

17. Swift 协议内部是什么？见证表、存在容器怎么理解？

进阶选学

回答总结

Swift 协议的运行时表示涉及协议描述符、协议见证表、类型元数据、值见证表和存在容器。协议描述符记录协议身份与要求；协议见证表记录具体类型如何满足协议要求，用于查找对应实现；类型元数据描述具体类型，并关联负责复制、销毁等管理操作的值见证表。any 协议值通过存在容器保存实际值及操作所需的类型和协议实现信息，大小与对齐合适时可放入内部缓冲区，否则需要外部存储。存在容器的具体布局取决于协议约束和平台；泛型也可以利用元数据与见证表，但不要求先构造存在容器。

进一步理解

只知道 any Speaker，为什么仍然能调用 speak()？

下面 small 装 Dog，large 装 BigSpeaker，调用方只使用 Speaker 接口。运行时既要保存实际值，也要知道它的具体类型，还要能找到它如何实现 speak()。承载这些值与必要信息的表示称为“存在容器”。因此 any Speaker 不是一个完全丢失类型信息的黑盒，而是让调用方通过统一接口使用不同具体值。

协议见证表和值见证表，为什么要分开？

调用 small.speak() 时，需要知道“Dog 如何实现 Speaker.speak”，这是协议见证表负责的事。复制或销毁容器内的值时，需要知道“Dog 这种值怎样复制或销毁”，这是值见证表负责的事，并通过类型元数据关联。协议描述符则说明 Speaker 这个协议是谁、提出哪些要求。把它们分开看，就是接口说明、接口实现记录、具体类型说明和值管理规则。

值太大放不下，存在容器怎么办？

普通非类限定协议的典型表示带有一小块值缓冲区。值的大小与对齐合适时，可直接放进去；BigSpeaker 有四个 Int，在示例的常见三机器字缓冲区里放不下，就需要容器之外的存储。两者都能调用 speak()，差别在于存放和管理成本。下面 MemoryLayout 测量的是容器自身，不会把外部存储也加进去。

18. async/await 和 GCD 有什么区别？await 会阻塞线程吗？

重点理解

回答总结

await 标记可能挂起的位置；真正挂起时，任务保存状态并让出执行资源，不会占住线程等待结果。GCD 用队列和代码块组织任务提交与调度，Swift 的 async/await 用可挂起的异步函数表达流程，并与错误处理、结构化并发、取消和 actor 隔离配合。GCD 的 async 表示提交后不等待完成，Swift 的 async 表示函数允许异步挂起。结果就绪后，挂起的任务会被调度恢复，但 await 不保证一定挂起或切换线程；异步函数中的同步计算和阻塞操作仍会占用线程。执行位置还受隔离规则及编译设置影响，不能认为加上 async 或 Task 就一定在后台执行。

进一步理解

await 等网络结果时，线程在做什么？

可以把任务理解为“先请求，再处理结果”这份工作。网络结果没回来时，任务若在 await 处真正挂起，会保存“回来后从哪里继续”的状态，并让出执行资源，线程可以去做别的工作。结果就绪后再安排任务继续，恢复时未必还是原来的线程。await 只标记可能挂起的位置；如果结果已经就绪，也可能直接继续执行。

为什么 async 函数也可能让界面卡顿？

给函数加 async，只表示它可以异步挂起，不会自动把每一行代码搬到后台。如果它在主 actor 上连续进行大量同步计算，这段计算仍占用执行线程，界面就可能没机会更新。Task {} 也可能继承当前位置的主 actor 隔离，所以把计算包进 Task 并不能单凭这一点解决卡顿。同步 I/O 和信号量等待同样不会因为出现在 async 函数里就变成非阻塞操作。

GCD 的 async 与 Swift 的 async，为什么容易混淆？

DispatchQueue.async 表示“把代码块提交到队列，提交方不等它做完”；Swift 函数上的 async 表示“这份工作允许在执行途中挂起”。前者主要组织队列与回调，后者让后续处理写在 await 后面，用返回值和 throws 传递结果。它们可以配合使用；是否在后台执行，还要看队列、actor 隔离和执行规则，不能只看 async 这个单词。

代码示例（看注释与结果）

import Foundation
import Dispatch

// GCD：提交代码块，结果常通过回调传递
// @Sendable：闭包可能跨并发隔离使用，编译器会检查它捕获的值是否安全，见第 20 题
// 此处没有捕获外部可变状态；@Sendable 不表示这段闭包会自动异步执行
func gcdName(completion: @escaping @Sendable (String) -> Void) {
    DispatchQueue.global().async {
        completion("小明") // 这里的回调不保证在主线程
    }
}

// async/await：用返回值表达后续结果
func asyncName() async throws -> String {
    try await Task.sleep(for: .milliseconds(10)) // 模拟非阻塞等待
    return "小明"
}
func demo() async throws {
    let name = try await asyncName() // 当前任务可能挂起
    print(name) // 等调用返回后，继续执行
}
try await demo() // 单独 Swift 文件的顶层异步入口

19. async let、TaskGroup、Task 有什么区别？怎么取消？

重点理解

回答总结

async let 和 TaskGroup 用于创建结构化子任务：前者适合数量固定的任务，后者适合运行时动态添加任务。子任务生命周期受作用域管理，退出前必须等待它们结束，取消沿结构化父子关系传播。Task {} 创建非结构化任务，生命周期不受创建作用域约束，也不会仅因创建者取消就自动取消，需要通过任务句柄等待结果或主动取消。Swift 采用协作式取消，cancel() 只发出请求，任务需通过取消检查或支持取消的异步操作响应，因此请求取消不等于任务已经结束。任务组通常按完成顺序提供结果，不保证与添加顺序一致。

进一步理解

同时请求两份数据，为什么适合 async let？

若页面固定需要用户资料和订单，可以启动两个 async let，再等待两份结果。它们是当前任务下的结构化子任务，作用域结束前必须收尾，不会悄悄遗留在外面继续运行。若请求数量由列表长度决定，就用 TaskGroup 在循环中添加任务。任务组通常按完成顺序提供结果；需要原始列表顺序时，要随结果带上索引并重排。

为什么 cancel() 之后还需要 await？

cancel() 发出“请尽快结束”的请求，不会强行打断正在执行的每一行代码。任务要通过 checkCancellation()、isCancelled，或能响应取消的 API 发现请求，再退出。下面 Task.sleep 能响应取消，而 await handle.value 用于等到任务真正结束。若任务已经完成，再调用 cancel() 也不会撤回已经完成的结果。

离开函数后，Task {} 为什么还可能继续运行？

Task {} 创建非结构化任务，它的生命周期不被创建它的作用域包住。创建者返回或被取消，不代表这个任务自动结束；需要保存任务句柄，按业务等待或请求取消。它通常会继承创建位置的 actor 隔离等上下文，但“继承上下文”不等于“建立结构化父子关系”。因此不能把所有 Task 都当成 async let 一样管理。

    try Task.checkCancellation() // 已取消则抛 CancellationError
    return id
}

    async let a = fetch(1) // 固定数量的两个子任务
    async let b = fetch(2)
    let values = try await (a, b)

        for id in 1...3 {
            group.addTask { id } // 动态数量；结果按完成顺序收集
        }
        var sum = 0
        for await value in group { sum += value }
        return sum
    }

    print(await loadMany())     // 6

20. actor、@MainActor、Sendable 各自解决什么问题？

重点理解

回答总结

actor 通过隔离规则限制外部访问，使自身的隔离代码串行执行，避免对这些状态发生数据竞争。异步方法在 await 真正挂起时，其他任务仍可能进入同一 actor，这种重入意味着恢复后应重新检查依赖状态，不能把整个方法当作不可分割的事务。@MainActor 将声明隔离到全局主 actor，在 iOS 中常用于约束 UI 状态的访问，但不会自动移走同步耗时计算。Sendable 表示类型的值可以安全地跨隔离域传递或共享，需要类型本身满足相应安全条件，并不会自动加锁。

进一步理解

actor 是怎样保护共享计数器的？

假设两个任务同时给普通变量加 1，可能都先读到 0，再各自写入 1，漏掉一次计数。下面 Counter 把 value 放在 actor 的隔离范围内，increment() 中没有 await，读、加、写这一段不会与其他任务对该 actor 的访问交错。外部调用要经过 actor 的访问规则，而不是直接随意读写 value。actor 管理的是访问顺序，不是为每个实例分配一条专用线程。

既然 actor 会串行访问，为什么提款还要检查两次余额？

设余额是 100，两笔提款各要取 80。第一笔检查余额足够后，await 等待授权；如果此时真正挂起，第二笔就可能进入 actor，也通过第一次余额检查。等两笔恢复时，余额可能已经被另一笔修改。恢复后重新检查，并在检查到扣款之间不再 await，才能防止两笔都成功。允许挂起期间进入其他任务叫“重入”，所以整个异步方法不能自动当作一个不可打断的事务。

@MainActor 与 Sendable 为什么不能互相替代？

ScreenModel 的 title 是 UI 状态，用 @MainActor 约束它在哪里访问和修改。Snapshot 则是传递给它的一份计数结果，Sendable 表达“这种值可以安全跨隔离域传递或共享”。前者管访问隔离，后者管跨域值的安全条件。Sendable 不会自动加锁；@MainActor 也不会把其中的同步重计算移走，不能当成解决卡顿的开关。

代码示例（看注释与结果）

actor Counter {
    private var value = 0
    func increment() -> Int {
        value += 1 // 本段没有 await，检查与修改都在隔离内完成
        return value
    }
}
struct Snapshot: Sendable { let count: Int }

@MainActor
final class ScreenModel {
    private(set) var title = "0"
    func apply(_ snapshot: Snapshot) {
        title = String(snapshot.count) // 在主 actor 上更新 UI 状态
    }
}
func demo() async {
    let counter = Counter() // actor 是引用类型，赋值会共享同一实例
    let number = await counter.increment() // 跨 actor 可能需要等待调度
    let snapshot = Snapshot(count: number)
    let model = await ScreenModel()
    await model.apply(snapshot)
    print(await model.title) // 1
}
await demo()

    private var balance = 100

        _ amount: Int,

        guard await authorize() else { return false } // 可能挂起：其他提款可进入

        return true
    }
}

// @Sendable 约束 authorize 的捕获安全，async 表示它可能异步挂起。

let wallet = Wallet()
async let firstWithdrawal = wallet.withdraw(80) {
    try? await Task.sleep(for: .milliseconds(10)) // 模拟等待授权结果
    return true
}
async let secondWithdrawal = wallet.withdraw(80) {
    try? await Task.sleep(for: .milliseconds(10))
    return true
}
let withdrawals = await (firstWithdrawal, secondWithdrawal)
print([withdrawals.0, withdrawals.1].filter { $0 }.count) // 1：余额只够一笔
// 哪一笔成功不保证；第二次检查确保不会两笔都扣款。

别答错：把“读余额 → await 授权 → 扣钱”写进 actor 也可能出逻辑错误，恢复后应重新验证余额或重新设计状态机。

进阶补充：Sendable 的检查与 actor 调用边界

结构体、枚举的相关成员需满足 Sendable 条件；普通非隔离类通常需要 final、存储属性不可变且 Sendable，全局 actor 类等另有规则，actor 自动满足 Sendable。@unchecked Sendable 是开发者自行承担同步正确性的承诺，不会生成保护代码。同一隔离内调用同步方法无需 await，跨隔离通常需要；普通 actor 不保证严格先进先出，@MainActor 同步函数也不能理解为从任意上下文调用都会自动跳线程。
