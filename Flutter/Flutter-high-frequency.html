1. extends、implements 和 mixin

重点理解

回答总结

extends 继承父类实现，implements 要求满足接口，with 把 mixin 的实现加入类。 在类修饰符允许的范围内，一个类可以直接继承一个父类，实现多个接口。接口的方法体不会随 implements 带入，具体类需要自己提供实现，或从父类和 mixin 获得实现。

mixin 可以用 on 声明它依赖的超类能力。使用该 mixin 的类必须先满足这一约束，这样 mixin 才能使用约束类型提供的成员。

同名方法的签名兼容时，类自己声明的实现优先。接着按 with 的列表从右向左查找，最后到父类。只有当前实现调用 super，才会继续执行查找链上的实现。

代码示例（看注释与结果）

class Animal { void breathe() => print('呼吸'); }
abstract interface class Runnable { void run(); }
class Dog extends Animal implements Runnable {
  @override
  void run() => print('跑');
}
mixin Walk on Animal { void go() => breathe(); }
class Cat extends Animal with Walk {}
mixin First { void say() => print('First'); }
mixin Second { void say() => print('Second'); }
class Mixed with First, Second {}

void main() {
  Dog().run(); // 跑
  Cat().go(); // 呼吸：复用了 Animal 的方法
  Mixed().say(); // Second：后面的同名实现优先，不会自动输出 First
}

别答错：implements 不带来方法实现，多个 mixin 也不会自动依次执行同名方法。

进阶补充：mixin 与类修饰符的库边界

mixin 不能声明构造函数；mixin class 可以同时作为类与 mixin，不能声明生成构造，但可以声明 factory。Dart 3 中 interface 限制库外继承，base 限制库外实现，final 同时限制库外继承和实现，sealed 将直接子类型限制在当前库。base 的子类型还需使用相应修饰符。这些限制中的库通常指一个 Dart 文件及其 part 文件，不是整个 package。

官方核对：类修饰符与库边界。

2. Future 和 async / await

重点理解

回答总结

Future 代表一个“以后才会拿到”的结果，await 让异步代码能像同步代码那样按顺序往下写。 加了 async 的函数在遇到第一个 await 之前都会立刻同步执行；等它遇到还没完成的 Future 时，当前函数就会先暂停交出控制权，让所在的 isolate 去处理点击、绘制等其他事情，等结果回来了再接着往下跑。

想用 try / catch 接住异步错误，就必须把 await 写在 try 里面。如果调用时没写 await，try / catch 只接得住同步抛出的异常，异步错误必须另外给返回的 Future 挂上 .catchError() 来处理。

需要同时等好几个请求都成功时，用 Future.wait，它会按传入的顺序把结果一起返回。如果想把“回调式老接口”封装成 Future，可以用 Completer 手动触发完成或报错（每个 Completer 只能完成一次）。还要记住：把耗时的纯 CPU 循环塞进 Future 并不等于开了多线程，跑起来时照样会卡住当前 isolate。

代码示例（看注释与结果）

import 'dart:async';

Future<int> fetch() async {
  print('开始');
  await Future<void>.delayed(Duration.zero);
  throw FormatException('模拟失败');
}
Future<int> load() async {
  try {
    return await fetch(); // await 把 Future 的错误送到这个 catch
  } on FormatException {
    return 0;
  }
}
Future<void> main() async {
  final pending = load();
  print('调用后');
  print(await pending);
  // 输出顺序：开始、调用后、0
  // 错误示例（不执行）：try { fetch(); } catch (_) {}
  // 上面的 catch 只能接同步抛出，不能接 fetch 返回的 Future 的异步错误。
}

进一步理解

把大循环放进 Future，为什么界面还是卡？

Future(() { ... }) 把回调排到当前 isolate 的事件队列。轮到它执行时，循环仍会占住这个 isolate，输入和构建只能等。异步 I/O 则能在等待期间让出执行机会。CPU 计算的并行处理见第 5 题。

别答错：Future 不会自动把同步计算搬到后台，异步错误要在正确的等待位置处理。

进阶补充：多个 Future 的错误时序

Future.wait 默认会等所有任务都结束，再把最先遇到的错误抛出来；如果把 eagerError 设为 true，只要有一个失败就会立刻报错，但其余还在跑的任务仍会继续执行完。另外，不要想当然以为“每多写一个 then 就一定会按固定微任务顺序排队”，因为像 Completer.sync 这类同步完成的特例，回调触发时机和普通 Future 不太一样。

官方核对：Future 的同步完成特例。

基础语法：Future 与 async/await。

3. Future 和 Stream 有什么不一样

重点理解

回答总结

一次性的结果（比如发一次网络请求）用 Future，源源不断产生的数据流（比如倒计时、蓝牙消息、下载进度）用 Stream。 流在结束时会发一个完成通知。想自己制造一条流，可以用 async* 配合 yield 往外吐数据；接收方可以用 await for 一条条等，或者用 listen 拿到订阅对象，随时暂停、恢复或取消。

Stream 分两种：单订阅流一辈子只能被监听一次；广播流允许同时有多个监听者，但普通广播流不会“补发历史消息”，你什么时候开始监听，就只能收到那之后的新事件。

界面上展示流数据常用 StreamBuilder，它能自动管理订阅和释放。不过它只按屏幕刷新节奏（按帧）更新 UI：如果同一帧里连续推来好几条数据，StreamBuilder 可能只按最后一条状态刷新，中间几条就跳过了。所以像记日志、累加计数这种“每条数据都不能漏”的业务逻辑，别写在 StreamBuilder 的 builder 里，而要放在流的监听回调里。自己手动 listen 的订阅，记得在不用时取消。

代码示例（看注释与结果）

Stream<String> messages() async* {
  yield 'hello';
  yield 'stop';
  yield '不会打印';
}
Future<void> main() async {
  await for (final event in messages()) {
    print(event);
    if (event == 'stop') break; // 退出时取消本次订阅
  }
  print('结束');
  // 输出顺序：hello、stop、结束
}

进一步理解

后来才监听，能收到先前的数据吗？

普通广播流只把事件交给当时的监听者。单订阅 StreamController 可以在首次监听前缓冲，async* 生成器通常在订阅开始后才运行。

为什么不要在 build 中反复 listen？

同一节点可以构建多次，每次手动监听都可能累加订阅。把订阅放在对应的生命周期内并在退出时取消，或交给 StreamBuilder。需要逐笔处理的逻辑放在事件消费端。

别答错：StreamBuilder 不保证呈现每个中间事件，不应承担逐事件业务处理。

进阶补充：暂停订阅与流错误

广播流虽然不会给后来者补发历史事件，但如果某个已经存在的监听者调用了暂停（pause），部分流实现可以为其暂存期间的数据。另外，在 await for 的循环体里做异步等待时，底层可能会自动暂停订阅来控速；如果流里抛出了未处理的错误，await for 循环会直接中断并把错误抛出来。

官方核对：StreamBuilder 快照与构建时序。

4. Dart 是不是单线程？事件循环怎么跑

重点理解

回答总结

单个 isolate 同一时刻只执行一段 Dart 代码。 异步等待可以让它在此期间处理其他事件，在 Dart VM 等支持的平台上，多个 isolate 还可以并行计算。

当前同步代码结束后，事件循环先清空微任务队列，再取一个普通事件。普通事件处理完成后，再清空执行期间新增的微任务。

微任务不能打断同步代码。持续补充微任务会让点击、定时器等普通事件排不上；长时间运行的同步计算也会占住当前 isolate。

代码示例（看注释与结果）

import 'dart:async';

void main() {
  print('同步开始');
  Timer.run(() => print('普通事件'));
  scheduleMicrotask(() => print('微任务'));
  print('同步结束');
}
// 输出：同步开始 → 同步结束 → 微任务 → 普通事件
// 微任务虽然后写，仍先于下一个普通事件；不会打断当前同步代码。

5. Isolate 是什么，和 Future 有什么区别

重点理解

回答总结

Future 管“什么时候拿到结果”（异步等待），isolate 管“代码到底在哪块隔离的内存里跑”（并发执行）。 直接在当前线程里建一个 Future，里面的 Dart 代码还是在当前 isolate 排队执行；而在 Dart VM 等平台上，多个 isolate 可以真正利用多核并行计算。

每个 isolate 都有自己独立的内存堆和事件循环，互相之间不能直接读写对方的普通变量，也就省去了传统多线程加锁、死锁的麻烦。它们只能通过 SendPort 和 ReceivePort 收发消息（支持基本类型、简单集合等，大对象默认需要复制一份过去）。如果只是一次性重计算，直接用 Isolate.run 最省事；需要长期双向通信时，再用 Isolate.spawn。

像网络请求、读文件这类“等待型”异步任务，直接用 Future 就够了，没必要新开 isolate；只有大图压缩、大 JSON 解析这类“纯吃 CPU”的重活才值得放进后台 isolate（同时还要权衡创建 isolate 和传递数据的开销）。Flutter 提供的 compute 在手机和桌面端会启用后台 isolate，但在 Web 端会退化为在当前事件循环里执行，这一点面试别答错。

代码示例（看注释与结果）

纯 Dart 示例，用 Dart VM 运行；这里展示 Isolate.run，不适用于浏览器。

import 'dart:isolate';

int sumSquares(int count) {
  var total = 0;
  for (var i = 1; i <= count; i++) {
    total += i * i;
  }
  return total;
}

Future<void> main() async {
  final result = await Isolate.run(() => sumSquares(10000));
  print(result); // 333383335000：计算在另一个 isolate 中完成
  // 数量仅为演示；是否值得拆出 isolate，应测量真实计算与通信成本。
}

进一步理解

大量字节怎样交给另一个 isolate？

普通 List 跨 isolate 发送时通常要把整份数据拷贝一份，字节多了开销很大。对于大块二进制数据（如图片字节），可以用 TransferableTypedData 包装：虽然用 fromList 包装时会先复制一次原始字节，但随后跨 isolate 发送包装对象时只需要“移交所有权”，接收方直接拿走底层内存，不再发生跨线程拷贝（作为代价，发送端发出去后就不能再通过这个包装读取数据了，而原来的普通数组如果还在手里则不受影响）。

图示说明

别答错：普通 Dart 可变对象不跨 isolate 直接共享，Web compute 不等同于后台并行。

进阶补充：消息传递与端口释放

像字符串、数字等底层确认不可变的数据在部分版本中可以直接共享引用，减少拷贝；但绑定了原生底层句柄的对象（如部分文件句柄、Socket）无法跨 isolate 发送。Isolate.exit 可以在工作 isolate 结束使命时顺手把最终结果“移交”给主 isolate，省去一次额外拷贝。另外，手动创建的 ReceivePort 不用时记得调 close()，否则会让 isolate 一直挂着不退出。如果走 FFI 共享原生 C 内存，就得自己处理线程同步与内存释放。

6. Widget 有哪几类，为什么不能改

重点理解

回答总结

Widget 是不可变配置。配置需要变化时，新建 Widget，由框架更新对应的 Element。 可变数据放在 State 或其他状态持有者里。

StatelessWidget 根据构造参数和祖先依赖构建界面，父级传入新配置或相关依赖变化时都可能重建。StatefulWidget 的配置也不可变。State 由对应的 StatefulElement 关联，原节点复用时可以保留。同一份 State 改完数据后，还要通知框架构建。

InheritedWidget 向后代提供可订阅数据。RenderObjectWidget 创建或更新渲染对象。ParentDataWidget 把子节点的布局参数交给配套的父布局。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: Counter())));

class Counter extends StatefulWidget {
  const Counter({super.key}); // Widget 配置没有可变的 count 字段
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int count = 0; // 可变数据放在 State
  @override
  Widget build(BuildContext context) => Center(child: TextButton(
    onPressed: () => setState(() => count++),
    child: CountLabel(count: count), // 每次传入当前值，创建新的配置
  ));
}

class CountLabel extends StatelessWidget {
  const CountLabel({super.key, required this.count});
  final int count; // 这份 Widget 配置创建后不能修改
  @override
  Widget build(BuildContext context) => Text('计数：$count');
}
// 点击后从 0 变 1：State 更新，CountLabel 得到新参数并再次 build。

别答错：State 不保存在某一份 Widget 配置中，StatelessWidget 也可以多次重建。

进阶补充：其他 Widget 基类的职责

InheritedWidget 和 ParentDataWidget 属于 ProxyWidget，不自行创建 RenderObject。RenderObjectWidget 按孩子数量还有 Leaf、SingleChild、MultiChild 等基类。Widget 的不可变约定也不意味着 final 字段指向的 List 会自动不可变，配置对象引用的数据仍应遵守相应不可变设计。

延伸核对：Widget 配置与节点更新。

7. State 的生命周期

重点理解

回答总结

State 首次挂载时，框架依次调用 initState、didChangeDependencies 和 build。 每份 State 的 initState 只执行一次。主题等 InheritedWidget 依赖放在 didChangeDependencies 或 build 中登记。

收到祖先的依赖更新通知后，框架会调用 didChangeDependencies。原节点收到类型和 Key 都匹配的新配置时，框架调用 didUpdateWidget，随后构建。依赖配置的请求或订阅可在这个回调里更新。

deactivate 表示节点离开当前位置。若同一帧结束前没有重新插入，框架才调用 dispose。在 dispose 中释放控制器、取消订阅。异步结果回来后，先确认 State 仍挂载且未开始销毁，再更新界面。

应用切到前台或后台时，用应用生命周期回调处理。State 的挂载状态只描述它所关联的树节点。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: LifecycleDemo()));

class LifecycleDemo extends StatefulWidget {
  const LifecycleDemo({super.key});
  @override
  State<LifecycleDemo> createState() => _LifecycleDemoState();
}

class _LifecycleDemoState extends State<LifecycleDemo> {
  int version = 1;
  bool visible = true;
  @override
  Widget build(BuildContext context) => Scaffold(body: Column(children: [
    TextButton(onPressed: () => setState(() => version++),
      child: const Text('更新配置')),
    TextButton(onPressed: () => setState(() => visible = !visible),
      child: const Text('移除 / 插入节点')),
    if (visible) Probe(version: version), // 同位置、同类型、没有 key
  ]));
}

class Probe extends StatefulWidget {
  const Probe({super.key, required this.version});
  final int version;
  @override
  State<Probe> createState() => _ProbeState();
}

class _ProbeState extends State<Probe> {
  @override
  void initState() { super.initState(); debugPrint('initState'); }
  @override
  void didChangeDependencies() {
    super.didChangeDependencies();
    debugPrint('didChangeDependencies');
  }
  @override
  void didUpdateWidget(Probe oldWidget) {
    super.didUpdateWidget(oldWidget);
    debugPrint('配置：${oldWidget.version} → ${widget.version}');
  }
  @override
  Widget build(BuildContext context) {
    debugPrint('build');
    return Text('版本 ${widget.version}');
  }
  @override
  void deactivate() { debugPrint('deactivate'); super.deactivate(); }
  @override
  void dispose() { debugPrint('dispose'); super.dispose(); }
}
// 首次：initState → didChangeDependencies → build。
// 点击“更新配置”：didUpdateWidget → build，不再执行 initState。
// 移除后等一帧：deactivate → dispose；再插入会创建新的 State。

进一步理解

页面换了用户编号，为什么仍显示旧数据？

父级可以沿用原节点，只更换配置里的用户编号。这时 initState 不会重跑。可在 didUpdateWidget 比较两个编号，取消旧用户的订阅或请求，再开始加载新用户。

为什么资源释放放在 dispose？

节点在 deactivate 后仍可能在同一帧重新挂回。过早释放控制器或订阅，恢复时就会缺少需要的资源。系统直接结束进程时，也不能指望框架有机会逐个调用 dispose。

图示说明

别答错：deactivate 不等于销毁，dispose 期间 mounted 仍可能为 true。

进阶补充：super 调用、mounted 与应用生命周期

initState 中先调用 super.initState；deactivate、dispose 通常在自己的处理结束后调用对应 super。dispose 执行期间 mounted 可能仍为 true，不能因此认为此时还能 setState。应用前后台变化应使用 WidgetsBindingObserver 或 AppLifecycleListener，开发期 reassemble 用于热重载，不能替代正式运行中的初始化或生命周期管理。

延伸核对：State 的完整生命周期。

8. setState 做了什么

重点理解

回答总结

setState 先同步执行回调，再把当前 Element 标记为需要重建。 回调改完字段后就能读到新值，画面会在后续构建和渲染之后更新。

只修改字段不会自动通知框架。调用 setState 也不会比较字段的新旧值。同一个节点在构建前被标记多次，通常可以合并处理。子节点能否复用取决于新旧配置的匹配情况，已有的相同配置也可以跳过更新。

先等待异步结果，确认 State 仍有效，再用同步回调写入。setState 的回调不能返回 Future，销毁期间和销毁后都不能调用。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: Counter())));
class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}
class _CounterState extends State<Counter> {
  int count = 0;
  Future<void> addLater() async {
    await Future<void>.delayed(const Duration(milliseconds: 300));
    if (!mounted) return;
    setState(() => count++); // 同步更新数据，再请求构建
    debugPrint('字段已经是 $count'); // 不必等画面绘制就能读到新值
  }
  @override
  Widget build(BuildContext context) {
    debugPrint('build：$count');
    return Center(child: TextButton(
      onPressed: addLater, child: Text('计数：$count'),
    ));
  }
}
// 点击：等待 300ms → 更新字段 → 下一次构建显示新值。
// 不要写 setState(() async { await ...; count++; })。

进一步理解

为什么要先 await，再调用 setState？

框架在回调同步执行完后安排重建。如果把异步等待写进回调，等待之后的字段更新可能错过这次构建。先做完异步工作，确认 State 仍有效，再把字段修改放进同步回调。

别答错：setState 回调不能是 async，也不能在 dispose 后调用。

延伸核对：setState 的同步执行与构建通知。

9. BuildContext 是什么

重点理解

回答总结

BuildContext 是 Element 实现的接口，代表组件在树上的位置。 用它查找祖先时，只会向上查。要读取当前 build 刚创建的数据提供者，取提供者下方节点的 context，例如让 Builder 提供一个更内层的位置。

依赖式读取会为当前 Element 登记依赖，祖先更新时可以通知它。普通查找只取得结果。State 可在 didChangeDependencies 或 build 中登记祖先依赖。

跨过 await 后，使用 context 前要检查该 context 的 mounted。页面等待期间可能已被移除，另一个节点的挂载状态无法证明当前 context 依然有效。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const Demo());
class Demo extends StatelessWidget {

10. Key 有什么用

重点理解

回答总结

Key 帮框架把新 Widget 和旧节点对应起来。 在同一父节点匹配子项时，runtimeType 和 key 都相同，框架才可以用新配置更新原 Element，有状态节点才能保留原 State。

ValueKey 比较值，ObjectKey 比较对象身份，每个 UniqueKey 实例都有独立身份。把稳定 Key 放在父节点直接匹配的子项上，同层子项的 Key 要唯一。懒列表重排时，可能还要用 findChildIndexCallback 提供新索引。

GlobalKey 可以在同一帧内把节点迁到其他父节点下，还可访问关联的 context 或匹配的 State。应长期保存该 Key，并保证同时挂载的节点中唯一。State 已经销毁后，Key 无法恢复它。

11. InheritedWidget 是干什么的

重点理解

回答总结

InheritedWidget 让后代读取祖先提供的数据，并按需要登记依赖。 共享数据可由外部 State 持有，InheritedWidget 自身仍是不可变配置。

dependOnInheritedWidgetOfExactType 查找最近且精确匹配类型的祖先，并把当前 Element 记为依赖者。非依赖式查询只读取当下的结果。

新配置到来后，updateShouldNotify 决定是否通知已登记的节点。返回 false 时，新配置仍然换上。需要订阅数据的某一部分时可以用 InheritedModel，需要转发可监听对象的通知时可以用 InheritedNotifier。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: ShareDemo())));
class CountScope extends InheritedWidget {
  const CountScope({super.key, required this.count, required super.child});
  final int count;
  static int of(BuildContext context) =>
      context.dependOnInheritedWidgetOfExactType<CountScope>()!.count;
  @override
  bool updateShouldNotify(CountScope oldWidget) => count != oldWidget.count;
}
class ShareDemo extends StatefulWidget {
  const ShareDemo({super.key});
  @override
  State<ShareDemo> createState() => _ShareDemoState();
}
class _ShareDemoState extends State<ShareDemo> {
  int count = 0;
  @override
  Widget build(BuildContext context) => CountScope(
    count: count,

      TextButton(onPressed: () => setState(() => count++),
        child: const Text('加一')),
      const CountText(), // 同一个常量配置，依赖通知仍可使它重建
    ]),
  );
}
class CountText extends StatelessWidget {
  const CountText({super.key});
  @override
  Widget build(BuildContext context) => Text('共享计数：${CountScope.of(context)}');
}
// 状态由 ShareDemo 持有；CountScope 传递数据并通知已登记的依赖者。

12. 状态管理怎么选

重点理解

回答总结

选状态管理不要先背框架名字，先回答清楚四个问题：状态归谁管、谁能改、谁需要跟着刷新、不用时什么时候释放。 只是单个页面或小组件自己用的状态（比如开关、计数器），直接用 setState 最干净；如果局部有几处需要联动但不想重建整棵子树，用 ValueNotifier + ValueListenableBuilder 就能精准刷新。

需要跨组件、跨页面共享时再上状态管理库：InheritedWidget / Provider 顺着组件树往下传数据，轻量且好上手；Riverpod 脱离了 BuildContext 的树位置限制，用容器统一管理依赖和生命周期，方便测试和组合；Cubit 通过调方法直接发新状态，直观好写；Bloc 则把所有交互抽象成 Event → State 的单向流，适合状态流转复杂、需要严格追溯和团队规范的中大型项目。

想控制刷新范围，关键在于“把监听点放得足够小”：只在真正展示数据的叶子组件里去监听，如果一个大对象里只有某个字段变了，就用 select 只盯着那个字段。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: LocalCounter())));
class LocalCounter extends StatefulWidget {
  const LocalCounter({super.key});
  @override
  State<LocalCounter> createState() => _LocalCounterState();
}
class _LocalCounterState extends State<LocalCounter> {
  final count = ValueNotifier<int>(0); // 此 State 持有并释放状态
  @override
  Widget build(BuildContext context) => Column(children: [
    TextButton(onPressed: () => count.value++, child: const Text('加一')),
    ValueListenableBuilder<int>(
      valueListenable: count, // 只有这个 builder 订阅 count
      builder: (_, value, child) => Text('计数：$value'),
    ),
    const Text('这段文字没有订阅 count'),
  ]);
  @override
  void dispose() { count.dispose(); super.dispose(); }
}
// 修改 count.value 会通知监听者，不需要重建整个 LocalCounter。
// 先把持有者、修改入口、订阅范围和释放位置说清，再考虑共享状态方案。

进一步理解

read、watch 和 select 分别做什么？

简单记：read 只“拿一次当前值”（比如点击按钮时调方法），不订阅后续变化；watch 是“一直盯着”，数据一变当前组件就重建；select 是“只盯着其中某一个字段”。要注意，这些库大多通过新旧值比较（==）来判断是否刷新——如果你直接往一个 List 里 add 元素而不是返回新列表，前后引用指向的还是同一个对象，比较结果相等，UI 就不会刷新（父组件自己重跑 build 的情况除外）。

一个计数器和跨页面订单怎样选？

局部计数只由当前组件使用，用 setState 就能管理。订单需要被多个页面读取，还可能涉及请求、缓存和失败重试，可以用独立的共享状态持有者明确这些规则。

别答错：只修改可变对象内部内容，不一定触发值比较式通知。

进阶补充：通知机制与自动销毁别混用

ValueNotifier 只有在新旧 value 不相等时才自动通知（原地改内部元素不触发），而 ChangeNotifier 必须手动调 notifyListeners()。不同库的精细控制手段也别记混：Provider/Riverpod 常用 watch、read、select，Bloc 用 buildWhen 控制重建条件，GetX 则要分清响应式 Obx 和手动更新的 GetBuilder。另外，Riverpod 是否在页面退出后自动释放状态，要看定义时是否开启了自动销毁（autoDispose）以及当前版本和容器生命周期，并不是所有 Provider 默认都会自动清零。

官方核对：Riverpod 自动销毁与版本 API。

13. Navigator 和 MaterialApp 做了什么

重点理解

回答总结

Navigator 就像管理页面“栈”的调度员（压栈打开新页、出栈返回上一页），而 MaterialApp 是应用的大管家，顺带帮你配好主题、多语言和顶层导航器。 普通写法用 MaterialApp 就自带了一个开箱即用的 Navigator；如果需要深度适配浏览器 URL 或复杂深链接，则改用 MaterialApp.router，把页面栈交由 Router 规则统一生成。

调 push 打开新页面时，它会返回一个 Future 等着接收结果；新页面调 pop(result) 关闭时，就能把这个结果传回给上一页。默认用 MaterialPageRoute 跳转时，被盖在下面的旧页面其实还留在树里没被销毁，只是看不见了。

Navigator.of(context) 会顺着组件树往上找最近的那一层导航器。如果页面里嵌套了局部导航（比如底部 Tab 里各自有独立子栈），跳转时要传对内层或外层的 context；另外跳转代码要放在点击回调或明确的生命周期流程里，千万别直接写在随时可能重跑的 build 方法中，否则页面会反复入栈。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: HomePage()));
class HomePage extends StatelessWidget {
  const HomePage({super.key});
  @override
  Widget build(BuildContext context) => Scaffold(body: Center(
    child: TextButton(
      child: const Text('打开 B'),
      onPressed: () async {
        final result = await Navigator.of(context).push<String>(
          MaterialPageRoute<String>(
            builder: (pageContext) => Scaffold(body: Center(
              child: TextButton(
                onPressed: () => Navigator.of(pageContext).pop('已选中'),
                child: const Text('返回结果'),
              ),
            )),
          ),
        );
        if (!context.mounted) return;
        ScaffoldMessenger.of(context).showSnackBar(
          SnackBar(content: Text(result ?? '没有结果')),
        );
      },
    ),
  ));
}

进一步理解

什么时候需要把地址和页面栈一起管理？

按钮打开详情后返回结果，可以直接用 push 和 pop。如果浏览器地址、外部深链接和应用页面要保持一致，就要解析地址并同步页面配置，可以用 Router 或采用相应的路由封装。

别答错：页面被遮住不等于销毁，跳转不应放在可能重复执行的 build 中。

进阶补充：返回拦截与路由封装库

需要拦截系统返回键时（如编辑未保存提示），新版本推荐用 PopScope：通过 canPop 决定能不能直接返回；onPopInvokedWithResult 只是在返回动作发生后通知你结果，在这个回调里是“来不及反悔撤销这次返回”的，想拦住必须提前把 canPop 设为 false。要替换当前页或清空历史栈可以用 pushReplacement、pushAndRemoveUntil。至于 go_router 这类路由库，本质上是在 Router API 上帮你更方便地做路径解析和重定向封装，底层依然靠 Flutter 自己的页面栈机制运行。

延伸核对：导航栈与路由结果。

14. 动画怎么做，vsync 是什么

重点理解

回答总结

只是想让宽高、颜色平滑过渡到新目标值，直接用现成的隐式动画（如 AnimatedContainer）最省心；如果需要自己控制播放、暂停、倒放或无限循环，就得用 AnimationController。 可以把动画拆成三个角色：AnimationController 像进度条（默认按时间输出 0.0 到 1.0），Curve 控制节奏（先快后慢等缓动效果），Tween 负责把 0~1 的进度换算成具体数值（比如 40 到 120 的宽度、红到蓝的颜色）。

vsync 的核心作用是“跟着屏幕刷新信号走，省电又防掉帧”：它接收一个 TickerProvider（常用 SingleTickerProviderStateMixin），每当屏幕准备刷新一帧时才发一次回调，不会在两帧之间白算；更重要的是，当这个页面被切走或不可见时，TickerMode 会自动把它的逐帧回调静默停掉，避免看不见的动画还在后台空转耗费资源（注意：回调虽然停了，但流逝的时间仍在按时钟走）。

写动画界面时，尽量用 AnimatedBuilder 把刷新范围圈在真正会动的小组件里，静态不变的子树通过 child 参数传进去复用，避免整页跟着每帧重绘。只要自己创建了 AnimationController，退出页面时务必在 dispose 里释放。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: Box())));
class Box extends StatefulWidget {
  const Box({super.key});
  @override
  State<Box> createState() => _BoxState();
}
class _BoxState extends State<Box> with SingleTickerProviderStateMixin {
  late final AnimationController _controller;
  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this, duration: const Duration(milliseconds: 600),
    )..repeat(reverse: true);
  }
  @override
  Widget build(BuildContext context) => Center(child: AnimatedBuilder(
    animation: _controller,
    builder: (context, child) => SizedBox(
      width: 40 + 80 * _controller.value, height: 40, child: child,
    ),
    child: const ColoredBox(color: Colors.blue),
  ));
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}

进一步理解

进度怎样换算成不同属性？

示例把控制器的 0.0–1.0 进度映射成 40–120 的宽度。有多个属性要共用一段动画时，可以分别用 Tween 映射颜色、位移等值。

静默后恢复，动画为什么可能跳到后面？

因为页面不可见时，TickerMode 只是暂停了每帧派发回调，并没有把时钟拨停。等页面切回来恢复回调时，控制器会按真实过去的时间算出当前应该在哪个进度，于是画面就可能直接跳到后面（甚至已经播完）。如果希望切走时真正停在原地，要主动调用控制器的 stop()。

别答错：Ticker 静默不等于时间停止，Controller 必须及时释放。

进阶补充：Ticker 数量、动画子树与转场

一个 State 整个生命周期只提供一个 Ticker 时可用 SingleTickerProviderStateMixin，可能先后或同时提供多个时用 TickerProviderStateMixin。AnimatedBuilder 的 child 可保存不随动画变化的子树。Hero 用相同 tag 对应转场两端，并在 Overlay 显示过渡内容，不是用 GlobalKey 把原 Element 直接迁移到另一页。

官方核对：TickerMode 静默与时间推进。

15. 布局时，约束和尺寸怎么传

重点理解

回答总结

Flutter 布局就一句话：约束往下传，尺寸往上传，位置由父组件定。 父组件先告诉子组件“你的宽高最小能多少、最大不能超过多少”（约束）；子组件在允许范围内自己决定要多大并报上去（尺寸）；最后父组件再决定把子组件摆在哪个坐标（位置）。如果某一维的最小值等于最大值，那这一边就写死了；最大值是无穷大，表示父组件对这一边暂不设上限。

在 Row 和 Column 里，当父级总长度有限时，剩下的空间可以按比例分给弹性子组件：Expanded 会强迫孩子把分到的空间全部填满，Flexible 则允许孩子比分配的空间更小。但如果外层本身在排列方向上就没有上限（比如把 Column 放进可以无限往下滑的 SingleChildScrollView 里），系统根本算不出“还剩多少空间”，这时加 Expanded 就会直接报错。

ListView 等滚动列表默认需要一个有限的显示区域高度（或宽度）。如果外层高度无限，有些人会给列表加 shrinkWrap: true，让列表根据内容总长度自己撑开高度——但这等于要一口气把所有列表项先测量一遍，列表一长就会明显卡顿，所以仍应优先用 Expanded 或定高容器来限制列表尺寸。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(MaterialApp(home: Scaffold(

    )),
  ]),
)));
// Scaffold 给 Column 有限高度，Expanded 把剩余高度给列表。
// 错误示例：移除 Expanded，只留下默认 shrinkWrap:false 的 ListView，

Column 里放 ListView，为什么常报高度无界？

想根据父级给的约束动态决定怎么排版，可以用 LayoutBuilder；需要让一行里不同高度的孩子对齐最高那个时可用 IntrinsicHeight，但会带来二次测量开销。AspectRatio、FittedBox 等组件不管怎么缩放，最终都必须服从父级传下来的约束范围。另外，Expanded 和 Flexible 必须直接放在 Row、Column 或 Flex 下面（中间不能隔着非 Flex 的普通容器或放进普通列表子项里）。顺便一提，debug 模式下布局越界或无界会弹红字报错，release 模式虽然去掉了这些开发断言，但布局本身依然是错的，不能指望线上环境自动合法。

16. Widget、Element、RenderObject、Layer 和一帧渲染

重点理解

回答总结

可以把三棵树理解成：Widget 是“设计图纸”（轻量且不可变，随时重画一份新的）；Element 是“施工管家”（真正在树里长久站岗，手里攥着对应的 State，负责对比新旧图纸，类型和 Key 对得上就只更新属性不拆重建）；RenderObject 是“实际干活的工人”（真正去量尺寸、算位置、记录怎么画以及处理点击命中）；Layer 则是把画好的各块内容分层贴在一起交给引擎合成。 注意它们不是严格 1:1 对应的：很多纯组合类的 Widget 自己没有 RenderObject，好几个 RenderObject 也经常共用同一个 Layer。

每次状态变化触发一帧刷新时，框架只会针对“需要更新”的节点按顺序干活：Build（重新生成配置）→ Layout（重新算宽高位置）→ Paint（记录绘制指令并塞进 Layer），最后交给引擎合成并把像素画到屏幕上（光栅化）。

所以不是每次 setState 都要把所有步骤全跑一遍：像本例只换个背景色而不改尺寸，就只需要重绘（Paint），不需要重新布局（Layout）。如果某个局部动画特别频繁、画起来又很重，可以套一层 RepaintBoundary 把它隔成独立图层，避免连累周围静态内容一起重绘；但它也会增加额外的图层和显存开销，要看实测收益再加。

17. 一次点击为什么只有一个组件响应

重点理解

回答总结

父子组件都包了 GestureDetector 并监听点击时，默认只有里面的子组件能触发 onTap，因为 Flutter 用了一套“手势竞技场（GestureArena）”来裁决谁赢，而内层组件处于树的更深处，通常优先胜出。 不过在最终分出胜负之前，父组件和外层的 Listener 其实都能收到手指按下的原始事件（父组件的 onTapDown 也可能先触发，竞选失败后再回调 onTapCancel）。

一次触摸大致分两步走：第一步是命中测试（HitTest），从根节点往下找手指点在了哪些组件范围里，把它们排进派发名单；第二步是手势竞争，路径上所有手势识别器都会观察这一串按下、移动、抬起事件，谁先满足条件并宣布“我认领了”（或别人中途放弃），谁就赢得这次手势。比如你点在按钮上没松手直接滑动，拖动识别器一旦达标胜出，原本的点击就会立刻被取消。

如果想不管竞争结果、单纯监听原始触摸事件，用 Listener；如果想让空白区域也能点到、或者让点击穿透到底下的兄弟组件，可以调整 HitTestBehavior（deferToChild 看孩子、opaque 挡住后方、translucent 透传给后方）。但注意 behavior 只管“谁能接到触摸事件”，改不了父子组件抢 onTap 时谁赢的规则。

虽然普通父子点击通常只剩一个赢家，但手势竞技场并不是死规定永远只能有一个对象响应：各个识别器既可以主动“认领”也可以“弃权”，手指全部抬起时如果还没决出胜负，竞技场会按规则兜底收尾；此外像 GestureArenaTeam 这类团队机制还能让多个识别器互相配合。轻微的手指抖动不会立刻取消点击，只有移动距离超过系统的拖动阈值（slop，不同设备略有差异）才会被判成拖动。

18. Flutter 如何和 Android / iOS 通信

重点理解

回答总结

Dart 与 Android、iOS 交换消息时用平台通道，调用兼容 C ABI 的函数时可用 FFI。 要把平台的原生视图放进 Flutter 界面，则使用 PlatformView。

MethodChannel 发送调用并接收结果，EventChannel 把平台事件传成流，BasicMessageChannel 用来双向传消息。两端要使用相同的通道名和兼容的编解码协议。Pigeon 可以根据接口生成两端的类型化通道代码。

Dart 异步等待期间，原生处理函数仍遵守平台和通道的线程规则。FFI 调用还需要匹配原生签名与调用约定，并管理内存和资源。

代码示例（看注释与结果）

import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

void main() => runApp(const MaterialApp(home: SettingsPage()));
class SettingsPage extends StatefulWidget {
  const SettingsPage({super.key});
  @override
  State<SettingsPage> createState() => _SettingsState();
}
class _SettingsState extends State<SettingsPage> {
  static const channel = MethodChannel('app/settings');
  String text = '点击读取';
  Future<void> readName() async {
    String next;
    try {
      next = await channel.invokeMethod<String>('getName') ?? '未设置';
    } on MissingPluginException {
      next = '尚未实现原生 getName';
    } on PlatformException catch (e) {
      next = '平台错误：${e.code}';
    }
    if (!mounted) return;
    setState(() { text = next; });
  }
  @override
  Widget build(BuildContext context) => Scaffold(body: Center(
    child: TextButton(onPressed: readName, child: Text(text)),
  ));
}

进一步理解

怎样把业务对象交给 Swift 或 Kotlin？

先把业务对象变成编解码器支持的结构，例如由字符串、数字、列表和映射组成的数据。两端还要约定方法名、参数和结果。直接传 Dart 类实例不会把它变成 Swift 或 Kotlin 实例。

原生处理函数耗时，Dart 异步等待能解决吗？

默认情况下，平台处理函数通常在平台主线程运行。耗时操作可按平台规则放到后台任务队列。最后要更新原生界面时，再切回平台要求的线程。

别答错：通道异步不代表原生 handler 自动在后台，Dart 调用端也不等于完整双端实现。

进阶补充：后台 isolate、TaskQueue 与示例范围

完成注册的后台 isolate 可以请求平台能力并接收回复，但不能任意接收平台主动推送。原生 TaskQueue 可以改变 handler 的执行队列，访问原生 UI 时仍需回到合适线程。本题代码只提供 Dart 调用端，未注册 app/settings 的 getName 原生实现时会提示尚未实现；真实通信还要在 Android/iOS 注册同名通道并返回兼容结果。FFI 内存非法访问可能导致进程崩溃，不能依赖 Dart catch 恢复。

官方核对：平台通道线程与后台 isolate 限制。

19. 怎样减少重建、长列表卡顿和大图开销

重点理解

回答总结

性能优化第一条铁律：先在真机的 profile 模式下用 DevTools 录一段操作，看清瓶颈到底在 UI 构建布局、GPU 光栅化、图片解码还是同步计算，改完后在同设备同场景下对比帧耗时，别凭感觉瞎优化。

针对三个高频痛点，常见落地手段很明确：减少无效重建——把状态和监听往下沉到真正要变的叶子组件，不变的组件多用 const 并抽成独立类或通过 child 复用；解决长列表卡顿——用 ListView.builder 按需加载而不是一次性塞进 children，行高固定时加上 itemExtent 或 prototypeItem 省掉逐个算高度，支持增删排序时用稳定的 ValueKey（必要时配合 findChildIndexCallback 帮框架快速找回位置），并且只对真正需要保留输入状态或播放进度的少数条目加保活（KeepAlive）。

降低大图内存与卡顿——如果原图 2000px 但头像只显示 48 逻辑像素，给 Image 传入按屏幕像素比算好的 cacheWidth / cacheHeight，让解码时直接按小图尺寸解码（不过这不会减少原图下载字节数，最好后端就下发缩略图）；控制预加载数量，复杂高频重绘的局部可以用 RepaintBoundary 隔离开；纯 CPU 算力重活确认划算时再丢进独立 isolate；最后别忘了在 dispose 里把控制器、定时器和监听全清掉。

进一步理解

列表已经用了 builder，为什么滚动还可能慢？

按需创建条目只减少创建工作。条目布局复杂、嵌套收缩测量、持续重绘或同时解码多张图片时，仍要分别处理。如果行高统一，可以用 itemExtent 或 prototypeItem 减少布局测量。

20. 滑出屏幕后，状态怎么留住

进阶选学

回答总结

列表项刚滑出屏幕一点时，通常还留在滚动容器的预留缓存区（cacheExtent）里，暂时不会销毁；一旦滑得太远彻底移出这个缓存范围，框架就会把它的节点和 State 回收掉以省内存。 如果希望某页或某一项滑出屏幕后依然保住状态（比如切 Tab 后输入框里的字、选中的开关还在），可以让对应的 State 混入 AutomaticKeepAliveClientMixin。

具体用法有三步：重写 wantKeepAlive => true 告诉父容器“留着我”，在 build 方法第一行调用 super.build(context)，后续如果不需要再保活了再调用 updateKeepAlive() 通知更新。不过保活会让这个页面的 State 和内存资源一直留在树里不销毁，虽然屏幕外不会重绘，但你自己订阅的流、定时器不会自动暂停，需要自己管好。

如果不需要保住整个页面状态，只是想记住列表滚动到第几行（比如切到别的 Tab 再切回来还能回到上次滚的位置），给滚动组件加上唯一的 PageStorageKey 并确保开启了滚动位置保存（keepScrollOffset）即可。PageStorage 会在当前路由/树共享的临时存储空间里记录这个偏移量；但一旦进程被杀或整个页面被彻底关闭，业务数据还是得靠本地存储或状态库持久化。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: PageViewDemo())));

class PageViewDemo extends StatelessWidget {
  const PageViewDemo({super.key});
  @override
  Widget build(BuildContext context) => PageView(
    children: const [TabPage(), Center(child: Text('第二页，滑回去看计数'))],
  );
}
class TabPage extends StatefulWidget {
  const TabPage({super.key});
  @override
  State<TabPage> createState() => _TabState();
}
class _TabState extends State<TabPage>
    with AutomaticKeepAliveClientMixin<TabPage> {
  int count = 0;
  @override
  bool get wantKeepAlive => true;
  @override
  Widget build(BuildContext context) {
    super.build(context); // 必须调用，忽略返回值
    return Center(child: TextButton(
      onPressed: () => setState(() { count++; }),
      child: Text('计数：$count'),
    ));
  }
}
// 在第一页加一，滑到第二页再滑回来，计数会保留。

别答错：保活、缓存范围与滚动位置恢复是不同机制。

进阶补充：保活依赖与存储作用域

ListView.builder、PageView 等默认都会在每个子项外自动包一层 AutomaticKeepAlive 来响应子项的保活请求；如果你手动关闭了 addAutomaticKeepAlives: false，子项里的 mixin 就会失效。另外，PageStorageKey 只是在同一个 PageStorage 作用域内按 Key 区分并恢复滚动位置（例如配合开启了 keepScrollOffset 的滚动控制器），别把它当成全局持久缓存。

21. 线程模型，以及高刷新率上怎么看掉帧

进阶选学

回答总结

查掉帧先看两张时间条：UI 耗时和 Raster 耗时谁超标了，而且预算要按目标屏幕刷新率算。 60Hz 屏幕每帧只有约 16.7 毫秒，到了 120Hz 高刷屏直接腰斩到约 8.3 毫秒。虽然引擎允许上一帧的 Raster 和下一帧的 UI 流水线并行，但只要任意一段长期超时，画面就会掉帧卡顿。

Flutter 引擎按职责分成四个 Task Runner：UI 跑 Dart 代码（Widget 构建、布局计算和记录绘制指令）；Raster 负责光栅化（把绘制指令真正画成像素纹理并交给 GPU 显示）；Platform 处理宿主原生交互；IO 负责加载图片、解码资源等 I/O 准备。这四份工作到底分别落在系统哪几个线程上，取决于不同平台和引擎版本的配置。

排查时切记一定要用真机的 profile 模式打开 DevTools Performance 录制（debug 模式下有大量调试检查，测出来的掉帧不作数）：如果是 UI 超时，重点查是不是主线程做了同步大计算、布局嵌套过深或频繁全树重建；如果是 Raster 超时，重点查是不是用了太多复杂遮罩、阴影、大尺寸图绘制或反复触发离屏绘制。

22. 什么时候自定义布局

进阶选学

回答总结

能用 Row、Column、Stack、Align 这些现成组件拼出来的布局，绝对先用组合。 如果只是想画不规则线条、图表或波浪背景，布局尺寸用现成容器定好，画图交给 CustomPaint 就行。如果现成容器满足不了，需要自己算子组件的位置或尺寸关系，先试轻量级的 CustomSingleChildLayout 或 CustomMultiChildLayout。

只有当连多子布局代理也搞不定（比如父容器自己的宽高必须等几个孩子先量完尺寸、互相参考后再反推出来），或者有明确性能数据表明现有组件嵌套太深拖慢了布局时，才值得自己去继承 RenderObjectWidget 和 RenderBox。手写 RenderBox 必须守规矩：在父级给的约束内定好自身大小，再依次测量并摆好每个子节点的位置。

自己写渲染层时很容易漏掉三件事：第一，改了尺寸要调 markNeedsLayout，只改颜色形状只需调 markNeedsPaint；第二，不规则图形如果能点击，必须自己补上命中测试（如 hitTestSelf），不然点上去没反应；第三，别忘了补上无障碍读屏语义，有需要时再按绘制开销决定是否隔离重绘。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: Center(
  child: CustomPaint(size: Size(160, 80), painter: LinePainter()),
))));

class LinePainter extends CustomPainter {
  const LinePainter();
  @override
  void paint(Canvas canvas, Size size) {
    final paint = Paint()..color = Colors.blue..strokeWidth = 4;
    canvas.drawLine(Offset.zero, Offset(size.width, size.height), paint);
  }
  @override
  bool shouldRepaint(covariant LinePainter oldDelegate) => false;
}

// 此处只是装饰，没有点击与语义需求；交互图形还应补齐命中与语义。

进一步理解

什么时候布局代理还不够？

CustomMultiChildLayout 能按顺序测量和定位多个子项，但自身尺寸不能依赖子项布局后的结果。若父节点尺寸必须由这类测量结果决定，现有组件也无法表达时，才考虑自定义 RenderBox。

画出来了，为什么仍可能点不到或读不出来？

绘制只产生像素。异形交互区域还需要命中测试，读屏需要标签和可用动作。自定义渲染时，按实际交互提供这些信息。

别答错：绘制正确不代表命中测试和辅助功能语义也正确。

进阶补充：Flow、parentData 与语义

Flow 适合做高频动画里移动多个子组件的位置，因为它在绘制阶段直接用变换矩阵移动孩子、不反复触发布局测量，但它并不能像自定义 RenderBox 那样任意改写父子尺寸协商。另外，像 Positioned、Expanded 这类组件之所以能给父组件传坐标或比例，靠的就是把参数挂在子节点的 parentData 上让配套父布局去读取。自定义渲染时是否开启 isRepaintBoundary 要看重绘收益和图层内存成本的权衡，semantics 则负责提供读屏所需的名称与操作。

官方核对：Flow 在绘制阶段变换孩子位置。

23. 混合栈怎么组织

进阶选学

回答总结

当一个原生 Android/iOS App 里混着嵌入了好几个 Flutter 页面时，页面跳转就会同时牵扯原生的页面栈（Activity / ViewController）和 Flutter 自己的路由栈，这就是混合栈问题。 设计混合栈第一步，要先拍板“所有页面进出和回退到底由原生统一管，还是各自管各自的片段”，并把页面可见性、系统返回键和页面生命周期同步好。

每个原生容器只是用来装画面的“壳”，真正跑 Dart 代码和渲染的是背后的 FlutterEngine。如果只创建并缓存一个共享引擎，下次再进 Flutter 页时秒开不卡顿，但页面退出后引擎里的全局状态、定时器甚至旧路由可能还留着，下次进来得自己做好页面切换和状态清理。

如果业务上想让不同 Flutter 模块彻底隔离（互相不影响路由栈和全局变量），就得给不同流程开多个引擎。直接新开多个引擎内存开销很大，所以官方提供了 FlutterEngineGroup，让后续新开的引擎可以共享底层部分资源以省内存；但各个引擎之间的数据通信、宿主绑定和销毁还是得分别管好。

24. var、Object、dynamic，以及空安全

基础优先

回答总结

var 让编译器推断类型，Object 可以保存任意非空对象，dynamic 将大部分成员检查推迟到运行时。 例如 var x = 1 推断为 int，之后只能赋给它符合 int 的值。只有在缺少初始值和其他类型信息时，var 才会推断为 dynamic。

访问具体子类型特有的成员时，先用 is 检查 Object 中的值，或显式转换类型。Object? 还可以保存 null。调用 dynamic 成员时，编译器通常不检查成员是否存在。方法不存在或参数不合要求时，运行时仍可能抛错。

类型名加 ? 才能保存 null。?. 遇到 null 就跳过成员访问，?? 在左边为 null 时计算备用值，! 则在运行时检查值是否非空。编译器能证明某处的类型更具体时，会按该类型检查后续访问，这叫类型提升。

不带初始值的 late 变量要先赋值再读。带初始化表达式的 late 变量会在第一次读取时执行尚未完成的初始化。

代码示例（看注释与结果）

String? readName() => null;

void main() {
  var x = 1;
  x = 2;
  // x = 'two'; // 错误示例：取消注释会产生编译错误
  Object obj = x;
  print(obj.toString()); // 2
  dynamic raw = x;
  try {
    raw.missing(); // 错误示例：能编译，运行时抛 NoSuchMethodError
  } on NoSuchMethodError {
    print('没有这个方法');
  }
  String? name = readName();
  print(name ?? '访客'); // 访客
  try {
    print(name!); // 错误示例：这里为 null，运行时抛错，可捕获
  } catch (_) {
    print('空值断言失败');
  }
  Object value = readValue();
  if (value is String) {
    print(value.length); // 4：类型提升后可以使用 String 的成员
  }
  late final String greeting = makeGreeting();
  print('准备读取');
  print(greeting); // 首次读取才输出“执行初始化”，再输出“你好”
  print(greeting); // 再次读取只输出“你好”
}
Object readValue() => 'Dart';
String makeGreeting() {
  print('执行初始化');
  return '你好';
}

进一步理解

为什么判空以后通常不用写 !？

name 是 String? 时，若编译器能证明 name != null 在使用处仍成立，就会把它按 String 检查。可能变化的字段无法提升时，可以先读到局部 final 变量，再判空。

别答错：dynamic 不是任意类型转换，late 也不是自动提供默认值。

进阶补充：空安全运算符与类型提升边界

??= 只在变量为 null 时赋值，...? 仅在集合非空时展开元素；这些操作不改变变量的声明类型。字段提升取决于语言版本及字段条件，不能把局部变量的提升规则直接套到公开字段、可变字段或 getter 上。必要时先保存到局部 final 再判空。空值断言失败、缺失成员和 late 初始化错误属于可捕获的 Dart 运行时错误，不等同于原生进程崩溃；未处理的错误仍可能终止 isolate。

官方核对：类型提升的条件与失败原因。

基础语法：变量、late 与常量。

25. const 和 final 的区别

基础优先

回答总结

共同点是“只能赋值一次”；区别在于 final 在程序跑起来时赋值（运行时常量），const 必须在写完代码编译时就确定下来（编译期常量）。 比如获取当前时间 final now = DateTime.now() 可以，但写成 const 就会报错。另外，用 final 修饰一个 List，只是这个变量不能再指向别的列表，但往里面 add 元素依然是可以的；而 const 修饰的列表连里面的内容都彻底锁死，改了运行时会报错，而且在同一个 isolate 里相同的 const 对象只会保留一份内存实例，大家共用（即 identical 为 true）。

如果给类写了 const 构造函数，就要求它的所有实例字段都必须是 final。注意：写了 const 构造函数不代表每次创建出来都是常量——只有在调用时显式写了 const（或者处在外层 const 列表等常量环境里），才会生成共享复用的常量对象；直接写 Box(n) 照样可以传运行时变量进去当普通对象用。

在 Flutter 里写 UI 时多给不变的子组件加 const 有个实惠的好处：父组件刷新的时候，如果传给子组件的还是那份一模一样的常量实例，框架就能直接跳过子组件的更新检查，省下重建开销（当然，如果子组件自己有 State 或监听了全局主题，该刷的时候还是会刷）。

代码示例（看注释与结果）

class Box {
  final int n;
  const Box(this.n);
}

void main() {
  final list = <int>[];
  list.add(1);
  print(list); // [1]
  const a = [1];
  const b = [1];
  print(identical(a, b)); // true：相同常量被规范化
  try {
    a.add(2); // 错误示例：能编译，运行时抛 UnsupportedError
  } on UnsupportedError {
    print('常量列表不能修改');
  }
  final n = int.parse('1'); // 运行时值
  final box = Box(n); // const 构造也能普通调用
  const box2 = Box(1);
  const boxes = [Box(1)]; // 隐式 const 上下文
  print(identical(box, box2)); // false
  print(identical(box2, boxes.single)); // true
}

别答错：final 不等于对象内容不可变；const 也不意味着组件以后永不重建。

进阶补充：const 构造函数的语法限制

能加 const 的普通构造函数不能有花括号函数体，且它自己以及父类的所有实例字段都必须是 final（初始化列表也只能用编译期能算出的常量）。另外，类的普通成员属性不能直接写 const，想在类上挂常量得用 static const。同一 isolate 内相同的 const 对象共享同一份实例，但不同 isolate 各自独立，不要假设跨 isolate 它们还是同一个内存地址。

延伸核对：final 与 const。

26. Dart 是值传递还是引用传递

基础优先

回答总结

Dart 按值传参。传入对象时，函数拿到的是引用的副本。 形参和调用方变量起初指向同一个对象，所以函数给列表添加元素后，调用方也能读到新元素。

给形参重新赋值只会改变函数内的引用。要让调用方也改用新列表，可以把新列表返回，由调用方赋值。

需要独立修改时，可以复制数据。浅复制只复制外层列表，里面的可变对象仍可能由两份列表共用。

代码示例（看注释与结果）

void grow(List<int> list) { list.add(1); }
void reset(List<int> list) { list = []; }

void main() {
  final values = <int>[];
  grow(values);
  print(values); // [1]：同一个可变对象被修改
  reset(values);
  print(values); // [1]：给形参重新赋值不影响调用方变量
}

27. extension 是干什么的

基础优先

回答总结

extension 让已有类型可以用新的方法、访问器或运算符。 编译器根据接收者的静态类型和调用处可见的扩展选择实现。普通 dynamic 调用只查运行时成员，因此找不到扩展提供的方法。

扩展可以定义计算属性和静态成员。实例数据仍要放在原对象或包装对象中。原类型已有同名实例成员时，隐式调用优先使用原成员。

其他库的扩展要先导入。多个可见扩展都适用且编译器无法选出唯一实现时，可以调整导入范围，或用 扩展名(对象).成员 明确指定。

代码示例（看注释与结果）

extension StringX on String {
  bool get isBlank => trim().isEmpty;
}

void main() {
  String name = '  ';
  print(name.isBlank); // true：按静态类型 String 选择扩展
  dynamic raw = name;
  try {
    print(raw.isBlank); // 错误示例：能编译，运行时查找实例 getter
  } on NoSuchMethodError {
    print('dynamic 不会自动调用扩展');
  }
  print(StringX(raw as String).isBlank); // true：显式调用扩展
}

进一步理解

两个扩展都提供同一个成员怎么办？

可以显式写 StringX(value).isBlank，指定要用的扩展。想让整个文件只看见其中一个扩展时，可以调整导入的 show 或 hide 列表。

别答错：扩展按静态类型选择，不能当作运行时重写。

延伸核对：扩展的静态解析与冲突处理。

28. 工厂构造函数和普通构造函数

基础优先

回答总结

普通构造函数（包括命名构造）的职责是“每次老老实实创建一个全新的本类实例”；而 factory 工厂构造函数更像一个“对象加工厂”，不一定非要新建对象——它可以从缓存里捞一个旧实例还给你，也可以根据条件返回一个子类对象。 因为工厂函数进门时新对象还没影子，所以里面不能用 this，必须自己 return 一个对象出去。

像 User.fromJson 这种叫“命名构造函数”，它既可以写成普通构造函数（直接把字段赋值初始化好），也可以加个 factory 关键字（比如需要先校验参数、走缓存，或者根据 JSON 里的类型返回不同的子类）。

自己写了大括号函数体的 factory 不能声明成 const；只有那种直接把创建工作转发给另一个常量构造函数的“重定向工厂”（比如 const factory A() = B;），才能加上 const。

代码示例（看注释与结果）

class User {
  User(this.name);
  User.fromJson(Map<String, Object?> json) : name = json['name'] as String;
  static final Map<String, User> _cache = {};
  factory User.cached(String name) =>
      _cache.putIfAbsent(name, () => User(name));
  final String name;
}

void main() {
  print(User.fromJson({'name': '小明'}).name); // 小明
  print(identical(User.cached('小明'), User.cached('小明'))); // true
  print(identical(User('小明'), User('小明'))); // false
}

进一步理解

什么时候把查缓存放在工厂里？

示例按名字复用 User，因为名字相同就算同一项。真实业务中要先选稳定的身份标识，再决定缓存何时清理。只需把输入转换成字段时，普通命名构造就够用。

别答错：factory 不自动缓存，命名构造也不等于工厂构造。

进阶补充：解析输入的边界

User.fromJson 假设 name 存在且为 String。真实解析要分别处理缺字段、空值和错误类型。

延伸核对：生成构造、命名构造与工厂。

29. Flutter 和原生开发的差别

基础优先

回答总结

Flutter 的普通 Widget 由 Flutter 框架和引擎布局、绘制。 在 iOS 显示 FilledButton 时，Flutter 引擎绘制按钮，手势由 Flutter 处理。使用 UIKit 等原生界面机制时，系统框架负责相应工作。Flutter 因此可以在多端共享大部分界面和逻辑。

状态变化后，build 生成新的 Widget 配置。框架尽量复用已有节点，再按需要布局和绘制。

需要相机或系统权限时，可以通过插件接入平台实现，也可按接口需要使用平台通道或 FFI。必须显示原生视图时用 PlatformView，并处理视图生命周期和合成开销。性能取决于实际工作量，可以用帧时间和资源占用比较。

进一步理解

接入地图或相机时，什么时候需要原生视图？

只需要调用拍照或查询权限，可以通过插件取得结果，再用 Flutter 组件展示。确实需要把某个原生地图控件放进界面时，才用 PlatformView，并评估它和 Flutter 内容一起合成的成本。

别答错：自绘与声明式是不同概念，跨平台也不代表无需原生适配。

进阶补充：渲染后端与平台差异

Skia、Impeller 及 Web 渲染路径的可用性取决于平台、版本与配置。Impeller 通过提前准备部分图形程序减少运行时着色器编译相关开销，不保证消除布局、计算、图片或其他 GPU 工作造成的卡顿。PlatformView 使用原生视图，也有额外的合成与生命周期成本，不能按普通自绘组件推断。

官方核对：Impeller 平台支持范围。

30. Flutter 的整体架构

基础优先

回答总结

Framework 组织界面和交互，Engine 执行 Dart 并提供渲染能力，Embedder 把引擎接入操作系统。

Framework 用 Dart 提供 Widget、布局、动画和手势等 API，经 dart:ui 调用引擎接口。Engine 提供文字排版、运行环境和图形渲染。Embedder 接入窗口、渲染表面、系统输入和平台消息。

UI、Raster、IO、Platform 表示任务职责。Task Runner 把任务安排到可执行的环境，具体映射到哪些线程由平台与引擎配置决定。

进一步理解

系统点击怎样变成新的 Flutter 画面？

31. main 和 runApp 分别做什么

基础优先

回答总结

main 是 Dart 程序入口，runApp 把根 Widget 接入 Flutter 并安排构建。 调用返回后，框架还要完成构建、布局和绘制，画面由引擎呈现。

runApp 会确保 WidgetsFlutterBinding 已初始化。这个绑定把帧调度、输入和平台消息接到框架。若在 runApp 前就要调用依赖绑定的插件或平台 API，先调用 WidgetsFlutterBinding.ensureInitialized()，再按实际依赖等待初始化结果。

修改 main 中的初始化流程后，用热重启重新执行入口。热重载不会重新执行 main。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() {
  final binding = WidgetsFlutterBinding.ensureInitialized();
  binding.addPostFrameCallback((_) {
    debugPrint('框架已完成首帧工作');
  });
  runApp(const MaterialApp(home: Scaffold(body: Center(child: Text('Hello')))));
}
// 帧回调在框架完成本次帧的布局和绘制工作后执行。

进一步理解

什么时候要用帧回调？

如果操作依赖布局结果，例如读取组件尺寸，可以在框架的帧工作完成后执行。依赖插件返回值的启动逻辑，则应等待插件自己的初始化结果。

别答错：runApp 返回不代表首帧已经显示，热重载也不会重跑 main。

延伸核对：runApp 与绑定初始化。

32. 热重载和热重启

基础优先

回答总结

热重载更新兼容的 Dart 代码并安排重建，通常保留现有状态。热重启重新运行 main，重新创建 Dart 内存状态。 磁盘上的数据仍保留。

热重载不会重复执行已经运行过的 main、已有 State 的 initState 或已经完成的全局与静态字段初始化。改的是这些初始化逻辑时，用热重启验证。

遇到不兼容热重载的 Dart 结构变化，按工具提示重启。改了原生代码或插件集成，一般需要停止应用并重新构建。能使用哪些热更新功能，由目标平台和调试环境决定。

代码示例（看注释与结果）

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: ReloadDemo())));
class ReloadDemo extends StatefulWidget {
  const ReloadDemo({super.key});
  @override
  State<ReloadDemo> createState() => _ReloadDemoState();
}
class _ReloadDemoState extends State<ReloadDemo> {
  int count = 0;
  @override
  void initState() { super.initState(); debugPrint('初始化'); }
  @override
  Widget build(BuildContext context) => Center(child: TextButton(
    onPressed: () => setState(() => count++),
    child: Text('计数：$count'),
  ));
}
// 先点击到 3，把文字“计数”改成“当前计数”，保存并热重载：
// 新文字生效，数字仍为 3，不会再次输出“初始化”。
// 热重启：重新输出“初始化”，数字回到 0。

别答错：热重载保留旧状态，修改初始化逻辑后通常需要热重启验证。

进阶补充：平台支持与限制

手机和桌面的有状态热重载依赖 debug 的 VM/JIT 开发路径；Web debug 使用自己的开发编译器，不能套用原生机器码编译的说法。部分枚举、泛型等结构修改无法直接热重载，应按工具提示重启。profile、release 不提供开发期热重载能力。

官方核对：热重载限制。

33. 包和插件有什么区别

基础优先

回答总结

一句话分清：package（包）主要是纯 Dart 代码或 Flutter UI 组件的复用单位；plugin（插件）是包的一种特殊形式，专门用来桥接 Android、iOS、桌面等各平台的原生能力。 只要包里需要调相机、定位、蓝牙等系统 API，并包含了对应的原生代码和平台配置，它就是插件。

你在自己项目里写一个 MethodChannel 只是在当前工程里通了信，算不上插件；把它按规范整理成独立目录、写好 pubspec.yaml 里的平台注册声明，让其他项目 pub add 就能直接接入原生代码，这才叫 Flutter 插件（底层通信既可以用平台通道，也可以用 FFI 调原生库）。

现在很多官方和大型三方库都采用联邦插件（Federated Plugin）架构，说白了就是“把一个大插件按端拆开维护”：顶层一个面向业务的入口包 + 中间一个约定接口规范的 platform_interface 包 + 底下 Android、iOS、Web 各自独立的平台实现包。这样不同平台可以由不同团队独立发版修 Bug，互不干扰。接入时记得确认入口包默认引入了你要的目标平台实现。

终端操作示例

这是项目结构示例。命令会创建两个新目录，请在空的练习目录执行。

# 在空的工作目录中，分别创建普通包和支持 Android/iOS 的插件：
flutter create --template=package interview_utils
flutter create --template=plugin --platforms=android,ios interview_device
# 普通包：从 lib/ 提供 Dart API，可按需要加入 Flutter 组件。
# 插件：除 Dart API 外，还有 android/、ios/ 与 pubspec 中的插件声明。
# 模板仅建立骨架；具体平台功能仍需实现，再由 example 应用验证。

别答错：plugin 是一类 package，通道只是实现手段。

进阶补充：联邦插件的角色

面向应用的包提供业务使用的 API，platform_interface 包约定各平台必须实现的接口，android/ios 等实现包分别接入系统。哪些实现被默认接入，需要看 pubspec 的插件声明与工具链注册约定，不能把平台接口包当成已经提供所有平台能力的实现包。

官方核对：联邦插件的三种角色。

34. 构建模式和多端产物

基础优先

回答总结

debug 用于调试，profile 用于分析性能，release 用于分发。 支持的原生目标通常在 debug 使用 JIT，在 profile 和 release 使用 AOT。Web 有独立的编译路径。

发布优化可以通过 tree shaking 移除不可达代码。Dart 混淆需要在支持的目标上显式启用，并保留还原堆栈所需的符号文件。分发签名按各平台要求配置。

Android 可构建 APK 或 AAB，iOS 可生成归档和分发包，桌面端生成平台应用，Web 输出 JavaScript 或 Wasm 等静态资源。验证体积和性能时，用实际要交付的目标和构建模式。

终端操作示例

这是构建命令示例，在终端按目标平台选用；不需要安装示例中所有平台工具。

# 在已完成相应平台配置的 Flutter 工程中，按目标选择命令：
flutter run --debug                 # 开发调试
flutter run --profile               # 性能分析，选择支持该模式的目标真机
flutter build appbundle --release   # Android AAB；分发签名需另外配置
flutter build ipa --release         # iOS：需要 macOS、Xcode 与签名配置
flutter build web --release         # Web 静态资源，位于 build/web

# 若 Android 目标需要 Dart 混淆，可改用下列构建方式，并保存符号目录：
flutter build appbundle --release --obfuscate --split-debug-info=build/symbols
# 这些是不同用途的命令，不要求依次全部运行；混淆与签名互不替代。

别答错：release 不自动开启混淆，也不自动保证分发签名正确。

进阶补充：入口保留与符号信息

tree shaking 根据有效入口的可达性移除代码，原生回调等额外入口需要按规则保留，不能只按源码里是否显式调用判断。启用 --obfuscate 时通常配合 --split-debug-info 并保存符号文件，用于还原错误堆栈。不同平台的签名和分发要求独立于 Dart 混淆，构建完成不代表全部交付配置已验证。

官方核对：构建模式与 Web 差异。
