一、Dart

1. var、Object、dynamic，以及空安全

结论：var 让编译器自己判断类型，判断完这个变量是什么类型就定了。Object 是所有非空对象的共同父类型，不该调用的方法编译器仍会报错。dynamic 几乎不做编译期检查，类型用错了要到运行时才暴露。

机制：

  • 用 var 定下来的是变量的类型，不是值。变量还能重新赋值，但只能赋同一种类型的值。
  • 变量声明成 Object 时，只能直接调用 Object 上本来就有的方法。要用某个具体类的方法，得先判断类型，或者强制转换。
  • dynamic 可以装任何值，包括 null。对它调用任何方法，编译器都不报错。
  • 空安全：类型后面加 ?，表示这个值可以是 null。! 表示“我确定这里不是 null”，其实是 null 就抛异常。late 表示先声明、稍后再赋值，还没赋值就去读，会抛 LateInitializationError。late final 只能赋一次。

追问：

  • 类型是 Object 时可以直接调 toString，不能直接调子类才有的方法。类型是 dynamic 时，调什么都能编译过。
  • 写代码时就能确定类型，就不要用 dynamic。值可能为空时用 ? 和 ??。先用 if (value != null) 判断过，判断内部的 value 就会被当成非空，一般不需要再写 !。

2. const 和 final 的区别

结论：二者都只能赋值一次。final 在运行时确定，只锁住变量本身，对象里面还可以改。const 在编译期就定死，对象本身和里面的内容都不能改。

机制：

  • final 锁住的是变量，不能再让它指向别的对象；对象里面还能改。例如 final list = <int>[] 之后仍可以 add。实例字段可以用 final。
  • const 的值必须在编译时就能算出来。const [] 不能添加或修改元素。实例字段不能写成 const，类里的常量要写成 static const。
  • const 构造函数要求字段都是 final，传入的参数也必须是编译时就能确定的值。参数相同的 const 对象在程序里是同一个对象，不会各存一份。

追问：

  • const 为什么可能少重建：父组件重新 build 时，如果子 Widget 还是上次那个对象，框架发现新旧是同一个，就不再往下更新这棵子树。参数相同的 const 构造会得到同一个对象，所以更容易走这条捷径。
  • final 列表可以改元素，const 列表不可以。值要到运行时才能算出来、算完这个变量就不能再指向别的对象时，用 final。

3. Dart 是值传递还是引用传递

结论：传给函数的是“指向这个对象的地址”的一份拷贝，不是把对象再复制一份。面试里把这叫做值传递：传走的是地址的副本。函数参数和外面的变量不是同一个变量。

机制：函数里改对象的字段，外面看得到。函数里让参数去指向另一个对象，外面的变量不变。

追问：

  • void add(List<int> list) { list.add(1); } 改的是同一个列表，调用方能看到多出来的元素。
  • void reset(List<int> list) { list = []; } 只是让函数自己的参数指向一个新列表，调用方手里还是原来那个列表。

4. extends、implements 和 mixin

结论：extends 是继承一个父类，实现和类型关系一起拿过来。implements 是按接口把成员自己写全，不复用对方的实现。with 混入的 mixin 是一段现成方法，用来复用代码。Dart 不能同时继承多个类。

机制：

  • 一个类只能 extends 一个父类，但可以实现多个接口、混入多个 mixin。每个类都能被别人 implements，类本身就充当自己的接口。
  • mixin 不能写普通构造函数。on 用来规定：只有继承了某个类的类，才能混入这段代码。mixin 里面也可以调用那个指定父类的方法。
  • 几个 mixin 里有同名方法时，with 后面写得靠后的覆盖靠前的。不要把 mixin 说成“为了实现多重继承”。

追问：

  • 只是想复用一段行为，用 mixin 或组合。为了让子类替换父类出现，才用继承。
  • Dart 3 还能限制库外的人怎么用这个类：标成 interface，库外只能当接口实现，不能继承；标成 base，库外只能继承，不能当接口实现；标成 final，库外不能继承也不能实现；标成 sealed，子类必须写在同一个库里，switch 可以检查分支有没有写全。

5. extension 是干什么的

结论：extension 给已经有的类型加方法或 getter，不用改原来的类，也不用继承。调用时看起来像这个类型本来就有这个方法。

机制：

  • 调哪个扩展，看的是变量写出来的类型，编译时就定了。类型写成 dynamic 时，编译器不知道有这个扩展，调不到。
  • 类型自己已经有的同名方法优先，扩展盖不掉。扩展里不能加字段，所以不能用它存状态。
  • 扩展所在的库要被 import 进来才看得到。两个扩展方法同名、调用处分不清时，藏起其中一个，或者写成 扩展名(对象).方法()。
extension StringX on String {
  bool get isBlank => trim().isEmpty;
}

追问：适合不加状态的工具方法。要保存数据，或者希望子类能改写，用类或 mixin。

6. 工厂构造函数和普通构造函数

结论：普通构造函数每次都新建一个当前这个类的对象。工厂构造函数看着也是在构造，函数体里返回谁，调用方拿到的就是谁，所以可以返回已经有的对象、缓存，或者一个子类实例。

机制：

  • 普通构造函数一定会生成当前类的新对象。工厂构造函数用 factory 标出，里面可以 return 一个已有实例。
  • factory 不能写成 const。编译期就能定死的对象，用带 const 的普通构造函数。
  • 名字只是多一个入口。User.fromJson 写成普通的命名构造函数，仍然会新建；写成 factory User.fromJson，才可以返回已有对象或子类。

追问：从 JSON 创建对象，如果只是把字段填上，命名构造函数就够。要控制“这次不新建”或“返回的是子类”，用 factory。

二、异步和并发

7. Future 和 async / await

结论：Future 表示一件异步的事稍后会有一个结果，成功或失败只会到来一次。async 函数一被调用，马上先返回一个 Future。

机制：

  • await 先停住当前函数后面还没跑的代码。等的那个 Future 完成后，后面的代码再继续。一个 async 函数里可以没有 await，也可以有多个。
  • Future 完成后，接着跑的代码进微任务队列，比点击、定时器这些普通事件更优先。用 Future(() {}) 包起来的函数体进事件队列，所以它会排在已经排队的微任务后面。
  • Future 还是在当前这条执行线上跑，不会并行。这条执行线叫 isolate。它适合网络、定时器和文件：等待的时候不占着 CPU，界面还能响应。

追问：

  • await 抛出的错误用 try/catch 接。没有写 await 时，用 catchError 或 onError。
  • 很吃 CPU 的计算，即使用 Future 包起来，真正算的那一段仍然占着当前这条执行线，界面还是会卡。这种工作要放到另一个 isolate。

8. Future 和 Stream 有什么不一样

结论：Future 是稍后到来的一个结果。Stream 是一段时间内连续到来的多个事件，可以有多次数据、多次错误，以及最后一次结束。

机制：

  • Future 适合一次请求。Stream 适合 WebSocket、传感器、下载进度这类会持续来数据的场景。
  • 单订阅 Stream 只能有一个监听者，事件按顺序交给它，适合读文件这种读完就结束的数据。再 listen 一次会报错。
  • 广播 Stream 可以同时有多个监听者，新来的事件分给正在听的人，适合网络状态、主题切换。后开始听的人，听不到开始之前已经发出的事件。
  • 自己写一条会连续产出数据的流，函数标成 async*，每 yield 一次就往外发一个事件。yield* 是把另一条流里的事件接着转出去。
  • await for 用来一个一个取 Stream 里的事件：来一个就执行一次循环，流结束后循环结束。函数会停在这里等下一个事件，但不会把整条 isolate 卡住。可以用 break 提前退出，退出后要取消订阅或关掉资源。
await for (final event in stream) {
  print(event);
  if (event == 'stop') break;
}

追问：

  • 单订阅流适合 await for。广播流如果用 await for，函数会一直停到这条流结束。
  • 页面销毁时要取消 StreamSubscription，否则回调里可能再去 setState。

9. Dart 是不是单线程？事件循环怎么跑

结论：同一条执行线上的代码是一条一条跑的，不会两条同时跑。这条执行线叫 isolate。一个 Flutter 应用可以有多个 isolate。每个 isolate 自己排两个队：微任务队列放更优先的小任务，事件队列放点击、定时器、网络完成这类普通事件。

机制：当前这段同步代码跑完后，先把微任务全部做完，再从事件队列取一个事件来做，做完再把期间新来的微任务做完，然后重复。scheduleMicrotask 和 Future.microtask 进微任务队列；Future(() {})、Timer、网络和文件完成的回调进事件队列。

追问：

  • await 停住的是当前这个 async 函数后面还没跑的代码。这条 isolate 可以先去处理别的事件，界面不会因此卡住。
  • 如果微任务里不停地再添加微任务，点击和下一帧就一直轮不上。

10. Isolate 是什么，和 Future 有什么区别

结论：Isolate 是 Dart 用来真正并行的单位。每个 isolate 有自己的内存和事件循环，不能直接改另一个 isolate 里的对象，只能发消息。这种各自一份内存、只发消息的做法叫 actor 模型。Future 只是当前这条 isolate 上稍后才有的结果，不会并行。

机制：

  • 内存不共用，所以不用加锁。发消息的出口叫 SendPort，对面用 ReceivePort 收。送过去的数据通常会复制一份。少数情况可以把一块内存直接交给对方，交出去之后原来这边不能再使用。
  • Dart 虚拟机可以把多个 isolate 安排到不同的系统线程上同时跑。说“Dart 没有多线程”不准确：没有的是多个线程一起改同一块内存这种写法。Web 上 isolate 的实现不一样，不能假设和手机上完全相同。
  • compute 和 Isolate.run 适合做完一次、拿回一个结果。Isolate.spawn 适合需要一直待在后台、反复收消息的任务。
  • 解析很大的 JSON、压缩图片、加密，不要放在负责界面的那条主 isolate 上。

追问：

  • 网络请求用 Future 就够了，等待的时候不占 CPU。再包进 isolate 通常没有好处。
  • isolate 不是引擎里那几条专门的线程。引擎另外准备了界面、画像素、文件和平台消息四条线程。新开的 isolate 由 Dart 虚拟机自己安排跑在哪条系统线程上。

三、框架入门

11. Flutter 和原生开发的差别

结论：Flutter 自己把界面画出来，不使用 Android 或 iOS 的系统控件。同一套 Dart 界面在各端长得一样，复杂界面的流畅程度通常接近原生。

机制：你写的是这份数据下界面应该长什么样，框架自己对照上一帧更新，不用找到某个控件再改它的文字。这种写法叫声明式。框架先描述这一帧要画什么，引擎里的图形库再把这些描述画成像素交给 GPU。这个库叫 Skia 或 Impeller，用哪个看版本和平台。开发时边运行边编译，所以能热重载；正式包提前编译成机器码。调用系统能力时，用插件和 Platform Channel 补上。React Native 是把界面映射成系统控件，再用一条桥和 JavaScript 通信，两端更容易长得不一样。

  • Flutter 的好处是各端界面一致、改起来快、热重载直接能看到。
  • 代价是安装包更大，平台差异要靠插件补，部分系统能力（无障碍、桌面小组件、很深的系统接口）还是要原生配合。
  • 原生的好处是系统接口、包体积和平台上的调优更直接，多端要各写一套，维护成本更高。

追问：

  • 能接近原生，是因为正式包提前编译成机器码，而且界面是自己画的，不用每次更新都去操作一套系统控件。
  • 到底用 Skia 还是 Impeller 来画像素，看 Flutter 版本和平台，不要说死成某一个。

12. Flutter 的整体架构

结论：从贴着操作系统的一层到贴着业务代码，一共三层：对接系统的 Embedder，跑 Dart 和把界面画成像素的 Engine，以及用 Dart 写组件的 Framework。

机制：

  • Embedder：对接操作系统的那一层。负责窗口和画布、创建线程、把系统事件送进引擎，以及注册插件。
  • Engine：主要是 C++，包含 Dart 运行时、文字、图形和平台事件，通过 dart:ui 交给上面用。画像素的库以前是 Skia，较新版本在多个平台换成 Impeller。
  • Framework：用 Dart 写的框架。从下往上大致是绘制、手势、渲染、Widget、Material / Cupertino。业务代码通常导入 package:flutter/material.dart，而不是只导入 dart:ui。

追问：

  • dart:ui 是 Framework 和 Engine 交界的那一层，不是整个 Flutter SDK。
  • Engine 自己不创建线程。线程由 Embedder 创建，并且在引擎活着的这段时间里不能把这些线程换掉。

13. main 和 runApp 分别做什么

结论：main 是 Dart 程序的入口。runApp 先把框架和引擎接上，再把传入的 Widget 挂成根节点，界面这三棵树从这里开始。

机制：常见写法是 main() { runApp(const MyApp()); }。runApp 之前如果要先用插件，先调用 WidgetsFlutterBinding.ensureInitialized()，把这层连接提前准备好。

追问：

  • runApp 的参数就是根 Widget，通常是 MaterialApp 或 CupertinoApp。
  • 热重载不会重新执行已经跑过的 main。改了启动逻辑，要热重启。

14. Widget 有哪几类，为什么不能改

结论：Widget 是一份不能改的界面配置，不只是“控件”。配置不能改，框架才能拿新旧两份来比，决定树上哪一段可以留着。最常拿来比较的是 StatelessWidget 和 StatefulWidget。另外还有 InheritedWidget、RenderObjectWidget 等。

机制：

  • StatelessWidget 没有单独的 State。界面只由构造参数，以及从上层拿来的数据决定。这些输入变了，由父组件再建一个新的 Widget。
  • StatefulWidget 通过 createState 交出 State，State 由 Element 保存。Widget 配置可以换成新的，只要这个 Element 还在，State 就还在。
  • Widget 会被频繁新建，所以要轻。真正留在树上、持有状态的是 Element。如果配置本身还能被改掉，框架就分不清这次 build 到底变了什么。

追问：

  • StatefulWidget 不会自己发现数据变了就重建。要调用 setState，或者它用到的上层数据变了，框架才会把它标成需要重新 build。
  • StatelessWidget 也可以拿到会变化的数据，只是它自己没有生命周期去响应。变化来自父组件传入的一份新配置。

15. State 的生命周期

结论：顺序是 createState → initState → didChangeDependencies → build。之后配置或上层数据变了，会再走进对应的更新方法。暂时离开树时走 deactivate，确定不要了才走 dispose。

机制：

  1. createState()：创建 State，整个生命周期只一次。
  2. initState()：第一次挂到树上时调用一次。在这里订阅不会变的数据源、创建 Controller。方法开头调用 super.initState()。这里还不能读 Theme、MediaQuery 这类从上层传下来的数据。
  3. didChangeDependencies()：紧跟在 initState 后面，以及用到的上层数据发生变化时再调用。读 Theme、MediaQuery、Provider 放这里。
  4. build()：不要在里面改数据或发请求，只根据当前配置和 State 把界面描述出来。
  5. didUpdateWidget(oldWidget)：父组件传入了新的 Widget，而且类型和 key 都没变、原来的 Element 还在用。在这里比较 oldWidget 和 widget，换订阅、重启动画。自己 setState 不会走进这个方法。
  6. reassemble()：热重载时调用。
  7. deactivate()：暂时从树上拿下来。如果带着 GlobalKey 挪到另一个父组件，随后可能再挂回去，这时不要把资源释放掉。重写的话，方法末尾调用 super.deactivate()。
  8. dispose()：确定不会再挂回去。释放 Controller、Timer、订阅，然后调用 super.dispose()。dispose 返回、节点和 State 断开之后，mounted 才变成 false。写在 dispose 里面的代码当时还能读到 mounted 为 true，但这里不能再 setState。

追问：

  • 父组件把 userId 换成另一个时，如果只在 initState 里订阅，页面会继续显示旧用户。要在 didUpdateWidget 里先取消旧的，再订阅新的。
  • 异步回调回来后先看 mounted。dispose 之后再 setState，debug 下会抛错。release 包去掉了这类检查，不一定抛错，但页面可能已经销毁，这么写仍然是错的。
  • Controller、动画、Timer、Stream 订阅如果没在 dispose 里取消，页面没了它们还抓着回调，或者回调还抓着 State，这就是常见的内存泄漏。
  • 应用进后台再回来，走的是 WidgetsBindingObserver 里的 AppLifecycleState，不是 deactivate。deactivate 只表示这个组件离开了树。

16. setState 做了什么

结论：setState 先立刻执行你传入的回调，再把当前组件标成需要重新 build，等到这一帧或下一帧才真正重建。它不会马上重画，也不会把整个应用都重建一遍。

机制：

  1. 回调里修改 State 的字段。
  2. 调用 markNeedsBuild()，把这个 Element 放进框架的待重建名单。
  3. 同一段同步代码里调用多次 setState，会合并成一次 build。
  4. 这次同步代码跑完后，在这一帧的构建阶段，或排到下一帧，从被标记的 Element 开始重新 build。新 Widget 和旧的子节点按类型和 key 比较，对得上的 Element 和 RenderObject 留着继续用。

追问：

  • setState 要写在真正发生变化的那个小组件上，需要重建的范围才小。写在页面最外层，里面那整棵子树都会重新 build。
  • build 里不能调用 setState，也不能发请求、订阅流。build 在一帧里可能被调用很多次。

17. BuildContext 是什么

结论：BuildContext 是 Element 对外露出的接口。它表示这份 Widget 配置现在挂在树上的哪个位置。

机制：Theme.of、Navigator.of、Provider.of 都从当前位置顺着父组件往上找，并记下“我用到了这份数据”。查找走的是 Element 树。

追问：

  • initState 里已经能拿到 context，但不能调用会向上查找并记住依赖的 of。Theme、MediaQuery，以及其他从上层 InheritedWidget 读数据的代码，放在 didChangeDependencies。
  • build 只负责描述界面。发请求、订阅、跳转放在生命周期或点击回调里，否则每次重建都会再做一次。

18. Key 有什么用

结论：Key 用来在同一层分清：这个 Element 对应的是哪一项数据。类型相同而且 key 相同，框架才复用原来的 Element。

机制：

  • 没有 Key：按位置和类型匹配。列表只是换了顺序，State 还会留在原来的格子上。
  • ValueKey：用一个稳定的业务值，例如条目 id，按这个值的 == 来区分。列表最常用这个。
  • ObjectKey：直接拿一个对象当身份，只有是同一个对象才算对上，比较用的是 identical。两个内容一样、但是新创建的对象，对不上。
  • UniqueKey：每次都是一个新身份。在 build 里写 UniqueKey()，旧的 State 会被丢掉。
  • GlobalKey：整个应用里只能有一个。组件换了父节点，State 还能留着，也可以拿到 currentState、currentContext、currentWidget。框架要在一张全局表里记着它，只适合少量跨组件访问，不能拿来做日常的状态管理。

追问：

  • 列表里每一项的 State 串了，给每一项加 ValueKey(item.id)，不是给整个 ListView 加一个 Key。
  • 普通 Key 只在同一个父组件的子组件之间比较。要换了父组件还保留 State，才考虑 GlobalKey。

19. 滑出屏幕后，状态怎么留住

结论：列表滑出缓存范围，或者 Tab、PageView 滑到旁边，那一项默认会从树上拿掉，State 跟着 dispose。还要留着状态时，让这项声明自己需要保活。

机制：State 混入 AutomaticKeepAliveClientMixin，wantKeepAlive 返回 true。build 里先调用 super.build(context)，框架才会把它登记成不要销毁。这种保活解决的是“滑出屏幕之后留不留在树上”。Key 解决的是同一次更新里“这项还是不是原来那项”，两件是不同的事。

class _TabState extends State<TabPage> with AutomaticKeepAliveClientMixin {
  @override
  bool get wantKeepAlive => true;

  @override
  Widget build(BuildContext context) {
    super.build(context);
    return const Text('kept');
  }
}

追问：

  • 只想记住滚动位置，用 PageStorageKey，不必把整个 State 留着。
  • wantKeepAlive 后来变成 false 时，调用 updateKeepAlive()，否则框架还按旧的来。

20. 热重载和热重启

结论：热重载在调试模式下把改过的代码送进正在运行的程序，然后重新 build，并尽量留着原来的 State。热重启会重新执行 main，State 被清空，但不会把原生工程重新装一遍。

机制：

  • 热重载找出改过的文件、只编译改过的部分、送到正在运行的程序里、合进现有代码，再重建 Widget。它不是只把画面重画一遍，也不是把应用完全关掉再打开。
  • 已经执行过的 initState、改过的全局变量和静态字段、枚举里有哪些值、泛型写法，以及原生代码，热重载盖不住。
  • 热重启会把启动流程再走一遍，适合状态已经和新代码对不上的时候。改了插件、资源或原生代码，需要完全重新启动。

追问：

  • 改了 initState 却看不到效果，是因为原来的 State 还在，初始化不会再跑。热重启一次就行。
  • debug 能热重载，是因为边运行边编译，这种模式叫 JIT。release 包提前编译成机器码，这种模式叫 AOT，没有热重载。

四、状态、路由和动画

21. InheritedWidget 是干什么的

结论：InheritedWidget 把一份数据放在比较靠上的位置，下面的组件按需来取。取的时候会登记“我依赖它”。这份数据变了，只重建登记过的组件，不是把它下面所有节点一律重建。

机制：

  • 子组件通过 dependOnInheritedWidgetOfExactType 向上找最近的那一个，并登记依赖。Theme.of、MediaQuery.of 就是这么找的。
  • 上层换成新的 InheritedWidget 时，框架问 updateShouldNotify。返回 true，登记过的组件才重新 build；返回 false，就只是换掉配置。
  • 只向上找、不登记的话，当时能读到值，之后变了不会通知你。Provider 里 watch 会登记，read 只取一次，就是这个差别。

追问：

  • initState 里不能做这种“查找并登记”。放到 didChangeDependencies。
  • Provider 是在 InheritedWidget 外面加了更好用的写法。数据怎么顺着树传下去，根子还是它。

22. 状态管理怎么选

结论：先看这份状态要活多久、谁要读它。只在一个组件里用，用 setState 或 ValueNotifier。要顺着组件树传给下面，用 InheritedWidget 或它的封装。要跨页面，并且业务逻辑要单独测试，再用 Riverpod 或 BLoC。

机制：

  • setState：状态和界面写在一起，影响范围最小。
  • InheritedWidget：数据放在上层组件里。下面的组件读取时，会记下“我依赖这份数据”。数据变了，只重建读过它的那些组件，不是把它下面所有节点一律重建。
  • Provider：在 InheritedWidget 外面包了一层常用写法，数据变了可以通知界面。读取时仍然从当前位置顺着父组件往上找。
  • Riverpod：状态在写代码时就声明好了，读取时不用靠 BuildContext 在树上找。可以只监听对象里的一个字段。没有人再监听时，可以自动释放。
  • BLoC / Cubit：界面把“发生了什么”交出去，业务算出新的状态再交回来，两边可以分开测。Cubit 是直接调用方法交出新状态。BLoC 多一层事件，界面只报告发生了什么。事件要按类型展开时用 BLoC，简单状态用 Cubit 就够。

追问：

  • Provider 找不到，通常是读取的位置不在 Provider 的下面，或者用了只读一次、之后变了也不会刷新的读法。Riverpod 把状态放在独立的容器里，就是为了不用在这棵组件树上找。
  • 按团队和要不要测试来选。简单页面上整套 BLoC，和复杂业务只靠一层层 setState，都是选得不合适，不是框架做不到。
  • 被问到 GetX 时，说清它把状态、路由和依赖放在一起、调用直接。刷新从哪来不如 Riverpod 或 BLoC 好追。不要只报一个库名。

23. Navigator 和 MaterialApp 做了什么

结论：Navigator 管页面栈：打开、返回、替换，以及页面之间的动画。MaterialApp 会放好主题、语言，并创建一个 Navigator。

机制：

  • Navigator.of(context) 从当前位置顺着父组件往上找，找到最近的那个 Navigator。
  • 直接 push 一个页面，是匿名路由。给页面起名字再用 pushNamed，名字和页面的对应关系写在 routes 或 onGenerateRoute 里。
  • final result = await Navigator.push(...)，下一页 pop(result)，这个返回值就是当时那个等待的结果。
  • go_router 用一份路由表写出页面和地址怎么对应，适合从外部链接直接打开某个页面、Web 地址，以及登录拦截。页面栈不复杂时，直接用 Navigator 就够。

追问：

  • 页面 A 打开页面 B 时，A 的 State 通常还在，也还挂在树上，只是被盖住、不再显示，不会重新走 initState。只有 A 被从栈里拿掉，才会 dispose。默认页面路由会把被盖住的页面留在内存里，这个开关叫 maintainState，默认是 true。
  • 在 build 里 push，每次重建都会再打开一页。跳转放在点击回调里，或者放在导航条件已经确定之后。

24. 动画怎么做，vsync 是什么

结论：只是某个属性要从现在的值变到新的值，用隐式动画，给出目标值和时长就行。要自己控制开始、暂停、重复，或者跟着手势走，用显式动画：自己拿着一个进度，再把进度映射成具体的值。

机制：

  • 隐式动画：AnimatedContainer、AnimatedOpacity、AnimatedPadding。目标值变了，框架在 duration 里自己过渡。
  • 显式动画：AnimationController 产生 0 到 1 的进度，Tween 把进度换成宽度、透明度这种实际值。界面用 AnimatedBuilder 或 FadeTransition 听这个值。
  • 屏幕每刷新一次会发一个信号，动画按这个信号往前走，不在两次刷新之间空转。这个信号叫 vsync。跟这个信号走的计时器叫 Ticker，一般由 SingleTickerProviderStateMixin 提供。一个 State 要同时跑好几个动画，用 TickerProviderStateMixin。页面不在屏幕上时，这个节拍会停。
  • AnimationController 要在 dispose 里释放，否则 Ticker 还挂着。

追问：

  • 两个页面上 tag 相同的 Hero，跳转时是同一块元素从旧位置移到新位置。这种共享元素过渡不用自己算两边的坐标。
  • 隐式动画省事，但不好中途停，也不好把几段动画接起来。需要这些控制时再上 AnimationController。

五、渲染

25. 布局时，约束和尺寸怎么传

结论：父组件把宽高的允许范围传给子组件，子组件在这个范围里决定自己的大小并交回去，父组件再决定子组件放在哪。范围里既有最小，也有最大。这三句的英文说法是：Constraints go down, sizes go up, parent sets position。

机制：

  • 这个允许范围的类型叫 BoxConstraints，里面是最小宽度、最大宽度、最小高度、最大高度。子组件交回去的尺寸必须落在里面。子组件不能自己决定放在父组件的哪个位置。
  • Row、Column 里的 Expanded，是让子组件把分到的那段主轴空间占满。Flexible 是最多用这么多，子组件可以更小。这两个都必须放在 Row、Column 或 Flex 里，并且这个方向上的最大尺寸得是有限的。
  • 纵向的 ListView 或 SingleChildScrollView 沿着滚动方向给出的是“多高都行”的无限高度。里面再放 Expanded，或者再放一个自己也要无限高的 ListView，就会报无界高度：一边要一个有限的上限，一边给不出。

追问：

  • 列表套在 Column 里报错，给列表一个有限高度，例如外包 Expanded，外层 Column 自己的高度也得是有限的。项很多时不要用 shrinkWrap 把列表撑开，那会一次布局很多子组件。
  • 文字在 Row 里横向溢出，是这段文字没有一个有限的最大宽度。用 Expanded 或 Flexible 把宽度限制住。

26. Widget、Element、RenderObject、Layer 和一帧渲染

结论：Widget 是一份不能改的界面配置。Element 是这棵树上真正留着的节点。RenderObject 负责算尺寸、绘制，以及判断点到了谁。Layer 是画完后交给画像素线程去合并的一层结果。

机制：

  • Widget 创建时展开成 Element。Element 拿着当前这份 Widget 配置。有状态时，再由 Element 创建并保存 State。需要参与布局的 Element，会创建或更新对应的 RenderObject。
  • 父 Element 更新子节点时，比较新旧 Widget 的类型和 key。两个都相同，就沿用原来的 Element，只更新配置。有一个不同，就卸掉旧的，再建新的。Element 可以复用，但不是永远不重建。
  • 一帧里：build 写出新的界面配置，layout 算尺寸和位置，paint 画出或更新图层。父组件先把宽高的允许范围传下去，最小和最大都有；子组件在这个范围里算出自己的大小交回去，父组件再决定子组件放在哪。
  • 图层交给画像素线程去合并、变成像素。RepaintBoundary 让一块区域单独重画，不要带着整页一起重画。

追问：

  • 没有 Key 时，同一层主要按位置和类型对上号。列表只是换了顺序，State 可能还留在原来的格子上，看起来像串了。
  • build 调用得很频繁，不等于整棵绘制树都重建。配置没变的 RenderObject 可以跳过重新布局或重新绘制。

27. 线程模型，以及高刷新率上怎么看掉帧

结论：引擎准备了四条专用线程：平台、界面、画像素、文件。Dart 的主 isolate 跑在界面这条线程上。屏幕是 120Hz 时，一帧大约只有 8.3 毫秒。这一帧能画完，并且系统允许这个刷新率，Flutter 就能跟上。

机制：

  • 平台线程：处理系统消息和插件调用。
  • 界面线程：跑 Dart 代码，做 build、layout、paint，产出这一帧的图层。
  • 画像素线程：把这些图层合成，再画成像素交给 GPU。现在的名字是 Raster 线程，旧文章里的 GPU 线程就是这一条。
  • 文件线程：解码图片、读资源，避免堵住界面线程和画像素线程。
  • 屏幕发出“该画下一帧了”的信号后，界面线程做完这一帧的构建，把图层交给画像素线程。哪一条超时，卡顿就出在哪一步。DevTools 的帧图可以区分是 build、layout 慢，还是画成像素这一步慢。

追问：

  • 主 isolate 跑在界面线程上，但 isolate 和这四条线程不是一回事。再用 spawn 开出来的 isolate，不归框架统一管。
  • 第一次用到某种绘制效果时，GPU 可能要临时把这段绘制程序编译出来，这一步叫编译着色器（shader）。卡顿发生在画像素这一步。Impeller 提前把这些绘制程序准备好，就是为了少做这种临时编译。测量要用 profile 模式，debug 模式本身更慢。

28. 什么时候自定义布局

结论：先用现有 Widget 拼。只有要画的形状，或者排列规则，Row、Column、Stack、CustomPaint 都做不到时，才自己写 RenderObject。

机制：

  • 组合：把现有 Widget 包一层，处理间距、点击和状态。
  • 自己画：用 CustomPaint 和 CustomPainter，适合图表、特殊形状。位置和大小仍然交给现有的布局组件。
  • 自己定布局：实现 RenderObjectWidget 和 RenderBox，重写怎么算大小、怎么画、怎么判断点到了谁。还要处理无障碍信息（semantics）、要传给父布局的额外数据（parentData），以及这块区域要不要单独重画（isRepaintBoundary）。

追问：

  • 三件套各管一段：Widget 暴露给外面的配置，Element 负责更新和挂到树上，RenderObject 真正去算布局和绘制。
  • 算大小时必须遵守父组件给的范围，再把自己的尺寸交回去。自己放在父组件的哪个位置，由父组件决定。

29. 一次点击为什么只有一个组件响应

结论：手指按下后，先找出点中了哪些组件，再让这些组件上的手势识别器去争这一次手势。争完只有一个获胜，所以父子都写了 onTap 时，通常只有子组件收到。

机制：

  • 先看这个点落在哪些组件的范围内，得到一条从最里层子组件到外层父组件的路径。
  • 路径上通过 GestureDetector 注册的识别器进入同一个竞技场，这个竞技场叫 Gesture Arena。手指移动或抬起时分出胜负。抬起时如果还剩多个，先加入的那个赢，一般就是更靠里的子组件。
  • Listener 直接收按下、移动、抬起，不进这个竞技场。父组件只是想知道手指在自己范围内动过，用 Listener，不要再叠一个会和子组件互抢的 onTap。

追问：

  • 列表里的按钮和列表的滑动会抢。手指移动超过一小段距离，滑动获胜，按钮的点击就取消。这是竞技场分出了胜负，不是事件丢了。
  • GestureDetector 的 behavior 决定空白处算不算点中自己：默认只认点中了子组件；设成 opaque，整块区域都算点中。

六、混合与构建

30. Flutter 如何和 Android / iOS 通信

结论：调用系统能力时走 Platform Channel：先把参数编成两边都认识的数据，异步发给原生，再把结果解回来。已经有 C 或 C++ 库，或者调用非常频繁、不想每次都走消息时，用 dart:ffi。

机制：

  • MethodChannel：调用一次方法，带回一个结果或一个错误。
  • EventChannel：原生不停地把事件推给 Dart，Dart 这边拿到的是 Stream。适合传感器、扫码这种连续回调。
  • BasicMessageChannel：按约定的编码方式双向传消息，不限定成“一次请求、一次返回”。
  • 这些通道不会自动帮你切到正确的线程。Dart 这边在主 isolate 上收发；原生那边要把调用切到它自己要求的线程。
  • FFI 按 C 语言的调用方式直接调函数，少一次把消息打包再拆开的过程，但内存里字段怎么排列要自己管。系统界面、Activity、权限这类平台对象，仍然用 Channel。

追问：

  • 要“调用一次、拿一个结果”，用 MethodChannel。原生要连续上报，用 EventChannel。不要在原生那边用一个死循环占住这条通道。
  • 参数和返回值必须能按默认那套规则装进去，这套规则叫 StandardMessageCodec。能直接装的是空、布尔、整数、小数、字符串、几种定长数组，以及 List 和 Map。自定义对象先拆成这些。

31. 包和插件有什么区别

结论：包（package）是一份可以依赖的代码，纯 Dart 的工具和 Widget 做成包就行。插件（plugin）也是一个包，但另外带了 Android、iOS 或其他平台上的实现，用来碰系统能力。

机制：插件在各平台有实现，一般通过 Platform Channel 或 FFI 调到原生，业务侧只依赖它的 Dart 接口。通道是通信办法，插件是把这个办法和各端实现打包给别人用的形式。不是每个插件都只用 MethodChannel。

追问：只在这一个应用里用的原生调用，写在应用自己的 Android、iOS 工程里就行。同一套原生能力要给多个应用用，再做成插件。

32. 混合栈怎么组织

结论：整个应用都是 Flutter 时，用自己的 Navigator。已有的原生 App 要一页一页嵌进 Flutter 时，才要让原生的页面栈和 Flutter 的页面栈对上。这时要选一个引擎还是多个引擎。

机制：

  • 一个引擎：内存更省。多个原生页面共用这一个引擎时，要处理哪一页正在显示、触摸事件给谁，以及谁在栈顶。
  • 多个引擎：每个原生容器一个引擎，彼此隔开，但启动更慢、内存更大，插件也要各注册一次。
  • flutter_boost 是这种嵌进原生导航的一种做法：原生页面当容器，里面放 Flutter 页，再用路由表和消息让两边的页面栈、生命周期对上。好处是能继续用原生的导航和转场，旧页面可以慢慢换。代价是容器怎么复用、内存、插件初始化和两边栈的同步，都要额外维护。

追问：

  • 新项目如果 Android 和 iOS 都用 Flutter 写，不需要 flutter_boost。
  • 最容易错的是生命周期：原生页面盖住 Flutter 页面时，Flutter 还在不在画，引擎里的定时器还在不在跑。

33. 构建模式和多端产物

结论：开发用 debug，量快慢用 profile，上架用 release。这三种模式的差别，比最后打成哪个平台更大。

机制：

  • debug：边运行边编译，这种模式叫 JIT。检查代码的 assert 和调试服务都还在，可以热重载。这时测出来的帧时间和包体积，不能当成正式包的结果。
  • profile：和 release 一样提前编译成机器码，这种模式叫 AOT，但还留着性能记录。用 DevTools 看卡顿，用这个模式。
  • release：同样是 AOT，去掉 assert，再删掉确定用不到的 Dart 代码（tree shaking），然后混淆、签名。
  • 打到哪个平台，只是最后交给谁去打包：Web 是 flutter build web 产出的静态文件；Android 是 apk 或 appbundle；iOS 走 flutter build ios 和 Xcode 归档；桌面是 macos、windows、linux。前面都是按模式编译、收资源和插件，再交给对应平台签名打包。

追问：

  • debug 下流畅，不能说明 release 没问题，反过来也一样。着色器卡顿和启动时间，要在 profile 或真机的 release 包上看。
  • 能删掉没用到的代码，是因为提前编译时可以从 main 看出哪些代码永远走不到。debug 是边运行边编译，不会做同样的删除，所以 debug 包的大小不能用来估计上架体积。
  • 上面说的 JIT / AOT 指手机和桌面这套 Dart 编译。Web 的 release 是编译成 JavaScript 或 Wasm，同样不能热重载。

七、性能

34. 怎样减少重建、长列表卡顿和大图开销

结论：先分清慢在哪一步：是重新 build，是算布局，还是画成像素。最常见的三处是重建范围太大、一次创建的子组件太多、图片按原图尺寸解码。

机制：

  • 重建：把会变的 State 放到真正会变的那个小组件里。不会变的部分做成 const。父组件重新 build 时，如果子组件还是同一个对象，框架就不再往下更新它。
  • RepaintBoundary 把一块绘制单独成一层。滚动条、动画图标重画时，就不会带着整页一起重画。每一块都是单独的一层，划得太多会多占内存，合并图层的成本也更高。
  • 长列表用 ListView.builder，滑到附近才创建那一项。ListView(children: ...) 会一次全部建完。每一项高度固定时，把高度告诉列表，省掉反复测量。每一项的 Key 用业务 id，不要在 build 里创建 UniqueKey。
  • 大图按屏幕上实际显示的像素大小来解码，把目标像素写进 cacheWidth 和 cacheHeight，并使用缓存。不要在 build 里当场把整张原图读进内存。上传前先压缩、缩小；大文件分段传，并带上进度、取消和重试。压缩和算哈希放到另一条 isolate，进度再用 Stream 或状态管理送回负责界面的那条。
  • Controller、订阅和 Timer 没在 dispose 里放开，对象会一直被抓住。这是最常见的内存泄漏，先看这里，再怀疑图片缓存。

追问：

  • profile 里界面线程的 build 很长，先拆 Widget，并把 setState 放到更小的组件上。画像素那条线程很长，再看是不是图层太多、用了模糊和裁剪，或者图太大。先不要换状态管理库。
  • const 省下的是：子组件还是同一个对象时，不再往下比较。构造参数里每次都新建一个对象，就写不成 const，这条捷径也不会发生。

附录：初级语法

下面几题在老题库里出现过，现在很少单独成题。空安全的 ?? 可以当作第 1 题的补充。

A1. ?? 和 ??=

  • a ?? b：a 为 null 时，结果是 b，否则是 a。
  • a ??= b：只在 a 为 null 时，才把 b 赋给 a。结果是赋值之后的值。

A2. 默认是强引用还是弱引用

普通变量会一直抓着对象，对象就不会被回收。这种一直抓住不放的引用叫强引用，Dart 里的普通变量默认就是强引用。缓存，或者“对象被回收时顺便做清理”，用 WeakReference 和 Finalizer。只有放进 WeakReference 的那一个引用是弱的，其他普通变量不变。

A3. getter 和 setter

class Temperature {
  double _celsius = 0;

  double get celsius => _celsius;
  set celsius(double value) {
    if (value < -273.15) {
      throw ArgumentError('below absolute zero');
    }
    _celsius = value;
  }

  double get fahrenheit => _celsius * 9 / 5 + 32;
}

A4. 库的可见性

Dart 没有 public、protected、private 这些关键字。同一个库里的声明默认同库都能用。名字以下划线开头，就只有当前这个库能用。一个文件要给外面用哪些声明，看它 export 了什么。

A5. 级联操作符 ..

.. 对同一个对象连续做几件事，整个表达式的结果还是这个对象，不是最后一次调用的返回值。对象可能是 null 时，用 ?..。
