一、Dart

1. var、Object、dynamic，以及空安全

核心回答

var 用于让编译器推断变量的静态类型，推断后仍按该类型检查赋值和成员访问。Object 可以保存任意非空对象，但只能直接使用该静态类型允许的成员，需要具体能力时先进行类型检查或转换；Object? 还允许空值。dynamic 将大部分成员检查推迟到运行时，使用错误可能在运行时才被发现。空安全通过可空类型与非空类型区分值是否允许为 null，可通过判空、?. 和 ?? 安全访问或提供默认值，! 则要求开发者保证当前值非空，否则会抛错。late 允许延迟初始化，但读取前未完成赋值会触发运行时错误；类型提升则让编译器在能够确认条件成立的范围内，按更具体的类型检查变量。

进一步理解

为什么 var 推断成整数后，不能再赋字符串？

执行 var count = 1 时，编译器已经把 count 推断为 int。以后可以换一个整数，但不能改成字符串，因为 var 只是省略类型声明，不是取消类型检查。Object 则允许保存不同非空类型的对象，但读取时只知道它是 Object；dynamic 连成员检查也大多推迟到运行时，所以“能编译”不代表调用一定正确。

为什么判空以后通常不必再写感叹号？

假设 name 是 String?，进入 name != null 的分支后，如果编译器能确认使用前它不会又变成 null，就会把这一范围内的 name 按 String 检查，这叫类型提升。! 则不负责证明，只要求运行时检查当前值非空，失败会抛错。能安全判空时，应先把有值和无值的处理路径写清楚。

late 是晚创建，还是晚赋值？

两种都可能。只有声明、没有初始化表达式时，代码要在第一次读取前完成赋值，否则抛 LateInitializationError。有初始化表达式时，表达式会留到第一次读取才执行。late 让检查推迟，不是自动补一个默认值；再加 final，则仍然只允许赋值一次。

代码示例（看注释与结果）

String? readName() => null;

void main() {
  var x = 1;
  x = 2;
  // x = 'two'; // 错误示例：取消注释会产生编译错误
  Object obj = x;
  print(obj.toString()); // 2
  dynamic raw = x;
  try {
    raw.missing(); // 错误示例：能编译，运行时抛 NoSuchMethodError
  } on NoSuchMethodError {
    print('没有这个方法');
  }
  String? name = readName();
  print(name ?? '访客'); // 访客
  try {
    print(name!); // 错误示例：这里为 null，运行时抛错，可捕获
  } catch (_) {
    print('空值断言失败');
  }
}

易错提醒：dynamic 不是任意类型转换，late 也不是自动提供默认值。

进阶补充：空安全运算符与类型提升边界

??= 只在变量为 null 时赋值，...? 仅在集合非空时展开元素；这些操作不改变变量的声明类型。字段提升取决于语言版本及字段条件，不能把局部变量的提升规则直接套到公开字段、可变字段或 getter 上。必要时先保存到局部 final 再判空。空值断言失败、缺失成员和 late 初始化错误属于可捕获的 Dart 运行时错误，不等同于原生进程崩溃；未处理的错误仍可能终止 isolate。

2. const 和 final 的区别

核心回答

final 限制变量只能赋值一次，值可以在运行时确定，但不会让它引用的可变对象自动不可变。const 声明编译期常量，其值必须能够在编译期确定，常量对象及其常量内容不可修改，同一 isolate 内相同的常量值可以复用同一实例。类通过 const 构造函数支持常量创建，实例字段必须为 final，初始化过程也必须满足常量规则；仅声明常量构造函数，不代表每次调用都是常量调用。Flutter 中复用相同的 Widget 实例，可以跳过由父级更新引起的部分配置更新，但不会阻止组件因自身状态或依赖变化而重建。

进一步理解

final 的列表，为什么还能 add？

final list 固定的是“这个变量指向哪个列表”，不是锁住列表里的内容。因此不能让 list 改指另一个列表，但如果原列表可变，仍然能添加元素。const 列表本身就是常量，不能添加、删除或替换元素。先区分变量的重新赋值与对象内容的修改，就不会把 final 当成深度不可变。

有 const 构造函数，为什么不一定复用对象？

const 构造函数表示这个类允许按常量方式创建。只有调用也处于 const 上下文、参数满足常量规则时，才得到可规范化复用的常量对象；普通调用仍可接收运行时数据并创建新实例。因此“构造函数带 const”与“本次调用创建常量”是两件事。

const Widget 为什么能减少部分更新，却不能保证永远不 build？

父组件重建后，如果仍把同一个 Widget 实例交给框架，这次父级配置更新就可以跳过。const 有助于复用相同实例。但子节点自己的 State 变化、主题等依赖变化，仍可单独请求重建。优化来自复用未变的配置，不是 const 把整个子树冻结了。

代码示例（看注释与结果）

class Box {
  final int n;
  const Box(this.n);
}

void main() {
  final list = <int>[];
  list.add(1);
  print(list); // [1]
  const a = [1];
  const b = [1];
  print(identical(a, b)); // true：相同常量被规范化
  try {
    a.add(2); // 错误示例：能编译，运行时抛 UnsupportedError
  } on UnsupportedError {
    print('常量列表不能修改');
  }
  final n = int.parse('1'); // 运行时值
  final box = Box(n); // const 构造也能普通调用
  const box2 = Box(1);
  const boxes = [Box(1)]; // 隐式 const 上下文
  print(identical(box, box2)); // false
  print(identical(box2, boxes.single)); // true
}

易错提醒：final 不等于对象内容不可变；const 也不意味着组件以后永不重建。

进阶补充：常量构造的要求

常量生成构造不能有普通函数体，包含继承字段在内的实例字段必须为 final，父构造和初始化列表也要满足常量要求。实例字段不能声明 const，类型级常量可用 static const。同一 isolate 内的常量规范化，不应扩大成跨 isolate 的进程全局身份保证。

3. Dart 是值传递还是引用传递

核心回答

Dart 的参数按值传递，传递的是对象引用的值，不会因为传参而复制整个对象。调用后，形参与实参是两个独立变量，但最初指向同一个对象，因此通过形参修改可变对象的内容，调用方能够观察到变化。给形参重新赋值只改变形参的指向，不会改变调用方变量的指向。需要让调用方改用另一个对象时，应返回新对象，再由调用方接收；需要避免共享对象被修改时，应使用不可变数据或按需要复制数据。

进一步理解

修改参数里的列表，为什么调用方也会看到？

调用 grow 时，函数拿到的是列表引用的一份副本，不是新建一个内容相同的列表。两个变量都能访问同一个列表，grow 向其中添加元素，调用方再读原列表自然也会看到。被共享的是对象，形参与实参仍是两个变量。

给参数换一个列表，为什么调用方却没有变？

reset 给形参重新赋值，只是让函数里的那个局部变量指向新列表，外面的变量仍指向原列表。若想让调用方也换成新列表，应返回它，再由调用方接收。这个行为正是按值传递的结果：传入的是引用值，不是外部变量本身的别名。

代码示例（看注释与结果）

void grow(List<int> list) { list.add(1); }
void reset(List<int> list) { list = []; }

void main() {
  final values = <int>[];
  grow(values);
  print(values); // [1]：同一个可变对象被修改
  reset(values);
  print(values); // [1]：给形参重新赋值不影响调用方变量
}

易错提醒：修改参数指向的对象，与给参数重新赋值，是两种操作。

4. extends、implements 和 mixin

核心回答

extends 用于单继承，同时获得父类可继承的实现和子类型关系；implements 只建立接口约束，不继承对方的实现，具体类必须自行提供或继承所需成员，一个类可以实现多个接口。mixin 通过 with 复用字段和方法，不要求多个使用者具有同一个业务父类；on 用于限制能够混入的父类型条件。多个 mixin 定义同名方法时，靠后的实现优先，只有显式调用 super 才会继续执行前面的实现。选择时，需要继承已有类型行为用 extends，只承诺接口能力用 implements，需要跨类复用一组实现用 mixin。

进一步理解

implements 一个类，为什么还要自己写方法？

extends 同时继承类型关系和可继承的代码；implements 只承诺“我满足这个接口”。即使接口类已经写过方法体，也不会因此复制到实现类。具体类可以自己实现，或由已有父类提供实现，但最终必须满足接口要求。

两个 mixin 都有同名方法，会执行两次吗？

不会自动执行两次。with 后面的 mixin 实现先起作用，只有它调用 super，才沿方法查找链继续进入前面的实现。可以把父类与多个 mixin 看成有顺序的查找链，而不是同时合并执行的方法集合。

on 为什么会限制哪些类能使用 mixin？

如果 mixin 内部需要调用某个父类型的能力，就用 on 明确这一前提。宿主在混入前必须满足该类型条件，编译器才能确认这些成员存在。mixin 用于复用实现，on 用于声明实现依赖的前提，两者都不是创建额外父类实例。

代码示例（看注释与结果）

class Animal { void breathe() => print('呼吸'); }
abstract interface class Runnable { void run(); }
class Dog extends Animal implements Runnable {
  @override
  void run() => print('跑');
}
mixin Walk on Animal { void go() => breathe(); }
class Cat extends Animal with Walk {}

void main() {
  Dog().run(); // 跑
  Cat().go(); // 呼吸：复用了 Animal 的方法
}

图示说明

易错提醒：implements 不带来方法实现，多个 mixin 也不会自动依次执行同名方法。

进阶补充：mixin 与类修饰符的库边界

mixin 不能声明构造函数；mixin class 可以同时作为类与 mixin，不能声明生成构造，但可以声明 factory。Dart 3 中 interface 限制库外继承，base 限制库外实现，final 同时限制库外继承和实现，sealed 将直接子类型限制在当前库。base 的子类型还需使用相应修饰符。这些限制中的库通常指一个 Dart 文件及其 part 文件，不是整个 package。

官方核对：类修饰符与库边界。

5. extension 是干什么的

核心回答

extension 用于在不修改原类型、不建立继承关系的情况下，为已有类型提供方法、getter 和 setter。扩展由编译器根据调用处的静态类型选择，不会把成员实际添加到原类中，因此不能通过 dynamic 的运行时成员查找调用扩展，也不能覆盖原类型已有的同名实例成员。扩展不能添加实例字段，不会为每个对象增加存储空间，但可以声明静态成员。其他库中的扩展需要导入并处于可见范围；存在同名扩展冲突时，可以调整导入范围或显式指定扩展名称。

进一步理解

扩展看起来像实例方法，为什么 dynamic 调不到？

扩展方法由编译器根据接收者的静态类型选定，并没有真正写进原类的运行时成员表。下面字符串变量能找到 StringX，是编译器已经知道它是 String；改为 dynamic 后，运行时只查对象本身的成员，不会替你搜索扩展。需要时可以显式指定扩展。

扩展能给每个对象增加一个字段吗？

不能。扩展不改变原对象的存储结构，所以能补方法和计算访问器，却不能替每个实例新增存储字段。getter 可以计算或读取已有数据，setter 可以操作已有状态；如果需要真正增加独立数据，就应在包装对象或其他明确的状态持有者中保存。

同名成员为什么有时选不到扩展？

原类型已经有同名实例成员时，优先使用原成员，扩展不能借同名方法实现运行时重写。两个可见扩展发生冲突时，可收窄导入范围，或用“扩展名(对象)”明确指定。决定权在编译期可见的类型和扩展范围，不在对象的运行时类型。

代码示例（看注释与结果）

extension StringX on String {
  bool get isBlank => trim().isEmpty;
}

void main() {
  String name = '  ';
  print(name.isBlank); // true：按静态类型 String 选择扩展
  dynamic raw = name;
  try {
    print(raw.isBlank); // 错误示例：能编译，运行时查找实例 getter
  } on NoSuchMethodError {
    print('dynamic 不会自动调用扩展');
  }
  print(StringX(raw as String).isBlank); // true：显式调用扩展
}

易错提醒：扩展按静态类型选择，不能当作运行时重写。

6. 工厂构造函数和普通构造函数

核心回答

普通生成构造函数负责创建并初始化当前类的实例，不能返回另一个对象；常量生成构造按常量方式调用时，可以复用规范化后的常量实例。工厂构造函数通过 factory 声明，负责返回当前类型或其子类型的对象，可以返回已有实例，也可以创建新实例，因此不保证每次调用都创建对象。工厂构造函数不能通过 this 访问正在初始化的当前实例，缓存和对象选择逻辑需要由实现自行提供。带函数体的工厂构造不能是常量构造，重定向的 const factory 则可以委托给兼容的常量构造。命名构造只是为构造入口命名，与是否使用工厂是两个不同维度。

进一步理解

factory 为什么可以两次返回同一个对象？

普通生成构造负责创建当前类的新实例，而工厂只负责返回一个类型兼容的对象。下面缓存构造先查 Map，已有对象就直接返回；没有才创建并记录。缓存由代码维护，不是 factory 自动提供的能力，因此还需要考虑缓存何时释放。

命名构造与工厂构造，是二选一吗？

不是。命名构造回答“这个入口叫什么”，factory 回答“这个入口怎样提供对象”。fromJson 可以是普通命名构造，也可以是工厂构造，要看是否声明了 factory。需要解析数据后选择不同子类型或复用对象时，工厂更灵活；只初始化本类字段时，生成构造就能完成。

为什么工厂里不能直接给 this 的字段赋值？

工厂执行时没有一个默认已分配、等待你初始化的当前实例，因此不能用 this 操作它。工厂应先处理输入、查缓存或选类型，然后调用合适的构造函数，最后把对象返回。真正建立实例字段的工作仍由相应生成构造完成。

代码示例（看注释与结果）

class User {
  User(this.name);
  User.fromJson(Map<String, Object?> json) : name = json['name'] as String;
  static final Map<String, User> _cache = {};
  factory User.cached(String name) =>
      _cache.putIfAbsent(name, () => User(name));
  final String name;
}

void main() {
  print(User.fromJson({'name': '小明'}).name); // 小明
  print(identical(User.cached('小明'), User.cached('小明'))); // true
  print(identical(User('小明'), User('小明'))); // false
}

易错提醒：factory 不自动缓存，命名构造也不等于工厂构造。

进阶补充：const factory 与输入校验

带函数体的工厂不能作为常量构造；重定向的 const factory 可以把创建交给兼容的常量构造。本题 fromJson 示例假设 name 字段存在且为 String，不满足时会在类型转换处抛错。实际解析应明确缺字段、空值和错误类型的处理，不能把示例里的强制转换当成完整校验。

二、异步和并发

7. Future 和 async / await

核心回答

Future 表示一次操作将来的完成结果，成功时提供一个值，失败时提供错误，本身不创建线程或并行执行环境。async 函数返回 Future，调用时先执行第一个 await 之前的同步代码，随后通过等待和恢复组织后续流程。await 等待结果时挂起当前异步函数，不会阻塞整个 isolate；收到异步错误时，可在等待处通过 try/catch 处理。同步耗时计算不会因为放进 Future 或标记为 async 就自动在后台运行。Future.wait 用于汇总多个结果，成功结果按输入顺序排列；Completer 用于主动控制一个 Future 何时成功或失败。

进一步理解

await 等请求时，为什么界面还能响应点击？

请求未完成时，当前异步函数把后续工作暂时放下，让事件循环处理其他事件。结果到达后，再恢复 await 后的代码。暂停的是这一段异步流程，不是整个 isolate；但 await 之前和恢复后的同步计算仍需执行，计算太久一样会卡住界面。

把大循环放进 Future，为什么还是卡？

Future(() {}) 只是把回调安排到当前 isolate 的事件队列，不会新建后台执行环境。轮到回调时，大循环仍占用这条执行路径，其他输入和帧工作就要等待。需要并行处理 CPU 重活时，在支持的平台考虑 isolate，而不是继续包更多 Future。

为什么 try/catch 只包函数调用，有时接不到异步错误？

异步函数返回 Future 后，错误可能在稍后才发生，调用处的同步 try/catch 已经结束。需要把 await 放在 try/catch 内，让错误在恢复等待时进入 catch。Future.wait 则把多个完成结果汇总，返回列表按输入顺序排列，不需要靠先完成的请求占第一个位置。

代码示例（看注释与结果）

import 'dart:async';

Future<int> fetch() async {
  print('开始');
  await Future<void>.delayed(Duration.zero);
  throw FormatException('模拟失败');
}
Future<int> load() async {
  try {
    return await fetch(); // await 把 Future 的错误送到这个 catch
  } on FormatException {
    return 0;
  }
}
Future<void> main() async {
  final pending = load();
  print('调用后');
  print(await pending);
  // 输出顺序：开始、调用后、0
  // 错误示例（不执行）：try { fetch(); } catch (_) {}
  // 上面的 catch 只能接同步抛出，不能接 fetch 返回的 Future 的异步错误。

8. Future 和 Stream 有什么不一样

核心回答

Future 表示一次完成结果，Stream 表示可以持续产生数据和错误的一串事件，并可通过结束事件表示不再产生数据。单订阅流只允许建立一次订阅，广播流允许多个监听者，普通广播流不会为尚未订阅的监听者保留历史事件。async* 用于定义返回流的函数，yield 产生事件；消费方可以通过 await for 顺序处理，或通过 listen 建立订阅，再用 StreamSubscription 暂停、恢复和取消。界面展示可以使用 StreamBuilder 管理订阅和快照，但构建过程不保证显示每一个中间事件，不能用它代替逐事件的业务处理。订阅应随使用方生命周期及时取消。

进一步理解

一个请求和持续的位置更新，为什么用不同类型？

一次请求只需要一个最终成功值或错误，Future 就够了。位置更新会连续到达，可能有错误，也可能主动结束，更适合 Stream。再次 await 同一个已完成 Future 仍可取得结果；流能否再次订阅，则要看它是单订阅还是广播流。

后来才监听广播流，为什么收不到之前的数据？

普通广播流只把事件交给当时的监听者，不保存一份历史给未来监听者。普通单订阅 StreamController 可以在首次监听前缓冲；async* 则通常等开始监听才运行。能否得到旧值取决于具体流实现，不能只凭“这是一个 Stream”判断。

为什么不能在 build 里每次都 listen？

build 可能因多种原因反复执行，每次 listen 都可能增加一个订阅，导致重复处理事件或资源泄漏。应在合适生命周期建立并在 dispose 取消，或让 StreamBuilder 管理。StreamBuilder 适合展示最新快照，帧构建可能跳过中间快照，因此逐笔业务处理仍应放在事件消费逻辑中。

代码示例（看注释与结果）

Stream<String> messages() async* {
  yield 'hello';
  yield 'stop';
  yield '不会打印';
}
Future<void> main() async {
  await for (final event in messages()) {
    print(event);
    if (event == 'stop') break; // 退出时取消本次订阅
  }
  print('结束');
  // 输出顺序：hello、stop、结束
}

易错提醒：StreamBuilder 不保证呈现每个中间事件，不应承担逐事件业务处理。

进阶补充：暂停订阅与快照时序

普通单订阅 StreamController 可以缓冲首次监听前的事件；普通广播流不为未来订阅者补发历史，但某个已存在的订阅暂停时，可以为该订阅缓冲。await for 中途等待也可能暂停订阅，未处理的流错误会使循环退出并抛出。StreamBuilder 的快照构建由帧调度决定，不保证一事件一次 build。

官方核对：StreamBuilder 快照与构建时序。

9. Dart 是不是单线程？事件循环怎么跑

核心回答

Dart 在单个 isolate 内同一时刻只执行一段 Dart 代码，但一个进程可以运行多个 isolate，在 Dart VM 上可以由不同系统线程执行，因此不能把整个 Dart 应用理解为只有一条线程。每个 isolate 通过事件循环调度工作：先完成当前同步代码，再清空微任务队列，然后执行一个普通事件，之后再次处理微任务。微任务优先于下一个普通事件，但不能中断正在执行的同步代码。await 只挂起当前异步函数，不会停止事件循环；长时间同步计算或持续追加微任务，都可能使输入事件和帧处理得不到执行机会。

进一步理解

为什么先写的 Timer，可能后于微任务执行？

先后书写不等于不同队列之间的执行优先级。当前同步代码结束后，事件循环会先清空微任务队列，再取下一个普通事件。因此已经排好的微任务会先于下一个 Timer 或 Future 事件执行，但不会插入尚未结束的同步函数中。

一直添加微任务，为什么会影响点击和刷新？

清空微任务时新加入的微任务也要继续处理。如果每个微任务都再添加一个，队列长期清不空，普通事件就一直排不上。微任务适合短小且需要优先完成的收尾工作，不适合用来无限拆分计算并期待界面自然恢复。

单个 isolate 串行，为什么又能做并发？

异步 I/O 等待时，当前 isolate 可以处理别的事件，多个任务的等待与推进可以交错，这属于并发组织。若要同时执行多段 Dart 计算，则需要其他 isolate 等独立执行环境。在 VM 上它们可分配到不同线程，不能把异步等待与 CPU 并行混为一谈。

10. Isolate 是什么，和 Future 有什么区别

核心回答

Isolate 是独立执行 Dart 代码的环境，拥有自己的内存状态和事件循环，普通可变对象不能跨 isolate 直接共享修改，而是通过消息协作。Future 只表示将来的结果，不提供独立执行环境；Dart VM 上的多个 isolate 才能够并行执行 Dart 计算。SendPort 和 ReceivePort 用于发送、接收消息，数据传递需要遵守可发送类型与复制或转移规则。一次性计算可以使用 Isolate.run 或 Flutter 的 compute，持续通信可以使用 Isolate.spawn。创建和传递数据都有成本，适合处理会阻塞界面的 CPU 密集计算，而不是仅为等待 I/O 增加 isolate；Web 上的 compute 仍在当前事件循环执行，不能获得同样的并行能力。

进一步理解

Future 与 isolate，分别解决哪个问题？

Future 表示“这件事完成后交出什么结果”，并不决定谁来计算。isolate 提供另一套执行环境，让计算有机会与界面工作并行。把大量解析放进当前 isolate 的 Future 仍会占用它；交给另一个 isolate，再通过结果消息返回，才把这份计算移出了当前执行路径。

为什么不能让两个 isolate 直接修改同一个 List？

普通可变 Dart 对象按 isolate 隔离。发送一个可发送的 List，接收端通常获得复制后的对象图，而不是与发送端共享可变列表。这样不必围绕普通 Dart 对象加锁，但要付出消息传递成本。大块字节数据可考虑 TransferableTypedData，仍需遵守其转移和读取规则。

什么情况下搬到 isolate，反而更慢？

如果只是等待网络，新增 isolate 并不会让网络更快，却增加启动和传递数据的成本。短小计算也可能不抵这些成本。应先测量，再把确认影响界面的 CPU 重活搬走；Web 的 compute 没有同样的后台 isolate 能力，不能照搬移动端结论。

11. Flutter 和原生开发的差别

核心回答

Flutter 的普通组件由自身框架和引擎完成布局与绘制，不会为每个组件创建对应的系统原生控件；原生开发则可以直接使用平台提供的控件和界面体系。Flutter 采用声明式界面，业务代码根据状态生成 Widget 配置，框架更新节点后完成布局和绘制，能够复用多端界面与业务代码。平台能力仍需通过插件、平台通道或 FFI 接入，嵌入原生视图可以使用 PlatformView。移动端和桌面开发模式支持热重载，发布模式通常提前编译为机器码，Web 使用不同的编译路径。跨平台复用同时带来引擎体积、平台适配和混合视图成本，最终性能取决于实际构建、布局、绘制和计算开销。

进一步理解

Flutter 的按钮，为什么不等于一个 UIButton？

普通 Flutter 按钮由 Widget 配置驱动框架与引擎绘制，并不为每个按钮创建一个系统按钮。因而不同平台可以共用界面实现，平台控件的自动行为也不会无条件全部获得。确实需要系统视图时，可以嵌入 PlatformView，代价与普通 Flutter 绘制不同。

数据变了以后，为什么重新 build 不等于重建整屏原生控件？

build 返回当前状态下的配置，框架再把新配置与已有 Element 对应，尽可能更新原节点及渲染对象。业务代码不必逐一命令按钮、文字改成什么，但应控制状态更新范围。声明式描述与节点复用共同工作，并不是每次把整个应用销毁再画。

既然跨平台，为什么仍然要写 Swift 或 Kotlin？

相机、系统权限或平台专有接口仍由目标平台提供，Flutter 的 Dart 界面代码不能凭空替代这些实现。插件可以封装差异，平台通道传递调用和结果，FFI 可接入兼容 C 接口的库。能复用的是适合共享的部分，平台行为和集成工作仍需分别处理。

易错提醒：自绘与声明式是不同概念，跨平台也不代表无需原生适配。

进阶补充：渲染后端与平台差异

Skia、Impeller 及 Web 渲染路径的可用性取决于平台、版本与配置。Impeller 通过提前准备部分图形程序减少运行时着色器编译相关开销，不保证消除布局、计算、图片或其他 GPU 工作造成的卡顿。PlatformView 使用原生视图，也有额外的合成与生命周期成本，不能按普通自绘组件推断。

官方核对：Impeller 平台支持范围。

12. Flutter 的整体架构

核心回答

Flutter 主要分为 Framework、Engine 和 Embedder 三层。Framework 使用 Dart 提供 Widget、布局、手势、动画和组件体系，是业务开发主要使用的接口。Engine 提供 Dart 运行环境、文字排版、图形渲染等底层能力，并通过 dart:ui 与框架连接。Embedder 负责把引擎接入操作系统的窗口、渲染表面、输入事件和平台运行环境。引擎通过任务调度入口安排 UI、光栅化、资源和平台相关工作，这些职责不保证各自独占一条系统线程，具体映射取决于平台和引擎版本。

进一步理解

点击从系统进入，最后怎样影响 Flutter 画面？

操作系统先把输入交给平台接入层 Embedder，引擎与框架再把输入转成事件和手势，业务修改状态后，框架完成构建、布局和绘制指令记录，最后由引擎生成画面。三层各有责任，不是 Dart 组件直接控制操作系统所有细节。

Framework 与 Engine，为什么不能合称组件库？

按钮、布局和动画等高层组织主要在 Framework；Dart 执行、文字排版和图形渲染等底层能力由 Engine 提供。Framework 经 dart:ui 使用引擎接口。dart:ui 是连接边界，不等于全部 Flutter API，业务通常导入的是组件与框架库。

四种任务职责，为什么不一定是四条线程？

Task Runner 是任务安排到哪里执行的入口，不等于独占线程。UI、Platform 等职责可以在某些平台版本映射到同一线程，Raster 以及其他运行时线程又有各自任务。因此分析卡顿要看实际调度与耗时，不能先假设永远存在四条互不影响的线程。

13. main 和 runApp 分别做什么

核心回答

main 是 Dart 程序入口，负责启动应用逻辑和必要的初始化；runApp 则把根 Widget 接入 Flutter 框架，并安排后续首帧构建。runApp 会确保 WidgetsFlutterBinding 初始化，绑定负责连接框架与引擎的帧调度、输入及平台消息。若在调用 runApp 前就需要使用依赖绑定的插件，应先调用 WidgetsFlutterBinding.ensureInitialized()。runApp 返回不代表画面已经显示完成，界面还要经过构建、布局和绘制。热重载不会重新执行已经运行过的 main，热重启会重新执行入口和启动逻辑。

进一步理解

runApp 调用完，为什么还没显示首帧？

runApp 接入根 Widget 并安排帧工作，Widget 本身只是配置。框架还要建立节点、构建、布局并记录绘制内容，引擎再输出像素。函数返回只代表这次接入调用完成，不代表屏幕已经呈现；需要首帧后的操作，应使用相应帧回调。

为什么有些插件必须先 ensureInitialized？

如果 main 中先调用依赖框架绑定的平台能力，再执行 runApp，此时 runApp 尚未帮忙初始化绑定。先调用 ensureInitialized 可以保证连接引擎消息等基础能力准备好。它不是替插件完成所有初始化，插件自身需要的异步准备仍应按 API 处理。

修改 main 后热重载，为什么旧值还在？

main 已在应用启动时执行过，热重载会更新代码并尽量保留状态，不会从入口重跑。新的启动逻辑没有重新执行，原状态自然可能继续存在。要验证新的启动和初始化流程，需要热重启；改动原生配置时还可能要重新构建。

import 'package:flutter/material.dart';

void main() {
  WidgetsFlutterBinding.ensureInitialized();
  // 若此处需要 await 插件初始化，把 main 声明为 Future<void> main() async。
  runApp(const MaterialApp(home: Scaffold(body: Center(child: Text('Hello')))));

14. Widget 有哪几类，为什么不能改

核心回答

Widget 是描述界面和行为的不可变配置，配置变化时通常创建新 Widget，再由框架更新已有节点，而不是修改旧配置。常用的 StatelessWidget 没有独立 State，根据参数和依赖数据构建界面；StatefulWidget 通过 State 保存可变数据，State 与 Element 关联，复用节点时可以保留。没有 State 不代表只构建一次，有 State 也不代表修改字段就会自动刷新。其他重要类型中，InheritedWidget 提供可订阅的祖先数据，RenderObjectWidget 创建和更新负责布局绘制的对象，ParentDataWidget 提供父布局需要的子节点参数。配置不可变有利于安全复用并明确更新边界，实际可变状态由 State、Element 等对象管理。

进一步理解

Widget 不可变，计数器为什么还能变？

不可变的是“这一份界面配置”，不是整个应用状态。计数放在 State 中，数值变化后请求构建，产生新的 Widget 配置。框架用新配置更新原 Element，State 仍可保留。于是数据可变、配置不可变，两者并不冲突。

父组件创建了新的 StatefulWidget，为什么 initState 没再执行？

State 不由每份 Widget 配置永久占有，而是关联到 StatefulElement。只要新旧配置按类型和 key 匹配、节点被复用，就只是更新配置，不重新创建 State。initState 对一个 State 执行一次，build 则可以执行很多次。

StatelessWidget 为什么也会重建？

它没有自己独立的 State，但仍会接收父级的新配置，也可以依赖主题、屏幕信息等祖先数据。父级更新或相关依赖通知，都可能使其 build 再次执行。“无状态”只描述它不持有独立 State，不代表输出永远不变。

15. State 的生命周期

核心回答

State 首次创建后的主要顺序是 initState、didChangeDependencies、build。initState 对每个 State 只执行一次，适合初始化资源；需要登记祖先数据依赖的逻辑应放在 didChangeDependencies 或 build，依赖变化后可能再次执行。父级用同类型、同 key 的新配置更新现有节点时，会调用 didUpdateWidget，随后重新构建，适合比较配置并切换订阅。deactivate 表示离开当前位置，仍可能重新插入；dispose 表示永久结束该 State 的使用，应释放资源、取消订阅，此后不能再调用 setState。异步完成后需要确认节点仍有效，同时应尽量在销毁时取消不再需要的工作。State 生命周期与应用前后台生命周期是不同机制。

进一步理解

为什么依赖主题的初始化不能全放 initState？

initState 适合每个 State 只做一次的准备，但此时不应登记 InheritedWidget 依赖。主题等祖先数据可能后来变化，应在 didChangeDependencies 或 build 中读取并订阅。框架首次构建前会调用 didChangeDependencies，之后相关依赖变化也有机会再处理。

参数换了，为什么只在 initState 发请求会显示旧数据？

父级可能复用原节点，只换入新的用户编号配置；旧 State 的 initState 不会重跑。应在 didUpdateWidget 比较旧配置和新配置，必要时切换请求、订阅或动画。这个回调来自配置更新，不是每次 setState 都会触发。

deactivate 与 dispose，为什么不能都用来清理资源？

deactivate 只表示节点离开当前位置，同帧内还可能重新插入，贸然销毁仍要使用的资源会破坏状态。dispose 才表示不再复用，应取消 Timer、订阅并释放 Controller。异步回调要防止在销毁后更新；进程被系统直接终止时，也不能依赖 dispose 必然执行。

16. setState 做了什么

核心回答

setState 先同步执行传入的回调，再将当前 Element 标记为需要重建，由框架在适当的构建阶段调用 build。它不会监听字段变化，也不会立即把界面绘制到屏幕；只修改字段而不通知框架，界面不一定更新。同一节点在下一次构建前被重复标记，通常只需构建一次，子节点是否继续更新取决于配置和依赖变化，不等于整个应用重新创建。回调必须同步完成，不能声明为 async；应先完成异步工作，再确认 State 仍有效并更新状态。销毁后不能调用 setState，将状态放在真正变化的较小组件中，可以控制更新范围。

进一步理解

为什么直接给字段赋值，画面不一定变？

字段变化只是 Dart 对象里的数据变了，框架不会自动监听所有字段。setState 在执行修改回调后，把当前 Element 标记为需要构建。即使回调没有修改数据，仍然会请求构建，因此它是通知机制，不是比较新旧字段的工具。

setState 后立刻读到新数据，为什么屏幕可能还是旧画面？

回调同步执行，所以字段立即更新；但界面更新要等待构建和绘制流程。多次标记同一个未构建节点通常可合并处理，不表示多次同步绘制。新旧配置匹配时还能复用子节点，因此一次 setState 也不等于整个应用重建。

为什么不能把 setState 的回调写成 async？

框架要求回调同步完成后就安排构建，async 中 await 后的修改可能发生在更晚的时刻，脱离这次更新通知。正确顺序是先等待异步结果，再确认 State 未失效，然后同步更新数据。不再需要的请求或订阅应尽量取消，而不是只靠 mounted 兜底。

17. BuildContext 是什么

核心回答

BuildContext 是 Element 实现的接口，表示一个节点在 Element 树中的位置，用于查找祖先及获取环境数据。依赖式读取不仅查找数据，还会登记当前节点与祖先数据的依赖关系，使相关数据变化后能够通知重建；普通查找只返回当前结果，不自动订阅。查询范围由 context 所处的位置决定，只能向祖先查找，不能查找当前节点将创建的后代。initState 中已有 context，但不能通过它登记 InheritedWidget 依赖。跨异步等待后使用某个 context，应检查该 context 自己的 mounted，已卸载的 context 不能继续用于祖先查询。

进一步理解

为什么同一段代码换个 context，就找不到 Navigator 或 Provider？

context 表示具体节点的位置，查找从这个位置向祖先进行。如果 Provider 是当前 build 将创建的后代，当前 context 就不能向上找到它。应在 Provider 下方的节点使用自己的 context；这不是查找名称的问题，而是树位置不同。

读取一次数据，为什么后来变化不一定刷新？

依赖式读取会额外记录“这个节点依赖这个祖先数据”，之后数据通知才能找到它。普通查找只是拿到当前对象，不留下数据变化订阅。Theme.of 等常登记依赖，Navigator.of 则查找导航器；Provider 的 watch 与 read 也应区分，不能把所有 of 或读取操作一概而论。

跨 await 后，为什么要检查这个 context 自己的 mounted？

等待期间用户可能已经离开，原节点被移除，旧 context 失效。调用前检查这个 context.mounted，才能确认它仍对应有效节点。某个 State 的 mounted 只说明它自己的关联状态，不能代替另一个子节点 context 的检查。

18. Key 有什么用

核心回答

Key 用于帮助框架判断新 Widget 应当更新哪个旧节点。在同一个父节点的匹配范围内，类型和 key 相同，才可以用新配置更新原 Element 并保留 State；没有 key 时通常主要按位置和类型匹配。ValueKey 按值比较，ObjectKey 按对象身份比较，UniqueKey 每次创建都是新身份。局部 key 在同一父节点的子项之间保持唯一，并应放在真正参与匹配的那一层。GlobalKey 要求在活动树中唯一，可支持同帧跨父节点移动并保留 State，也可访问节点状态，但应长期保存并控制使用范围。Key 只是身份标识，不能恢复已经销毁的状态；懒列表重排还可能需要提供 key 到新下标的映射。

进一步理解

列表重新排序后，输入内容为什么可能留在原位置？

没有稳定 key 时，框架通常按同层的位置和类型复用节点。数据换了顺序，旧 State 可能留在位置上，新数据却传了进来。把稳定业务身份放在实际参与匹配的子项 key 上，才能告诉框架“这是同一项移动了”，而不是“原位置换了配置”。

ValueKey、ObjectKey 与 UniqueKey，应该怎样区分？

ValueKey 用值的相等规则比较，适合稳定编号；ObjectKey 判断是否为同一个对象，新建但内容相同的对象仍可能不匹配。UniqueKey 每次创建都不同，如果在每次 build 中新建，就会主动放弃旧节点身份。Key 不保存数据，状态能保留的前提仍是原节点可被复用。

什么时候才需要 GlobalKey？

局部 key 只在同一父节点的孩子间匹配。确需同帧跨父节点移动并保留 State，或受控访问某个节点的 State 时，可以考虑长期保存的 GlobalKey。它必须在活动树中唯一，也有重新挂载等成本；不能靠同一个 key 复活已经 dispose 的状态。

进阶补充：Key 的匹配层级

局部 key 必须放在父节点实际匹配的直接子项层级，给整个列表设置一个 key 不能区分列表内各数据项。ListView.builder 等懒构建组件重排时，还可能需要 findChildIndexCallback 将 key 对应到新的下标。GlobalKey 的跨父级迁移要求同帧移除和插入，不能无条件保留任意已移除节点。

19. 滑出屏幕后，状态怎么留住

核心回答

懒构建的滚动组件通常只维护当前显示及缓存范围内的子项，离开范围后节点可能被移除，State 随之销毁，但滑出屏幕不代表立即销毁。需要保留现有节点与状态时，可以使用 AutomaticKeepAliveClientMixin，通过 wantKeepAlive 表达保活需求，在 build 中调用 super.build(context)，并由上层 AutomaticKeepAlive 处理请求；需求变化后调用 updateKeepAlive()。保活会增加内存占用，不代表子项持续布局和绘制。只需要恢复滚动位置时，可使用 PageStorageKey 配合滚动偏移保存机制，它不等同于保留整个 State，也不是磁盘持久化。

进一步理解

子项滑出屏幕，为什么有时还在，有时又重建？

列表不只保留屏幕正好可见的部分，还可能缓存附近子项。离开屏幕但仍在缓存范围内，State 可以继续存在；离开维护范围、又未保活时，节点可能被移除。再滑回来就创建新 State，所以不能用“是否可见”简单判断是否销毁。

混入 KeepAlive 后，为什么仍可能没保住状态？

mixin 只是发出请求，还需要祖先 AutomaticKeepAlive 接收，并由列表布局按约定保留。wantKeepAlive 表达需求，build 中应调用 super.build 并忽略返回值，需求改变后调用 updateKeepAlive。如果关闭默认保活包装或缺少相应祖先，仅写 mixin 不足以生效。

只想记住滚动位置，也要保活全部子项吗？

不必。PageStorage 可在同一存储区域内保存滚动偏移，重新创建滚动组件时再恢复；它不保存每个输入框等任意 State。保活保留现有节点，滚动恢复保留位置记录，两者成本与效果不同。大量子项全部保活会增加内存，应按实际需求选择。

20. 热重载和热重启

核心回答

热重载将修改后的 Dart 代码更新到正在运行的应用中，并请求现有组件重建，尽量保留原有状态；它不会重新执行已经运行过的 main、已有 State 的 initState 或已完成的全局与静态字段初始化。热重启会重新启动 Dart 应用，重新执行入口并创建状态，原有 Dart 状态被清除，但不等同于重新构建和安装整个原生工程。热重载用于支持该能力的 debug 开发环境，profile 和 release 不提供热重载。部分类型结构变化需要热重启，原生代码和插件集成配置变化通常需要停止应用后重新构建。

进一步理解

改了 build 立刻生效，改 initState 为什么却没变？

热重载更新方法代码后，会让现有节点重建，因此新的 build 逻辑能运行。原 State 仍在，已经执行过的 initState 不会再调用，初始化出的字段也可能保留旧值。这不是新代码没加载，而是没有重新走创建状态的过程。

热重启与重新安装，清掉的是同一种状态吗？

热重启重新启动 Dart 应用，main 与 State 初始化重新执行，Dart 内存状态被清除。它不等于卸载应用，也不一定清除磁盘或系统保存的数据，更不负责重新编译所有原生修改。修改插件原生实现或集成配置时，通常要停止应用并重新构建。

热重载时很流畅，可以说明发布性能吗？

不能。热重载属于 debug 开发工具，开发模式保留额外检查，编译与优化方式也不同。性能要在适合测量的模式及目标设备上观察。手机桌面的 JIT 与 Web 的开发编译路径不同，也不能把一端的实现套到另一端。

21. InheritedWidget 是干什么的

核心回答

InheritedWidget 用于沿组件树向后代提供共享数据，避免逐层传递参数。后代通过依赖式查询找到最近的指定类型祖先，并登记当前 Element 的依赖关系；新的配置替换旧配置时，updateShouldNotify 决定是否通知已登记的依赖者重建。只读取、不登记依赖，可以取得当前值，但不会因后续数据变化自动收到依赖通知。通知只针对相关依赖者，不等同于无条件重建整个子树；普通父级配置更新仍可能另外触发子节点构建。需要细分数据依赖时可以使用 InheritedModel，需要连接可监听对象时可以使用 InheritedNotifier。

进一步理解

后代为什么能跳过多层构造参数直接读取数据？

数据提供者放在祖先位置，后代通过 context 向上查找最近的相应 InheritedWidget。中间组件不需要把数据逐层原样传递。找到数据只是第一步，还要看读取方法是否登记依赖，决定后来更新时能否通知到这个后代。

updateShouldNotify 返回 false，数据就没换吗？

新 Widget 配置仍然替换了旧配置，false 只是表示不发出这一次依赖变化通知。已经登记依赖的节点不会因此被标记，但仍可能因父级新配置等其他原因重建。所以“依赖通知”和“普通父子更新”必须分别看。

共享对象改了内部字段，为什么界面没收到通知？

InheritedWidget 不会自动监听任意对象内部变化。它通常在新旧配置更新时决定是否通知；若想响应 ChangeNotifier 等对象的通知，可以使用 InheritedNotifier 或相应封装。只需要模型某一部分时，InheritedModel 的 aspect 可以进一步区分依赖。

22. 状态管理怎么选

核心回答

选择状态管理方式，首先要明确状态由谁持有、怎样修改和通知、哪些界面订阅，以及何时释放。局部状态可以使用 setState 或 ValueNotifier；跨组件共享数据可以通过 InheritedWidget 或状态管理库组织。Provider 基于树提供数据并管理依赖，Riverpod 通过容器组织状态和依赖，Cubit 通过方法产生状态，Bloc 通过事件处理产生状态。选择时应结合状态作用域、业务复杂度、测试需求和团队维护成本，而不是只比较库名。性能主要取决于状态与订阅的位置，以及更新范围；只订阅所需数据可以减少无关通知，但换库本身不会自动解决大范围重建。

进一步理解

换一个状态管理库，为什么页面还是大范围重建？

如果状态和订阅仍放在很高的位置，一次变化仍可能重建一大片子树。库提供的是持有、通知和订阅方式，不会自动知道哪块界面真正依赖哪个字段。先把状态与订阅放到合适位置，再考虑用 select 等机制缩小依赖。

read、watch 和 select，分别改变了什么？

read 取得当前数据，不建立变化订阅；watch 让界面跟随被订阅的数据更新；select 只选择其中一部分，比较结果变化时才触发相应更新。若选中的还是原地修改的可变对象，新旧比较可能看不出变化；父级普通重建也不会被订阅过滤自动阻止。

局部计数与跨页面订单状态，为什么不必使用同样方案？

局部计数由单个组件持有，用 setState 或 ValueNotifier 就容易管理。跨页面订单还涉及请求、缓存、错误和测试，需要明确数据所有者及释放时机，可以用团队熟悉的共享状态方案组织。先按作用域和逻辑复杂度选择，再比较具体库的维护成本。

23. Navigator 和 MaterialApp 做了什么

核心回答

Navigator 管理由 Route 组成的导航栈，负责进入、返回、替换和转场；MaterialApp 配置主题、本地化及导航入口，根据构造方式接入 Navigator 或 Router。push 加入路由并返回等待其结果的 Future，pop 弹出路由并可传回结果，嵌套导航时查询到的是当前位置对应的导航器。旧路由被覆盖不等于销毁，是否保留取决于路由策略和节点生命周期。直接调用 push/pop 属于命令式导航，需要让地址、深链和页面配置保持一致时，可以使用 Router 体系组织。返回控制应声明是否允许弹出并处理返回结果，导航副作用不应放在可能重复执行的 build 中。

进一步理解

打开新页面，旧页面为什么没 dispose？

push 把新路由放到导航栈上，旧路由可能只是被盖住。普通 MaterialPageRoute 默认保留状态，返回时继续使用旧节点。是否销毁取决于路由保留策略、转场和整个 Navigator 是否还在，不能仅凭“看不见了”判断。

从第二页返回一个结果，为什么可以 await push？

push 返回的 Future 表示这条路由结束后的结果。第二页通过 pop 传回数据，第一页面向这个 Future 等待即可。调用时要区分嵌套导航器，Navigator.of 从当前位置向上找到最近的导航器，不一定是应用最外层。

什么时候地址与路由配置需要一起管理？

简单按钮跳转可直接 push/pop；如果浏览器地址、外部深链和应用页面必须互相对应，就需要把路径解析成页面配置，再同步到导航状态。Router 提供这些连接机制，go_router 等库进行封装。MaterialApp 的普通构造与 router 构造也不同，不能假设所有形式都自动带同样的 Navigator。

24. 动画怎么做，vsync 是什么

核心回答

Flutter 动画通过随时间变化的值驱动界面属性更新。隐式动画由组件内部管理过程，调用方提供目标值和时长；显式动画由代码持有 AnimationController，控制开始、停止、反向和重复。Controller 提供进度，Tween 映射取值范围，曲线调整进度变化方式。vsync 接收 TickerProvider，由它提供与帧调度配合的 Ticker，避免使用独立定时器盲目驱动动画。Ticker 可以受 TickerMode 控制而静默，但静默不等于暂停时间推进。Controller 应随 State 销毁而释放，动画监听和重建应限制在实际变化的区域。

进一步理解

只改目标宽度，为什么能自动过渡？

隐式动画组件内部持有并管理动画过程，接到新目标后逐帧计算中间值。调用方不用手动推进，但控制粒度有限。要跟随手势、反向播放或编排多个阶段，则通常需要显式 Controller 自己控制进度。

Controller、Tween 和曲线，分别算什么？

Controller 推进时间和进度；Tween 把进度转换成宽度、颜色等目标范围；曲线改变进度随时间的分布。把三者分开，就能让同一个进度驱动不同属性，而不是每个属性各写一个 Timer。AnimatedBuilder 再把变化限制在依赖这些值的区域。

vsync 为什么不是简单传一个 60 或 120？

它接收 TickerProvider，由后者创建与帧调度配合的 Ticker。TickerMode 可以让 Ticker 暂时不回调，但时间仍在流逝，恢复后进度可能追上当前时间。需要真正暂停时应管理 Controller，而不是仅依赖透明或不可见；不再使用时还要 dispose。

25. 布局时，约束和尺寸怎么传

核心回答

Flutter 盒布局遵循约束向下传递、尺寸向上返回、父节点决定位置的规则。父节点通过 BoxConstraints 给出允许的宽高范围，子节点在范围内确定尺寸；紧约束表示尺寸已确定，无界约束表示没有有限上限，不是要求尺寸无限大。Flex 根据可用主轴空间分配尺寸，Expanded 要占满分配空间，Flexible 默认允许小于分配空间；主轴无界时无法直接计算这类剩余空间分配。滚动视口通常需要滚动方向上的有限尺寸，约束冲突应从父子布局关系解决。shrinkWrap 可以按内容确定滚动尺寸，但可能增加测量成本，不能作为无成本的通用修复。

进一步理解

给子组件写 width，为什么不一定得到这个宽度？

width 表达了尺寸意图，但最终还必须满足父级传来的约束。若父级要求固定宽度，子组件不能任意选择更小或更大；若给出范围，子组件才能在范围内选择。父级再决定它放在哪里，因此约束、尺寸和位置是三个不同环节。

Column 里放 ListView，为什么常报高度无界？

纵向列表需要知道视口高度，Column 的普通非弹性布局却可能不给它有限高度。若外层 Column 自己高度有限，可以用 Expanded 为列表分配剩余高度。若外层本来就纵向无界，再加 Expanded 也无法算出“剩多少”，应先调整整个滚动与约束关系。

shrinkWrap 为什么不是所有布局报错的默认答案？

它让滚动组件根据内容决定自身尺寸，可能为测量而布局更多子项，滚动中也可能重复计算。少量内容可以合适，但长列表容易增加开销。要先判断是视口缺少有限尺寸，还是确实需要内容决定尺寸，不能只以消除报错为目标。

26. Widget、Element、RenderObject、Layer 和一帧渲染

核心回答

Widget 是不可变配置，Element 是持有当前配置并维护节点关系的对象，有状态节点还通过 Element 保存 State；RenderObject 负责布局、记录绘图指令和命中测试，Layer 则组织需要合成的绘制内容。框架在匹配范围内根据类型和 key 决定复用旧节点还是创建新节点，Widget 与 RenderObject 并非一一对应。完整更新通常经过构建、布局、绘制，再由引擎完成合成和光栅化，实际只处理需要更新的阶段，并可复用未变化的结果。因此重新执行 build 不等于重新创建所有节点，也不等于重绘所有像素；独立重绘边界用于隔离绘制变化，但也有图层和内存成本。

进一步理解

Widget 每次都新建，为什么 State 还能保留？

Widget 是当前配置，Element 是持续存在的树节点。父级产生新配置后，框架在匹配范围内比较类型和 key，匹配则更新旧 Element；有状态节点继续使用原 State。因此新 Widget 不等于新 State，也不等于重新创建 RenderObject。

build、paint 与 raster，为什么不是同一步？

build 生成配置，layout 确定尺寸和位置，paint 记录如何绘制，引擎再把绘制内容光栅化为像素。某帧只改变颜色，可能只需重绘而不重做布局；没有变化的部分还能复用。定位卡顿先分清时间花在哪个阶段，才知道该缩小重建还是减少绘制成本。

每个 Widget 都有一个 Layer 吗？

不是。许多 Widget 只负责组合，不创建 RenderObject；许多 RenderObject 又在现有图层中绘制，并不各有独立层。需要重绘隔离或特定合成效果时才可能产生不同层结构。Layer 用来组织合成，也不等于必然分配一张离屏位图。

27. 线程模型，以及高刷新率上怎么看掉帧

核心回答

Flutter 引擎传统上按 Platform、UI、Raster、IO 划分任务职责，分别处理平台交互、Dart 界面工作、光栅化及资源相关工作，但不保证对应四条独立系统线程，部分平台与版本会合并 UI 和 Platform 的执行线程。主 isolate 负责构建、布局和记录绘制指令，Raster 与 GPU 配合生成像素，不能把 Raster 线程直接等同于显卡。屏幕刷新率越高，持续供帧的时间预算越短，60Hz 约为 16.7 毫秒，120Hz 约为 8.3 毫秒。排查掉帧应在真机 profile 模式下观察 DevTools 帧时间，区分界面阶段和光栅阶段瓶颈，再分析同步计算、布局、绘制及资源处理，不能用 debug 帧时间代表发布性能。

进一步理解

UI 帧慢与 Raster 帧慢，优化方向为什么不同？

UI 路径主要包含 Dart 构建、布局和绘图指令记录，复杂计算或频繁测量可能拖慢它。Raster 路径把内容转成像素，复杂效果、大量绘制等可能拖慢它。先看 DevTools 中哪个阶段耗时，再找具体调用或绘制负担，不能一看到掉帧就只减少 build。

60Hz 能跟上，为什么 120Hz 仍可能掉帧？

刷新间隔从约 16.7 毫秒缩短到约 8.3 毫秒，同样的工作在高刷新率下有更紧的时间要求。帧管线还受设备和调度影响，不能把一个固定耗时当成所有设备都流畅。应在实际目标刷新率和设备上持续测量。

四条任务职责与后台 isolate，为什么不能混为一谈？

UI、Raster 等描述引擎任务安排，后台 isolate 则是独立 Dart 执行环境，另有生命周期与消息成本。某些平台把 UI 与 Platform 合到同一线程，主 isolate 的同步重活也可能影响平台响应。需要根据实际平台版本理解线程映射，不是按“四个名称”推断四条固定线程。

28. 什么时候自定义布局

核心回答

自定义布局应优先使用现有组件组合，只有现有规则无法满足或测量证明需要时，才下沉到更底层。只改变绘制内容可以使用 CustomPaint；需要安排子节点约束和位置，可以使用自定义布局代理；需要改变更底层的测量与布局协议时，再实现 RenderObjectWidget 和 RenderObject。自定义 RenderBox 必须在父级约束内确定自身尺寸，并按协议布局和定位子节点；布局与绘制应分开，不能在绘制阶段修改布局结果。配置变化后应根据影响请求重新布局或重绘，同时正确处理命中测试、辅助功能语义及父布局数据。独立重绘边界需要结合实际重绘成本决定，而不是默认添加。

进一步理解

只想画一张特殊卡片，需要自己写 RenderObject 吗？

如果尺寸和子节点布局都能由现有组件确定，只是背景、曲线或装饰特殊，用 CustomPaint 就能画。自行实现 RenderObject 意味着还要负责约束、尺寸、命中和语义等协议，成本高得多。先确认变化的是绘制内容还是布局规则。

什么时候布局代理还不够？

CustomSingleChildLayout 和 CustomMultiChildLayout 可以按规则给子节点约束并安排位置，但并非支持所有尺寸依赖关系。例如 MultiChildLayout 自身尺寸不能依赖孩子布局后的结果。确需更特殊的测量协议时，才考虑自定义 RenderBox。

画面看起来正确，为什么点击或读屏仍可能有问题？

绘制只决定像素，命中测试决定哪里能收到指针，语义描述决定辅助功能知道什么。自定义渲染不能只把图画对，还要维护这些协议。配置影响尺寸时请求 layout，只影响外观时请求 paint，不能在 paint 中偷偷改变布局结果。

易错提醒：绘制正确不代表命中测试和辅助功能语义也正确。

进阶补充：Flow 与父布局数据

Flow 主要通过绘制变换安排孩子，不等同于任意改变布局测量。parentData 是父布局保存在孩子上的布局参数，应由配套父布局解释。semantics 提供读屏需要的名称和行为。isRepaintBoundary 可以隔离重绘，但增加层及资源开销，必须结合测量选择。

29. 一次点击为什么只有一个组件响应

核心回答

一次点击涉及命中测试和手势识别两个过程。命中测试确定哪些节点能收到指针事件，手势识别器再根据按下、移动和抬起判断具体动作；多个识别器对同一指针存在竞争时，通过手势竞技场决定接受或拒绝。普通父子点击识别器竞争时，通常内层胜出并触发最终点击回调，但其他识别器也可能收到原始事件及部分提前回调。拖动识别器胜出时，点击可能被取消，不能把收到事件等同于最终点击成功。Listener 监听原始指针，不参与手势竞技场；HitTestBehavior 影响命中范围及后方命中，不直接改变父子点击竞争规则。

进一步理解

父子都写 onTap，为什么常常只有子组件触发？

指针先命中一条路径，父子识别器都可能收到事件，再进入手势竞技场。普通点击竞争中，内层识别器通常先加入并胜出，父级最终 onTap 不执行。不是父级完全没收到指针，而是最终手势归属不同。

手指一滑，按钮点击为什么取消？

点击与拖动识别器都在观察同一串事件。移动达到拖动判断条件后，拖动可能接受该手势，点击识别器则取消。提前发生的 onTapDown 不等于最终 onTap 一定发生，还要正确处理取消回调。

把 behavior 改成 opaque，为什么父级仍抢不到点击？

HitTestBehavior 改变自身区域及后方目标能否命中，不会改写父子点击识别器的竞技场规则。若只想观察手指按下、移动而不争夺最终点击，可以使用 Listener 获取原始事件。只有确实要识别手势时，才参与对应竞争。

30. Flutter 如何和 Android / iOS 通信

核心回答

Flutter 主要通过 Platform Channel 在 Dart 与平台实现之间交换消息。MethodChannel 用于一次方法调用及结果返回，EventChannel 用于持续事件流，BasicMessageChannel 用于约定格式的双向消息；双方通过 codec 编解码，不直接共享同一个对象。通道是异步通信机制，但不会自动把原生处理逻辑移到后台，仍需遵守平台线程要求。Pigeon 可以根据接口定义生成两端类型化通信代码，底层仍使用平台通道。调用兼容 C 接口的原生函数可以使用 FFI，但需要正确管理类型、调用约定和内存生命周期；嵌入原生界面则使用 PlatformView，不能与数据通信混为一谈。

进一步理解

为什么 Dart 不能直接把任意对象传给 Swift？

两端处于不同语言与对象体系，平台通道需要把支持的数据编码成字节，再由对方还原。标准 codec 能处理字符串、数字、列表等，业务对象要先变成兼容结构或约定自定义编码。两边的通道名、方法名、参数和结果类型必须一致。

调用是异步的，原生 handler 为什么还会卡主线程？

异步描述调用结果如何返回，不保证原生工作在哪条线程执行。默认 handler 通常在平台主线程，耗时操作要按平台规则使用后台任务队列或自行调度；访问 UI 时仍须满足主线程要求。Dart 侧在等待，不代表原生侧自动变轻。

Pigeon、FFI 与 PlatformView，是三种同样的通道吗？

Pigeon 根据接口定义生成两端通信代码，减少手写类型约定，底层仍是平台通道。FFI 按兼容 C 接口直接调用原生函数，需要管理内存与调用约定。PlatformView 则把原生视图嵌进界面，涉及视图生命周期和合成，不只是传数据。

import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

void main() => runApp(const MaterialApp(home: SettingsPage()));
class SettingsPage extends StatefulWidget {
  const SettingsPage({super.key});
  @override
  State<SettingsPage> createState() => _SettingsState();
}
class _SettingsState extends State<SettingsPage> {
  static const channel = MethodChannel('app/settings');
  String text = '点击读取';
  Future<void> readName() async {
    String next;
    try {
      next = await channel.invokeMethod<String>('getName') ?? '未设置';
    } on MissingPluginException {
      next = '尚未实现原生 getName';
    } on PlatformException catch (e) {
      next = '平台错误：${e.code}';
    }
    if (!mounted) return;
    setState(() { text = next; });
  }
  @override
  Widget build(BuildContext context) => Scaffold(body: Center(
    child: TextButton(onPressed: readName, child: Text(text)),
  ));
}

易错提醒：通道异步不代表原生 handler 自动在后台，Dart 调用端也不等于完整双端实现。

进阶补充：后台 isolate、TaskQueue 与示例范围

完成注册的后台 isolate 可以请求平台能力并接收回复，但不能任意接收平台主动推送。原生 TaskQueue 可以改变 handler 的执行队列，访问原生 UI 时仍需回到合适线程。本题代码只提供 Dart 调用端，未注册 app/settings 的 getName 原生实现时会提示尚未实现；真实通信还要在 Android/iOS 注册同名通道并返回兼容结果。FFI 内存非法访问可能导致进程崩溃，不能依赖 Dart catch 恢复。

31. 包和插件有什么区别

核心回答

package 是代码、资源和依赖的发布复用单位，可以包含 Dart 逻辑、Flutter 组件及资源。plugin 是按 Flutter 平台集成约定提供平台实现和注册信息的一类 package，使应用能够通过 Dart 接口使用对应能力。插件内部可以采用 Platform Channel 或 FFI，具体取决于实现；应用中存在通道代码不代表已经封装为可复用插件。联邦插件把面向应用的 API、平台接口和各平台实现分离，通常分别发布，方便各平台独立维护。应用一般依赖面向应用的包，由其接入相应平台实现，选择时还需确认目标平台支持和维护情况。

进一步理解

项目里写了 MethodChannel，为什么不等于做成插件？

通道只是通信手段，可能仅存在当前应用中。插件还要提供可依赖的 Dart API、各平台实现和工具链识别的注册信息，其他应用才能按约定集成。包是发布单位，插件是其中具有平台集成能力的一类。

插件为什么还要拆成接口包和多个平台包？

多平台实现由不同维护者负责时，把面向应用的 API、平台契约及 Android/iOS 等实现分离，可以独立演进和测试。应用通常依赖入口包，不直接依赖接口包来获得功能。是否自动带入某个平台实现，仍应检查插件配置。

插件一定使用 MethodChannel 吗？

不一定。需要调用兼容 C 接口库时可以采用 FFI，也可以结合不同手段。判断平台支持和成本要看实际实现及注册方式，不能只根据“plugin”这个名称推断通信路径。

易错提醒：plugin 是一类 package，通道只是实现手段。

进阶补充：联邦插件的角色

面向应用的包提供业务使用的 API，platform_interface 包约定各平台必须实现的接口，android/ios 等实现包分别接入系统。哪些实现被默认接入，需要看 pubspec 的插件声明与工具链注册约定，不能把平台接口包当成已经提供所有平台能力的实现包。

官方核对：联邦插件的三种角色。

32. 混合栈怎么组织

核心回答

混合栈同时涉及原生容器栈和 Flutter 路由栈，需要统一处理页面进入、返回、可见性、输入及生命周期。FlutterEngine 负责运行 Dart 内容，原生容器负责展示，容器不可见不代表引擎中的动画、定时器和订阅已经停止。复用已启动引擎可以减少启动成本，但根 isolate、导航栈和全局状态通常延续，需要明确重置与宿主绑定规则。多引擎拥有各自的根 isolate 和导航状态，隔离更清楚，但会增加资源和管理成本；FlutterEngineGroup 可以共享部分底层资源，并不等于多个页面共用同一个引擎。方案选择取决于原生导航需求、状态隔离和内存预算，不能只关注页面能否打开。

进一步理解

原生页面盖住 Flutter，为什么定时器可能还在运行？

页面容器不可见，不代表 FlutterEngine 已停止。引擎内的 Dart 状态、Timer 和订阅可能继续运行，动画与绘制也各有控制机制。两边应同步可见性与生命周期，并明确哪些工作暂停、哪些保留，不能只处理一次 push/pop。

复用预热引擎，为什么会看到上一次的页面状态？

复用的是仍在运行的引擎，根 isolate、Navigator 栈和全局数据通常还在。启动变快的同时，旧状态也延续了。需要在业务进入和退出边界决定复用、重置或隔离，不能把“新容器”当成“新 Dart 应用”。

EngineGroup 共享资源，为什么不是共享同一份 State？

EngineGroup 可以为多个引擎共享部分底层资源，但每个引擎仍有自己的根 isolate 和路由状态。它与复用同一个引擎不同。原生插件单例等进程资源还可能共用，所以多引擎也不代表所有平台状态完全隔离。

33. 构建模式和多端产物

核心回答

Flutter 的 debug 模式面向开发调试，保留断言和额外检查，并在支持的平台提供热重载；profile 面向性能测量，保留分析能力；release 面向发布，启用发布优化并关闭调试检查。移动端和桌面的 debug 通常使用 JIT，profile 和 release 使用 AOT，Web 则使用自己的编译路径。发布优化中的 tree shaking 删除从有效入口不可达的 Dart 代码，但混淆需要显式开启，release 也不代表签名已经满足分发要求。Android 常见产物为 APK 或 AAB，iOS 通过归档导出分发包，桌面生成各平台应用，Web 生成包含 JavaScript 或 Wasm 等文件的静态资源。性能和体积应在对应的目标平台及构建模式下评估。

进一步理解

为什么性能测试应使用 profile，而不是直接看 debug？

debug 为调试保留了检查和开发开销，移动桌面端还采用不同于发布的编译方式。profile 更接近发布执行环境，又保留分析工具，便于定位瓶颈。最终交付仍要验证真机 release，不能用 debug 的帧时间或包体积推断结果。

release 已经优化，为什么还要单独配置混淆？

tree shaking 删除不可达代码，混淆改变符号名称，两者作用不同。release 不会自动开启 Dart 混淆，启用后还要保存符号信息用于还原堆栈。签名又属于平台分发配置，能构建 release 不代表所有分发证书都正确。

Web release 为什么不能说成手机那种机器码 AOT？

移动桌面产物可提前编译为目标机器码，Web 则根据构建路径输出 JavaScript 或 Wasm 及资源，运行与包装方式不同。相同的“release”主要表达发布用途，不意味着不同目标共享同一种二进制产物。

tree shaking 根据有效入口的可达性移除代码，原生回调等额外入口需要按规则保留，不能只按源码里是否显式调用判断。启用 --obfuscate 时通常配合 --split-debug-info 并保存符号文件，用于还原错误堆栈。不同平台的签名和分发要求独立于 Dart 混淆，构建完成不代表全部交付配置已验证。

34. 怎样减少重建、长列表卡顿和大图开销

核心回答

Flutter 性能优化应先在真机 profile 模式下定位瓶颈，再分别处理构建、布局和光栅化开销。减少无关重建需要缩小状态与订阅范围，并复用不变的 Widget；长列表应按需创建子项，统一尺寸时可提供尺寸信息，避免不必要的嵌套测量和大量保活。需要维持重排身份时使用稳定的 Key，并满足懒列表的索引映射要求。绘制瓶颈可以按测量结果设置重绘边界、减少复杂效果，并按显示所需的物理像素尺寸解码图片，控制预加载和缓存规模。CPU 密集计算可在适用平台交给后台 isolate，Controller、Timer 和订阅则应及时释放，避免无效工作。优化效果应由帧时间、内存和实际交互表现验证。

进一步理解

为什么先减少 build，卡顿可能一点没改善？

如果瓶颈是光栅化或大图解码，少一次 build 未必减少那些耗时。先在 profile 帧图中区分构建、布局和光栅阶段，再查看具体工作。优化要针对实际瓶颈，而不是把 const 或状态管理库当成统一答案。

长列表用了 builder，为什么滚动还可能慢？

builder 延迟创建 Widget，但不能消除复杂布局、重绘和图片成本。高度统一时可以提供 itemExtent 或 prototypeItem，减少位置计算；大量 shrinkWrap、保活和复杂嵌套仍可能增加工作。重排时还要给子项稳定 key，并按列表需要提供索引映射。

图片只显示一小块，为什么仍占很多内存？

文件大小与解码后的像素内存不是同一件事。一张大图即使缩小显示，若按原始像素解码，仍可能占用大量内存。应按逻辑显示尺寸乘 devicePixelRatio 确定目标物理像素，再考虑 cacheWidth/cacheHeight，并控制预加载数量。解码尺寸也不会替代网络下载尺寸优化，Web 网络图片还有平台限制。
