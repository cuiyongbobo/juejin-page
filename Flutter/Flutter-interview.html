一、Dart

1. var、Object、dynamic，以及空安全

静态类型是编译器根据声明和分析所知道的类型，运行时类型是程序执行时对象实际所属的类型。两者可以不同：Object 变量也能保存一个 int。空安全让类型明确区分“允许 null”和“不允许 null”，null 表示缺少值。

口述版

  • var 让编译器推断变量的静态类型，也就是编译时用来检查赋值和成员访问的类型。推断后类型不会随赋值改变，但变量的值可以改变。
  • Object 可以接收任意非 null 的 Dart 对象。使用变量时，只能直接访问静态类型允许的成员；要访问具体类型的成员，先做类型检查或转换。Object? 还允许 null。
  • dynamic 允许跳过大部分静态成员检查，改在运行时查找成员。成员不存在或值不适合这次操作时，运行时会抛错。
  • T? 允许 null。! 在当前表达式中把值当作非空使用，实际为 null 就抛错，不改变变量的声明类型。
  • ?. 在左侧为 null 时不访问后面的成员，并返回 null；?? 在左侧为 null 时取右侧值；??= 只在左侧为 null 时赋值；...? 展开集合，集合为 null 时不添加元素。
  • late 把部分初始化检查推迟到运行时。没有初始化表达式时，读取前必须赋值；有初始化表达式时，第一次读取才执行它。late final 只能赋值一次。
  • 类型提升是编译器根据判空、类型判断等条件，在后续有效范围内按更具体的类型检查变量。能否提升取决于编译器能否确认变量不会在使用前变成其他类型或 null。

解析

这道题要区分变量的声明类型、对象的实际类型和 null。编译器根据静态类型检查代码，不会因为变量后来保存了另一个对象，就自动改变声明类型。类型允许重新赋值，与变量能否重新赋值是两个独立问题。

String? readName() => null;

void main() {
  var x = 1;
  x = 2;
  // x = 'two'; // 错误示例：取消注释会产生编译错误
  Object obj = x;
  print(obj.toString()); // 2
  dynamic raw = x;
  try {
    raw.missing(); // 错误示例：能编译，运行时抛 NoSuchMethodError
  } on NoSuchMethodError {
    print('没有这个方法');
  }
  String? name = readName();
  print(name ?? '访客'); // 访客
  try {
    print(name!); // 错误示例：这里为 null，运行时抛错，可捕获
  } catch (_) {
    print('空值断言失败');
  }
}

?.、??、??=、...? 是空安全里的读写简写：?. 在左侧为 null 时跳过后续成员访问并返回 null；?? 在左侧为 null 时使用右侧默认值；??= 只在左侧为 null 时赋值；...? 将非 null 集合的元素加入当前集合，集合为 null 时不添加。它们不修改变量声明的类型，也不是强制类型转换；表达式的类型和局部变量的提升要由流分析决定。把 ?? 和 || 混用是常见错误：|| 只看真假，?? 只看是不是 null。

局部变量通过 if (value != null) 判空后，只要编译器能确认使用前不会再变成 null，就能在有效范围内按非空类型使用，一般不必再写 !。这是类型系统的流分析，不是运行时把对象变了。如果变量可能被别的执行路径写入 null，编译器可能拒绝提升；具体还取决于写入和闭包调用的位置。对字段，Dart 3.2 起仅满足条件的私有 final、非外部字段支持提升；公开字段、可变字段和普通 getter 不能直接套用此规则。拿不准时先保存到局部 final 变量，再判空。

late 允许延迟初始化非空变量，但需要调用方保证读取前已赋值，或提供首次读取时才执行的初始化表达式。没有初始化表达式时，读在写之前会抛 LateInitializationError。初始化表达式留到第一次读取才执行。只能赋一次再写成 late final。分析器警告是开发工具，不是另一套语言规则。dynamic 也不会让程序跑得更快。

错误要分开看：编译错误会阻止生成可运行程序；!、缺失成员调用、LateInitializationError 是可用 try/catch 捕获的运行时错误。late final 的重复赋值有时会被静态检查发现，有时触发运行时检查。错误类名带 Error 并不等于进程一定崩溃：未处理的 Dart 错误可能终止 isolate，Flutter 框架在构建、布局等回调中还会捕获并报告部分错误；原生非法内存访问等进程级崩溃通常不能靠 Dart 的 catch 恢复。

官方核对：类型提升的条件与失败原因。

基础语法：变量、late 与常量。

2. const 和 final 的区别

口述版

  • final 变量只能赋值一次，值可以在运行时确定。它限制变量重新赋值，不限制所引用的可变对象修改内容。
  • const 声明编译期常量。常量对象及其引用的常量内容都不可修改；同一个 isolate 中，相同类型、相同常量内容的对象会复用同一实例，这叫常量规范化。
  • 实例字段不能声明为 const，类级常量用 static const。const 生成构造要求实例字段都为 final，并满足父构造和初始化列表的常量要求。
  • 常量构造只有按常量方式调用时才要求常量实参并复用常量实例。处于 const 上下文时可以省略调用处的 const；不处于 const 上下文的普通生成构造调用仍创建新对象。
  • Flutter 更新子节点时，相同 Widget 实例可以跳过这次父级引发的配置更新。const 有助于复用实例，但子节点仍可因自身状态或依赖变化而重建。

解析

final 限制的是变量重新赋值，对象本身是否可变取决于对象类型。下面的 final list 不能再指向另一个列表，但可以对原列表 add。const 列表则连元素也不能修改。相同常量的规范化，是指运行时复用同一个常量实例。

class Box {
  final int n;
  const Box(this.n);
}

void main() {
  final list = <int>[];
  list.add(1);
  print(list); // [1]
  const a = [1];
  const b = [1];
  print(identical(a, b)); // true：相同常量被规范化
  try {
    a.add(2); // 错误示例：能编译，运行时抛 UnsupportedError
  } on UnsupportedError {
    print('常量列表不能修改');
  }
  final n = int.parse('1'); // 运行时值
  final box = Box(n); // const 构造也能普通调用
  const box2 = Box(1);
  const boxes = [Box(1)]; // 隐式 const 上下文
  print(identical(box, box2)); // false
  print(identical(box2, boxes.single)); // true
}

const 生成构造不能有普通函数体，实例字段（含继承字段）必须都是 final，父构造和初始化列表也要满足常量构造要求。用它普通地构造对象时可以传运行时值；只有常量调用才要求实参是编译期常量。不写 const 关键字，只在调用处不处于 const 上下文时才是新实例。带函数体的工厂不能是编译期常量构造，那是另一题。跨 isolate 发消息时对象通常会被拷贝，不能把 const 身份当成进程里全局唯一。

Flutter 里父组件重新 build 时，子 Widget 若仍是同一个对象，框架可跳过这次由父级引发的配置更新；它仍可因自己的 State 或依赖变化而重建。这是 Element.updateChild 的行为，不是 const 有魔法跳过 build。参数不是编译期常量时不能常量调用；也可把不变的 Widget 保存后重复传入，利用相同实例跳过配置更新。

3. Dart 是值传递还是引用传递

口述版

  • Dart 的参数按值传递。变量保存的是对象引用，传参时复制这份引用，不复制整个对象；形参是函数自己的局部变量。
  • 形参与实参最初指向同一个对象。通过形参修改可变对象的内容，调用方也能看到。
  • 给形参重新赋值，只改变形参的指向，不改变调用方变量。需要调用方改用新对象时，应返回新对象，再由调用方接收。

解析

引用是用于访问对象的值，不必把它等同于语言可直接操作的内存地址。传参后，调用方变量和形参是两个变量，但保存了指向同一对象的引用。下面的 grow 修改这个对象，reset 只是给形参换了引用，所以两次调用的结果不同。

void grow(List<int> list) { list.add(1); }
void reset(List<int> list) { list = []; }

void main() {
  final values = <int>[];
  grow(values);
  print(values); // [1]：同一个可变对象被修改
  reset(values);
  print(values); // [1]：给形参重新赋值不影响调用方变量
}

这是语言保证：没有 C++ 那种「外面那个变量的别名」。编译器可能内联、可能省略一些拷贝，但不会把「给参数重新赋值」变成修改调用方的变量。想避免被外面改到，传不可变对象，或者在边界上拷一份。

4. extends、implements 和 mixin

口述版

  • extends 是单继承：子类获得父类可继承的实现，同时也是父类的子类型。创建子类实例时要调用父类构造函数。
  • implements 只建立接口约束，不带来对方的方法实现。具体类必须自己提供或继承接口要求的实例成员；一个类可以实现多个接口，抽象类可以暂不提供全部实现。
  • mixin 用 with 把字段和方法复用到类中。on 指定混入前必须满足的父类型条件，使 mixin 能依赖该类型的成员。
  • 多个 mixin 定义同名方法时，with 中靠后的实现优先。它调用 super 才会继续查找前面的实现，不调用就不会自动执行前面的同名方法。
  • mixin 不能声明构造函数；mixin class 可以同时当类和 mixin，不能声明生成构造，但可以声明 factory。
  • Dart 3 的类修饰符限制库外的继承和实现：interface 允许实现、禁止继承；base 允许继承、禁止实现；final 两者都禁止；sealed 把直接子类型限制在同一个库中。

解析

子类型关系表示：需要父类型的地方可以接受子类型对象。extends 同时建立这种关系并继承实现；implements 只承诺提供接口成员，不复制接口类的方法体；with 则把 mixin 中的实现加入当前类的方法查找链。

class Animal { void breathe() => print('呼吸'); }
abstract interface class Runnable { void run(); }
class Dog extends Animal implements Runnable {
  @override
  void run() => print('跑');
}
mixin Walk on Animal { void go() => breathe(); }
class Cat extends Animal with Walk {}

void main() {
  Dog().run(); // 跑
  Cat().go(); // 呼吸：复用了 Animal 的方法
}

要区分 mixin M 与 mixin class M：Dart 3.11.4 中前者不能声明任何构造函数，后者不能声明生成构造但可有 factory。生成构造负责创建和初始化新实例；factory 负责返回兼容类型的对象。on 限制宿主，mixin 里面可以调用这个宿主类型的成员。同名方法由线性化决定谁先被调用：靠后的盖住靠前的。靠后的方法调用 super 时，前面那一份会接着执行。这不是编译器随便挑一个更快的版本，也不是没写 super 就会自动叠着跑。

Dart 3 还可以限制库外的人怎么用这个类，这是语言规则，不是 lint。mixin class 既能当类，也能当 mixin。只是复用代码、不需要类型关系时，优先考虑组合。

这里的“库”不是整个项目或 package：通常一个 Dart 文件就是一个库，part 文件属于它声明加入的库。组合是让对象持有另一个对象并调用它，而不是建立继承关系。线性化是把父类和多个 mixin 排成方法查找链，super 沿链向前找。上述修饰符限制违反时属于编译错误。

类修饰符中的“库外”通常指其他 Dart 文件，part 文件除外。base 的子类型还必须声明为 base、final 或 sealed；sealed 自带 abstract，不能直接实例化，它的间接子类型能否声明在库外，取决于直接子类型的修饰符。这些限制由编译器检查。

官方核对：类修饰符与库边界。

5. extension 是干什么的

口述版

  • extension 在不修改原类、不建立继承关系的情况下，为已有类型提供方法、getter 或 setter。
  • 编译器根据调用处表达式的静态类型选择扩展，类型提升也会影响选择。运行时对象的实际类型不会重新决定用哪个扩展；dynamic 调用不会自动查找扩展。
  • 类型本身已有的同名成员优先。扩展不能增加实例字段，因此不能直接为每个对象新增一份存储空间；扩展可以声明静态成员。
  • 其他库的公开扩展需要导入后才能使用。扩展冲突时可调整导入范围，或用 扩展名(对象).方法() 显式指定。

解析

接收者是成员调用中点号左侧的表达式。扩展根据接收者的静态类型在编译期选定，不把新方法实际添加到原类中。因此 dynamic 的运行时成员查找不会自动找到扩展。下面的显式扩展调用，是直接指定使用 StringX。

extension StringX on String {
  bool get isBlank => trim().isEmpty;
}

void main() {
  String name = '  ';
  print(name.isBlank); // true：按静态类型 String 选择扩展
  dynamic raw = name;
  try {
    print(raw.isBlank); // 错误示例：能编译，运行时查找实例 getter
  } on NoSuchMethodError {
    print('dynamic 不会自动调用扩展');
  }
  print(StringX(raw as String).isBlank); // true：显式调用扩展
}

扩展不能覆盖类型已有的成员，也不能加实例字段。两个扩展撞名时，可以 hide 其中一个，或写成 扩展名(对象).方法()。同库扩展可直接使用；其他库的扩展需要导入并且处于可见范围内。

编译器可能把这次调用内联掉。那是优化，不改变「按写出来的类型选定」这个规则。调用看起来像实例方法，其实不是运行时按对象的真实类型分发。

6. 工厂构造函数和普通构造函数

口述版

  • 生成构造负责创建并初始化当前类的实例，函数体不能返回另一个对象。不处于 const 上下文的普通调用，每次创建新实例。
  • 常量生成构造按常量方式调用时，会复用规范化后的常量实例；只有声明了 const 构造还不够，调用处也必须满足常量求值规则。
  • factory 构造负责返回该类或其子类型的对象。带函数体时必须返回对象，可以返回已有实例，也可以创建新实例；其中不能使用 this 访问一个正在初始化的实例。
  • 带函数体的 factory 不能是 const 构造。重定向的 const factory 可以把调用交给兼容的常量构造。
  • 命名构造和工厂构造是两回事。名称中带 fromJson 不代表使用了 factory，是否为工厂由声明中的 factory 关键字决定。

解析

生成构造负责创建当前类的实例，工厂构造负责返回类型兼容的对象。工厂可以返回缓存对象或子类型，因此不能假设每次调用都创建新实例。下面的 User.cached 返回缓存中的对象；缓存复用由 Map 实现，不是 factory 关键字自动提供。

class User {
  User(this.name);
  User.fromJson(Map<String, Object?> json) : name = json['name'] as String;
  static final Map<String, User> _cache = {};
  factory User.cached(String name) =>
      _cache.putIfAbsent(name, () => User(name));
  final String name;
}

void main() {
  print(User.fromJson({'name': '小明'}).name); // 小明
  print(identical(User.cached('小明'), User.cached('小明'))); // true
  print(identical(User('小明'), User('小明'))); // false
}

生成构造函数用初始化列表和函数体，不能返回另一个实例。const 生成构造在 const 上下文里返回规范化实例，这是常量规范化规则，不是执行 factory 函数体来查询缓存。factory 必须返回一个这个类型能接受的对象。工厂不是一项性能优化，也不是「更快的 new」。它只是放宽「必须新造当前类」。

对象在编译期就要定死，用 const 生成构造。不能 const 的是带函数体的工厂；重定向的 const factory 是语言允许的，不要说成所有 factory 都不能 const。

fromJson 示例假设 name 字段确实存在且为 String；缺失或类型不对会在 as String 处抛出可捕获的类型错误。缓存是示例自己维护的 Map，不是 factory 自动提供的功能；真实项目还要考虑缓存的释放。

二、异步和并发

7. Future 和 async / await

异步表示先发起操作，等待期间允许当前 isolate 处理别的任务；不等于同时执行多段 Dart 代码。await 后面尚未执行的部分常叫“续体”。微任务是当前同步工作结束后、下一个普通事件前处理的短任务，完整顺序见第 9 题。

口述版

  • Future 表示一次操作最终的完成状态：成功时带一个值，失败时带一个错误，也可能始终不完成。Future 本身不负责创建并行执行环境。
  • async 函数返回 Future。调用后先同步执行到第一个 await；等待期间把执行机会交还给调用方和事件循环。
  • await 等待结果，再继续执行当前异步函数的后续代码，不阻塞整个 isolate。即使普通 Future 已完成，await 后的代码也不会在当前同步调用栈中立刻执行。
  • await 收到 Future 的错误时，会在等待处抛出，可用包住 await 的 try/catch 处理。仅调用异步函数而不等待，外层同步 try/catch 接不到它的异步错误。
  • Future(() {}) 把回调安排到事件队列，回调仍在当前 isolate 执行。耗时的同步计算不会因为包进 Future 就自动转到后台。
  • Future.wait 汇总多个 Future，成功结果按输入顺序排列；Completer 让代码主动决定 Future 何时成功或失败。

解析

Future 对象保存的是操作的完成状态，未完成时可以注册等待逻辑，完成后取得成功值或错误。async 函数先同步执行第一个 await 之前的代码，再把控制权交回调用方；等待的 Future 完成后，函数从 await 后继续。下面用 return await 让 fetch 的异步错误在当前 try/catch 内被处理。

import 'dart:async';

Future<int> fetch() async {
  print('开始');
  await Future<void>.delayed(Duration.zero);
  throw FormatException('模拟失败');
}
Future<int> load() async {
  try {
    return await fetch(); // await 把 Future 的错误送到这个 catch
  } on FormatException {
    return 0;
  }
}
Future<void> main() async {
  final pending = load();
  print('调用后');
  print(await pending);
  // 输出顺序：开始、调用后、0
  // 错误示例（不执行）：try { fetch(); } catch (_) {}
  // 上面的 catch 只能接同步抛出，不能接 fetch 返回的 Future 的异步错误。
}

scheduleMicrotask 和 Future.microtask 明确调度微任务，Future(() {}) 通过事件调度运行。一个 Future 完成后，可以在同一次异步处理过程中继续调用已注册的回调，不一定为每一级 then 重新加入微任务；Completer.sync 还允许符合约束的同步完成。不能把每个 then/await 续体都画成一个独立的新微任务，也不能推断未完成的网络请求一定先于点击返回。这是运行时的事件循环规则，不是编译器把异步优化成同步。Future 不会因为你多包一层就变成并行。

多个 Future 用 Future.wait 汇总：默认会等所有 Future 都结束，再带着第一个错误完成；eagerError: true 时在第一个错误发生后就以错误完成，但不会取消其他任务。结果列表按输入顺序排列，不按完成先后。要把回调式 API 包成 Future，或者手动决定何时完成，用 Completer；completer.complete(value) 和 completeError 只能调一次。

官方核对：Future 的同步完成特例。

基础语法：Future 与 async/await。

8. Future 和 Stream 有什么不一样

口述版

  • Future 完成一次，结果是一个值或一个错误；完成后再次 await 仍能取得同一个完成结果。Stream 可以连续产生数据和错误事件，并用 done 事件表示结束。
  • 单订阅流只允许建立一次订阅，即使取消后也不能再次监听。广播流允许多个监听者同时订阅。
  • 普通广播流不会为尚未订阅的监听者保存历史事件。普通单订阅 StreamController 会保存监听前添加的事件；async* 则在监听后才开始执行。是否补发旧值取决于具体实现。
  • async* 声明返回 Stream 的函数，yield 发出一个事件。await for 按事件执行循环，等待期间不阻塞整个 isolate。
  • listen 返回 StreamSubscription，用它暂停、恢复或取消订阅。订阅的生命周期应与使用方对应，State 销毁时要取消自己持有的订阅。
  • StreamBuilder 管理流订阅，并把最新快照交给 builder。界面构建不保证展示每一个中间事件，逐事件的业务处理应放在订阅逻辑中。

解析

Future 是一次结果，可以被多次 await；Stream 是一串事件，可以持续发出数据、错误，或发 done 结束。它们自身不创建 isolate，底层操作仍可能在其他线程或 isolate 执行。

Stream<String> messages() async* {
  yield 'hello';
  yield 'stop';
  yield '不会打印';
}
Future<void> main() async {
  await for (final event in messages()) {
    print(event);
    if (event == 'stop') break; // 退出时取消本次订阅
  }
  print('结束');
  // 输出顺序：hello、stop、结束
}

async* 每 yield 一次就往外发一个事件。yield* 是把另一条流里的事件接着转出去。单订阅流不能再次 listen，即使第一次订阅已取消。普通单订阅 StreamController 会在 listen 前缓冲，async* 则等监听才开始生产事件；广播 StreamController 不为尚未订阅的人保留过去的事件。这是单订阅和广播最容易混淆的地方。dart:async 的普通广播流不补发过去的事件；保留最新值的实现会在订阅时交出那一份。await for 挂起的是当前这个异步函数，不会把整条 isolate 卡住。「await for 会把线程堵死」是老说法。

界面里用 StreamBuilder，它在订阅、事件和错误到来时更新快照并请求重建，但 builder 由帧管线调度，可能只看到部分中间快照，不能拿它处理每一笔业务事件；不要在 build 里自己 listen，那会每次重建都多一个订阅。需要把流拆开、合并、去重，用 StreamTransformer 或 stream.map / where / expand。

await for 可以用于广播流，但循环体等待期间订阅会暂停，普通广播流的该订阅会缓冲这段时间的事件。没有 break 且流不结束时，循环后的代码不会执行；收到未处理的错误时循环会退出并向外抛。不同实现可有不同生产策略。页面 dispose 之后订阅还在，是常见的 setState() called after dispose() 来源。

官方核对：StreamBuilder 快照与构建时序。

9. Dart 是不是单线程？事件循环怎么跑

口述版

  • 一个 isolate 内，同一时刻只执行一段 Dart 代码；一个进程可以运行多个 isolate。Dart VM 可以将不同 isolate 安排到不同系统线程上执行。
  • 事件循环每次先执行完当前同步代码，再清空微任务队列，然后取一个普通事件执行；该事件执行完后，再次清空微任务队列。
  • scheduleMicrotask 和 Future.microtask 安排微任务；Future(() {}) 和 Timer 安排普通事件。输入和异步 I/O 的完成也通过事件调度处理。
  • await 只挂起当前异步函数的后续执行，不停止事件循环；尚未结束的同步代码也不会被微任务中断。
  • 微任务执行期间新增的微任务也要处理完。持续追加微任务会使普通事件和帧调度长期得不到执行机会。

解析

事件循环负责在同步执行结束后，依次取出已排队的任务执行。微任务的优先级高于下一个普通事件，但不能中断正在执行的同步代码；微任务队列必须清空后，才会处理下一个普通事件。

同一个 isolate 上不会有两段 Dart 代码同时执行。一个应用可以有多个 isolate，Dart VM 可以把它们安排到不同的系统线程上。隔离的是普通 Dart 可变对象，不是说引擎或原生代码完全没有共享内存。

想排在点击和定时器前面、又不能太重，用微任务。普通的稍后执行用 Future(() {}) 或 Timer，进事件队列。await 停住的是当前这个 async 函数，不是这条 isolate。

10. Isolate 是什么，和 Future 有什么区别

口述版

  • Isolate 是独立执行 Dart 代码的环境，有自己的内存状态和事件循环。普通可变 Dart 对象不跨 isolate 直接共享，不能直接修改对方的对象。
  • Future 表示将来的结果，isolate 提供独立执行环境。只创建 Future 不会并行；在 Dart VM 上，把计算交给另一个 isolate 才能与当前 isolate 并行执行。
  • SendPort 发送消息，ReceivePort 接收消息。可发送的可变对象通常会复制，运行时认可的不可变对象可以共享；带原生资源的对象存在发送限制。
  • TransferableTypedData 用于转移字节数据的使用权。发送后，发送端不能再从该包装对象取得字节视图；创建包装对象时使用的原始数组仍可使用。
  • Isolate.run 和 Flutter 的 compute 用于执行一次计算并返回结果；Isolate.spawn 可创建持续收发消息的 isolate。ReceivePort 用完要 close，否则可能阻止 isolate 退出。
  • Flutter Web 不支持通过 dart:isolate 创建并行 isolate；compute 在 Web 上仍使用当前事件循环。引擎的 UI、Raster 等任务线程也不等于 Dart isolate。

解析

Isolate 各自维护普通 Dart 对象状态，通过消息传递协作。这里的“堆”指存放对象的内存区域；“独立”强调不能直接读写对方的可变 Dart 对象，并不保证底层运行时绝不共享任何内存。Future 只是结果对象，不提供这样的独立执行环境。

VM 上 isolate 可以被安排到不同系统线程。Flutter Web 不支持直接用 dart:isolate 创建并行 isolate；compute 在 Web 上运行于当前事件循环，繁重计算仍会阻塞界面。Flutter 引擎另外有界面、画像素、平台、文件这几条线程，它们不是 isolate。主 isolate 跑在界面线程上；你 spawn 出来的 isolate 不归这套线程编制。

消息能发的类型有限：基本类型、List/Map、SendPort、TransferableTypedData 等；共享代码的 isolate（如 Isolate.spawn 创建）可发送多数对象，但 Socket、ReceivePort、带原生资源的对象等不能发；可变对象图会复制，字符串等不可变对象可共享。同组 isolate 之间用 Isolate.exit 发送最终消息后发送者立即退出，可通过转交避免复制；不是任意对象、任意 isolate 都能无条件零拷贝。ReceivePort 用完要 close，否则对应的 isolate 可能一直不退出。

只是等 I/O，再包进 isolate 多的是启动和拷贝，不是并行收益。全局变量也是各有一份，不是加锁就能一起改。「Dart 没有多线程」不准确。普通 Dart 可变对象由 isolate 隔离；FFI 指向的原生共享内存需要另外处理同步和生命周期。

官方核对：Flutter isolate 的平台限制。

官方核对：可转移字节数据。

三、框架入门

11. Flutter 和原生开发的差别

声明式界面是先描述当前数据应该显示什么，再由框架更新界面。JIT 是运行期间编译代码，方便开发期更新；AOT 是提前编译，移动端和桌面发布包通常提前生成机器码。两种编译方式本身都不保证界面流畅。

口述版

  • Flutter 的普通组件由引擎统一绘制，不为每个组件创建对应的系统原生控件。图形渲染使用 Skia 或 Impeller，具体取决于平台和版本；嵌入的 PlatformView 使用原生视图。
  • Flutter 使用声明式界面：业务代码根据当前状态返回 Widget 配置，框架据此更新 Element 和 RenderObject，再完成布局与绘制。
  • 手机和桌面的 debug 模式使用 JIT，支持开发时热重载；release 模式使用 AOT，提前生成机器码。Web 使用自己的编译与渲染路径。
  • 访问平台能力通常通过插件、Platform Channel 或 FFI。跨平台界面代码可以复用，平台差异仍需由相应平台实现处理。
  • Flutter 安装包通常包含引擎等运行所需内容，体积有额外成本。性能取决于构建模式、界面更新、布局、绘制和业务计算的实际开销。

解析

自绘是指 Flutter 根据组件配置自行记录和执行绘图指令，不为每个普通组件创建系统控件。声明式是指 build 返回当前状态对应的配置，由框架更新节点。两者分别回答“怎样生成画面”和“业务代码怎样描述画面”。

对照着看：原生开发可以使用系统控件，也能自绘；React Native 的常见组件由原生视图实现，具体通信和渲染方式受版本与架构配置影响。Flutter 的系统能力靠插件和 Platform Channel，必要时用 PlatformView 嵌一块原生视图。桌面小组件、很深的系统接口仍然要原生配合。

手机和桌面的热重载在 debug 的 JIT 里，是开发期工具，不是它比原生快的原因。Web debug 另有热重载，见第 20 题。release 没有热重载；手机和桌面的 release 是 AOT。画像素的库是 Skia 或 Impeller，当前官方文档中 iOS 使用 Impeller；Android API 29+ 默认启用，低版本或不支持 Vulkan 的设备有回退路径。其他平台仍需按版本和配置核对。「流畅程度通常接近原生」依赖 AOT、自绘管线，以及没有在界面线程上做重活，不是语言保证。

官方核对：Impeller 平台支持范围。

12. Flutter 的整体架构

口述版

  • Flutter 自下而上分为 Embedder、Engine 和 Framework 三层。
  • Embedder 是平台适配层，负责把引擎接入操作系统的窗口、渲染表面、输入事件和任务调度环境。
  • Engine 提供 Dart 运行环境、文字排版和图形渲染等底层能力，主要用 C++ 实现，并通过 dart:ui 暴露给 Dart 层。
  • Framework 用 Dart 实现 Widget、布局、手势、动画及 Material/Cupertino 组件。业务代码主要使用这一层，dart:ui 只是它与引擎连接的底层接口。
  • Task Runner 是执行某类任务的调度入口，不保证独占一个系统线程。传统任务分为 UI、Raster、IO、Platform，现代多个平台会让 UI 和 Platform 共用线程；VM 和后台 isolate 还可能使用其他线程。

解析

Embedder 解决如何接入操作系统，Engine 提供执行和绘制能力，Framework 把这些能力组织成 Dart 组件 API。业务代码一般调用 Framework 的组件，Framework 再通过 dart:ui 使用引擎能力。

线程映射属于平台和引擎实现：UI 与 Platform 在 iOS/Android 从 Flutter 3.29 起默认合并，macOS/Windows 从 3.35 起默认合并；Linux 的合并节点见第 27 题。Dart VM 的 GC 等辅助线程和后台 isolate 另算。dart:ui 不是整个 Flutter SDK，不要说「写 App 时直接导入 dart:ui 就等于用了整套框架」。业务代码一般不直接对着 Engine 写。

官方核对：架构与任务调度。

13. main 和 runApp 分别做什么

口述版

  • main 是 Dart 程序入口，启动初始化和调用 runApp 的代码通常写在这里。
  • runApp 确保 WidgetsFlutterBinding 初始化，把传入的 Widget 作为根组件接入框架，并安排首帧。调用返回不代表屏幕已经显示完成。
  • WidgetsFlutterBinding 连接框架与引擎，负责接收帧调度、输入和平台消息等。runApp 前需要使用依赖绑定的插件时，应先调用 WidgetsFlutterBinding.ensureInitialized()。
  • 热重载不会重新执行已经运行过的 main；热重启会重新执行入口和启动逻辑。

解析

runApp 接入的是根 Widget 配置，不是已经绘制好的画面。框架随后建立或更新节点，按帧调度完成构建、布局和绘制。WidgetsFlutterBinding 负责把引擎回调接到框架；提前使用依赖它的平台能力时，需要先初始化绑定。

import 'package:flutter/material.dart';

void main() {
  WidgetsFlutterBinding.ensureInitialized();
  // 若此处需要 await 插件初始化，把 main 声明为 Future<void> main() async。
  runApp(const MaterialApp(home: Scaffold(body: Center(child: Text('Hello')))));
}

热重载不重跑已经执行过的 main，热重启会。这是开发期工具。release 没有热重载，不是框架在正式包里的行为。改了启动代码却看不到效果，不是 runApp 没执行过，而是热重载没有重跑 main。在绑定还没准备好时就用插件，会在 runApp 之前失败。

14. Widget 有哪几类，为什么不能改

口述版

  • Widget 是描述界面和行为的不可变配置。配置更新时通常创建新的 Widget，框架用它更新树上已有的 Element，而不是直接修改旧 Widget。
  • StatelessWidget 没有独立的 State，build 根据构造参数和已订阅的上层数据生成界面。没有 State 不代表只 build 一次。
  • StatefulWidget 通过 createState 创建 State。State 由 StatefulElement 保存，可变数据放在 State 中；复用同一个 Element 时，State 也能保留。
  • 修改 State 字段不会自动更新界面。setState 会请求重建；父级传入新配置或已登记的依赖发出通知，也可能触发重建。
  • InheritedWidget 负责向后代提供可订阅的数据。RenderObjectWidget 负责创建和更新执行布局、绘制的 RenderObject。ParentDataWidget 向父布局提供它需要的子节点布局参数。
  • RenderObjectWidget 按孩子数量分为 Leaf、SingleChild、MultiChild；InheritedWidget 和 ParentDataWidget 属于 ProxyWidget，它们自己不创建 RenderObject。

解析

State 与 Element 关联，而不是存放在某一份 Widget 配置里。父组件可以反复创建新的 StatefulWidget；只要框架继续复用原 StatefulElement，它保存的 State 就不需要重新创建。因此 build 次数和 State 的创建次数不是一回事。

字段用 final 是语言层面锁住绑定。@immutable 是框架和分析器的约定。Widget 会被频繁新建，所以要轻，这是设计，不是某次渲染优化碰巧复用了 Widget。如果配置本身还能被改掉，框架就分不清这次 build 到底变了什么。不可变让同一份配置能安全复用，框架通过类型、key 和更新逻辑协调节点，而不是深度比较所有字段。final 字段若指向可变 List，List 本身并不会自动不可变。不可变的是配置，Element 和 State 是可变的。

按基类看，常见的 Widget 基类包括 StatelessWidget、StatefulWidget、ProxyWidget 和 RenderObjectWidget，这不是穷尽所有子类的分类。ProxyWidget 自己不创建 RenderObject，只把数据往下传，InheritedWidget 和 ParentDataWidget 都属于它；RenderObjectWidget 再按孩子数量分成 Leaf、SingleChild、MultiChild 三种。

StatelessWidget 没有自己的 State，也就没有 initState 和 dispose。它在 build 里调用 Theme.of 这类会 depend 的方法时，StatelessElement 会登记依赖，上层数据通知后一样会重建。父组件传入新配置也会重建。数据变了却没刷新，不是 StatefulWidget 坏了，是没有 setState，也没有依赖通知。Widget 不只是控件，间距、主题、继承数据的包装也是 Widget。

15. State 的生命周期

口述版

  • 新建 State 后，首次初始化顺序是 initState、didChangeDependencies、build。每个 State 的 initState 只执行一次，先调用 super.initState，再初始化自己的资源。
  • 需要读取并订阅 InheritedWidget 数据时，放在 didChangeDependencies 或 build，不能放在 initState。didChangeDependencies 首次构建前会执行，已订阅的数据变化后还会再执行。
  • 父级用同类型、同 key 的新 Widget 更新现有节点时，调用 didUpdateWidget，随后 build；可在这里比较新旧配置并切换订阅。单独调用 setState 不触发 didUpdateWidget。
  • deactivate 表示节点离开当前位置，但同一帧内仍可能重新插入树中，因此不在这里释放需要保留的资源；super.deactivate 放在方法末尾。
  • 确定不再复用该 State 时调用 dispose。先释放 Controller、取消 Timer 和订阅，再调用 super.dispose；这个 State 此后不能再 setState。
  • mounted 表示 State 是否仍关联 Element。dispose 返回并断开关联后变为 false；dispose 执行期间可能仍为 true，也不能据此认为还能 setState。
  • 应用前后台变化属于另一套生命周期，可用 WidgetsBindingObserver 或 AppLifecycleListener 监听。进程被系统直接终止时，不保证执行 dispose。

解析

生命周期描述一个 State 从创建、更新到销毁的过程。initState 属于首次初始化；build 可以多次调用；deactivate 只是离开当前位置；dispose 才表示该 State 不再复用。同一个 State 销毁后，不能重新挂回树中。

build 里不改数据、不发请求、不订阅。didUpdateWidget 里比较 oldWidget 和 widget，换订阅、重启动画。父组件把 userId 换成另一个，只写在 initState 里，页面会继续显示旧用户。

异步回调回来先看 mounted。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。写在 dispose 里面的代码当时还能读到 true，不代表还能 setState。super.initState() 写在方法末尾是错的。末尾调用 super 的是 deactivate 和 dispose。

setState() called after dispose() 这类检查包在 assert 里，profile 和 release 会去掉 assert。State 已经和 Element 断开后再调用，常见版本会因为 element 已经是空而抛错。检查被拿掉，不表示这次调用变得合法。reassemble 是热重载这条开发期路径，正式包不会走它来更新你的 initState。热重载不会重跑 initState。

同一个 StatefulWidget 配置对象可以在不同位置创建多个 State；“一次”是针对某个 State 实例。GlobalKey 在同帧换位置时，deactivate 后还可能 activate，再进入后续构建。订阅外部数据时，通常在 initState 建立，在 didUpdateWidget 按新配置切换，在 dispose 取消。

16. setState 做了什么

口述版

  • setState 先同步执行传入的回调，再调用当前 Element 的 markNeedsBuild，把它标记为需要重新构建。
  • 回调通常修改 State 中的数据。setState 不会立即把新界面画到屏幕，框架会在合适的帧构建阶段调用 build。
  • 同一个 Element 在下一次构建前被重复标记，通常只需要构建一次。重建从当前节点开始，子节点是否继续更新取决于新旧配置和依赖变化，不等于整个应用重新创建。
  • 把可变状态放在尽量小的组件中，可以缩小这次更新涉及的子树。不要在自己的 build 中调用 setState，也不要在 build 中启动请求或建立订阅。
  • 回调必须同步完成，不能声明为 async 或返回 Future。先等待异步工作完成，再检查 mounted 并用 setState 更新数据；State 销毁后不能调用。

解析

setState 不负责监听字段，也不会比较字段的新旧值。它先执行你提供的修改逻辑，再告诉框架当前 Element 需要 build。即使回调没有修改任何值，也会请求构建；只修改字段而不发出通知，框架则不一定知道需要刷新。

只有一小块在变，setState 写在那一块自己的 State 上。同一段点击处理里要改好几个字段，可以多次 setState，框架会合成一次 build，更好的写法是一次回调里改完。想让更小的区域听一个值，用 ValueListenableBuilder、Selector 或 Bloc 的 buildWhen。

新 Widget 和旧子节点按类型和 key 比较，对得上就更新原 Element。这是框架的复用，不是语言保证。build 里发现自己想 setState、发请求或订阅，是副作用放错地方了。不同节点在一帧中可以分别 build，不应依赖固定构建次数。

setState 的回调要同步完成。写成 async 时，await 之后的代码不在这次标记的范围内，debug 下框架还会直接报「回调返回了 Future」。正确做法是先把异步结果拿回来，再调用一次 setState。State 已经 dispose 之后再调用，debug 下会被 assert 拦住，release 下也可能因为 Element 为空而抛错。

17. BuildContext 是什么

口述版

  • BuildContext 是 Element 实现的接口，表示某个节点在 Element 树上的位置。每个节点有自己的 context，用它访问当前节点的祖先和环境数据。
  • Theme.of、MediaQuery.of 等依赖式查询会查找相关祖先，并把当前 Element 登记为依赖者。登记表示上层相关数据变化时，框架会通知这个节点重新构建。
  • Navigator.of、context.read 和 findAncestor 系列方法只查找，不登记数据依赖；读取成功不代表以后变化时会自动重建。
  • 查询只能从当前节点向祖先查找，不能直接找到当前节点将要创建的后代。能否查到目标取决于使用的是哪个位置的 context。
  • initState 中已有 context，但不能用它登记 InheritedWidget 依赖。跨 await 再使用 context 前，应检查这个 context 自己的 context.mounted。

解析

BuildContext 提供当前 Element 的树位置和查询接口。查找祖先从这个位置向上进行，不是在 Widget 对象中搜索。当前 build 返回的组件属于后代，因此不能用当前 context 向上找到这些新创建的后代。

要跟着主题、MediaQuery、Provider 变，在 didChangeDependencies 或 build 里用 of。只取一次当前值，用不登记的读法，并接受它不会再通知你。跳转、发请求、订阅放生命周期或点击回调。异步回来再用 context，先看 context.mounted（State 里用 mounted）；跨 await 使用 context 的 lint 就是 use_build_context_synchronously。State 和 Element 断开之后，该 context 已失效，不能继续用来查询祖先。

initState 里禁止 depend 的检查，在 debug 下会用 assert 拦住。这是框架约束。release 拿掉 assert，不表示这个时机突然变得正确。State 通过 context 找到自己的 Element，context 不是 State 的别名。

跨 await 使用某个 context 时，应检查这个 context 自己的 mounted；State 的 mounted 只对应它自己的 context，不能代替另一个子节点 context 的检查。找到已卸载节点后也不能用祖先查询补救。MediaQuery 的部分 API 采用 aspect 订阅，仅相关字段变化才通知。

18. Key 有什么用

口述版

  • Key 帮助框架判断新 Widget 应更新哪个旧节点。同一个父节点的匹配范围内，runtimeType 和 key 都相同，才能用新配置更新原 Element 并保留其 State。
  • 没有 Key 时主要按位置和类型匹配；数据顺序改变后，原 State 可能仍属于原位置，而没有跟随业务数据移动。
  • ValueKey 按值的 == 比较，ObjectKey 按对象的 identical 比较；UniqueKey 每次创建都是不同身份，更新时会使旧节点无法匹配。
  • LocalKey 只在同一个父节点的孩子之间比较，并要求同级唯一。Key 要放在父节点实际用来匹配的那层 Widget 上。
  • GlobalKey 在活动树中必须唯一，并应长期保存。同一帧中移除旧位置并插入新位置时，它可以让节点跨父级移动并保留 State，也可用于访问 currentState 等信息。
  • Key 不能恢复已销毁的 State。懒列表重排时，还需按组件要求通过 findChildIndexCallback 等方式把 Key 对应到新下标。

解析

框架需要把新的子 Widget 与旧 Element 对应起来，再决定更新还是销毁重建。Key 是这次匹配的身份标识，不是数据存储空间。图中的列表重排说明：没有稳定身份时，State 可能留在原位置，而不是跟着数据项移动。

ObjectKey 用 identical，ValueKey 用 ==。这是这两个类自己的相等实现，不要记反。两个内容一样、但是新创建的对象，ObjectKey 对不上。UniqueKey 每次都是一个新身份，用来故意丢掉旧 State。写在 build 里，旧 State 每次都被丢掉。

列表每一项的 State 串了，给每一项加 ValueKey(item.id)，不是给整个 ListView 加一个 Key。本地 Key 只在同一个父组件的子组件之间比较。换了父组件还要留 State，才考虑 GlobalKey。GlobalKey 能在换父节点时把 State 挪过去，也能拿 currentState、currentContext、currentWidget，代价是全局登记。复用 Element 能少做销毁和创建，但 Key 本身不是一项渲染加速开关。

Key 要放在列表真正匹配的那层子节点上。ListView.builder 重排已有数据时，通常还要通过 findChildIndexCallback 把 key 映射到新下标，不能承诺只加 ValueKey 就在所有懒列表中保住 State。Key 不能复活已经 dispose 的状态。

19. 滑出屏幕后，状态怎么留住

口述版

  • 懒构建的滚动组件只维护当前需要显示或缓存的子项。未请求保活的子项离开缓存范围后可能被移除，State 随之销毁；滑出屏幕不等于立刻销毁。
  • AutomaticKeepAliveClientMixin 用来请求保留 State。wantKeepAlive 返回 true，并在 build 中调用 super.build(context)，忽略其返回值。
  • 祖先必须有 AutomaticKeepAlive 接收请求；默认列表代理通常会添加。只有混入 mixin，但没有祖先处理请求，不足以完成保活。
  • 保活使子项离开缓存范围后仍保留节点和 State，不要求它继续布局或绘制，会增加内存占用。wantKeepAlive 改变后要调用 updateKeepAlive() 更新请求。
  • PageStorageKey 配合 keepScrollOffset 可在同一 PageStorage 存储区域内恢复滚动偏移，保存的是滚动位置，不等于保留整个 State，也不等于持久化到磁盘。

解析

Key 解决更新时“新配置对应哪个旧节点”，保活解决离开滚动缓存范围后“旧节点是否销毁”。保活保留的是现有 Element 和 State；PageStorage 恢复滚动位置则是在重新创建滚动组件后读回偏移，两者机制不同。

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: PageViewDemo())));

class PageViewDemo extends StatelessWidget {
  const PageViewDemo({super.key});
  @override
  Widget build(BuildContext context) => PageView(
    children: const [TabPage(), Center(child: Text('第二页，滑回去看计数'))],
  );
}
class TabPage extends StatefulWidget {
  const TabPage({super.key});
  @override
  State<TabPage> createState() => _TabState();
}
class _TabState extends State<TabPage>
    with AutomaticKeepAliveClientMixin<TabPage> {
  int count = 0;
  @override
  bool get wantKeepAlive => true;
  @override
  Widget build(BuildContext context) {
    super.build(context); // 必须调用，忽略返回值
    return Center(child: TextButton(
      onPressed: () => setState(() { count++; }),
      child: Text('计数：$count'),
    ));
  }
}

保活是 AutomaticKeepAlive 和可滚动组件之间的约定。必须遵循调用 super.build(context) 的约定并忽略其返回值；不能依赖某个版本在 initState 中也申请过保活的实现细节。若关闭 addAutomaticKeepAlives 或移除了相关祖先，仅混入 mixin 不够。列表的缓存范围、Tab 是否预加载相邻页，依组件和参数而定，不要说成「滑出一像素就一定 dispose」。保活不是让它继续画在屏幕上，只是离开缓存范围后仍留在树上。它用内存换「不要销毁」，包太多会更占内存，不是渲染优化开关。只需在重建滚动组件后恢复偏移时，可在同一个 PageStorage 存储区域（bucket）中配合唯一 PageStorageKey 和默认开启的 keepScrollOffset；它不保存任意业务状态，也不是进程重启后的持久化。

官方核对：保活所需的祖先与调用约定。

20. 热重载和热重启

口述版

  • 热重载更新正在运行的 Dart 代码，并请求现有组件重新构建，尽量保留原 State。它不会重新执行已运行过的 main、initState 或已完成的全局/静态字段初始化。
  • Flutter 通过 reassemble 通知现有节点处理热重载，再安排 build。修改初始化逻辑后，旧状态可能仍保持原值。
  • 热重启会重新启动 Dart 应用，重跑 main 并重新创建 State，原有 Dart 状态被清除；它不等于重新编译和安装整个原生工程。
  • 热重载只用于支持它的 debug 开发环境。手机和桌面依赖 VM 的 JIT；Web debug 使用自己的开发编译器。profile 和 release 不提供热重载。
  • 部分类型结构变化会被热重载拒绝。原生代码、插件集成配置等变化通常需要停止应用并重新构建，具体限制由工具链决定。

解析

热重载更新代码并复用现有 Dart 状态，热重启重新启动 Dart 应用并清空原状态。main 和 initState 属于已经执行过的初始化逻辑，热重载不会补执行它们；要按新初始化逻辑重新创建状态，通常需要热重启。

手机和桌面的 debug 是 JIT，边运行边编译。profile 和 release 是 AOT，提前编译成机器码。这是工具链，不是 Dart 语法。热重载会找出改过的部分、送进正在运行的程序、再重建 Widget。它不是只把画面重画一遍，也不是把应用关掉再打开。改了 initState 没效果，是因为旧 State 还在，不是热重载失败。debug 能热重载，不能用来证明 release 的性能。

Web debug 从 Flutter 3.35 起默认也有有状态热重载，实现是浏览器里的开发编译器，不是上面这套 VM JIT，同样不重跑 main 和 initState。Web 的 release 是编译成 JavaScript 或 Wasm，不要把手机上的 JIT / AOT 原句套过去。Web 的 release 同样不能热重载。

官方核对：热重载限制。

21. InheritedWidget 是干什么的

口述版

  • InheritedWidget 在树的祖先节点保存数据，使后代不用逐层传递构造参数也能读取。
  • 后代通过 dependOnInheritedWidgetOfExactType 查找最近的指定类型祖先，并登记依赖。登记后，框架知道哪些 Element 需要在数据变化时更新。
  • 新的 InheritedWidget 替换旧配置时，updateShouldNotify 比较新旧数据；返回 true 才通知已登记的依赖者。返回 false 仍会更新祖先配置，只是不发出这次依赖通知。
  • 只查找但不登记依赖的读取方式，可以取得当前数据，却不会因为后续数据变化自动重建。依赖登记应在 build 或 didChangeDependencies 中进行。
  • InheritedModel 通过 aspect 区分依赖的数据部分，按相关性通知；InheritedNotifier 监听 Listenable，在监听对象发出变化通知时更新依赖者。

解析

登记依赖，就是把读取数据的 Element 加入祖先的依赖记录。后续祖先发出通知时，框架沿记录找到需要更新的节点；仅仅读过数据但没有登记的节点，不会收到这次依赖通知。

通知本身不是把 InheritedWidget 下面的所有节点一律标脏。InheritedWidget 自己的 child 如果在父级重建时还是同一个 Widget 实例，子树可以走普通的 identical 跳过。如果父级每次都 new 一个新的 child，那是普通的父级重建，和「通知依赖者」不是同一条路径。

依赖粒度可以更细：InheritedModel 用 aspect 区分同一个模型里的不同字段，只有 updateShouldNotifyDependent 认为相关的依赖者才重建；InheritedNotifier 把 Listenable 和 InheritedWidget 合在一起，notifyListeners 时通知依赖者。

Provider 封装了基于 InheritedWidget 的数据提供和依赖订阅机制。这是封装，不是另一套渲染机制。读的位置必须在 Provider 下面。沿树向上找不到，就不是「数据没刷新」。initState 里调用会登记依赖的 of 是时机错了（不登记的 read 可在合适情况下读取一次），不是 InheritedWidget 不能在第一帧读。

22. 状态管理怎么选

口述版

  • 状态管理要明确四件事：数据由谁保存、修改后怎样通知、哪些界面重建、何时释放数据。重建范围由状态和订阅的位置决定，换库不会自动缩小范围。
  • setState 管理单个 State 的可变数据并请求重建。ValueNotifier 保存一个值，配合 ValueListenableBuilder 更新监听区域；值按 == 比较发生变化时才通知。
  • InheritedWidget 和 Provider 沿组件树提供数据。watch 建立依赖，read 只读取当前值；ChangeNotifier 通过 notifyListeners 发出通知，Selector/select 可比较选中的部分来减少无关更新。
  • Riverpod 由 Provider 容器管理状态，不依赖 BuildContext 向上查找。ref.watch 订阅，select 选择部分数据；autoDispose 开启时，没有监听者后可自动释放，默认值取决于声明方式和版本。
  • Cubit 用方法产生新状态；Bloc 先接收事件，再由事件处理逻辑产生状态。BlocBuilder 根据状态更新界面，buildWhen 可过滤是否执行这次重建。
  • GetX 的 Obx 追踪构建回调读取的响应式值；GetBuilder 依赖控制器的 update 通知。选择时还要考虑业务逻辑的测试、变化来源能否追踪，以及团队维护成本。

解析

状态对象保存数据，通知机制告诉界面数据发生了变化，订阅关系决定哪些节点需要更新。三者需要分别看清。setState 请求当前 Element 重建；InheritedWidget 按依赖记录通知；状态管理库通常是在这些基础机制上组织数据和订阅。

「select 能少重建」依赖你真的只订阅了那个字段。父级如果整页 setState，仍可能通过普通父子更新路径重建下面的组件；select 只能过滤由相应订阅引起的更新。事件要按类型展开用 Bloc，只是几个方法改状态用 Cubit 就够。跨页面、不希望绑着 BuildContext、逻辑要单测，用 Riverpod 或 Bloc。团队已经统一某个库，先服从团队，再讲你知道的边界。

Provider 的常见实现是 InheritedWidget 包一个 ChangeNotifier。notifyListeners 触发后，Consumer 和 context.watch 的订阅者会请求重建；context.select/Selector 会比较选中的值，通常只有比较结果变化才通知；context.read 不订阅。Selector 用 shouldRebuild 控制只在选中的值变化时重建。

Provider 找不到，通常是读取的位置不在它下面。read 能拿到当前值，但之后变了也不会刷新。简单页面套一整套 Bloc，和复杂业务只靠一层层 setState，都是边界选错。性能问题先看是谁在重建，不要先换状态管理库。

ChangeNotifier 是“数据已变化”的通知对象；ValueNotifier 只在新旧 value 用 == 比较不等时通知，直接修改 value 所指 List 的内容不会自动通知。Listenable 是可注册监听回调的接口。Selector 和 Riverpod select 应选择不可变值，避免原地修改导致新旧比较看不出变化。自动销毁通常在没有监听者持续一帧后触发，重新计算或容器销毁也可能释放状态。

23. Navigator 和 MaterialApp 做了什么

口述版

  • Navigator 管理 Route 组成的栈，负责进入、返回、替换和转场。栈顶通常是当前显示的路由，下面的路由是否保留由具体 Route 策略决定。
  • MaterialApp 配置主题、本地化和导航入口。常见 home/routes 配置会创建 Navigator；MaterialApp.router 接入 Router，不能认为每种 MaterialApp 配置都一定创建 Navigator。
  • Navigator.of(context) 从当前节点向上找到最近的 Navigator；嵌套导航时，它不一定是最外层导航器。
  • push 传入 Route；pushNamed 根据名字生成 Route。push 返回的 Future 会在该路由被弹出时完成，结果可由 pop 的参数传回。pushReplacement 替换当前路由，pushAndRemoveUntil 可移除不再需要的旧路由。
  • 保留状态的路由被新路由遮住时，不会仅因遮挡就 dispose。普通 MaterialPageRoute 默认 maintainState 为 true；Navigator 或其祖先被移除等情况仍可导致销毁。
  • Navigator 的 push/pop 是命令式导航；Router 配合路由信息解析把地址和页面配置对应起来，go_router 对这些能力作了封装。PopScope 用 canPop 声明是否允许返回，并通过回调接收返回操作的结果。

解析

路由栈记录进入和返回的顺序，栈顶是最近进入且未退出的路由。push 加入路由，pop 移除当前路由并返回结果；被遮住的旧路由仍可能保留。路由子树一般在退出转场后销毁，整个 Navigator 或祖先被移除也会导致销毁。

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: HomePage()));
class HomePage extends StatelessWidget {
  const HomePage({super.key});
  @override
  Widget build(BuildContext context) => Scaffold(body: Center(
    child: TextButton(
      child: const Text('打开 B'),
      onPressed: () async {
        final result = await Navigator.of(context).push<String>(
          MaterialPageRoute<String>(
            settings: const RouteSettings(name: '/detail'),
            builder: (pageContext) => Scaffold(body: Center(
              child: TextButton(
                onPressed: () => Navigator.of(pageContext).pop('已选中'),
                child: const Text('返回结果'),
              ),
            )),
          ),
        );
        if (!context.mounted) return;
        ScaffoldMessenger.of(context).showSnackBar(
          SnackBar(content: Text(result ?? '没有结果')),
        );
      },
    ),
  ));
}

页面里直接打开下一页用 push。复杂深链与 Web 地址通常优先用 Router 或 go_router；简单命名路由的深链支持有局限。跳转放点击回调，或者放在导航条件已经确定之后。在 build 里 push，每次重建都会再打开一页。

Navigator 1.0 是命令式 push/pop，适合页面不多的应用；Navigator 2.0 把路由栈交给 RouterDelegate 和 RouteInformationParser，适合深链和 Web。实际项目里常用 go_router 包一层。返回拦截用 PopScope 的 canPop 和 onPopInvokedWithResult，不要再写 WillPopScope。

路由动画、以及被盖住的页面是否还在继续 build，依具体 Route 和 TickerMode 而定。不要说成「被盖住就完全没有代码在跑」或「一定每帧都在 build」。go_router 是路由库，不是 Navigator 的替代运行时。栈不复杂时不必上。MaterialApp 不只是套一层视觉风格，它按构造形式和导航配置提供 Navigator 或 Router，不能保证每种配置都有 Navigator。

24. 动画怎么做，vsync 是什么

动画是随时间连续改变的值，再把值应用到大小、颜色或位置。Ticker 是跟随帧调度发送回调的对象；vsync 参数接收 TickerProvider，由它创建 Ticker 并配合可见性控制回调。

口述版

  • 隐式动画由组件内部管理动画过程，只需提供新的目标属性和 duration；显式动画由代码持有 AnimationController，主动控制开始、停止、反向和重复。
  • AnimationController 默认产生 0 到 1 的进度值，Tween 把进度映射为目标取值范围，CurvedAnimation 改变进度随时间变化的曲线。
  • vsync 参数接收 TickerProvider，由它提供跟随帧调度的 Ticker。Ticker 在需要时接收帧回调，不是自己用 Timer 持续触发。
  • 一个 State 整个生命周期只创建一个 Ticker 时用 SingleTickerProviderStateMixin；可能先后或同时创建多个时用 TickerProviderStateMixin。Controller 必须在 State 的 dispose 中释放。
  • TickerMode 可以静默 Ticker 的回调，但时间仍流逝，恢复时进度可能直接跳到新的位置。不可见或透明并不自动代表 Ticker 已停止。
  • AnimatedBuilder 监听 Animation 并重建 builder 返回的部分；不随动画变化的子树可通过 child 传入。Hero 用相同 tag 匹配转场两端，在 Overlay 中显示过渡组件，不是把原 Element 跨页面移动。

解析

动画值随着时间推进，界面使用这些值改变显示属性。隐式动画由组件管理 Controller，显式动画由调用方管理 Controller。vsync 参数实际接收的是 TickerProvider，由它创建与帧调度配合的 Ticker，而不是传入一个刷新率数值。

import 'package:flutter/material.dart';

void main() => runApp(const MaterialApp(home: Scaffold(body: Box())));
class Box extends StatefulWidget {
  const Box({super.key});
  @override
  State<Box> createState() => _BoxState();
}
class _BoxState extends State<Box> with SingleTickerProviderStateMixin {
  late final AnimationController _controller;
  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this, duration: const Duration(milliseconds: 600),
    )..repeat(reverse: true);
  }
  @override
  Widget build(BuildContext context) => Center(child: AnimatedBuilder(
    animation: _controller,
    builder: (context, child) => SizedBox(
      width: 40 + 80 * _controller.value, height: 40, child: child,
    ),
    child: const ColoredBox(color: Colors.blue),
  ));
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}

Ticker 向调度器注册帧回调，并在回调中提供从启动至今的经过时间，不是独立 Timer。一个 State 生命周期只提供一个 Ticker 时用 SingleTickerProviderStateMixin。整个生命周期可能先后或同时创建多个 Controller 时用 TickerProviderStateMixin。Ticker 停不停，看的是 TickerMode.of(context)。普通路由被不透明页面完全遮盖时通常会静默 Ticker，半透明覆盖则未必。静默只是不发帧回调，时间仍流逝，恢复时会追上经过的时间；要真正暂停进度，显式调用 stop 并自行管理恢复。列表里滚出屏幕、子树里没有 TickerMode(enabled: false) 的 Controller 会继续 tick。这是 mixin 配合 TickerMode 的行为，不要把它说成「页面不可见操作系统就会让动画暂停」。不 dispose Controller，可能留下仍在请求帧回调的 Ticker，持续消耗资源。这和 Widget 能不能 const 无关。

AnimatedBuilder 的 child 参数可以放不随动画变化的部分，避免每次 tick 都重建整棵子树。曲线用 CurvedAnimation 包一层，数值范围映射用 Tween.animate，多个动画可以用 Interval 编排。AnimationStatus 用来在 completed / dismissed 时做下一步。

隐式动画适合目标值变化，连续跟随手势进度或精确编排多个阶段时，显式 Controller 通常更合适。tag 相同的两个 Hero，飞行发生在 Overlay 的 shuttle 上，不用自己算两边的坐标。这不是把原来的 Element 重新挂到新页面上；要挪同一个 Element，用 GlobalKey。屏幕是 120Hz 时节拍更密，前提是设备真的在用这个刷新率。刷新率是否生效，依设备和平台配置而定。

25. 布局时，约束和尺寸怎么传

下面先讨论使用 BoxConstraints 的盒布局。约束是 min/max 宽高的允许范围，不一定等于父组件最终尺寸。Row 的主轴是横向，Column 的主轴是纵向；与主轴垂直的方向叫交叉轴。Sliver 使用另一套滚动布局协议，见第 34 题。

口述版

  • 盒布局使用 BoxConstraints 传递最小/最大宽高。父节点向下传约束，子节点在范围内确定尺寸，父节点最后决定子节点的位置。
  • 某一维的最小值等于最大值，称为紧约束，该维尺寸已经确定；最大值为无限称为无界，表示父节点没有提供有限上限，不是要求子节点把尺寸设成无限。
  • Expanded 要占满 Flex 分配的主轴空间；Flexible 默认 fit 为 loose，允许子节点比所分配空间更小，设为 tight 时同样要占满。两者必须遵守 Row、Column 或 Flex 的父数据要求。
  • 滚动视口通常需要滚动方向上的有限尺寸，再沿该方向给内容无界约束。Flex 在无界主轴上无法计算 Expanded 应分到多少剩余空间；需要由上层提供合理的有限约束。
  • shrinkWrap 让滚动组件按内容确定自身在滚动方向的尺寸，可能需要布局更多子项，滚动时也可能反复计算，不能当作没有成本的约束修复方式。
  • LayoutBuilder 根据收到的父级约束生成布局；IntrinsicHeight/IntrinsicWidth 查询孩子的固有尺寸，会增加测量成本。AspectRatio、FittedBox、ConstrainedBox 分别处理宽高比、缩放和附加约束。
  • 子节点尺寸必须满足约束。debug 会检查并报告多种违反布局协议的问题；release 去掉部分 assert，不代表违反约束的布局可以正常工作。

解析

BoxConstraints 是允许的尺寸范围，size 是子节点最终选定的尺寸，offset 是父节点安排的位置。三者不是同一个值。尺寸必须满足约束；debug 用 assert 检查部分违规，release 关闭检查后，错误布局仍然可能产生无效尺寸或后续异常。

import 'package:flutter/material.dart';

void main() => runApp(MaterialApp(home: Scaffold(
  body: Column(children: [
    const Text('标题'),
    Expanded(child: ListView.builder(
      itemCount: 100,
      itemBuilder: (context, index) => ListTile(title: Text('第 $index 项')),
    )),
  ]),
)));
// Scaffold 给 Column 有限高度，Expanded 把剩余高度给列表。
// 错误示例：移除 Expanded，只留下默认 shrinkWrap:false 的 ListView，
// debug 下会报告纵向 viewport 高度无界；不能依赖 release 抛同一错误。

Column 里放纵向 ListView，报无界高度，是因为列表还要一个有限的最大高度，外面沿滚动方向给不出这个上限。给列表一个有限高度，例如外包 Expanded，而且外层 Column 自己的高度也得有限。纵向滚动组件里面再放一个自己也要无限高的 ListView，是同一类无界。Expanded 必须放在 Flex 里；Flex 的主轴最大尺寸无限时，Expanded 报的才是无界约束。直接作为 ListView 子项时，其 FlexParentData 与实际父渲染对象不匹配，debug 常报 ParentDataWidget 用法错误；错误先后并非跨版本保证。

LayoutBuilder 拿到的是父级传下来的 BoxConstraints，适合按可用宽度切换布局。IntrinsicHeight / IntrinsicWidth 会查询孩子的固有尺寸（IntrinsicHeight 通常用最大固有高度），再据此施加约束并布局，孩子多或嵌套深时开销明显。AspectRatio、FittedBox、ConstrainedBox 都是在现有约束上再做一层换算，不改变「约束向下、尺寸向上」的协议。

子组件想自己决定在父组件里的位置，做不到。用 Align、Center、Positioned 这种父布局。能跳过子树布局，是因为约束和尺寸没有变，RenderObject 可以标记为不必重来。那是框架优化，协议本身不变。shrinkWrap 让滚动组件按孩子把自己的尺寸量出来，项很多时会一次布局很多孩子，不要拿它当默认解法。

26. Widget、Element、RenderObject、Layer 和一帧渲染

口述版

  • Widget 是不可变配置；Element 是树上持有当前 Widget 的节点，有状态的 Element 还保存 State。框架在匹配范围内按 runtimeType 和 key 决定更新旧节点还是创建新节点。
  • RenderObject 负责布局、记录绘图指令和命中测试。Widget 与 RenderObject 不是一一对应，许多 Widget 只组合其他组件。
  • Layer 把绘制内容组织为可合成的层。大多数 RenderObject 在已有层中绘制，部分节点按绘制和合成需要创建独立层；Layer 不等于一张离屏位图。
  • 完整更新顺序是 build 生成 Widget 配置，layout 确定尺寸和位置，paint 记录绘图指令，再由引擎合成和光栅化为像素。某帧可以复用未变化的构建、布局或绘制结果。
  • 重建不等于所有 RenderObject 重新创建，也不等于所有像素重新绘制。RepaintBoundary 建立独立重绘边界，减少相邻区域相互引发的重绘，同时增加层和内存成本。

解析

Widget 描述配置，Element 维护树节点及当前配置，RenderObject 执行布局和绘制，Layer 组织需要合成的绘制内容。更新时可以保留旧 Element 和 RenderObject，仅换上新配置；“重建”通常指重新执行 build，不必然表示销毁并重新创建节点。

这是三棵树的分工，不是编译优化。标脏就是把节点标记为需要更新，框架据此执行相应阶段。某一帧只处理需要更新的工作：没有人 markNeedsBuild，这一帧可以不 build；只有 markNeedsPaint，就只重画。配置没变的 RenderObject 在布局或绘制阶段里还可以再跳过自己。build 调用得很频繁，不等于整棵绘制树都重建，也不表示 Layer 和像素每次都全量重来。没有 Key 的列表只是换了顺序，同一层按位置和类型对上号，State 可能留在原来的格子上。框架不会按业务 id 认出列表项。

层不是按 Widget 类型一刀切的：RepaintBoundary 的 isRepaintBoundary 为 true，会单独成层；以本机 Flutter 3.41.6 为例，有孩子且 alpha 大于 0 的 RenderOpacity 使用合成层，alpha=255 时也可保留 OpacityLayer；全不透明时引擎可省去中间缓冲，不能据此推断框架没有层。RenderTransform 的纯平移可走偏移绘制，filterQuality 非空还可走 ImageFilterLayer；Clip 要看 clipBehavior 和合成需求。PlatformView 依平台与合成模式可能使用纹理或平台视图层，不能统一叫 TextureLayer。BackdropFilter、ShaderMask 也有各自的层路径。不要把「成层」说成只有某几个 Widget 才会发生。

某一小块经常重画，给它 RepaintBoundary。每一块都单独成层会多占内存，合成也更贵，不要到处包。BuildContext 也不是 Widget。

这里的 paint 主要记录绘图指令，raster（光栅化）才把指令变成像素。Layer 是组织合成的层，和“必须申请一张离屏位图”不是一回事；saveLayer 是画布上的离屏绘制操作，也不能与 Layer 对象一一对应。细节属于当前框架/引擎实现，不能当成 Dart 语言保证。

官方核对：Flutter 3.41.6 的 Opacity、Transform、Clip 实现。

27. 线程模型，以及高刷新率上怎么看掉帧

口述版

  • 传统引擎任务分为 Platform（平台消息）、UI（Dart 界面工作）、Raster（光栅化）和 IO（资源处理）。它们是任务职责，不保证对应四条独立系统线程；现代多个平台默认合并 UI 和 Platform 的执行线程。
  • 主 isolate 执行 build、layout 和 paint。Raster 处理绘制内容并配合 GPU 生成像素；它是 CPU 上的任务线程，旧文档称 GPU 线程也不表示它就是显卡。
  • 图片解码可能交给 IO 调度入口或引擎工作线程池，具体取决于阶段、格式和版本。后台 isolate 及 VM 辅助线程另算，Web 也不直接套用这套任务模型。
  • 刷新率决定帧间隔：60Hz 约 16.7 毫秒，120Hz 约 8.3 毫秒。UI 或 Raster 阶段超出持续供帧所需的时间，就可能错过屏幕刷新机会，表现为掉帧。
  • 在真机 profile 模式下用 DevTools 帧图判断耗时主要在构建、布局还是光栅化。debug 有额外检查和开发开销，不能用它的帧时间代替发布性能。
  • 着色器是 GPU 执行绘制效果的程序，运行时编译可能造成卡顿。Impeller 尽量提前准备这类程序以减少相关开销，但不保证消除所有掉帧。

解析

下面四格表示传统任务职责，不保证与四条系统线程一一对应。Web 不按 Platform、UI、Raster、IO 来分。先分清各自干什么，再看这一帧的时间花在 UI 还是花在光栅。不要把 isolate 和这四条线程说成同一套东西。

用 DevTools 的帧图区分是 build、layout 慢，还是画成像素这一步慢。测量用 profile。debug 本身更慢，不能当成正式包的帧时间。debug 不掉帧不能说明 release 没问题，反过来也一样。

第一次用到某种绘制效果，GPU 可能要临时编译着色器，卡在画像素这一步。Impeller 提前准备这些绘制程序，就是为了少做这种临时编译。着色器预编译、Impeller、光栅缓存，是引擎为了减少卡顿做的实现。它们不是「Dart 单线程所以不会掉帧」。60Hz 大约 16.7 毫秒一帧。Flutter 能跟上的前提是这一帧做完了，而且系统允许这个刷新率。

主 isolate 跑在界面线程上。再用 spawn 开出来的 isolate，不归这四条线程编制，框架也不替你统一管理。把 Raster 线程直接叫 GPU，容易让人以为卡在显卡上。掉帧不一定是 Dart 慢，也可能是光栅、着色器或图片解码。

默认 UI/Platform 合并节点：iOS/Android 为 Flutter 3.29，macOS/Windows 为 3.35，Linux 官方迁移说明为 3.39。旧版本、定制 Embedder 和配置可能不同。合并后主 isolate 的同步重活也会占住平台主线程；Raster、VM 辅助线程和后台 isolate 仍有自己的职责。

官方核对：macOS/Windows 线程合并。

官方核对：Linux 线程合并。

28. 什么时候自定义布局

口述版

  • 先用现有布局组件组合；只需要特殊绘制时用 CustomPaint，让现有布局决定绘制区域的尺寸。
  • 需要改变子节点的位置和约束时，可用 CustomSingleChildLayout 或 CustomMultiChildLayout；Flow 适合通过绘制变换安排孩子。需要自定义更底层的布局协议时，再实现 RenderObjectWidget 和 RenderObject。
  • RenderObjectWidget 保存配置并创建、更新 RenderObject；自定义 RenderBox 要在父级约束内确定自己的 size，按协议布局和定位孩子。自身在父级中的位置仍由父级决定。
  • 布局阶段计算尺寸和位置，paint 阶段记录绘制指令，不应在 paint 中修改布局结果。配置变化后，要按影响调用 markNeedsLayout 或 markNeedsPaint。
  • 命中测试决定指针是否落在交互区域；semantics 提供读屏所需的名称和行为；parentData 保存父布局附在孩子上的偏移等布局参数。自定义实现要处理自己负责的这些协议。
  • isRepaintBoundary 表示是否形成独立重绘边界。独立成层有机会减少相邻区域重画，也会增加内存和合成成本。

解析

组合布局是让现有组件执行测量和定位。CustomPaint 主要负责既定区域内的绘制。自定义 RenderObject 则需要直接遵守布局协议：接收约束、确定自身尺寸、布局孩子，并在必要时提供绘制、命中和辅助功能语义。

能用 Row、Column、Stack、Padding、CustomPaint 拼出来，不要写 RenderObject。继承一个 Widget 再重写 build，那是组合，不是自定义布局协议。不要在 paint 里偷偷改布局，下一轮约束会对不上。一上来写 RenderObject，通常是把能组合的东西复杂化了。

isRepaintBoundary 决定这块会不会单独成层。成层能少带动别人重画，也会增加内存和合成成本。它是取舍，不是写上就更快。

semantics 是给读屏等辅助功能的语义信息，不能只画出按钮却不说明用途。parentData 是父布局附在孩子上的布局数据（如偏移、flex），由对应父布局约定。CustomMultiChildLayout 适合自定义孩子位置，但它自身的尺寸不能依赖孩子的布局结果；这类需求才可能要自定义 RenderBox。

官方核对：Flow 在绘制阶段变换孩子位置。

29. 一次点击为什么只有一个组件响应

口述版

  • 指针按下时先做命中测试，确定指针位置命中了哪些节点。原始指针事件通常从内层向祖先派发，能收到原始事件不等于最终识别出点击。
  • GestureDetector 使用识别器判断点击、拖动等手势。对同一指针有竞争的识别器进入手势竞技场，由规则决定谁接受、谁拒绝该手势。
  • 普通父子点击识别器竞争时，通常内层识别器先加入并最终胜出，所以只触发一个最终 onTap；这不代表其他识别器从未收到事件或提前回调。
  • 移动超过拖动判定容差时，拖动识别器可能胜出，点击识别器被取消。手势团队等机制可以协作，不能说任何手势都永远只有一个响应者。
  • Listener 接收原始指针事件，不参加手势竞技场。HitTestBehavior 控制自身空白区域和后方目标能否命中，不负责改变父子点击识别器的胜负规则。

解析

命中测试判断指针位置对应哪些节点，手势识别判断这串按下、移动、抬起事件代表什么动作。多个识别器可能收到同一串原始事件，再通过竞技场确定接受或拒绝。因此收到指针事件与最终触发 onTap 是两件事。

竞技场处理胜负时，先声明接受的识别器，或其他识别器都拒绝后剩下的识别器会胜出；如果仍没有结果，竞技场的 sweep 收尾操作会选择第一个剩余候选者。命中路径从里向外加入，所以一般是更靠里的子组件。如果某个识别器更早声明接受或拒绝，例如滑动超过 slop，就按那个结果，不必等到抬起。手势阈值的具体像素依设备和手势设置而定，说出「超过一小段移动，拖动赢、点击取消」即可，不要背死一个魔法数字。

父组件只是想知道手指在自己范围内动过，用 Listener，不要再加一个 onTap 去和子组件抢。透明区域也要点中自己，用 behavior: HitTestBehavior.opaque。不是父组件收不到指针，而是 onTap 这种识别器在竞技场里输了。列表滑动把按钮点击取消，是竞争结果，不是点击事件丢失。

slop 是区分轻微抖动和拖动的移动容差。onTapDown 等回调可能在竞技场最终裁决前发生，输了还可能收到 onTapCancel，因此“最终一个 onTap 胜出”不等于其他识别器从未执行回调。opaque 让自身区域可命中并阻挡后方目标，translucent 允许后方目标也有机会命中；它们不改变父子 tap 竞技场的胜负规则。

官方核对：父子手势竞争与提前回调。

官方核对：手势竞技场的接受、拒绝和收尾规则。

30. Flutter 如何和 Android / iOS 通信

口述版

  • Platform Channel 在 Dart 和平台实现之间传异步消息。codec 把参数编码为字节、再在另一端还原，两边不直接共享同一个原生对象。
  • MethodChannel 用方法名和参数发起调用，取得一次成功结果、错误或未实现结果。EventChannel 把平台持续产生的事件转为 Dart Stream；BasicMessageChannel 按约定格式双向收发消息。
  • StandardMessageCodec 支持 null、布尔、数字、字符串、类型化数组、List 和 Map 等。自定义对象需要转换成支持的数据结构，或使用双方一致的自定义编码。
  • Dart 侧通常在根 isolate 收发；完成注册的后台 isolate 可以发请求并收回复，但不能任意监听平台主动推送的消息。原生 handler 默认在平台主线程执行，通道不会自动把耗时工作搬到后台。
  • 平台 TaskQueue 可让 handler 在后台执行；访问原生 UI 时仍需满足主线程要求。dart:ffi 直接调用兼容 C 接口的原生函数，省去通道编解码，但需要正确处理调用约定和内存生命周期。
  • Pigeon 根据接口定义生成两端的类型化通信代码，底层仍使用平台通道。PlatformView 用于把原生视图嵌入 Flutter 界面，需要管理平台视图的生命周期与合成成本。

解析

平台通道先把数据编码为消息，再交给另一端处理，结果也通过消息返回。FFI 则按原生函数的参数和返回值规则调用兼容 C 接口的函数。前者需要约定编码格式，后者需要正确匹配原生类型、调用约定和内存生命周期。

import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

void main() => runApp(const MaterialApp(home: SettingsPage()));
class SettingsPage extends StatefulWidget {
  const SettingsPage({super.key});
  @override
  State<SettingsPage> createState() => _SettingsState();
}
class _SettingsState extends State<SettingsPage> {
  static const channel = MethodChannel('app/settings');
  String text = '点击读取';
  Future<void> readName() async {
    String next;
    try {
      next = await channel.invokeMethod<String>('getName') ?? '未设置';
    } on MissingPluginException {
      next = '尚未实现原生 getName';
    } on PlatformException catch (e) {
      next = '平台错误：${e.code}';
    }
    if (!mounted) return;
    setState(() { text = next; });
  }
  @override
  Widget build(BuildContext context) => Scaffold(body: Center(
    child: TextButton(onPressed: readName, child: Text(text)),
  ));
}

消息会按 codec 编解码，这是通道的成本，不是编译器可有可无的一步。FFI 省掉的是这次消息编码与解码，换来的是你自己保证调用约定和对象生命周期。系统界面、Activity、权限等通常交给插件和 Channel；FFI 本身不是只能调用“非 UI”代码，但调用平台 API 时必须满足线程、ABI 和生命周期约束。热路径上的 C 库用 FFI，并自己管内存。少了一次编解码，不代表更简单。

Pigeon 根据 Dart 定义生成两端代码，方法名和参数类型在编译期就能对上，适合通道多、团队协作的场景；它底层仍然是 Platform Channel。PlatformView 把原生视图嵌进 Flutter 的层树，性能取决于平台实现和混合模式，页面销毁时要确认原生视图也释放。

默认 MethodChannel 的原生 handler 在平台主线程上执行。通道不会把一次耗时调用自动挪到后台。要在后台处理，创建 TaskQueue 再交给 MethodChannel；从那条线程碰 UI，再切回平台主线程。Result 可以异步提交，也可以在别的线程提交。具体插件内部用 Channel 还是 FFI，依实现而定，不要说每个插件都只用 MethodChannel。EventChannel 在 Dart 侧是 Stream，不是再包一个 MethodChannel 死循环。

上述是可运行的 Dart 调用端：未安装对应原生实现时，点击会显示“尚未实现原生 getName”，并不代表已经完成跨端通信。真实集成还需 Android/iOS 注册同名 app/settings 通道、处理 getName 并返回 String 或 null；类型不符还可能触发 Dart 类型错误。codec 是把值转成字节并还原的编码器；ABI 是原生函数的参数、返回值和调用约定。原生内存越界可能导致进程崩溃，不能指望 Dart catch 捕获。

官方核对：平台通道线程与后台 isolate 限制。

31. 包和插件有什么区别

口述版

  • package 是可被其他代码依赖的发布和复用单位，可以包含 Dart 代码、Flutter Widget 和资源等内容。
  • plugin 是一种 package，按 Flutter 插件约定提供平台实现和注册信息，让应用通过 Dart 接口使用相应能力。插件可以支持一个或多个平台。
  • Platform Channel 和 FFI 是插件可采用的通信方式，具体取决于实现。应用工程里出现通道代码，不代表它已经被封装为可复用插件。
  • federated plugin 把面向应用的 API、平台接口和各平台实现拆为不同角色，通常分别发布为多个包。应用主要依赖面向应用的包，由它接入对应平台实现。

解析

包是依赖和发布的单位，插件是遵守 Flutter 平台集成约定的一类包。插件通常提供 Dart API 和对应平台的实现、注册信息；包也能包含 Widget 或资源，不是只有纯 Dart 工具函数才算包。

有 Channel 代码，不等于已经做成了可复用插件。它可能只是写在当前应用工程里。通道或 FFI 是插件内部的通信手段。选哪一种依插件作者而定，不是「插件」这三个字保证了只用某一种通道。业务侧只依赖它的 Dart 接口。

federated plugin 把接口和实现拆开：通常由 xxx_platform_interface 包声明各平台必须实现的接口（可借助 plugin_platform_interface 工具包），xxx_android/xxx_ios 等实现，面向应用的 xxx 包转发调用。应用通常依赖面向应用的包，不是直接依赖 platform_interface。默认平台实现和被面向应用的包正式推荐的实现（endorsed）由 pubspec.yaml 的 plugin 配置声明，具体发现方式依 Flutter 版本和工具链而定。

官方核对：联邦插件的三种角色。

32. 混合栈怎么组织

口述版

  • 混合栈同时管理原生页面和 Flutter 路由。原生容器负责承载 Flutter 界面，两套导航需要同步当前页面、返回操作、可见性、输入和生命周期。
  • FlutterEngine 是运行 Flutter 内容的引擎实例，原生页面容器负责展示它。页面被盖住与引擎停止执行不是同一件事，绘制、动画、定时器和订阅需要分别管理。
  • 复用同一个已启动引擎可以减少重复启动成本，但 Dart 状态和导航栈通常延续，需要显式管理重置；引擎与宿主的绑定还必须遵守平台规则。
  • 多个引擎各自拥有根 isolate 和导航状态，隔离更明确，但内存、启动和插件注册成本更高；进程内的原生资源仍可能共享。
  • FlutterEngineGroup 创建多个引擎并共享可复用的底层资源；FlutterEngineCache 在 Android 中按标识保存已有引擎。共享资源与复用同一个引擎是不同机制。
  • flutter_boost 是协调原生容器和 Flutter 路由的可选第三方方案。全部页面由 Flutter 管理时，通常直接使用 Flutter 导航即可。

解析

混合栈里，原生页面是外层容器，Flutter 页面画在容器里。两边要同时知道谁在栈顶、谁该接收触摸、谁被盖住之后还要不要继续画、定时器还要不要跑。没有「混合栈自动正确」这层保证。

新项目 Android 和 iOS 都用 Flutter 写，用 Navigator，不引入 flutter_boost。已有原生壳、逐页替换，才做混合栈。最容易错的是生命周期：原生页面盖住 Flutter 页面时，Flutter 还在不在画，引擎里的定时器还在不在跑。混合栈最难的通常不是把页面打开，而是盖住之后绘制和定时器有没有停。

flutter_boost 能继续用原生导航，旧页面可以慢慢换。容器怎么复用、内存、插件初始化和两边栈的同步，都要额外维护。官方 add-to-app 怎么复用引擎，依 Flutter 版本而定，不要把某个第三方库的内部实现说成框架保证。一个引擎被多个原生页共用，不是天然安全。

Android/iOS 上 FlutterEngineGroup 让多个引擎共享可复用的底层资源，比各自冷启动快，内存也更省；每个引擎仍然是独立的 isolate 和 Navigator。FlutterEngineCache 在 Android 上按 id 缓存已经启动的引擎，新页面直接进入预热好的引擎。复用的代价是状态：上一个页面的 Navigator 栈、全局变量和订阅还在，要么明确重置，要么按页面划分引擎。

共享同一引擎意味着 Dart 根 isolate、导航和全局状态通常延续；多个引擎则各有根 isolate，但原生插件单例或进程资源仍可能共享。一个引擎不能无条件同时绑定多个普通宿主页面显示，必须按平台 attachment 规则切换。flutter_boost 是可选第三方方案，现有导航和团队维护能力也影响是否采用。

官方核对：Android/iOS 的多引擎与 EngineGroup。

33. 构建模式和多端产物

口述版

  • debug 用于开发和调试，保留 assert 等检查并支持调试工具。手机和桌面使用 JIT，支持热重载；该模式的包体积和帧时间不能代表发布结果。
  • profile 用于性能测量，手机和桌面使用 AOT，关闭 assert 并保留性能分析能力；Web profile 使用自己的编译路径，不是生成原生机器码。
  • release 用于发布，手机和桌面提前编译为机器码，关闭 assert，并通过 tree shaking 删除从有效入口不可达的 Dart 代码。原生回调等额外入口需要按规则保留。
  • release 不会自动开启 Dart 混淆。受支持目标可用 --obfuscate 配合 --split-debug-info，保存符号文件以便还原错误堆栈；签名由平台和工程配置决定。
  • Android 常见产物为 APK/AAB，iOS 通过归档和导出生成分发包，桌面生成各平台应用。Web 生成静态资源，代码编译为 JavaScript 或 Wasm，不使用移动端的机器码 AOT 描述，也不提供 release 热重载。

解析

构建模式决定编译优化、检查和调试能力，目标平台决定最终应用的包装形式。手机和桌面的 debug 使用 JIT，profile/release 使用 AOT；Web 有不同编译路径，不能把一端的编译方式直接套给另一端。

tree shaking 是根据 main、保留入口等的可达性删除不可达的 Dart 代码；原生回调入口等可能要用 pragma 保留，不能简单按源码中是否调用判断，影响的是产物体积。debug 是边运行边编译，不会做同样的删除。debug 帧时间不能当成正式包，是因为 JIT、assert 还在，以及额外检查，不是因为少做了 tree shaking。混淆 --obfuscate 要单独打开。release 不等于已打开混淆，也不等于未签名。Android/iOS 构建可根据工程配置自动签名，能否上架还要核对分发证书和渠道要求。着色器和启动时间也要在 profile 或真机 release 上看。debug 流畅，不能说明 release 没问题，反过来也一样。

上面说的 JIT / AOT 指手机和桌面这套 Dart 编译。Web 的 release 是编译成 JavaScript 或 Wasm，同样不能热重载，不要说成机器码 AOT。

官方核对：构建模式与 Web 差异。

七、性能

34. 怎样减少重建、长列表卡顿和大图开销

口述版

  • 先用真机 profile 和 DevTools 确定瓶颈：build 是生成配置，layout 是测量和定位，raster 是生成像素。根据实际耗时选择优化方式。
  • 减少无关重建：把状态和订阅放在真正变化的组件中，复用不变的 Widget。const 要求常量参数，相同实例可跳过父级引发的配置更新，但自身状态和依赖变化仍可重建。
  • 长列表用 ListView.builder 按需创建 Widget。统一主轴尺寸时可用 itemExtent 或 prototypeItem，让列表直接计算子项位置；大量子项使用 shrinkWrap 可能增加布局开销。
  • 需要跨重排保留节点身份时，给直接匹配的子项设置稳定、同级唯一的 Key，并按需提供 findChildIndexCallback。组合不同滚动内容可用 CustomScrollView 和 Sliver。
  • RepaintBoundary 可以隔离部分重绘，需结合测量使用。cacheWidth/cacheHeight 请求按目标物理像素尺寸解码，物理尺寸由逻辑尺寸乘 devicePixelRatio 得到；Web 网络图片不支持这两个解码参数。
  • precacheImage 可提前加载图片，不能保证图片永久留在缓存中。CPU 密集计算可交给后台 isolate；Controller、Timer、订阅在不再使用时应释放或取消，避免持续工作和内存占用。

解析

build 耗时长，需要检查配置生成、业务计算和子树更新范围；layout 耗时长，需要检查测量次数和布局结构；raster 耗时长，需要检查绘制效果、图层与图片像素等开销。它们是排查方向，具体原因要以性能记录为准。

父组件重新 build 时，相同子 Widget 实例可跳过本次配置更新；不是保证整棵子树永远不 build。即使不能 const，也可复用已保存的不变 Widget 实例。在 build 里写 UniqueKey()，会让项的 State 每次都被丢掉，列表更抖。

ListView(children:) 在父组件 build 时就把子 Widget 都放进列表，项一多，这份列表本身就占内存。Element 和 RenderObject 仍然是滑到缓存范围才挂上。ListView.builder 连 Widget 也留到要显示时再造。shrinkWrap 才会为了算出自己的尺寸，一次布局很多孩子。

RepaintBoundary 能让滚动条、动画图标单独重画。每一块都是单独的一层，划得太多会多占内存，合并图层也更贵。不要在 build 里把整张原图读进内存。cacheWidth 和 cacheHeight 请求的解码尺寸单位是物理像素；Flutter Web 的网络图片会忽略这两个解码尺寸参数，其他端还受图片格式/codec 影响。解码参数以物理像素计；若直接传入逻辑宽度，解码宽度就会比目标物理宽度少 devicePixelRatio 倍，可能降低清晰度。上传前先压缩、缩小；大文件分段传，并带上进度、取消和重试。在非 Web 端，测量确认耗时的压缩和哈希计算可放到另一个 isolate，进度再用 Stream 或状态管理送回界面那条。

itemExtent 告诉列表每一项多高，滚动条和跳转就不用逐项测量，代价是高度必须真的固定。prototypeItem 测出一个统一主轴尺寸并应用于所有项，不是为不同类型各测一次。它与 itemExtent 不应同时配置；横向列表这里指定的是宽度。Sliver 让头部、列表、吸顶和嵌套滚动各自管理布局，CustomScrollView 再组合它们，比在 ListView 里套 SingleChildScrollView 更容易控制。预加载要分批，别一次预加载太多。

先换状态管理库，通常解决不了靠近根节点的大范围 setState 或大图解码。测量本身要用 profile。debug 的帧时间不是正式包的结果，这是构建模式的差别。

Sliver 是按滚动视口协议布局的一段内容，例如列表或吸顶标题；CustomScrollView 组合这些段落。precacheImage 是提前加载并尝试放入图片缓存，不保证长期驻留，缓存淘汰后仍可能重新加载。decode 尺寸优化不替代网络下载尺寸优化。后台 isolate 也有启动/通信成本，只搬走测量确认会阻塞界面的 CPU 重活；Web 的 compute 限制见第 10 题。
