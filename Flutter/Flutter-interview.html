一、Dart

1. var、Object、dynamic，以及空安全

口述版

var x = 1 推断成 int 之后类型就定了，还能再赋另一个 int，它不是常量。Object 是非空的公共父类型，只能直接调 Object 的成员，要装 null 写成 Object?。dynamic 几乎不做编译期检查，也可以是 null，调用错了运行时才抛。T? 表示可以是 null；! 是断言不是 null，是 null 就抛。late 推迟到读取前赋值，没赋就读抛 LateInitializationError。本地变量判空之后被当成非空，这是静态分析，字段多数时候不提升。能确定类型就不要用 dynamic。

解析

这道题问的是编译器在这个名字上知道多少，以及 null 能不能混进来。推断完成后类型就锁住了，锁的是类型，不是这一次的值。

var x = 1;          // 静态类型是 int，之后只能再赋 int
Object obj = x;     // 只能直接调 Object 的成员
dynamic raw = json; // 成员检查推迟到运行时，也可以是 null
String? name;
final text = name!; // 是 null 就抛，不是把对象改成非空类型

本地变量写过 if (value != null) 之后，花括号里的 value 会被提升成非空，一般不必再写 !。这是类型系统的流分析，不是运行时把对象变了。类的字段很多时候不会自动提升。Dart 3.2 起，一部分私有、非外部字段可以提升，依版本而定，不要说成所有字段都会提升。

late 用在字段要等一会儿才有、但读取前一定赋过的地方。只能赋一次再写成 late final。分析器警告是开发工具，不是另一套语言规则。dynamic 也不会让程序跑得更快。

追问

  • 结构暂时不定，例如一块原始 JSON，怎么写？局部用 dynamic，尽快收成具体类型。只知道是个对象、还要拦住乱调用，用 Object 或更具体的类型，调用子类方法前先判断或转换。
  • Object 和 dynamic 都能装别的对象，差别在哪？Object 仍做静态检查。dynamic 连 null 都收，任何调用都编译得过。
  • ! 是把类型变成非空吗？不是。它是「我断言当前值不是 null，错了就抛」。

2. const 和 final 的区别

口述版

final 在运行时赋值一次，之后这个变量不能再指向别的对象。对象如果可变，里面仍能改，例如 final list = <int>[] 之后还能 add。const 必须在编译期算出来，用 const 造出的对象深度不可变，相同常量在同一个 isolate 里会规范化成同一个对象。实例字段不能写 const，类常量写成 static const。类有 const 构造，调用时不写 const，得到的仍是普通新实例。父组件重新 build 时，子 Widget 若还是同一个对象，Element.updateChild 就不再向下更新这棵子树，这是框架行为，不是语言保证 build 不会被调用。

解析

final 锁的是绑定：这个名字不能再指向别处。房间里的东西仍可能搬动。const 做的是编译期常量，真正用 const 造出来的对象深度不可变，而且会规范化。

final list = <int>[];
list.add(1);                 // 可以。锁的是绑定，不是列表内容
const a = [1];
const b = [1];               // 同一个 isolate 里 a 和 b 是同一个对象
// a.add(2);                 // 运行时失败，常量深度不可变

class Box {
  static const zero = 0;     // 实例字段不能写 const
  final int n;
  const Box(this.n);
}
final box = Box(1);          // 有 const 构造，调用时不写 const，仍是普通新实例

const 构造函数要求字段都是 final，调用时传入的参数也必须是编译期常量。带函数体的工厂不能是编译期常量构造，那是另一题。跨 isolate 发消息时对象通常会被拷贝，不能把 const 身份当成进程里全局唯一。

Flutter 里父组件重新 build 时，子 Widget 若仍是同一个对象，框架就不再向下更新这棵子树。这是 Element.updateChild 的行为，不是 const 有魔法跳过 build。构造参数里每次都 new 一个新对象，就写不成 const，这条捷径也不会发生。

追问

  • 只是不想改字段指向，列表内容还要变，写哪个？final。不要写成 const。
  • 值要到运行时才知道呢？final。编译期就知道、并且希望当常量复用，才用 const。
  • const 是「运行时不可变对象」的同义词吗？不是。final 也能让字段不再换指向，但它不是编译期常量，也不会规范化。

3. Dart 是值传递还是引用传递

口述版

Dart 的参数按值传递，传走的值是对象引用的一份拷贝。参数和调用方的变量不是同一个变量，也不是 C++ 那种别名。函数里改对象的字段，调用方看得到，因为两份引用指向同一个对象。函数里给参数重新赋值，只改这个局部变量，调用方的变量不变。所以 list.add(1) 调用方能看到，list = [] 调用方看不到。想让调用方改去指另一个对象，就把新对象 return 出去。

解析

参数是函数自己的一个新变量，里面拷了一份地址。你拿这个地址去改房间里的东西，外面看得到；你让这个新变量改去指另一间房，外面那个变量不动。

void grow(List<int> list) { list.add(1); }   // 调用方看得到
void reset(List<int> list) { list = []; }    // 调用方看不到

这是语言保证：没有 C++ 那种「外面那个变量的别名」。编译器可能内联、可能省略一些拷贝，但不会把「给参数重新赋值」变成修改调用方的变量。想避免被外面改到，传不可变对象，或者在边界上拷一份。

追问

  • 对象能被改，所以是引用传递？不准确。传递的是引用的值。函数参数和外面的变量不是同一个变量。
  • 希望调用方的变量改去指另一个对象，怎么做？不要给参数重新赋值，让函数把新对象 return 出去。

4. extends、implements 和 mixin

口述版

extends 是单继承：子类复用父类的实现，并且是父类的子类型，还要接上父类构造。implements 不复用实现，接口上的成员要自己写全；每个类本身就是自己的接口，也可以同时实现多个。mixin 用 with 把一份现成实现混进类里，可以有字段和方法，不能写生成构造函数。on 限制只有指定类型的子类才能混入。多个 mixin 有同名成员时，with 里靠后的覆盖靠前的，由线性化决定落到哪一份实现，不是叠在一起执行。Dart 3 的 interface 是库外只能实现、不能继承，base 相反，final 是库外既不能继承也不能实现，sealed 是子类必须写在同一个库里。需要子类型关系并且要父类实现，才 extends；只复用一段行为，用 mixin 或组合。

解析

Dart 仍然只能 extends 一个类。要复用的是「实现加上是一个什么类型」，用继承；只是一份契约，用 implements；一段可以拼上去的行为，用 mixin。

class Animal { void breathe() {} }
class Dog extends Animal implements Runnable {}
mixin Walk on Animal { void go() => breathe(); }
class Cat extends Animal with Walk {}

mixin 不能有生成构造函数，所以不会出现多个父类构造对不上。on 限制宿主，mixin 里面可以调用这个宿主类型的成员。调用最后落到哪一份实现，由类型关系和 mixin 的线性化决定，不是编译器随便挑一个更快的版本。

Dart 3 还可以限制库外的人怎么用这个类，这是语言规则，不是 lint。mixin class 既能当类，也能当 mixin。只是复用代码、不需要类型关系时，优先考虑组合。

追问

  • mixin 是多重继承吗？不是。类仍然只能 extends 一个父类。mixin 是一份现成实现，不是为了变成多个父类。
  • mixin 只能有方法吗？不是。也可以有字段。它只是不能有生成构造函数。
  • 同名方法会不会都执行？不会。with 后面靠后的覆盖靠前的。

5. extension 是干什么的

口述版

extension 给已经有的类型加方法或 getter，不用改原类，也不用继承。调哪一个在编译期就定了，看的是变量写出来的类型，所以 dynamic 上调不到。类型自己的同名成员优先，扩展里不能加字段，也就不能存状态。扩展所在的库要 import 才看得到。它适合不加状态的工具方法；要保存数据，或者希望子类改写，用类或 mixin。

解析

扩展像贴在静态类型上的一层便利贴。编译器看变量写出来的类型，决定用哪一张。运行时对象实际是子类，也不会因此改选另一张。

extension StringX on String {
  bool get isBlank => trim().isEmpty;
}
String name = '  ';
name.isBlank;              // 编译期按 String 选定
dynamic raw = name;
// raw.isBlank;            // 静态类型是 dynamic，看不见扩展

扩展不能覆盖类型已有的成员，也不能加实例字段。两个扩展撞名时，可以 hide 其中一个，或写成 扩展名(对象).方法()。没导入就当没有。

编译器可能把这次调用内联掉。那是优化，不改变「按写出来的类型选定」这个规则。调用看起来像实例方法，其实不是运行时按对象的真实类型分发。

追问

  • 调用方手里可能是 dynamic，还能依赖扩展吗？不能。编译器不知道有这张便利贴。
  • 扩展能盖掉类里已经有的同名方法吗？不能。类型自己的成员优先，扩展不是 override。
  • 要保存数据，或者希望子类改写呢？用类或 mixin，不要用扩展。

6. 工厂构造函数和普通构造函数

口述版

生成构造函数每次都会创建当前这个类的新实例，不能返回另一个对象。factory 的函数体必须 return 一个这个类型能接受的对象，所以可以返回已有实例，也可以返回子类型。带函数体的 factory 不能是编译期常量构造；重定向形式的 const factory 可以。名字叫 fromJson 不表示它是工厂，没有 factory 关键字就仍然会新建当前类。只是把字段填进一个新对象，用命名构造；要返回已有实例或子类型，才用工厂。

解析

普通构造函数是车间，每次开工必出一台当前型号的新机器。工厂构造函数是前台：可以给你仓库里那一台，也可以给你一台子型号。调用方的静态类型仍然可以是父类。

class User {
  User(this.name);
  User.fromJson(Map<String, Object?> json) : name = json['name'] as String;
  factory User.cached(String name) => _cache.putIfAbsent(name, () => User(name));
  final String name;
}

生成构造函数用初始化列表和函数体，不能返回另一个实例。factory 必须返回一个这个类型能接受的对象。工厂不是一项性能优化，也不是「更快的 new」。它只是放宽「必须新造当前类」。

对象在编译期就要定死，用 const 生成构造。不能 const 的是带函数体的工厂；重定向的 const factory 是语言允许的，不要说成所有 factory 都不能 const。

追问

  • fromJson 是不是天然的工厂？不是。没写 factory，就仍然会新建当前类。
  • 工厂返回子类时，调用方看到的类型是什么？静态类型仍然可以是父类，运行时拿到的是那个返回值。
  • 缓存和单例写在哪？写在 factory 里。名字不决定能不能缓存，factory 关键字才决定。

二、异步和并发

7. Future 和 async / await

口述版

Future 表示稍后会完成一次，结果是一个值或一个错误。async 函数一被调用就先返回这个 Future，函数体仍在当前 isolate 上，不会因此并行。await 挂起的是当前这个异步函数剩下的代码：等的那个 Future 完成后，续体以微任务继续，比定时器和点击更优先。这次等待不会把 isolate 的事件循环堵住。Future(() {}) 的函数体进事件队列。很吃 CPU 的计算即使用 Future 包起来，计算的那一段仍在当前 isolate 上执行，要放到另一个 isolate。

解析

Future 是一张回执，成功或失败只会来一次。async 函数一被调用，就先把回执递给你。await 是把这个函数剩下的活挂起来，回执到了再继续。一个 async 函数里可以没有 await，也可以有多个。

Future<int> load() async {
  try {
    return await fetch();     // 错误发生在 await 上，try/catch 接得住
  } catch (e) {
    return 0;
  }
}
final pending = fetch();     // 没 await，旁边的 try/catch 接不住

Future 完成后的续体进微任务，比点击、定时器这些事件更优先。scheduleMicrotask 和 Future.microtask 也进微任务。网络和文件回调进事件队列。这是运行时的事件循环规则，不是编译器把异步优化成同步。Future 不会因为你多包一层就变成并行。

追问

  • await 会把线程堵住吗？不会。挂起的是当前这个异步函数剩下的代码，isolate 可以先去干别的。
  • 拿到 Future 但没有 await，错误怎么接？try/catch 接不住。用 catchError，或者继续把这个 Future 交给调用方。
  • 很吃 CPU 的计算包一层 Future 就行吗？不行。真正计算的那一段仍占着当前 isolate，要放到另一个 isolate。

8. Future 和 Stream 有什么不一样

口述版

Future 完成后只有一个结果，完成之后再 await 或 then 仍能拿到它。Stream 是一串事件，可以有多次数据和多次错误，最后有一次结束。单订阅流只能 listen 一次，再听会报错，适合读完就结束的数据。广播流可以同时有多个监听者，后订阅的拿不到订阅之前已经发出的事件。async* 里 yield 一次就发出一个事件。await for 挂起的是当前这个异步函数，来一个事件执行一次循环，流结束循环就结束，不会把整条 isolate 堵住。页面 dispose 时要取消 StreamSubscription。

解析

Future 是一封信，拆开一次就结束。Stream 是一条水管，可以多次出水、多次报错，最后有一个结束信号。两者都在当前 isolate 上调度，都不是并行。

await for (final event in stream) {
  print(event);
  if (event == 'stop') break;   // 离开时取消这次订阅
}

async* 每 yield 一次就往外发一个事件。yield* 是把另一条流里的事件接着转出去。单订阅不能听第二次。广播可以多人听，但不补发过去的事件。await for 挂起的是当前这个异步函数，不会把整条 isolate 卡住。「await for 会把线程堵死」是老说法。

广播流上不要随便 await for。流不结束，这个函数就会一直停在循环里。广播流的缓冲策略、暂停时还丢不丢事件，依具体 Stream 实现而定，不要说成所有广播流行为完全一样。页面 dispose 之后订阅还在，是常见的 setState() called after dispose() 来源。

追问

  • 多个地方同时听网络状态，用哪一种？广播 Stream。后开始听的人拿不到历史事件。读文件这种读完就结束的数据用单订阅。
  • 单订阅流 listen 两次会怎样？报错，不是两个人各拿一份。
  • break 或页面销毁时要做什么？取消 StreamSubscription，关掉文件、socket 这类资源。

9. Dart 是不是单线程？事件循环怎么跑

口述版

同一个 isolate 上不会有两段 Dart 代码同时执行。整个进程可以有多个 isolate，所以不能把 Dart 说成进程里只有一条系统线程。当前这段同步代码跑完之后，先把微任务队列清空，再从事件队列取一个事件；这个事件做完，再清空期间新来的微任务。scheduleMicrotask、Future.microtask 和 Future 完成后的续体进微任务。Future(() {})、Timer、手势、网络和文件完成进事件队列。await 只挂起当前这个 async 函数，事件循环继续。同步死循环还没结束时，微任务也插不进来。微任务里如果不停再添加微任务，事件队列里的点击和下一帧就一直排不上。

解析

一个 isolate 是一条执行线加两个队列。微任务是插队的小纸条，事件队列是正常排队的点击、定时器和 I/O。

同一个 isolate 上不会有两段 Dart 代码同时执行。一个应用可以有多个 isolate，Dart VM 可以把它们安排到不同的系统线程上。没有的是「多个线程一起改同一块内存」。

想排在点击和定时器前面、又不能太重，用微任务。普通的稍后执行用 Future(() {}) 或 Timer，进事件队列。await 停住的是当前这个 async 函数，不是这条 isolate。

追问

  • 「Dart 是单线程」对不对？说得太满。准确说法是：一个 isolate 里是单执行流，进程里可以有多个 isolate。
  • await 会把事件循环冻住吗？不会。界面不会因为这一个等待被卡住。
  • 微任务饥饿是偶发优化问题吗？不是。微任务没清空，下一个事件就不会被取出来。这是调度规则。

10. Isolate 是什么，和 Future 有什么区别

口述版

每个 isolate 有自己的堆和事件循环，彼此不共享堆，所以不能直接改另一个 isolate 里的对象，也不用为共享内存加锁。VM 可以把不同 isolate 安排到不同的系统线程上。Future 只是当前 isolate 的事件循环上稍后才有的一个结果，不会并行。通信用 SendPort 发、ReceivePort 收，消息默认拷贝一份。TransferableTypedData 是把那块内存的所有权移交过去，交出去之后原来的 isolate 不能再使用。一次算完拿回结果用 compute 或 Isolate.run，要一直待在后台收消息用 Isolate.spawn。引擎的界面、画像素、平台、文件线程不是 isolate。只是等 I/O，用 Future 就够。Web 上的实现通常接近 Worker，不要假设和手机完全相同。

解析

Isolate 是一间自己带桌子和信箱的房间。每间房有自己的内存和事件循环，不能伸手改另一间房的对象，只能寄信。这是 actor 模型，不是编译器可选的优化。

VM 上 isolate 可以被安排到不同系统线程。Web 上通常接近 Worker。Flutter 引擎另外有界面、画像素、平台、文件这几条线程，它们不是 isolate。主 isolate 跑在界面线程上；你 spawn 出来的 isolate 不归这套线程编制。

只是等 I/O，再包进 isolate 多的是启动和拷贝，不是并行收益。全局变量也是各有一份，不是加锁就能一起改。「Dart 没有多线程」不准确。没有的是多个线程共享同一块内存这种写法。

追问

  • 网络请求要不要丢进 isolate？不用。Future 在等待时不占 CPU。吃 CPU 的大 JSON、压图、加密才值得另开 isolate。
  • TransferableTypedData 是共享内存吗？不是。交出去之后，原来的 isolate 不能再使用这块内存。
  • 引擎那四条线程是 isolate 吗？不是。主 isolate 跑在界面线程上，spawn 出来的 isolate 不归这套编制。

三、框架入门

11. Flutter 和原生开发的差别

口述版

Flutter 的普通界面是自绘：不创建系统控件，由引擎里的 Skia 或 Impeller 把这一帧画成像素，用哪个看版本和平台。写法是声明式，业务代码描述这份数据下界面长什么样，框架用新的 Widget 配置去更新已有的 Element 和 RenderObject，不是拿到一个 Android 的 TextView 再改文字。同一套 Dart 界面因此在各端更一致。手机和桌面的 debug 是 JIT，才能热重载；release 是 AOT，没有热重载。系统能力用插件和 Platform Channel；地图、网页可以用 PlatformView 嵌一块原生视图，那一块就不是自绘。安装包通常更大。流畅不是语言保证，它依赖 AOT、这条自绘管线，以及没有在界面线程上做重活。

解析

先看界面是自己画出来的，还是把系统控件拼起来的。Flutter 交出去的是「这一帧界面应该长什么样」。自绘和声明式更新是架构，不是某次编译碰巧这么做。

对照着看：原生直接用系统控件；React Native 把组件映射成系统控件，再用桥和 JavaScript 通信，各端更容易长得不一样。Flutter 的系统能力靠插件和 Platform Channel，必要时用 PlatformView 嵌一块原生视图。桌面小组件、很深的系统接口仍然要原生配合。

热重载只存在于 debug 的 JIT，是开发期工具，不是它比原生快的原因。release 的 AOT 是发布构建，没有热重载。画像素的库是 Skia 或 Impeller，较新稳定版在 iOS 和 Android 上 Impeller 常常是默认，其他平台可能仍是 Skia，不要说死成某一个。「流畅程度通常接近原生」依赖 AOT、自绘管线，以及没有在界面线程上做重活，不是语言保证。

追问

  • Flutter 是不是永远碰不到原生视图？不是。地图、网页这类可以用 PlatformView 嵌进来，那一块就不是自绘。
  • 热重载是它比原生快的原因吗？不是。那只在开发期的 debug。
  • 画像素是不是一定用 Skia？不是。Impeller 是否默认，看 Flutter 版本和目标平台。

12. Flutter 的整体架构

口述版

Flutter 自下而上是 Embedder、Engine、Framework。Embedder 对接窗口、线程、系统事件和插件。Engine 主要是 C++，包含 Dart 运行时和图形，通过 dart:ui 交给上层，画像素用 Skia 或 Impeller。Framework 用 Dart 写绘制、手势、渲染、Widget 和 Material。线程是 Embedder 建的，引擎活着的时候不能换。业务代码导入的是 material，不是整个引擎。

解析

从贴着操作系统的一层，问到贴着业务代码的一层。

Engine 自己不创建线程。线程由 Embedder 创建，并且在引擎活着的这段时间里不能把这些线程换掉。dart:ui 不是整个 Flutter SDK，不要说「写 App 时直接导入 dart:ui 就等于用了整套框架」。业务代码一般不直接对着 Engine 写。

追问

  • Framework 是 dart:ui 吗？不是。Material 和 Widget 在 Framework 里，dart:ui 只是交界。
  • 四条线程是 Engine new 出来的吗？不是。创建线程的是 Embedder。
  • Impeller 换掉 Skia，三层架构变了吗？没有。那是引擎里画像素库的实现，依版本和平台而定。

13. main 和 runApp 分别做什么

口述版

main 是 Dart 程序的入口。runApp 先确保 WidgetsFlutterBinding 已经初始化，再把传入的 Widget 挂成根，并调度第一帧。这次调用返回时，并没有同步把整棵界面画完。根通常是 MaterialApp 或 CupertinoApp。如果 runApp 之前就要用插件，先调用 WidgetsFlutterBinding.ensureInitialized()。热重载不会重新执行已经跑过的 main，改了启动逻辑要热重启。

解析

main 是开门，可以先做初始化，再调用 runApp。runApp 是把根 Widget 交给绑定层，Widget、Element、RenderObject 这三棵树和第一帧从这里排上日程。挂上不等于这一调用返回时像素已经画完。

void main() {
  WidgetsFlutterBinding.ensureInitialized(); // runApp 之前就要用插件时才需要
  runApp(const MyApp());
}

热重载不重跑已经执行过的 main，热重启会。这是开发期工具。release 没有热重载，不是框架在正式包里的行为。改了启动代码却看不到效果，不是 runApp 没执行过，而是热重载没有重跑 main。在绑定还没准备好时就用插件，会在 runApp 之前失败。

追问

  • runApp 返回时屏幕画完了吗？没有。它负责挂根并调度帧，不是同步把整棵界面画完。
  • 什么时候要 ensureInitialized？runApp 前面有 await 插件、绑定还没用过的时候。
  • 改了 main 热重载为什么没效果？热重载不会重新执行已经跑过的 main，要热重启。

14. Widget 有哪几类，为什么不能改

口述版

Widget 是不可变配置，框架拿新旧两份来比，所以 build 里会不断新建，它自己要轻。真正留在树上、可以复用的是 Element。StatelessWidget 没有单独的 State，界面由构造参数和它依赖的上层数据决定。StatefulWidget 通过 createState 创建 State，State 由 StatefulElement 保存；runtimeType 和 key 都没变、这个 Element 被复用时，State 还在。自己的字段变了，它不会自动重建，要 setState。父组件传入一份新配置，或者它 depend 过的 InheritedWidget 通知它，也会重建。InheritedWidget 用来让子孙登记依赖，RenderObjectWidget 用来配置 RenderObject，布局和绘制在 RenderObject 上，不在 Widget 上。

解析

Widget 是一张不能改的施工单，build 时会不断新开一张。Element 是树上的工位。StatefulWidget 把 State 交给 Element 保管，施工单换了，只要工位还在，State 就还在。

字段用 final 是语言层面锁住绑定。@immutable 是框架和分析器的约定。Widget 会被频繁新建，所以要轻，这是设计，不是某次渲染优化碰巧复用了 Widget。如果配置本身还能被改掉，框架就分不清这次 build 到底变了什么。不可变是为了比较。你仍然不该去改它。不可变的是配置，Element 和 State 是可变的。

StatelessWidget 也可以拿到会变化的数据，只是自己没有生命周期去订阅，变化来自父组件的新配置。数据变了却没刷新，不是 StatefulWidget 坏了，是没有 setState，也没有依赖通知。Widget 不只是控件，间距、主题、继承数据的包装也是 Widget。

追问

  • 没有要跨帧记住的本地状态，用哪个？StatelessWidget。要在这个节点活着期间记住字段、Controller、动画，用 StatefulWidget。
  • StatelessWidget 会被重建吗？会。父级给了新配置，或者它依赖的上层数据变了，它也会重建，只是没有 State 可以跨帧留着。
  • StatefulWidget 会自己发现字段变了就重建吗？不会。要 setState，或者用到的上层数据通知它。

15. State 的生命周期

口述版

顺序是 createState、initState、didChangeDependencies、build。initState 只在第一次挂到树上时调用一次，开头调用 super.initState()。这里不能调用 Theme.of、MediaQuery.of 这种会向上查找并登记依赖的方法，那些放 didChangeDependencies。父组件传入新 Widget、运行时类型和 key 都没变，走 didUpdateWidget；自己 setState 不走这里。暂时从树上拿下来是 deactivate，GlobalKey 换父节点时随后可能再挂回去，不要在这里释放资源。确定不会再挂回去才 dispose，先释放 Controller、Timer 和订阅，再调用 super.dispose()。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。打开新页面时，旧路由默认 maintainState 为 true，旧的 State 还挂在树上。应用进后台走 WidgetsBindingObserver，不是 deactivate。

解析

State 比单次 Widget 活得长。口袋还在，State 就在；口袋确定拆掉，才是 dispose。上面的调用顺序是框架保证，不是编译器优化。

build 里不改数据、不发请求、不订阅。didUpdateWidget 里比较 oldWidget 和 widget，换订阅、重启动画。父组件把 userId 换成另一个，只写在 initState 里，页面会继续显示旧用户。

异步回调回来先看 mounted。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。写在 dispose 里面的代码当时还能读到 true，不代表还能 setState。super.initState() 写在方法末尾是错的。末尾调用 super 的是 deactivate 和 dispose。

setState() called after dispose() 这类检查包在 assert 里，profile 和 release 会去掉 assert。State 已经和 Element 断开后再调用，常见版本会因为 element 已经是空而抛错。检查被拿掉，不表示这次调用变得合法。reassemble 是热重载这条开发期路径，正式包不会走它来更新你的 initState。热重载不会重跑 initState。

追问

  • push 新页面会 dispose 旧页面吗？不会。默认 maintainState 为 true，旧的 State 还挂在树上，也不会因此 deactivate。只有从栈里拿掉才会 dispose。
  • 应用进后台走哪个回调？WidgetsBindingObserver 的 AppLifecycleState。deactivate 只表示这个组件离开了树。
  • didChangeDependencies 里可以每次都重发请求吗？不要不比较就无条件重发。它在 initState 之后立刻会来一次，之后依赖变了还会再来。

16. setState 做了什么

口述版

setState 先同步执行回调，再对当前 Element 调用 markNeedsBuild。这次调用返回前不会把界面重画完，build 发生在这一帧的构建阶段，或排到下一帧。同一次事件循环里的多次标记合并成一次 build。重建从被标记的 Element 开始，重新描述它的子 Widget，不是整个应用。孩子里 runtimeType 和 key 都相同的 Element 会更新原节点，RenderObject 也不因此全部新建。所以要写在真正变化的那个 State 上，而且不能写在 build 里。

解析

setState 是 Flutter 框架的方法，不是 Dart 语言特性。回调同步执行，然后标记需要 build。

只有一小块在变，setState 写在那一块自己的 State 上。同一段点击处理里要改好几个字段，可以多次 setState，框架会合成一次 build，更好的写法是一次回调里改完。想让更小的区域听一个值，用 ValueListenableBuilder、Selector 或 Bloc 的 buildWhen。

新 Widget 和旧子节点按类型和 key 比较，对得上就更新原 Element。这是框架的复用，不是语言保证。build 里发现自己想 setState、发请求或订阅，是副作用放错地方了。build 一帧里可能走很多次。

追问

  • setState 是立即重建、立即重画吗？都不是。标记之后，build 等到这一帧的构建阶段，或排到下一帧。
  • 连续调用多次会 build 多次吗？同一段同步代码里不会。多次标记合并成一次 build。
  • 它会把整个应用都重建一遍吗？不会。但写在根上时，这棵子树的 build 都会跟着走。

17. BuildContext 是什么

口述版

BuildContext 由 Element 实现，每个 Element 一份，表示这个节点在 Element 树上的位置，不是 Widget，也不是全局单例。Theme.of、MediaQuery.of、Navigator.of，以及默认会监听的 Provider.of，都从当前 Element 向祖先查找最近的那个，并用 dependOnInheritedWidgetOfExactType 把当前 Element 登记为依赖者；之后 updateShouldNotify 为 true 时，重建的是这些依赖者。只查找、不 depend 的读法，当时能读到，之后变了不通知。查找走的是 Element 树。initState 里 context 已经有了，但还不能做这种查找并登记，要放到 didChangeDependencies 或 build。发请求和跳转不要放进 build。

解析

BuildContext 是 Element 对外露出的接口，一张位置凭证。查找走的是 Element 树，不是在 Widget 配置对象上递归。

要跟着主题、MediaQuery、Provider 变，在 didChangeDependencies 或 build 里用 of。只取一次当前值，用不登记的读法，并接受它不会再通知你。跳转、发请求、订阅放生命周期或点击回调。异步回来再用 context，先看 mounted。State 和 Element 断开之后，这张位置凭证不能再当树上的位置用。

initState 里禁止 depend 的检查，在 debug 下会用 assert 拦住。这是框架约束。release 拿掉 assert，不表示这个时机突然变得正确。State 通过 context 找到自己的 Element，context 不是 State 的别名。

追问

  • initState 里已经能拿到 context，就能 Theme.of 吗？不能。Element 已经挂上，但这里还不能做查找并登记。
  • Provider 的 read 之后还会刷新吗？不会。当时能读到，之后变了不通知。
  • 向上找的是 Widget 树吗？查找走的是 Element 树。

18. Key 有什么用

口述版

Key 用在 updateChildren 里：同一个父节点下，runtimeType 和 key 都相同，才复用原来的 Element。没有 Key 时按位置和运行时类型匹配。列表只是换了顺序，State 留在原来的下标上，不跟着数据项走。列表项用 ValueKey，按值的 == 比较。ObjectKey 用 identical，内容一样的两个新对象对不上。UniqueKey 每次构造都是新对象，写在 build 里旧 Element 不会被复用。本地 Key 只在同一个父节点的孩子之间比较。GlobalKey 登记在全局表里，同一个 key 整棵树只能挂一处；换父节点时可以把原来的 State 挪过去，也能拿到 currentState，不适合当日常状态管理。

解析

Key 解决的是同一次更新里，「这个父节点下面，哪个孩子还是上次那个孩子」。它不解决滑出屏幕后保不保活。

ObjectKey 用 identical，ValueKey 用 ==。这是这两个类自己的相等实现，不要记反。两个内容一样、但是新创建的对象，ObjectKey 对不上。UniqueKey 每次都是一个新身份，用来故意丢掉旧 State。写在 build 里，旧 State 每次都被丢掉。

列表每一项的 State 串了，给每一项加 ValueKey(item.id)，不是给整个 ListView 加一个 Key。本地 Key 只在同一个父组件的子组件之间比较。换了父组件还要留 State，才考虑 GlobalKey。GlobalKey 能在换父节点时把 State 挪过去，也能拿 currentState、currentContext、currentWidget，代价是全局登记。复用 Element 能少做销毁和创建，但 Key 本身不是一项渲染加速开关。

追问

  • ObjectKey 按内容 == 比较吗？不按。它用 identical。内容一样的两个新对象对不上。
  • 给 ListView 本身加 Key，能救每一项串位吗？不能。Key 要加在会重排的那些孩子上。
  • 只是想重置这个子树呢？换一个新 Key。不要在每次 build 里无意识地 UniqueKey()。

19. 滑出屏幕后，状态怎么留住

口述版

ListView、TabBarView、PageView 这类会懒构建的组件，子项离开缓存范围后会从树上卸掉，State 跟着 dispose。要留住，就让 State 混入 AutomaticKeepAliveClientMixin，wantKeepAlive 返回 true，并在 build 里先调用 super.build(context)。这一步才会向祖先登记不要销毁。登记之后，子节点离开缓存范围仍留在树上，只是不再显示。只记滚动位置用 PageStorageKey。wantKeepAlive 后来变成 false，要调用 updateKeepAlive()。这和 Key 的 updateChildren 匹配不是一件事。普通 Column 里的孩子本来就没有被懒构建卸掉。

解析

Key 管同一次更新里的身份，保活管滑出缓存范围之后还拆不拆工位。

class _TabState extends State<TabPage> with AutomaticKeepAliveClientMixin {
  @override
  bool get wantKeepAlive => true;

  @override
  Widget build(BuildContext context) {
    super.build(context);          // 不调用就不会登记
    return const Text('kept');
  }
}

保活是 AutomaticKeepAlive 和可滚动组件之间的约定。忘了 super.build(context)，wantKeepAlive 不会生效。列表的缓存范围、Tab 是否预加载相邻页，依组件和参数而定，不要说成「滑出一像素就一定 dispose」。保活不是让它继续画在屏幕上，只是离开缓存范围后仍留在树上。它用内存换「不要销毁」，包太多会更占内存，不是渲染优化开关。只需要滚动偏移时，用 PageStorageKey 就够。

追问

  • 保活和 Key 是一件事吗？不是。Key 管同一次更新里哪个孩子还是上次那个。保活管懒构建卸掉之后 State 还留不留。
  • 普通 Column 里滚出屏幕的孩子要 KeepAlive 吗？不用。它们根本没被懒构建卸掉。
  • wantKeepAlive 后来变成 false 呢？调用 updateKeepAlive()，否则框架还按旧值保留。

20. 热重载和热重启

口述版

热重载只在手机和桌面 debug 的 JIT 里有：把改过的库送进正在运行的 isolate，不重跑已经执行过的 main 和 initState，原来的 State 对象还在，然后走 reassemble 再 build。已经初始化的全局变量和静态字段、枚举形状、泛型签名、原生代码，这次更新换不掉。热重启会重新执行 main，State 重新创建，但不会把原生工程重新装一遍。改了插件、资源或原生代码，要完全重新启动进程。profile 和 release 是 AOT，没有热重载。

解析

热重载是在还活着的进程上打补丁，然后重新 build，口袋里的 State 尽量留着。热重启是把 main 再走一遍，口袋清空，但原生工程不重装。

手机和桌面的 debug 是 JIT，边运行边编译。profile 和 release 是 AOT，提前编译成机器码。这是工具链，不是 Dart 语法。热重载会找出改过的部分、送进正在运行的程序、再重建 Widget。它不是只把画面重画一遍，也不是把应用关掉再打开。改了 initState 没效果，是因为旧 State 还在，不是热重载失败。debug 能热重载，不能用来证明 release 的性能。

Web 的 release 是编译成 JavaScript 或 Wasm，不要把手机上的 JIT / AOT 原句套过去。Web 的 release 同样不能热重载。

追问

  • 只改了 build 里的界面，用哪一档？热重载。
  • 改了 initState 或 main 看不到效果呢？热重启。原来的 State 还在，初始化不会再跑。
  • 改了插件、资源或原生代码呢？完全重新启动。热重启不够。

四、状态、路由和动画

21. InheritedWidget 是干什么的

口述版

InheritedWidget 把数据放在祖先节点上。子组件调用 dependOnInheritedWidgetOfExactType，或 Theme、MediaQuery 的 of，或 Provider 的 watch，会找到最近的那一个，并把当前 Element 登记成那个 InheritedElement 的依赖者。祖先换成新的 InheritedWidget 之后，只有 updateShouldNotify 返回 true，框架才通知这些依赖者重建，不是把下面所有节点标脏。返回 false 时新配置会换上，已经登记的依赖者也不通知。只向上找、不登记的读法，例如 Provider 的 read，当时能读到，之后变了不重建。这种登记不能写在 initState，要放在 didChangeDependencies。

解析

数据放在比较靠上的位置之后，谁登记了依赖，谁才会因为这次通知而重建。没登记的人，只是当时读到了值。

通知本身不是把 InheritedWidget 下面的所有节点一律标脏。InheritedWidget 自己的 child 如果在父级重建时还是同一个 Widget 实例，子树可以走普通的 identical 跳过。如果父级每次都 new 一个新的 child，那是普通的父级重建，和「通知依赖者」不是同一条路径。

Provider 是 InheritedWidget 外面的写法。数据怎么顺着树传下去，根子还是 InheritedWidget。这是封装，不是另一套渲染机制。读的位置必须在 Provider 下面。沿树向上找不到，就不是「数据没刷新」。initState 里调用 of 是时机错了，不是 InheritedWidget 不能在第一帧读。

追问

  • 子组件要跟着这份数据变，用哪种读法？会登记依赖的 of 或 watch。回调里只取当前值，用 read。
  • InheritedWidget 是子树全部重建吗？不是。只重建登记过、并且 updateShouldNotify 为 true 时被通知的那些。
  • Provider 抛出找不到，先看什么？读取的位置是不是在 Provider 的下面。

22. 状态管理怎么选

口述版

先看状态放在哪、谁被通知、重建哪一段、要活多久。只在这个 State 的字段里，用 setState，它只把当前 Element 标成需要 build。还想把重建缩到一个值，用 ValueNotifier 和 ValueListenableBuilder。要沿 Element 树向下共享，用 InheritedWidget 或 Provider：watch 会 depend，read 不登记；读的位置必须在 Provider 下面。Riverpod 把状态放在独立的 Provider 容器里，不从 BuildContext 向上找；ref.watch 可以只订阅一个字段，没有监听者时可以释放。Cubit 在业务对象里用方法交出新状态；Bloc 再多一层事件，BlocBuilder 用 buildWhen 决定要不要重建，业务对象可以离开 Widget 测。GetX 常把状态、路由和依赖放在一起，这次重建是哪个响应式对象触发的，不如 markNeedsBuild 或 buildWhen 从调用点看得清。选型看这些边界，不是先报一个库名。

解析

setState 只标记当前 Element。InheritedWidget 只通知依赖者。这些重建范围是机制，不是换一个库就会自动变小。

「select 能少重建」依赖你真的只订阅了那个字段。父级如果整页 setState，下面的优化可能根本走不到。事件要按类型展开用 Bloc，只是几个方法改状态用 Cubit 就够。跨页面、不希望绑着 BuildContext、逻辑要单测，用 Riverpod 或 Bloc。团队已经统一某个库，先服从团队，再讲你知道的边界。

Provider 找不到，通常是读取的位置不在它下面。read 能拿到当前值，但之后变了也不会刷新。简单页面套一整套 Bloc，和复杂业务只靠一层层 setState，都是边界选错。性能问题先看是谁在重建，不要先换状态管理库。

追问

  • 还是局部，但父级 build 太重？把 State 拆小，或用 ValueListenableBuilder。
  • 要精细控制重建范围用什么？Selector、context.select、Riverpod 的 select、BlocBuilder 的 buildWhen。
  • GetX 的代价是什么？调用直接，但刷新从哪来不如 markNeedsBuild 或 buildWhen 好追。能说清这个再选。

23. Navigator 和 MaterialApp 做了什么

口述版

Navigator 管的是路由栈：打开、返回、替换，以及路由之间的转场，不是单个 Widget 的 State。MaterialApp 会放好主题和本地化，并创建一个 Navigator。Navigator.of(context) 从当前 Element 向上找最近的那个，嵌套时不一定是根上那个。直接 push 是匿名路由；pushNamed 用 routes 或 onGenerateRoute 按名字找页面。await push 的结果就是下一页 pop 时交回的值。A push B 时，A 默认 maintainState 为 true，这条路由的子树仍挂在树上，不会因此 deactivate 或 dispose，也不会重新走 initState。只有 A 被从栈里移出才会 dispose。上面还有别的路由时，旧路由是否还在 build，看具体 Route 和 TickerMode。深链和 Web 地址再用 go_router，它底下仍然落到页面栈上。不要在 build 里 push。

解析

Navigator 是一叠页面。push 是往上再放一张，下面那张通常还在，只是被挡住。pop 才从栈上拿走，拿走的那张才会 dispose。

final result = await Navigator.of(context).push(...);
Navigator.of(context).pop(result);

页面里直接打开下一页用 push。要统一路径、深链，用命名路由或 go_router。跳转放点击回调，或者放在导航条件已经确定之后。在 build 里 push，每次重建都会再打开一页。

路由动画、以及被盖住的页面是否还在继续 build，依具体 Route 和 TickerMode 而定。不要说成「被盖住就完全没有代码在跑」或「一定每帧都在 build」。go_router 是路由库，不是 Navigator 的替代运行时。栈不复杂时不必上。MaterialApp 不只是套一层视觉风格，它会把 Navigator 放好。

追问

  • 嵌套导航器时，Navigator.of 找到的是根上那个吗？不一定。它找的是最近的那个。
  • 下一页要把结果交回来怎么写？await Navigator.push，下一页 pop(result)。
  • 打开新页面时旧页面离开树了吗？默认没有。只有被从栈里拿掉才会 dispose。

24. 动画怎么做，vsync 是什么

口述版

某个属性只要从当前值过渡到新的目标值，用隐式动画，给出目标值和 duration，例如 AnimatedContainer。要开始、暂停、重复，或者跟着手势走，就自己持有 AnimationController。它默认的下限是 0、上限是 1，Tween 把这个进度映射成宽度或透明度，界面用 AnimatedBuilder 或 FadeTransition 订阅这个动画。vsync 的类型是 TickerProvider，一般由 State 的 mixin 提供。Ticker 注册的是调度器的帧回调，一帧回调一次，不是用 Timer 在两次刷新之间自己计时。一个动画用 SingleTickerProviderStateMixin，同时多个用 TickerProviderStateMixin。页面不可见，或者 TickerMode 关掉时，mixin 会让 Ticker 停。AnimationController 要在 dispose 里释放。两个页面上 tag 相同的 Hero，跳转时由框架把同一块元素从旧位置移到新位置。

解析

隐式动画是你只改终点和时长，框架开车。显式动画是你拿着一个 0 到 1 的进度，再映射成宽度或透明度。vsync 是屏幕每次刷新时的节拍，动画跟节拍走，不在两次刷新之间空转。

class _BoxState extends State<Box> with SingleTickerProviderStateMixin {
  late final AnimationController _controller = AnimationController(
    vsync: this,
    duration: const Duration(milliseconds: 300),
  );
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}

跟这个信号走的计时器叫 Ticker。一个 State 只有一个动画，用 SingleTickerProviderStateMixin。要同时跑好几个，用 TickerProviderStateMixin。页面不在屏幕上、或 TickerMode 关掉时，Ticker 会停。这是 mixin 配合 TickerMode 的行为，不要把它说成「操作系统保证动画一定暂停」。不 dispose Controller，Ticker 会漏掉。这和 Widget 能不能 const 无关。

隐式动画省事，但做不了手势驱动和复杂编排，也不好把几段接起来。两个页面上 tag 相同的 Hero，跳转时同一块元素从旧位置移到新位置，不用自己算两边的坐标。屏幕是 120Hz 时节拍更密，前提是设备真的在用这个刷新率。刷新率是否生效，依设备和平台配置而定。

追问

  • vsync 落到代码上是什么？TickerProvider，一般由 State 的 mixin 提供，不是一个抽象口号。
  • 隐式动画和显式动画怎么选？只是某个属性要从现在的值变到新的值，用隐式。要开始、暂停、重复，或者跟着手势走，用显式。
  • Controller 创建了必须做什么？在 dispose 里释放，否则 Ticker 还挂着。

25. 布局时，约束和尺寸怎么传

口述版

父组件把宽高的允许范围传给子组件，子组件在这个范围里决定自己的大小并交回去，父组件再决定子组件放在哪。这个范围是 BoxConstraints，最小和最大都有。最小等于最大是紧约束，这一维尺寸被定死。Expanded 是把分到的主轴占满，Flexible 是最多用这么多、可以更小，两者都必须放在 Row、Column 或 Flex 里，而且主轴最大尺寸得有限。纵向 ListView 沿着滚动方向给的是无限高，里面再放 Expanded 或另一个 ListView 就会报无界高度。列表套在 Column 里，要给一个有限高度；项很多不要靠 shrinkWrap。文字在 Row 里溢出，是缺少有限的最大宽度。

解析

尺寸不是子组件单方面宣布的，位置也不是子组件自己定的。违反就会在布局阶段失败。这不是一项可以关掉的优化。

Column(
  children: [
    Expanded(child: ListView.builder(...)), // 外层高度有限，列表才有上限
  ],
)

Column 里放纵向 ListView，报无界高度，是因为列表还要一个有限的最大高度，外面沿滚动方向给不出这个上限。给列表一个有限高度，例如外包 Expanded，而且外层 Column 自己的高度也得有限。纵向滚动组件里面再放 Expanded，或者再放一个自己也要无限高的 ListView，是同一类无界。

子组件想自己决定在父组件里的位置，做不到。用 Align、Center、Positioned 这种父布局。能跳过子树布局，是因为约束和尺寸没有变，RenderObject 可以标记为不必重来。那是框架优化，协议本身不变。shrinkWrap 让滚动组件按孩子把自己的尺寸量出来，项很多时会一次布局很多孩子，不要拿它当默认解法。

追问

  • Expanded 哪里都能用吗？不能。必须在 Flex 里，而且主轴不能是无界的。
  • 子组件能返回超出 constraints 的尺寸吗？不能。也不能自己设置自己在父组件里的位置。
  • 项很多时用 shrinkWrap 把列表撑开可以吗？会一次布局很多子组件，不要当默认解法。

26. Widget、Element、RenderObject、Layer 和一帧渲染

口述版

Widget 是不可变配置，build 时会新建，它不直接画。Element 拿着当前 Widget，有状态时保存 State；能复用就复用，runtimeType 或 key 变了就会换成新的。RenderObject 做布局、绘制和命中测试。Layer 是合成层，paint 时画出或更新，再交给 Raster 线程合成成像素。父 Element 更新孩子时，runtimeType 和 key 都相同就沿用原来的 Element，只更新配置；有一个不同就卸掉旧的，再建新的。一帧的顺序是 build、layout、paint，然后合成、光栅化。build 调用得多，不等于绘制树全量重建：配置没变的 RenderObject 可以跳过重新布局或重新绘制。RepaintBoundary 让一块区域单独成层重画；每一块都成层会多占内存，合成也更贵。

解析

四个角色分开：配置、活着的树节点、布局绘制、交给合成的层。不要说 Element 永远不会重建。

这是三棵树的分工，不是编译优化。配置没变的 RenderObject 可以跳过重新布局或重新绘制。build 调用得很频繁，不等于整棵绘制树都重建，也不表示 Layer 和像素每次都全量重来。没有 Key 的列表只是换了顺序，同一层按位置和类型对上号，State 可能留在原来的格子上。框架不会按业务 id 认出列表项。

某一小块经常重画，给它 RepaintBoundary。每一块都单独成层会多占内存，合成也更贵，不要到处包。BuildContext 也不是 Widget。

追问

  • 「Element 不会被重建，只会被更新」对吗？说绝对了。类型或 key 变了就会换新的。
  • build 次数多，是不是像素每次都全量重来？不是。配置没变的 RenderObject 可以跳过重新布局或重新绘制。
  • 没有 Key 时框架按什么认出列表项？只看位置和运行时类型，不看业务 id。

27. 线程模型，以及高刷新率上怎么看掉帧

口述版

这四条线程由 Embedder 创建，引擎活着的时候保持这几条，Engine 自己不创建它们。平台线程处理系统消息和插件调用。主 isolate 跑在界面线程上，做 build、layout、paint，产出这一帧的图层。画像素线程，也就是 Raster，把图层合成再画成像素交给 GPU；旧文章里的 GPU 线程指的是这一条光栅线程，不是显卡本身。图片解码和读资源在文件线程上，不要把解码做回界面线程。120Hz 时一帧预算大约 8.3 毫秒，系统是否真的给到这个刷新率，看设备和平台。掉帧用 profile 的帧图分清时间在界面线程还是画像素线程，debug 的帧时间不能当成正式包。第一次用到某种绘制效果，可能要临时编译着色器，卡顿出在画像素这一步。Impeller 提前准备这些绘制程序；它是不是默认，看版本和平台。spawn 出来的 isolate 不归这四条线程编制。

解析

先分清四条引擎线程各自干什么，再看这一帧的时间花在 UI 还是花在光栅。不要把 isolate 和这四条线程说成同一套东西。

用 DevTools 的帧图区分是 build、layout 慢，还是画成像素这一步慢。测量用 profile。debug 本身更慢，不能当成正式包的帧时间。debug 不掉帧不能说明 release 没问题，反过来也一样。

第一次用到某种绘制效果，GPU 可能要临时编译着色器，卡在画像素这一步。Impeller 提前准备这些绘制程序，就是为了少做这种临时编译。着色器预编译、Impeller、光栅缓存，是引擎为了减少卡顿做的实现。它们不是「Dart 单线程所以不会掉帧」。60Hz 大约 16.7 毫秒一帧。Flutter 能跟上的前提是这一帧做完了，而且系统允许这个刷新率。

主 isolate 跑在界面线程上。再用 spawn 开出来的 isolate，不归这四条线程编制，框架也不替你统一管理。把 Raster 线程直接叫 GPU，容易让人以为卡在显卡上。掉帧不一定是 Dart 慢，也可能是光栅、着色器或图片解码。

追问

  • 旧文章里的 GPU 线程是显卡吗？不是。指的是 Raster 这条光栅线程。GPU 是硬件。
  • 120Hz 是 Flutter 保证给到的吗？不是。一帧预算大约 8.3 毫秒，系统是否真的给到这个刷新率，看设备和平台配置。
  • 图片解码堵了，能不能做回 UI 线程？不要。解码在文件线程上。

28. 什么时候自定义布局

口述版

先用现有 Widget 拼。只有要画的形状特殊，用 CustomPaint，位置和大小仍然交给现有布局。排列规则用 Row、Column、Stack 都做不到，才实现 RenderObjectWidget 和 RenderBox，重写算大小、绘制和命中。三件套里，Widget 是配置，Element 负责挂到树上并更新，RenderObject 真正布局和绘制。算大小必须落在父组件给的约束里，再把尺寸交回去；自己在父组件里的位置由父组件决定。还要提供 semantics，把交给父布局的数据放进 parentData，并用 isRepaintBoundary 决定这块会不会单独成层。成层能少带动旁边重画，也会多占内存、让合成更贵。

解析

组合是用现成的积木搭。CustomPaint 是在一块已经布好局的区域上画画。自定义 RenderObject 是连「怎么量、怎么摆」都自己定，但仍然要服从父组件递下来的约束。自定义 RenderBox 也不能违反约束向下、尺寸向上、父定位置。

能用 Row、Column、Stack、Padding、CustomPaint 拼出来，不要写 RenderObject。继承一个 Widget 再重写 build，那是组合，不是自定义布局协议。不要在 paint 里偷偷改布局，下一轮约束会对不上。一上来写 RenderObject，通常是把能组合的东西复杂化了。

isRepaintBoundary 决定这块会不会单独成层。成层能少带动别人重画，也会增加内存和合成成本。它是取舍，不是写上就更快。

追问

  • 图表、特殊形状，但 Row 和 Stack 摆得开，写到哪一层？CustomPaint。只画，位置和大小仍交给现有布局。
  • 自定义布局还要守约束吗？要。算大小必须落在父组件给的范围内，位置由父组件决定。
  • 单独成层一定更快吗？不一定。少带动别人重画，同时多占内存，合成也更贵。

29. 一次点击为什么只有一个组件响应

口述版

手指按下后，先找出点中了哪些组件，得到从最里层到外层的一条路径。GestureDetector 注册的识别器进入手势竞技场，最后只有一个获胜，所以父子都写了 onTap 时，通常只有子组件收到。抬起时如果还剩多个，先加入的那个赢，一般就是更靠里的子组件。列表里的按钮和滑动会抢，移动超过一小段距离，滑动获胜，点击取消。父组件只想观察指针，用 Listener，不要再叠一个 onTap。behavior 设成 opaque 时，空白处也算点中自己。

解析

一次点击先做命中测试，再进手势竞技场。最后只有一个胜者，所以不是「事件丢了」，而是竞争分出了胜负。这不是事件系统随机丢事件，也不是编译器优化。

「先加入的获胜」是抬起时仍未分出胜负的规则。命中路径从里向外加入，所以一般是更靠里的子组件。如果某个识别器更早宣布自己胜出或失败，例如滑动超过 slop，就按那个结果，不必等到抬起。手势阈值的具体像素依设备和手势设置而定，说出「超过一小段移动，拖动赢、点击取消」即可，不要背死一个魔法数字。

父组件只是想知道手指在自己范围内动过，用 Listener，不要再加一个 onTap 去和子组件抢。透明区域也要点中自己，用 behavior: HitTestBehavior.opaque。不是父组件收不到指针，而是 onTap 这种识别器在竞技场里输了。列表滑动把按钮点击取消，是竞争结果，不是点击事件丢失。

追问

  • 父子都写了 onTap，为什么父组件像没收到？识别器在竞技场里输了。抬起时还剩多个，先加入的赢，一般是更靠里的子组件。
  • 父组件只想观察、不抢点击，用什么？Listener。它不进竞技场。
  • 列表滑动把按钮点击取消，是事件丢了吗？不是。移动超过触摸阈值后滑动获胜，点击被取消。

30. Flutter 如何和 Android / iOS 通信

口述版

Platform Channel 是异步消息：参数和返回值按 codec 编解码，不是共享原生对象。一次方法、一个结果或一个错误，用 MethodChannel。原生连续上报、Dart 侧拿到 Stream，用 EventChannel，不要在原生那边用死循环占住通道。不限定成一次请求一次返回，用 BasicMessageChannel。StandardMessageCodec 能直接装的是 null、布尔、整数、小数、字符串、定长的字节和数值数组，以及 List 和 Map；自定义对象先拆成这些。通道不会自动切线程：Dart 这边在主 isolate、也就是界面线程上收发，原生要把调用切到它自己要求的线程。已经有 C 或 C++ 库，或者调用非常频繁、不想每次都走消息，用 dart:ffi，自己保证调用约定和对象生命周期。Activity、权限这类平台对象仍然走 Channel。

解析

先看这次是「把消息编好异步送去原生」，还是「按 C 的调用方式直接调函数」。Platform Channel 是两边约好编码的异步信箱。FFI 是直接拨 C 函数，少一次装拆，但内存里字段怎么排列要自己管。

const channel = MethodChannel('app/settings');
final value = await channel.invokeMethod<String>('getName');

消息会按 codec 编解码，这是通道的成本，不是编译器可有可无的一步。FFI 省掉的是这次装拆，换来的是你自己保证调用约定和对象生命周期。系统界面、Activity、权限这类平台对象仍然用 Channel，不要用 FFI 硬拿。热路径上的 C 库用 FFI，并自己管内存。少了一次编解码，不代表更简单。

通道不会自动帮你切到正确的线程。具体插件内部用 Channel 还是 FFI，依实现而定，不要说每个插件都只用 MethodChannel。EventChannel 在 Dart 侧是 Stream，不是再包一个 MethodChannel 死循环。

追问

  • Platform Channel 会自动切到原生主线程吗？不会。原生那边要自己切，例如要碰 UI 时切到平台主线程。
  • 自定义对象能直接塞进通道吗？不能。先拆成 codec 能装的那些基本类型、List 和 Map。
  • FFI 适合拿 Activity 或 iOS 的 UI 对象吗？不适合。它适合 C ABI。平台对象走 Channel。

31. 包和插件有什么区别

口述版

包是一份可以依赖的代码，纯 Dart 的工具和 Widget 做成包就行。插件也是一个包，但另外带了 Android、iOS 或其他平台实现，这些实现才会去调用系统能力。业务侧只依赖它的 Dart 接口，里面一般通过 Platform Channel 或 FFI 调到原生。通道是通信办法，插件是把这个办法和各端实现打包给别人用的形式。只在一个应用里用的原生调用，写在应用自己的工程里就行；要给多个应用用，再做成插件。

解析

先问这份依赖里有没有各端实现。纯 Dart 是包。包再加上 Android、iOS 或其他平台实现，才是插件。插件首先是一个包，不是和包并列的另一种语言。pub 如何发现平台实现，是工具链的约定。

有 Channel 代码，不等于已经做成了可复用插件。它可能只是写在当前应用工程里。通道或 FFI 是插件内部的通信手段。选哪一种依插件作者而定，不是「插件」这三个字保证了只用某一种通道。业务侧只依赖它的 Dart 接口。

追问

  • 插件是不是必须只用 MethodChannel？不是。里面可以是 Platform Channel，也可以是 FFI。
  • 只在这一个应用里用的原生调用，要做成插件吗？不用。写在应用自己的 Android、iOS 工程里。
  • 包和插件是二选一的运行时吗？不是。插件首先是一个包，只是口袋里还有平台工程。

32. 混合栈怎么组织

口述版

整个应用都是 Flutter 时，用自己的 Navigator 就够，不需要 flutter_boost。已有原生壳、要逐页嵌进 Flutter，才要同时维护原生导航和 Flutter 导航。要明确的是：哪一页正在显示、触摸交给谁、原生页在 Flutter 页上面时 Flutter 还画不画、引擎里的定时器还跑不跑。这些没有自动对齐的框架保证。一个引擎被多个原生页共用更省内存，但可见性和触摸要自己对齐。一个容器一个引擎，彼此隔开，启动更慢、内存更大，插件也要各注册一次。flutter_boost 是原生当容器，用路由表和消息让两边的栈和生命周期对齐的一种做法，不是官方唯一方案。新项目不引入它。

解析

混合栈里，原生页面是外层容器，Flutter 页面画在容器里。两边要同时知道谁在栈顶、谁该接收触摸、谁被盖住之后还要不要继续画、定时器还要不要跑。没有「混合栈自动正确」这层保证。

新项目 Android 和 iOS 都用 Flutter 写，用 Navigator，不引入 flutter_boost。已有原生壳、逐页替换，才做混合栈。最容易错的是生命周期：原生页面盖住 Flutter 页面时，Flutter 还在不在画，引擎里的定时器还在不在跑。混合栈最难的通常不是把页面打开，而是盖住之后绘制和定时器有没有停。

flutter_boost 能继续用原生导航，旧页面可以慢慢换。容器怎么复用、内存、插件初始化和两边栈的同步，都要额外维护。官方 add-to-app 怎么复用引擎，依 Flutter 版本而定，不要把某个第三方库的内部实现说成框架保证。一个引擎被多个原生页共用，不是天然安全。

追问

  • 全 Flutter 项目要 flutter_boost 吗？不要。只用自己的 Navigator 或路由库。
  • 一个引擎给多个原生页共用，安全吗？要自己处理哪一页正在显示、触摸给谁、谁在栈顶。省的是内存，不是这些对齐。
  • flutter_boost 是官方唯一方案吗？不是。它是嵌进原生导航的一种做法。

33. 构建模式和多端产物

口述版

写界面用 debug。手机和桌面上它是 JIT，assert 还在，可以热重载；这时的帧时间和包体积不能当成正式包，因为 debug 不会做和 release 一样的 tree shaking。看卡顿用 profile：它和 release 一样是 AOT，assert 关掉，但留着给 DevTools 的性能记录。上架用 release：AOT，去掉 assert，并从 main 出发删掉确定走不到的 Dart 代码。混淆要单独加 --obfuscate，不是 release 就自动混淆；签名是按平台在打包时做的。Web 是 flutter build web 的静态文件，Android 是 apk 或 appbundle，iOS 走 flutter build ios 和 Xcode 归档，桌面是 macos、windows、linux。手机和桌面的 release 是机器码 AOT；Web 的 release 是 JavaScript 或 Wasm，同样不能热重载。

解析

模式决定有没有 assert、是 JIT 还是 AOT、能不能热重载。打成哪个平台是后面的打包步骤。JIT 才能热重载。AOT 是发布构建，没有热重载。这不是语言语法，是编译模式。

tree shaking 是提前编译时从 main 看出哪些 Dart 代码走不到，再删掉。debug 是边运行边编译，不会做同样的删除。混淆 --obfuscate 要单独打开。release 不等于已经混淆、已经签名。签名和混淆是另外的打包选项。着色器和启动时间也要在 profile 或真机 release 上看。debug 流畅，不能说明 release 没问题，反过来也一样。

上面说的 JIT / AOT 指手机和桌面这套 Dart 编译。Web 的 release 是编译成 JavaScript 或 Wasm，同样不能热重载，不要说成机器码 AOT。

追问

  • profile 是 debug 少打一点日志吗？不是。它和 release 一样是 AOT，assert 关掉，但留着给 DevTools 的性能记录。
  • release 是不是已经混淆、已经签名？都不是。混淆要单独打开，签名按平台在打包时做。
  • 用 debug 包的体积估计商店包可以吗？会估错。debug 不做同样的 tree shaking。

34. 怎样减少重建、长列表卡顿和大图开销

口述版

先用 profile 的帧图分清时间在 build、layout 还是光栅，不要用 debug 的帧时间下结论。build 长，是 setState 标在了过大的 Element 上：把它放到真正变化的 State 上，不变的子 Widget 写成 const。父组件重新 build 时，子 Widget 若还是同一个对象，Element.updateChild 不再向下更新它；这是跳过子树更新，不是 const 让 build 方法不会被调用到。长列表不要用 ListView(children:) 一次创建全部孩子，用 ListView.builder；高度固定就告诉列表。项很多时不要靠 shrinkWrap。每一项的 Key 用业务 id，不要在 build 里 UniqueKey()。RepaintBoundary 只包经常单独重画的小块。大图用 cacheWidth 和 cacheHeight 按显示像素解码。压缩和算哈希放到另一个 isolate。内存先看 dispose 里有没有放开 Controller、订阅和 Timer，再怀疑图片缓存。

解析

先分清慢在哪一步。build 慢，是施工单写得太多。layout 慢，是一次量了太多孩子。raster 慢，是图层、模糊和像素太大。三件事的药不一样。

父组件重新 build 时，子组件还是同一个对象，框架不再向下更新它。构造参数里每次都 new 一个对象，就写不成 const，这条捷径也不会发生。在 build 里写 UniqueKey()，会让项的 State 每次都被丢掉，列表更抖。

RepaintBoundary 能让滚动条、动画图标单独重画。每一块都是单独的一层，划得太多会多占内存，合并图层也更贵。不要在 build 里把整张原图读进内存。上传前先压缩、缩小；大文件分段传，并带上进度、取消和重试。压缩和算哈希放到另一条 isolate，进度再用 Stream 或状态管理送回界面那条。

先换状态管理库，通常解决不了根上 setState 或大图解码。测量本身要用 profile。debug 的帧时间不是正式包的结果，这是构建模式的差别。

追问

  • const 是让 build 方法不会被调用到吗？不是。子 Widget 还是同一个对象时，Element 不再向下比较。这是更新规则带来的跳过。
  • RepaintBoundary 包得越多越快吗？不是。划得太多会多占内存，合成也更贵。
  • 内存涨了先看什么？先看 dispose 里有没有放开 Controller、订阅和 Timer，再怀疑图片缓存。

附录：初级语法

下面几题在老题库里出现过，现在很少单独成题。空安全的 ?? 可以当作第 1 题的补充。

A1. ?? 和 ??=

口述版

a ?? b 在 a 为 null 时结果是 b，否则结果是 a，不会给 a 赋值。a ??= b 只在 a 为 null 时把 b 赋给 a，表达式的结果是赋值之后的值；a 已经非空就不赋值，结果仍是原来的 a。左边已经非空时，右边不会被求值。两者都只判断 null，不把空字符串、0 或 false 当成空。

解析

两个都看左边是不是 null。一个只决定表达式的结果，一个会在为空时把右边赋给左边。判断的是 null，这是空安全里的运算符，不是运行时偶然的短路优化。右边在左边已经非空时不会被求值，这是这两个运算符的语义。

final shown = name ?? '未命名'; // name 本身不变
name ??= '未命名';              // 只有原来是 null 才赋值

追问

  • ?? 会给左边赋值吗？不会。会赋值的是 ??=。
  • 空字符串、0、false 算空吗？不算。它们只处理 null。

A2. 默认是强引用还是弱引用

口述版

普通变量、字段和集合里的元素默认是强引用。对象还有可达的强引用时，垃圾回收不会收走它。弱引用不是默认，要显式放进 WeakReference；只剩弱引用时对象可以被回收，之后再取可能是 null。同一个对象上只要还有别的普通变量指着它，WeakReference 不会让它消失。对象被回收时要清理原生资源，用 Finalizer，时机由运行时决定，不要假设和 Java 的 finalize 一样。变量离开作用域，也不表示对象会立刻被回收。

解析

强引用是手里一直抓着对象，垃圾回收不能把它拿走。弱引用是一张可以失效的便条：对象若没有别的强引用了，就可以被回收。可达的强引用会保住对象。只有放进 WeakReference 的那一个引用是弱的。垃圾回收什么时候跑，是运行时的事，不是你把变量写成局部变量就会立刻回收。

缓存不想挡住回收，把那一个引用放进 WeakReference。其他普通变量不变，仍然是强的。闭包抓着 State，State 就还在，这就是强引用。

追问

  • Dart 默认是弱引用吗？不是。普通字段、局部变量、集合里的元素都是强引用。
  • 放进 WeakReference 之后对象一定消失吗？不一定。只要还有别的普通变量指着它，就不会消失。
  • 清理原生资源用什么？Finalizer。不要在析构时机上假设和 Java 的 finalize 一样。

A3. getter 和 setter

口述版

getter 和 setter 让外面像读写字段，实际走的是方法。setter 里可以校验，比如温度不能低于绝对零度。getter 可以没有自己的存储，例如华氏度每次由摄氏度算出来。真正的数据可以放在下划线字段里，库外只能通过公开的 getter 和 setter 碰到它。

解析

读访问调用 getter，赋值调用 setter。调用处的写法可以和字段一样。这是语言保证。getter 可能被内联，那是编译器优化，不改变「中间可以做校验和计算」这个语义。

class Temperature {
  double _celsius = 0;
  double get celsius => _celsius;
  set celsius(double value) {
    if (value < -273.15) throw ArgumentError('below absolute zero');
    _celsius = value;
  }
  double get fahrenheit => _celsius * 9 / 5 + 32;
}

赋值时要校验、要通知，用 setter，不要让外面直接改字段。值可以由别的字段算出来，只提供 getter，不必再存一份。库外不能碰的存储，字段名以下划线开头，再配公开的 getter / setter。setter 可以抛错，拒绝不合法的值。它不是一次必定成功的赋值。

追问

  • getter 必须有一块同名存储吗？不必。它可以是计算出来的。
  • setter 一定能赋值成功吗？不一定。它可以抛错，拒绝不合法的值。

A4. 库的可见性

口述版

Dart 没有 public、protected、private 这些关键字，可见性按库，不按类。名字以下划线开头，库外访问会编译失败；同一个库里的其他文件、其他类仍能用。没有下划线的名字，库外可以直接引用。export 把别的库的公开声明再导出到当前库的公开 API，导不出别人的下划线名字。tree shaking 可以在发布构建里删掉确定用不到的公开代码，那不改变「没有下划线就可以被库外引用」这条规则。

解析

一个库是一组一起编译的文件。下划线名字像库内部的抽屉，库外看不到。没有下划线的名字默认就能被库外使用。下划线可见性在库边界上检查，这不是分析器可关的风格，库外访问私有名字会编译失败。

下划线不是「这个类外面不能用」。同一个库里的其他文件、其他类也能用。Dart 没有 protected。想限制继承和实现，用 Dart 3 的类修饰符，那是第 4 题，不是下划线。tree shaking 可以删掉确定用不到的公开代码，那是发布构建的编译优化，不改变可见性规则。export 导出不了别人的下划线名字。

追问

  • 下划线是这个类外面不能用吗？不是。私有的是库。同一个库里的其他类也能用。
  • Dart 有 protected 吗？没有。限制继承和实现用 Dart 3 的类修饰符。
  • export 能把别人的私有名字再导出吗？不能。只能再导出公开声明。

A5. 级联操作符 ..

口述版

.. 的每次调用都作用在最初那个接收者上，整个表达式的值也是这个接收者，不是最后一次调用的返回值。最后一次即使返回 void 或其他类型，外面拿到的仍是原对象。普通的 . 才把这次的返回值交给下一次调用。?.. 是接收者非空才调用；左边是 null 时整段不调用，结果是 null，不会把对象变成非空。

解析

级联的结果是接收者本身。这是语言语义，不是格式化工具随便改写之后还能被优化掉的东西。编译器可以把它展开成几次调用。展开之后，结果仍然是原对象。

final paint = Paint()
  ..color = const Color(0xFF000000)
  ..strokeWidth = 2;   // 表达式的值仍是原来那个 Paint
final width = paint.strokeWidth; // 要用返回值，走普通的 .

连续配置同一个对象，用 ..。下一步要用上一次方法的返回值，用普通的 .。接收者可能是 null，用 ?..。左边是 null 时整段不调用，结果是 null。?.. 不是把对象变成非空。

追问

  • .. 的结果是最后一次调用的返回值吗？不是。最后那次即使返回 void 或其他类型，外面拿到的仍是原对象。
  • ?.. 会把对象变成非空吗？不会。只是左边为 null 时不要继续调用，结果是 null。
