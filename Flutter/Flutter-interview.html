一、Dart

1. var、Object、dynamic，以及空安全

判断框架：这道题问的是编译器在这个名字上知道多少，以及 null 能不能混进来。先分清「类型定死了没有」「静态检查还在不在」「值能不能是空」。

画面：var 是让编译器看右边，把类型写死；Object 是「我知道这是个非空对象，但只把它当成所有对象的公共父类型」；dynamic 是先关掉静态检查，等运行时再说。

写法编译器知道什么能不能是 null关键记忆
var x = 1推断成 int，之后只能再赋 int非空 int 不能锁的是类型，不是这次的值
Object静态类型就是 ObjectObject 不能，Object? 可以只能直接调 Object 的成员
dynamic几乎不做编译期检查可以任何调用都编译得过，错了运行时才爆
T? / late可空，或推迟赋值? 可以! 是断言，late 是稍后赋值

决策清单：

  • 右边一看就知道类型 → 用 var 或直接写出类型。
  • 只知道「是个对象」，还要拦住乱调用 → 用 Object 或更具体的类型，调用子类方法前先判断或转换。
  • 结构暂时不定，例如一块原始 JSON → 局部用 dynamic，尽快收成具体类型。
  • 值可能没有 → 声明成 T?，用 ?. 和 ??。本地变量写过 if (value != null) 后，花括号里的 value 会被提升成非空，一般不必再写 !。
  • 字段要等一会儿才有，但读取前一定赋过 → late。只能赋一次再写成 late final。还没赋值就读，抛 LateInitializationError。

哪些是保证，哪些是优化

  • 语言和运行时保证：推断完成后类型就定了；Object 上不能直接调用子类才有的方法；dynamic 把检查推迟到运行时；! 用在 null 上会抛错；late 未初始化就读会抛 LateInitializationError。
  • 类型系统的流分析，不是运行时把对象变了：本地变量判空之后被当成非空。类的字段很多时候不会自动提升。Dart 3.2 起，一部分私有、非外部字段可以提升，依版本而定，不要说成「所有字段都会提升」。
  • 分析器警告是开发工具，不是另一套语言规则。dynamic 也不会让程序跑得更快。

常见误区

  • Object 和 dynamic 都能装别的对象，但 Object 仍做静态检查。dynamic 连 null 都收。
  • var 不是常量。变量还能赋同类型的新值。
  • ! 不是「把类型变成非空」，而是「我断言它不是 null，错了就抛」。

口述版

var x = 1 的静态类型由初始值推断为 int。推断完成后这个静态类型不再变，之后只能再赋 int，但可以换成另一个 int，它不是常量。

Object 的静态类型就是非空的 Object，只能直接调用 Object 的成员，子类方法要先判断或转换；要装 null 得写成 Object?。

dynamic 几乎不做编译期的成员检查，也可以是 null，调用错了要到运行时才抛。

T? 表示这个类型可以是 null。! 是断言当前值不是 null，是 null 就抛，不是把对象改成非空类型。late 是推迟到读取前赋值，还没赋值就读会抛 LateInitializationError。

本地变量在 != null 之后会被类型系统提升成非空，这是静态分析，不是运行时把对象变了。字段多数时候不提升；Dart 3.2 起，一部分私有、非外部字段可以，不要说成所有字段都会。

能确定类型就不要用 dynamic。

2. const 和 final 的区别

判断框架：先拆成两件不同的事：这个名字还能不能再指向别处，以及这个值是不是编译期就定下来的常量。

画面：final 是给变量上锁，锁的是「这个名字不能再指向别处」，房间里的东西仍可能搬动。const 是做一份编译期常量，相同的常量在同一个 isolate 里会收成同一个对象。

finalconst
什么时候定下来运行时第一次赋值必须编译期就能算出来
锁住什么变量绑定，不能改指向常量值本身，而且是深度不可变
对象里面可以改。final list = <int>[] 之后仍能 addconst [] 不能增删改元素
实例字段可以写成 final不能。类里的常量写成 static const
是不是同一个对象每次普通构造都是新对象相同参数的 const 构造，在同一个 isolate 里规范化成同一个对象

决策清单：

  • 值要到运行时才知道，之后这个变量不能再指向别处 → final。
  • 编译期就知道，并且希望当常量复用 → const。
  • 只是不想改字段指向，列表内容还要变 → final，不要写成 const。
  • 希望父 Widget 重建时，子树因为还是同一个对象而被跳过 → 把子 Widget 写成 const。构造参数里每次都 new 一个新对象，就写不成 const。

哪些是保证，哪些是优化

  • 语言和运行时保证：final 不能再次赋值；const 必须是编译期常量；真正用 const 造出来的对象深度不可变；常量会规范化。
  • 不是语言保证：父组件重新 build 时，子 Widget 若仍是同一个对象，框架就不再向下更新这棵子树。这是 Flutter 里 Element.updateChild 的行为。
  • 容易混在一起的一点：类有 const 构造函数，只说明「可以」造常量。不带 const 去调用，得到的是普通实例。字段是 final 只保证不能换指向，不保证里面那份可变对象不能改。
  • 跨 isolate 发消息时对象通常会被拷贝，不能把 const 身份当成进程里全局唯一。

常见误区

  • const 不是「运行时不可变对象」的同义词。final 也能让字段不再换指向，但它不是编译期常量，也不会规范化。
  • const 能少重建，是因为框架发现新旧 Widget 是同一个对象，不是 const 有魔法跳过 build。
  • 实例字段不能写 const。要写 static const。

口述版

final 在运行时赋值一次，之后这个变量不能再指向别的对象。对象如果可变，里面仍能改，例如 final list = <int>[] 之后还能 add。

const 的值必须在编译期算出来，用 const 造出的对象深度不可变，相同常量在同一个 isolate 里会规范化成同一个对象。实例字段不能写 const，类常量写成 static const。const 构造函数要求字段都是 final，调用时传入的参数也必须是编译期常量。类有 const 构造，调用时不写 const，得到的仍是普通新实例。

Flutter 里父组件重新 build 时，子 Widget 若还是同一个对象，Element.updateChild 就不再向下更新这棵子树。这是框架行为，不是语言保证 build 不会被调用。const 对象本身深度不可变，那是另一条语言规则。

3. Dart 是值传递还是引用传递

判断框架：先问函数拿到的是「对象的另一份拷贝」，还是「指向对象的那份地址的拷贝」。Dart 传的是后者。

画面：参数是函数自己的一个新变量，里面拷了一份地址。你拿这个地址去改房间里的东西，外面看得到；你让这个新变量改去指另一间房，外面那个变量不动。

函数里做的事外面看不看得到原因
list.add(1)，或改对象字段看得到参数和外面的变量指向同一个对象
list = []看不到只是让参数这个局部变量指向新列表

决策清单：

  • 希望调用方看到内容变化 → 直接改这个对象的字段或集合。
  • 希望调用方的变量改去指另一个对象 → 不要给参数重新赋值，让函数把新对象 return 出去。
  • 想避免被外面改到 → 传不可变对象，或者在边界上拷一份。

哪些是保证，哪些是优化

  • 语言保证：参数是按值传递的。传走的值是对象引用的一份拷贝。没有 C++ 那种「外面那个变量的别名」。
  • 编译器可能内联、可能省略一些拷贝，但不会把「给参数重新赋值」变成修改调用方的变量。这不是一项可选优化。

常见误区

  • 「对象能被改，所以是引用传递」不准确。传递的是引用的值，函数参数和外面的变量不是同一个变量。
  • void reset(List<int> list) { list = []; } 不会清空调用方的列表。add 才会影响同一份列表。

口述版

Dart 的参数按值传递，传走的值是对象引用的一份拷贝。参数和调用方的变量不是同一个变量，也不是 C++ 那种别名。

函数里改对象的字段，调用方看得到，因为两份引用指向同一个对象。函数里给参数重新赋值，只改这个局部变量，调用方的变量不变。

所以 list.add(1) 调用方能看到，list = [] 调用方看不到。想让调用方改去指另一个对象，就把新对象 return 出去。

4. extends、implements 和 mixin

判断框架：先问你要复用的是「实现加上是一个什么类型」，还是「只是一份契约」，还是「一段可以拼上去的行为」。Dart 仍然只能 extends 一个类。

画面：extends 是「我是你的一种，你写好的实现我直接拿来」。implements 是「我承诺有这些成员，实现我自己写」。mixin 是一段现成实现，用 with 拼到类上，它不是为了变成多个父类。

extendsimplementsmixin / with
复用实现复用不复用，成员要自己写全复用，可以有方法，也可以有字段
类型关系子类是父类实现者可以当这个类型用混入后类具备这些成员
数量只能一个可以多个可以多个
构造要接上父类构造不继承对方的构造mixin 不能写生成构造函数

决策清单：

  • 需要「是一个」，并且要复用父类实现 → extends。
  • 只需要契约，实现各自不同 → implements。每个类本身就能被别人当成接口实现。
  • 一段没有自己构造过程的行为，多个类都要 → with mixin。只是复用代码、不需要类型关系时，优先考虑组合。
  • 只有某个类的子类才能混入 → 在 mixin 上写 on。mixin 里面可以调用这个宿主类型的方法。
  • 多个 mixin 有同名方法 → with 后面靠后的覆盖靠前的，不是报错合并。

细节：Dart 3 还可以限制库外的人怎么用这个类。这是语言规则，不是 lint。

  • interface：库外只能实现，不能继承。
  • base：库外只能继承，不能当接口实现。
  • final：库外不能继承，也不能实现。
  • sealed：子类必须写在同一个库里，switch 可以检查分支有没有写全。
  • mixin class：既能当类，也能当 mixin。依 Dart 3 的写法。

哪些是保证，哪些是优化

  • 语言保证：单继承、多实现、多 mixin；mixin 不能有生成构造函数；on 限制宿主；类修饰符限制库外的继承和实现。
  • 调用最后落到哪一份实现，由类型关系和 mixin 的线性化决定，不是编译器随便挑一个更快的版本。

常见误区

  • 不要把 mixin 说成「Dart 用它实现多重继承」。类仍然只能 extends 一个父类。
  • mixin 不只有方法，也可以有字段。它只是不能有生成构造函数。
  • 同名方法不是叠在一起执行，而是后面的覆盖前面的。

口述版

extends 是单继承：子类复用父类的实现，并且是父类的子类型，还要接上父类构造。

implements 不复用实现，接口上的成员要自己写全；每个类本身就是自己的接口，实现者可以当这个类型用，也可以同时实现多个。

mixin 用 with 把一份现成实现混进类里，可以有字段和方法，不能写生成构造函数。on 限制只有指定类型的子类才能混入，mixin 里可以调用这个宿主类型的成员。多个 mixin 有同名成员时，with 里靠后的覆盖靠前的，由线性化决定落到哪一份实现，不是叠在一起执行。

Dart 3 的 interface 是库外只能实现、不能继承，base 是库外只能继承、不能当接口实现，final 是库外既不能继承也不能实现，sealed 是子类必须写在同一个库里。

需要子类型关系并且要父类实现，才 extends；只复用一段行为，用 mixin 或组合。

5. extension 是干什么的

判断框架：这道题问的是，能不能在不改原来的类、也不继承的前提下，给某个静态类型加方法。解析发生在编译期，不看运行时再找一遍。

画面：extension 像贴在类型上的一层便利贴。编译器看变量写出来的类型，决定用哪一张。运行时对象实际是子类，也不会因此改选另一张便利贴。

点行为关键记忆
什么时候选定编译期，看静态类型不是运行时的虚函数
能不能加字段不能所以不能用它存状态
能不能盖掉原方法不能，类型自己的成员优先扩展不是 override
dynamic静态类型是 dynamic 时看不见扩展编译器不知道有这张便利贴
看得见吗扩展所在的库要被 import没导入就当没有
重名可以 hide 其中一个，或写成 扩展名(对象).方法()显式点名消歧义
 
extension StringX on String {
  bool get isBlank => trim().isEmpty;
}

决策清单：

  • 不加状态的工具方法，例如字符串判空白 → extension。
  • 要保存数据，或者希望子类能改写 → 用类或 mixin，不要用扩展。
  • 调用方手里可能是 dynamic → 不要依赖扩展方法。

哪些是保证，哪些是优化

  • 语言保证：扩展按静态类型解析；不能加实例字段；不能覆盖类型已有的成员；必须导入才可见。
  • 编译器可能把这次调用内联掉。那是优化，不改变「按写出来的类型选定」这个规则。

常见误区

  • 调用看起来像实例方法，其实不是运行时按对象的真实类型分发。
  • 扩展盖不掉类里已经有的同名方法。
  • 忘了 import，就调不到。两个扩展撞名时，要藏起一个或写扩展名。

口述版

extension 给已经有的类型加方法或 getter，不用改原类，也不用继承。

调哪一个在编译期就定了，看的是变量写出来的类型，所以 dynamic 上调不到。

类型自己的同名成员优先，扩展里不能加字段，也就不能存状态。扩展所在的库要 import 才看得到。

它适合不加状态的工具方法；要保存数据，或者希望子类改写，用类或 mixin。

6. 工厂构造函数和普通构造函数

判断框架：先问这次调用是不是一定新造「当前这个类」的对象，以及返回值能不能是仓库里已有的对象，或者一个子类实例。

画面：普通构造函数是车间，每次开工必出一台当前型号的新机器。工厂构造函数是前台：你以为在下单，前台可以给你仓库里那一台，也可以给你一台子型号。

生成构造、命名构造factory
会不会新建一定会生成当前类的新实例可以 return 已有实例，也可以返回子类
函数体用初始化列表和函数体，不能返回另一个实例必须返回一个这个类型能接受的对象
能不能 const可以写成 const 构造带函数体的不能是 const。重定向形式的 const factory 可以，这是语言规则
名字User.fromJson 只是名字名字不决定能不能缓存，factory 关键字才决定

决策清单：

  • 只是把 JSON 字段填进一个新对象 → 命名构造函数就够。
  • 要缓存、单例，或按参数返回子类 → factory。
  • 对象在编译期就要定死 → 用 const 生成构造，不要指望带函数体的工厂。

哪些是保证，哪些是优化

  • 语言保证：生成构造函数创建的是当前类的新实例。工厂可以返回已有对象或子类型。带函数体的工厂不能是编译期常量构造。
  • 工厂不是一项性能优化，也不是「更快的 new」。它只是放宽「必须新造当前类」。

常见误区

  • fromJson 不是天然的工厂。没写 factory，就仍然会新建。
  • 工厂返回子类时，调用方的静态类型仍然可以是父类。
  • 不要说「所有 factory 都不能 const」。不能 const 的是带函数体的那种；重定向的 const factory 是允许的。

口述版

生成构造函数每次都会创建当前这个类的新实例，不能返回另一个对象。factory 的函数体必须 return 一个这个类型能接受的对象，所以可以返回已有实例，也可以返回子类型；调用方拿到的就是这个返回值。

带函数体的 factory 不能是编译期常量构造；重定向形式的 const factory 可以。

名字叫 fromJson 不表示它是工厂，没有 factory 关键字就仍然会新建当前类。只是把字段填进一个新对象，用命名构造；要返回已有实例或子类型，才用工厂。

二、异步和并发

7. Future 和 async / await

判断框架：先分清三件事：结果是稍后才来的一次成功或失败，await 挂起的是哪一段代码，以及这段代码仍在不在当前 isolate 上。

画面：Future 是一张回执，成功或失败只会来一次。async 函数一被调用，就先把回执递给你。await 是把这个函数剩下的活挂起来，回执到了再继续。整条 isolate 可以先去干别的，不会被这张回执堵住。

写法进哪个队列会不会并行
async 函数调用时立刻返回一个 Future不会，仍在当前 isolate
await 后面的续体等的那个 Future 完成后，以微任务继续不会
Future.microtask、scheduleMicrotask微任务队列不会
Future(() {})、Timer、网络和文件回调事件队列不会
Isolate.run / compute另一条 isolate会，这才是真正并行

决策清单：

  • 一次网络、定时或文件 → Future。等待时不占着 CPU，界面还能响应。
  • 错误发生在 await 上 → try/catch。
  • 拿到 Future 但没有 await → try/catch 接不住，用 catchError，或者继续把这个 Future 交给调用方。
  • 很吃 CPU 的计算 → 不要只包一层 Future。真正计算的那一段仍占着当前 isolate，要放到另一个 isolate。

哪些是保证，哪些是优化

  • 语言和运行时保证：async 函数立即返回 Future；await 挂起的是当前这个异步函数剩下的代码，不是把 isolate 堵住；一个 async 函数里可以没有 await，也可以有多个。
  • 事件循环的调度：Future 完成后的续体进微任务，比点击、定时器这些事件更优先。Future(() {}) 的函数体进事件队列。这是运行时的事件循环规则，不是编译器把异步「优化成同步」。
  • Future 不会因为你多包一层就变成并行。

常见误区

  • await 不是把线程堵住，也不是立刻把后面的代码跑完。
  • Future 不是多线程。它只是当前 isolate 上稍后才有的一个结果。
  • 没写 await 时，旁边的 try/catch 接不住这个 Future 的错误。

口述版

Future 表示稍后会完成一次，结果是一个值或一个错误。async 函数一被调用就先返回这个 Future，函数体仍在当前 isolate 上，不会因此并行。

await 挂起的是当前这个异步函数剩下的代码：等的那个 Future 完成后，续体以微任务继续，比定时器和点击更优先。这次等待不会把 isolate 的事件循环堵住。

Future(() {}) 的函数体进事件队列。很吃 CPU 的计算即使用 Future 包起来，计算的那一段仍在当前 isolate 上执行，要放到另一个 isolate。

8. Future 和 Stream 有什么不一样

判断框架：先看结果来一次，还是一段时间内来很多次。再看这条流允许多少个监听者，以及你是想听完为止，还是中途取消。

画面：Future 是一封信，拆开一次就结束。Stream 是一条水管，可以多次出水、多次报错，最后有一个结束信号。

Future单订阅 Stream广播 Stream
来几次一个结果多个数据、错误，然后结束同样是一串事件，常常不结束
谁能听then / await只能有一个监听者，再 listen 会报错可以同时有多个监听者
迟到的人完成后仍能拿到那个结果事件按顺序交给这一个监听者听不到开始之前已经发出的事件
典型场景一次请求读文件这种读完就结束的数据网络状态、主题切换

细节：自己写一条会连续产出数据的流，函数标成 async*，每 yield 一次就往外发一个事件。yield* 是把另一条流里的事件接着转出去。await for 是一个一个取：来一个就执行一次循环，流结束后循环结束。

await for (final event in stream) {
  print(event);
  if (event == 'stop') break;
}

决策清单：

  • 一次请求 → Future。
  • 会持续来数据、读完就结束 → 单订阅 Stream，可以用 await for。
  • 多个地方同时听，而且常常不结束 → 广播 Stream。后开始听的人拿不到历史事件。
  • 广播流上不要随便 await for。流不结束，这个函数就会一直停在循环里。
  • break 或页面销毁时，取消 StreamSubscription，关掉文件、socket 这类资源。否则回调里可能再去 setState。

哪些是保证，哪些是优化

  • 库和运行时保证：单订阅不能听第二次；广播可以多人听，但不补发过去的事件；await for 挂起的是当前这个异步函数，不会把整条 isolate 卡住。
  • 「await for 会把线程堵死」是老说法，应当纠正。函数会停在这里等下一个事件，isolate 仍能处理别的事件。
  • 广播流的缓冲策略、暂停时还丢不丢事件，依具体 Stream 实现而定，不要说成所有广播流行为完全一样。

常见误区

  • Future 和 Stream 都在当前 isolate 上调度，都不是并行。
  • 单订阅流 listen 两次会报错，不是「两个人各拿一份」。
  • 页面 dispose 之后订阅还在，是常见的 setState() called after dispose() 来源。

口述版

Future 完成后只有一个结果，完成之后再 await 或 then 仍能拿到它。

Stream 是一串事件，可以有多次数据和多次错误，最后有一次结束。单订阅流只能 listen 一次，再听会报错，适合读完就结束的数据，例如读文件。广播流可以同时有多个监听者，后订阅的拿不到订阅之前已经发出的事件。

async* 里 yield 一次就发出一个事件。await for 挂起的是当前这个异步函数：来一个事件执行一次循环，流结束循环就结束，不会把整条 isolate 堵住。页面 dispose 时要取消 StreamSubscription。

9. Dart 是不是单线程？事件循环怎么跑

判断框架：先把「一个 isolate 里代码是不是一条一条跑」和「整个进程是不是只有一条系统线程」分开。然后再讲两个队列谁先谁后。

画面：一个 isolate 是一条执行线加两个队列。微任务是插队的小纸条，事件队列是正常排队的点击、定时器和 I/O。当前这段同步代码跑完，先把小纸条全部做完，再取一个正常事件，然后把期间新来的小纸条再做完。

来源队列什么时候跑
当前这段同步代码不在队列里，正在执行马上，跑完才轮到队列
scheduleMicrotask、Future.microtask、Future 完成后的续体微任务队列同步代码之后，下一个事件之前，全部清空
Future(() {})、Timer、手势、网络和文件完成事件队列微任务空了之后，一次取一个

决策清单：

  • 想排在点击和定时器前面、又不能太重 → 微任务。微任务里不要再无限追加微任务，否则下一帧和点击一直轮不上。
  • 普通的稍后执行 → Future(() {}) 或 Timer，进事件队列。
  • await 停住的是当前这个 async 函数，不是这条 isolate。界面不会因此被这一个等待卡住。

哪些是保证，哪些是优化

  • 运行时保证：同一个 isolate 上不会有两段 Dart 代码同时执行。微任务清空之后才取下一个事件。
  • 不要说成语言只有一个线程：一个应用可以有多个 isolate。Dart VM 可以把它们安排到不同的系统线程上。没有的是「多个线程一起改同一块内存」。
  • 事件循环不是编译器优化。同步死循环连微任务也不会被插进来，因为当前这段代码还没结束。

常见误区

  • 「Dart 是单线程」说得太满。准确说法是：一个 isolate 里是单执行流，进程里可以有多个 isolate。
  • await 不是把事件循环冻住。
  • 微任务饥饿会让点击和下一帧饿死。这是调度规则，不是偶发优化。

口述版

同一个 isolate 上不会有两段 Dart 代码同时执行。整个进程可以有多个 isolate，所以不能把 Dart 说成进程里只有一条系统线程。

当前这段同步代码跑完之后，先把微任务队列清空，再从事件队列取一个事件；这个事件做完，再清空期间新来的微任务。

scheduleMicrotask、Future.microtask 和 Future 完成后的续体进微任务。Future(() {})、Timer、手势、网络和文件完成进事件队列。

await 只挂起当前这个 async 函数，事件循环继续。同步死循环还没结束时，微任务也插不进来。微任务里如果不停再添加微任务，事件队列里的点击和下一帧就一直排不上。

10. Isolate 是什么，和 Future 有什么区别

判断框架：先问要不要真正并行，以及两段代码能不能改同一块内存。Future 解决「稍后有个结果」，Isolate 解决「另一间房间同时干活」。

画面：Isolate 是一间自己带桌子和信箱的房间。每间房有自己的内存和事件循环，不能伸手改另一间房的对象，只能寄信。Future 只是这间房里一张稍后兑现的回执。

FutureIsolate
在哪跑当前 isolate 的事件循环另一条 isolate，VM 可以把它放到别的系统线程
内存同一堆各自的堆，不共享，所以不用加锁
怎么交结果await / thenSendPort 发，ReceivePort 收。消息通常拷贝一份
适合网络、定时、文件，等待时不占 CPU大 JSON、压图、加密这种吃 CPU 的活
开销很小启动和拷贝都有成本，不是包一层就更快

决策清单：

  • 只是等 I/O → Future。再包进 isolate 通常没有好处。
  • 做完一次、拿回一个结果 → compute 或 Isolate.run。
  • 要一直待在后台、反复收消息 → Isolate.spawn。
  • 一块内存想交给对方、避免再拷贝 → TransferableTypedData 这类所有权移交。交出去之后，原来的 isolate 不能再使用这块内存。这是移交，不是共享。

哪些是保证，哪些是优化

  • 运行时模型：isolate 之间不共享堆，通信靠消息。这是 actor 模型，不是编译器可选的优化。
  • 实现差异：VM 上 isolate 可以被安排到不同系统线程。Web 上的实现不一样，通常接近 Worker，不能假设和手机完全相同。
  • Flutter 引擎另外有界面、画像素、平台、文件这几条线程。它们不是 isolate。主 isolate 跑在界面线程上；你 spawn 出来的 isolate 不归这套线程编制。

常见误区

  • Isolate 不共享内存。全局变量也是各有一份，不是加锁就能一起改。
  • 「Dart 没有多线程」不准确。没有的是多个线程共享同一块内存这种写法。
  • 网络请求用 Future 就够。把等待再丢进 isolate，多的是启动和拷贝，不是并行收益。

口述版

每个 isolate 有自己的堆和事件循环，彼此不共享堆，所以不能直接改另一个 isolate 里的对象，也不用为共享内存加锁。VM 可以把不同 isolate 安排到不同的系统线程上，这才和 Future 不一样：Future 只是当前 isolate 的事件循环上稍后才有的一个结果，不会并行。

通信用 SendPort 发、ReceivePort 收，消息默认拷贝一份。TransferableTypedData 是把那块内存的所有权移交过去，交出去之后原来的 isolate 不能再使用，不是两家一起改同一块内存。

一次算完拿回结果用 compute 或 Isolate.run，要一直待在后台收消息用 Isolate.spawn。引擎的界面、画像素、平台、文件线程不是 isolate；主 isolate 跑在界面线程上，spawn 出来的 isolate 不归这套线程编制。只是等 I/O，用 Future 就够。

Web 上的实现通常接近 Worker，不要假设和手机完全相同。

三、框架入门

11. Flutter 和原生开发的差别

判断框架：先看界面是自己画出来的，还是把系统控件拼起来的。再看开发期的热重载和正式包的编译，这是两件不同的事。

画面：Flutter 交出去的是「这一帧界面应该长什么样」。框架对照上一帧更新，引擎里的图形库再画成像素交给 GPU。你不是拿着一个 Android 的 TextView 去改它的文字。

Flutter原生React Native（对照）
界面从哪来自绘。一般不用系统控件系统控件映射成系统控件，再用桥和 JavaScript 通信
各端长得一不一样同一套 Dart 界面，更容易一致各端各写更容易长得不一样
系统能力插件、Platform Channel，必要时用 PlatformView 嵌一块原生视图直接调用桥
正式包怎么跑手机和桌面提前编译成机器码（AOT）各平台自己的编译JavaScript 引擎加原生控件
开发期debug 边运行边编译（JIT），才能热重载看平台工具链看平台工具链

决策清单：

  • 要各端一致的复杂自绘界面 → Flutter 合适。写法是声明式：描述这份数据下界面长什么样，而不是找到某个控件再改文字。
  • 桌面小组件、很深的系统接口 → 仍然要原生配合，或者用 PlatformView 嵌进去。那一块就不是 Flutter 自绘。
  • 代价要主动说：安装包通常更大，平台差异靠插件补。

哪些是保证，哪些是优化

  • 框架模型：自绘和声明式更新是 Flutter 的架构，不是某次编译碰巧这么做。
  • 依版本和平台而定：画像素的库是 Skia 或 Impeller。较新稳定版在 iOS 和 Android 上 Impeller 常常是默认，其他平台可能仍是 Skia。不要说死成某一个。
  • 工具链，不是生产特性：热重载只存在于 debug 的 JIT。release 的 AOT 是发布构建，没有热重载。
  • 「流畅程度通常接近原生」不是语言保证。它依赖 AOT、自绘管线，以及你没有在界面线程上做重活。

常见误区

  • Flutter 不是永远碰不到原生视图。地图、网页这类可以用 PlatformView 嵌进来。
  • 热重载不是它比原生快的原因。那只在开发期。
  • 不要把 Skia 说成唯一引擎。Impeller 是否默认，看 Flutter 版本和目标平台。

口述版

Flutter 的普通界面是自绘：不创建系统控件，由引擎里的 Skia 或 Impeller 把这一帧画成像素，用哪个看版本和平台。写法是声明式，业务代码描述这份数据下界面长什么样，框架用新的 Widget 配置去更新已有的 Element 和 RenderObject，不是拿到一个 Android 的 TextView 再改文字。同一套 Dart 界面因此在各端更一致。

手机和桌面的 debug 是 JIT，才能热重载；release 是 AOT，没有热重载。热重载只在开发期，不是它比原生快的原因。

系统能力用插件和 Platform Channel；地图、网页这类可以用 PlatformView 嵌一块原生视图，那一块就不是自绘。安装包通常更大，很深的系统接口仍要原生配合。

流畅不是语言保证，它依赖 AOT、这条自绘管线，以及没有在界面线程上做重活。

12. Flutter 的整体架构

判断框架：从贴着操作系统的一层，问到贴着业务代码的一层：谁对接窗口和线程，谁跑 Dart 和画像素，谁提供 Widget。

画面：Embedder 是把门和插座接到操作系统上的人。Engine 是带着 Dart 运行时和画笔的发动机。Framework 是用 Dart 搭好的组件仓库，业务代码通常住在这里。

层主要用什么写干什么关键记忆
Embedder各平台自己的语言窗口和画布、创建线程、把系统事件送进引擎、注册插件线程是这一层创建的
Engine主要是 C++Dart 运行时、文字、图形、平台事件，通过 dart:ui 交给上层画像素的库是 Skia 或 Impeller，依版本和平台
FrameworkDart从下往上大致是绘制、手势、渲染、Widget、Material / Cupertino业务代码通常导入 package:flutter/material.dart

哪些是保证，哪些是优化

  • 架构约束：Engine 自己不创建线程。线程由 Embedder 创建，并且在引擎活着的这段时间里不能把这些线程换掉。
  • dart:ui 是 Framework 和 Engine 交界的那一层，不是整个 Flutter SDK。不要说「写 App 时直接导入 dart:ui 就等于用了整套框架」。
  • Skia 换成 Impeller 是引擎实现的演进，依版本和平台而定，不是三层架构本身变了。

常见误区

  • Framework 不是 dart:ui。Material 和 Widget 在 Framework 里，dart:ui 只是交界。
  • 不要说 Engine 自己 new 了四条线程。创建线程的是 Embedder。
  • 业务代码一般不直接对着 Engine 写，而是对着 Framework。

口述版

Flutter 自下而上是 Embedder、Engine、Framework。Embedder 对接窗口、线程、系统事件和插件。Engine 主要是 C++，包含 Dart 运行时和图形，通过 dart:ui 交给上层，画像素用 Skia 或 Impeller。Framework 用 Dart 写绘制、手势、渲染、Widget 和 Material。

线程是 Embedder 建的，引擎活着的时候不能换。

业务代码导入的是 material，不是整个引擎。

13. main 和 runApp 分别做什么

判断框架：先分清 Dart 进程从哪开始，以及 Flutter 的界面树从哪挂上。挂上不等于这一调用返回时像素已经画完。

画面：main 是开门。runApp 是把根 Widget 交给绑定层，Widget、Element、RenderObject 这三棵树和第一帧从这里排上日程。

是什么做什么
mainDart 程序入口你的启动代码。可以先做初始化，再调用 runApp
runApp框架入口确保绑定已经接上，把传入的 Widget 挂成根，调度第一帧
WidgetsFlutterBinding.ensureInitialized()提前准备绑定runApp 之前就要用插件时，先把这层连接准备好

决策清单：

  • 根 Widget 通常是 MaterialApp 或 CupertinoApp。常见写法是 main() { runApp(const MyApp()); }。
  • runApp 前面有 await 插件 → 先调用 WidgetsFlutterBinding.ensureInitialized()。
  • 改了 main 里的启动逻辑 → 热重载不会重新执行已经跑过的 main，要热重启。

哪些是保证，哪些是优化

  • 语言和框架约定：main 是 Dart 入口。runApp 负责挂根并调度帧，不是在这次函数返回前同步把整棵界面画完。
  • 开发期工具：热重载不重跑 main，热重启会。release 没有热重载，这不是框架在正式包里的行为。

常见误区

  • runApp 不是「把 Widget 画到屏幕上」这一个同步动作。
  • 改了启动代码却看不到效果，不是 runApp 没执行过，而是热重载没有重跑 main。
  • 在绑定还没准备好时就用插件，会在 runApp 之前失败。先 ensureInitialized。

口述版

main 是 Dart 程序的入口。runApp 先确保 WidgetsFlutterBinding 已经初始化，再把传入的 Widget 挂成根，并调度第一帧。这次调用返回时，并没有同步把整棵界面画完。

根通常是 MaterialApp 或 CupertinoApp。如果 runApp 之前就要用插件，先调用 WidgetsFlutterBinding.ensureInitialized()。

热重载不会重新执行已经跑过的 main，改了启动逻辑要热重启。

14. Widget 有哪几类，为什么不能改

判断框架：先记住一句话：Widget 是配置，Element 是活着的树节点，State 放在 Element 里，RenderObject 才负责布局和绘制。这道题问的是配置为什么不能改，以及状态到底跟谁走。

画面：Widget 是一张不能改的施工单，build 时会不断新开一张。Element 是树上的工位。StatefulWidget 把 State 交给 Element 保管，施工单换了，只要工位还在，State 就还在。

类型是什么状态放哪什么时候重新描述界面
StatelessWidget没有单独的 State 对象没有自己的 State。界面由构造参数和上层数据决定父组件给了一份新配置，或者它依赖的上层数据变了
StatefulWidget通过 createState 交出 StateState 由 StatefulElement 保存要 setState，或者用到的上层数据变了。它不会自己发现字段变了
InheritedWidget放在树上、可供下面登记依赖的配置数据在它自己的字段里，通知的是依赖者updateShouldNotify 为 true 时，登记过的组件重建
RenderObjectWidget用来配置一个 RenderObject布局和绘制在 RenderObject 上配置更新时走 Element 去更新 RenderObject，不是 Widget 自己画

决策清单：

  • 没有要跨帧记住的本地状态 → StatelessWidget。它也可以拿到会变化的数据，只是自己没有生命周期去订阅，变化来自父组件的新配置。
  • 要在这个节点活着期间记住字段、Controller、动画 → StatefulWidget。
  • 数据变了却没刷新 → 不是 StatefulWidget 坏了，是没有 setState，也没有依赖通知。

哪些是保证，哪些是优化

  • 框架模型：Widget 应是不可变配置，所以框架才能拿新旧两份来比。字段用 final 是语言层面锁住绑定。@immutable 是框架和分析器的约定。
  • Widget 会被频繁新建，所以要轻。真正留在树上的是 Element。这是设计，不是某次渲染优化碰巧复用了 Widget。
  • 如果配置本身还能被改掉，框架就分不清这次 build 到底变了什么。不可变是为了比较，不是为了「对象在运行时永远不能被别的代码碰到」这种更强的说法。你仍然不该去改它。

常见误区

  • Widget 不只是控件。间距、主题、继承数据的包装也是 Widget。
  • StatefulWidget 不会自己发现数据变了就重建。
  • StatelessWidget 也会被父级重建，只是没有 State 可以跨帧留着。
  • 不可变的是配置。Element 和 State 是可变的，它们才是活着的那一层。

口述版

Widget 是不可变配置，框架拿新旧两份来比，所以 build 里会不断新建，它自己要轻。真正留在树上、可以复用的是 Element。

StatelessWidget 没有单独的 State，界面由构造参数和它依赖的上层数据决定。StatefulWidget 通过 createState 创建 State，State 由 StatefulElement 保存；runtimeType 和 key 都没变、这个 Element 被复用时，State 还在。自己的字段变了，它不会自动重建，要 setState。父组件传入一份新配置，或者它 depend 过的 InheritedWidget 通知它，也会重建。

另外，InheritedWidget 用来让子孙登记依赖，RenderObjectWidget 用来配置 RenderObject，布局和绘制在 RenderObject 上，不在 Widget 上。

15. State 的生命周期

判断框架：按「创建一次、跟着依赖走、父级换配置、暂时离树、确定销毁」这条线讲。不要把「打开新页面」和「这个 State 被销毁」说成同一件事。

画面：State 比单次 Widget 活得长。Widget 是每次 build 可能换掉的配置，State 是 Element 口袋里那份一直在的数据。口袋还在，State 就在；口袋确定拆掉，才是 dispose。

方法什么时候干什么不要干什么
createState整个生命周期一次创建 State不要在这里订阅会变的东西
initState第一次挂到树上，一次订阅稳定数据源、创建 Controller。方法开头调用 super.initState()不能 Theme.of、MediaQuery.of 这种会向上查找并登记依赖的调用
didChangeDependenciesinitState 之后立刻一次；之后依赖的 InheritedWidget 变了再调用读 Theme、MediaQuery、Provider不要不比较就在这里无条件重发请求
build可能很多次只根据当前配置和 State 描述界面不改数据、不发请求、不订阅
didUpdateWidget父组件传入新 Widget，运行时类型和 key 都没变比较 oldWidget 和 widget，换订阅、重启动画自己 setState 不会走进这里
reassemble热重载开发期重新装配不是正式包里的生命周期
deactivate暂时从树上拿下来GlobalKey 换父节点时，随后可能再挂回去不要在这里释放资源。重写的话，末尾调用 super.deactivate()
dispose确定不会再挂回去释放 Controller、Timer、订阅，然后调用 super.dispose()不能再 setState

决策清单：

  • 父组件把 userId 换成另一个 → 在 didUpdateWidget 里取消旧订阅、再订新的。只写在 initState 里，页面会继续显示旧用户。
  • 异步回调回来 → 先看 mounted。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。写在 dispose 里面的代码当时还能读到 true。
  • 应用进后台再回来 → 走 WidgetsBindingObserver 的 AppLifecycleState，不是 deactivate。deactivate 只表示这个组件离开了树。
  • 打开新页面 → 旧页面的 State 通常还在，也还挂在树上，只是被盖住。不要说 push 会 dispose 旧页面。

哪些是保证，哪些是优化

  • 框架保证：上面的调用顺序和次数是 State 生命周期，不是编译器优化。super.initState() 放开头，super.dispose() 放在自己的释放逻辑之后。
  • debug 才有的检查：setState() called after dispose() 这类 FlutterError 包在 assert 里，profile 和 release 会去掉 assert。State 已经和 Element 断开后再调用，常见版本会因为 element 已经是空而抛错。检查被拿掉，不表示这次调用变得合法。
  • reassemble 是热重载这条开发期路径，正式包不会走它来更新你的 initState。

常见误区

  • super.initState() 写在方法末尾是错的。末尾调用 super 的是 deactivate 和 dispose 这一类。
  • push 新页面不等于旧页面 deactivate，更不等于 dispose。默认 maintainState 为 true。
  • dispose 里面 mounted 还是 true，不代表还能 setState。
  • 热重载不会重跑 initState。它会走 reassemble。

口述版

顺序是 createState、initState、didChangeDependencies、build。initState 只在第一次挂到树上时调用一次，开头调用 super.initState()。这里不能调用 Theme.of、MediaQuery.of 这种会向上查找并登记依赖的方法，那些放 didChangeDependencies。

父组件传入新 Widget、运行时类型和 key 都没变，走 didUpdateWidget；自己 setState 不走这里。

暂时从树上拿下来是 deactivate，GlobalKey 换父节点时随后可能再挂回去，不要在这里释放资源。确定不会再挂回去才 dispose，先释放 Controller、Timer 和订阅，再调用 super.dispose()。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。

打开新页面时，旧路由默认 maintainState 为 true，旧的 State 还挂在树上，不会因此 deactivate，更不会 dispose。应用进后台走 WidgetsBindingObserver 的 AppLifecycleState，不是 deactivate。

16. setState 做了什么

判断框架：状态变了，谁被标记、什么时候重建、重建多大。先讲这三步，再讲 Element 能不能复用。

画面：setState 先把你传入的回调马上跑完，再给当前这个 Element 贴一张「待 build」的条子。真正的 build 要等到这一帧的构建阶段。同一段同步代码里贴多少张条子，也只 build 一次。

步骤时机范围
执行回调同步，立刻只改你在回调里写的字段
markNeedsBuild()同步标记当前这个 Element 进待重建名单
build这一帧的构建阶段，或排到下一帧从被标记的 Element 开始重新描述子 Widget，不是整个应用
比较孩子build 产出新配置之后运行时类型和 key 都相同的 Element、RenderObject 留着继续用

决策清单：

  • 只有一小块在变 → setState 写在那一块自己的 State 上。写在页面最外层，里面那整棵子树都会重新 build。
  • 同一段点击处理里要改好几个字段 → 可以多次 setState，框架会合成一次 build。更好的写法是一次回调里改完。
  • 想让更小的区域听一个值 → 不要只靠外层 setState，用 ValueListenableBuilder、Selector 或 Bloc 的 buildWhen。
  • build 里发现自己想 setState、发请求或订阅 → 副作用放错地方了。build 一帧里可能走很多次。

哪些是保证，哪些是优化

  • 框架保证：回调同步执行；然后标记需要 build；不会在 setState 返回前把界面重画完；同一次事件循环里的多次标记会合并成一次 build。
  • 框架的复用，不是语言保证：新 Widget 和旧子节点按类型和 key 比较，对得上就更新原 Element。build 被调用，不等于 RenderObject 全部新建。
  • setState 是 Flutter 框架的方法，不是 Dart 语言特性。

常见误区

  • setState 不是立即重建，更不是立即重画。
  • 它不会把整个应用都重建一遍，但写在根上时，这棵子树的 build 都会跟着走。
  • 多次 setState 不是多次 build。同一段同步代码里会合并。

口述版

setState 先同步执行回调，再对当前 Element 调用 markNeedsBuild。这次调用返回前不会把界面重画完，build 发生在这一帧的构建阶段，或排到下一帧。同一次事件循环里的多次标记合并成一次 build。

重建从被标记的 Element 开始，重新描述它的子 Widget，不是整个应用。孩子里 runtimeType 和 key 都相同的 Element 会更新原节点，RenderObject 也不因此全部新建。

所以要写在真正变化的那个 State 上，而且不能写在 build 里。

17. BuildContext 是什么

判断框架：BuildContext 问的是「这份配置现在挂在树上的哪个位置」，不是问 Widget 本身，也不是问一个全局上下文。

画面：BuildContext 是 Element 对外露出的接口，一张位置凭证。Theme.of、Navigator.of、Provider.of 拿着这张凭证顺着父节点往上找，并在找到的 InheritedWidget 上登记「以后变了叫我」。查找走的是 Element 树。

用法走哪会不会登记依赖
Theme.of、MediaQuery.of、Navigator.of、dependOnInheritedWidgetOfExactType从当前 Element 向祖先找最近的那个会。之后 updateShouldNotify 为 true 时会重建你
只查找、不 depend 的读法，例如 Provider 的 read同样向上找不会。当时能读到，之后变了不通知
initState 里的 contextElement 已经挂上，context 不是 null这里还不能做「查找并登记」

决策清单：

  • 要跟着主题、MediaQuery、Provider 变 → 在 didChangeDependencies 或 build 里用 of，不要写在 initState。
  • 只取一次当前值，不希望以后刷新 → 用不登记的读法，并接受它不会再通知你。
  • 跳转、发请求、订阅 → 放生命周期或点击回调。放进 build，每次重建都会再做一次。
  • 异步回来再用 context → 先看 mounted。State 和 Element 断开之后，这张位置凭证不能再当树上的位置用。

哪些是保证，哪些是优化

  • 框架保证：BuildContext 由 Element 实现。每个 Element 一份，不是全局单例。of 向上查找并登记依赖，是 InheritedWidget 的机制。
  • initState 里禁止 depend 的检查，在 debug 下会用 assert 拦住。这是框架约束。release 拿掉 assert，不表示这个时机突然变得正确。

常见误区

  • BuildContext 不是 Widget，也不是 State 的别名。State 通过它找到自己的 Element。
  • initState 里已经能拿到 context，不等于能调用 Theme.of。
  • 向上找的是 Element 树，不是「在 Widget 配置对象上递归」。

口述版

BuildContext 由 Element 实现，每个 Element 一份，表示这个节点在 Element 树上的位置，不是 Widget，也不是全局单例。

Theme.of、MediaQuery.of、Navigator.of，以及默认会监听的 Provider.of，都从当前 Element 向祖先查找最近的那个，并用 dependOnInheritedWidgetOfExactType 把当前 Element 登记为依赖者；之后 updateShouldNotify 为 true 时，重建的是这些依赖者。只查找、不 depend 的读法，当时能读到，之后变了不通知。

查找走的是 Element 树，不是在 Widget 对象上递归。initState 里 context 已经有了，但还不能做这种查找并登记，要放到 didChangeDependencies 或 build。发请求和跳转不要放进 build。

18. Key 有什么用

判断框架：Key 解决的是同一次更新里，「这个父节点下面，哪个孩子还是上次那个孩子」。它不解决滑出屏幕后保不保活，那是另一题。

画面：没有 Key 时，框架按座位号对人。列表只是换了顺序，State 还坐在原来的椅子上。Key 是贴在配置上的身份牌。类型相同，而且身份牌相同，才把原来的 Element 留下来。

Key怎么算对上什么时候用关键记忆
没有 Key同一个父节点下，按位置和运行时类型孩子不会重排，也没有要保住的 State重排后 State 会留在老位置
ValueKey用值的 ==列表项的稳定 id列表最常用这个
ObjectKeyidentical，必须是同一个对象你本来就拿唯一实例当身份两个内容一样、但是新创建的对象，对不上
UniqueKey每次都是一个新身份故意丢掉旧 State写在 build 里，旧 State 每次都被丢掉
GlobalKey整棵树里同一个 key 只能挂一处换了父节点还要留 State，或要拿 currentState、currentContext、currentWidget框架用一张全局表记着它，不能当日常状态管理

决策清单：

  • 列表每一项的 State 串了 → 给每一项加 ValueKey(item.id)，不是给整个 ListView 加一个 Key。
  • 本地 Key 只在同一个父组件的子组件之间比较。换了父组件还要留 State → 才考虑 GlobalKey。
  • 只是想重置这个子树 → 可以换一个新 Key。不要在每次 build 里无意识地 UniqueKey()。

哪些是保证，哪些是优化

  • 框架保证：更新孩子时，runtimeType 和 key 都相同才复用 Element。这是 updateChildren 的规则，不是编译器优化。
  • ObjectKey 用 identical，ValueKey 用 ==。这是这两个类自己的相等实现，不要记反。
  • GlobalKey 能在换父节点时把 State 挪过去，代价是全局登记。复用 Element 能少做销毁和创建，但 Key 本身不是一项渲染加速开关。

常见误区

  • ObjectKey 不是按内容 == 比较。内容一样的两个新对象对不上。
  • 给 ListView 本身加 Key，救不了每一项串位。
  • GlobalKey 不是用来做日常状态管理的。它适合少量跨组件访问。

口述版

Key 用在 updateChildren 里：同一个父节点下，runtimeType 和 key 都相同，才复用原来的 Element。没有 Key 时按位置和运行时类型匹配。列表只是换了顺序，原来那个下标上的 Element 会被更新成这个下标上的新 Widget，State 留在这个下标上，不跟着数据项走。

列表项用 ValueKey，按值的 == 比较。ObjectKey 用 identical，内容一样的两个新对象对不上。UniqueKey 每次构造都是新对象，和上一次的 key 不相等，写在 build 里旧 Element 不会被复用，State 被丢掉。

本地 Key 只在同一个父节点的孩子之间比较。GlobalKey 登记在全局表里，同一个 key 整棵树只能挂一处；换父节点时可以把原来的 State 挪过去，也能拿到 currentState，不适合当日常状态管理。

19. 滑出屏幕后，状态怎么留住

判断框架：这道题问的是懒加载把子项从树上拿掉之后，State 还留不留。它和 Key 那道题不是同一件事：Key 管同一次更新里的身份，保活管滑出缓存范围之后还拆不拆工位。

画面：ListView、TabBarView、PageView 默认只把附近的孩子留在树上，滑远了就 dispose。保活是这个孩子举手说：我走远了也别拆我的工位。

你想留住什么用什么留在哪
滑走之后，输入框、滚动内部的 State 还在AutomaticKeepAliveClientMixin，wantKeepAlive 返回 true，build 里先 super.build(context)继续留在树上，不显示也不等于 dispose
只记得滚动位置PageStorageKey不必把整个 State 留着
同一次更新里不要串项项上的 ValueKey和保活无关
wantKeepAlive 后来变成 false调用 updateKeepAlive()否则框架还按旧的来
 
class _TabState extends State<TabPage> with AutomaticKeepAliveClientMixin {
  @override
  bool get wantKeepAlive => true;

  @override
  Widget build(BuildContext context) {
    super.build(context);
    return const Text('kept');
  }
}

决策清单：

  • 是 ListView、Tab、PageView 这种会懒构建的组件，滑走后状态丢了 → 给那个 State 混入保活。
  • 普通 Column 里的孩子不会因为「滚出屏幕」被拆掉，因为它们根本没被懒构建。这种情况不要靠 KeepAlive 解释。
  • 保活会占内存。只需要滚动偏移时，用 PageStorageKey 就够。

哪些是保证，哪些是优化

  • 框架机制：保活是 AutomaticKeepAlive 和可滚动组件之间的约定。忘了 super.build(context)，就不会登记成不要销毁。
  • 列表的缓存范围、Tab 是否预加载相邻页，依组件和参数而定，不要说成「滑出一像素就一定 dispose」。
  • 保活不是渲染优化开关。它是用内存换「不要销毁」，包太多会更占内存。

常见误区

  • 保活不等于 Key。两件是不同的事。
  • 忘了 super.build，wantKeepAlive 不会生效。
  • 保活不是让它继续画在屏幕上，只是离开缓存范围后仍留在树上。

口述版

ListView、TabBarView、PageView 这类会懒构建的组件，子项离开缓存范围后会从树上卸掉，State 跟着 dispose。

要留住，就让 State 混入 AutomaticKeepAliveClientMixin，wantKeepAlive 返回 true，并在 build 里先调用 super.build(context)。这一步才会向祖先登记不要销毁；忘了调用，wantKeepAlive 不会生效。登记之后，子节点离开缓存范围仍留在树上，只是不再显示，不是继续画在屏幕上。

只记滚动位置用 PageStorageKey，不必把整个 State 留在树上。wantKeepAlive 后来变成 false，要调用 updateKeepAlive()，否则框架还按旧值保留。

这和 Key 的 updateChildren 匹配不是一件事。普通 Column 里的孩子本来就没有被懒构建卸掉。

20. 热重载和热重启

判断框架：先分清开发期工具和发布构建。热重载问的是「进程还在，State 还在不在」；热重启问的是「Dart 入口重跑了没有」；AOT 问的是正式包还能不能做这两件事。

画面：热重载是在还活着的进程上打补丁，然后重新 build，口袋里的 State 尽量留着。热重启是把 main 再走一遍，口袋清空，但原生工程不重装。

热重载热重启完全重新运行
main / initState不重跑已经执行过的重跑 main，State 重新创建进程重来
State尽量保留，并走 reassemble、重新 build清空清空
改不了什么已初始化的全局变量和静态字段、枚举形状、泛型签名、原生代码原生代码、插件注册、资源仍不一定生效可以带上原生和资源
哪种构建有debug 的 JITdebug任意模式都要重新启动进程

决策清单：

  • 只改了 build 里的界面 → 热重载。
  • 改了 initState 或 main，却看不到效果 → 热重启。原来的 State 还在，初始化不会再跑。
  • 改了插件、资源或原生代码 → 完全重新启动，不是热重启就够。

哪些是保证，哪些是优化

  • 编译模式：手机和桌面的 debug 是 JIT，边运行边编译。profile 和 release 是 AOT，提前编译成机器码。这是工具链，不是 Dart 语法。
  • 开发期工具，不是生产特性：热重载会找出改过的部分、送进正在运行的程序、再重建 Widget。它不是只把画面重画一遍，也不是把应用关掉再打开。release 没有这项能力。
  • Web 的 release 是编译成 JavaScript 或 Wasm，不要把手机上的 JIT / AOT 原句套过去。Web 的 release 同样不能热重载。

常见误区

  • 热重载不等于热重启，更不等于重装应用。
  • 改了 initState 没效果，是因为旧 State 还在，不是热重载失败。
  • debug 能热重载，不能用来证明 release 的性能。

口述版

热重载只在手机和桌面 debug 的 JIT 里有：把改过的库送进正在运行的 isolate，不重跑已经执行过的 main 和 initState，原来的 State 对象还在，然后走 reassemble 再 build。

已经初始化的全局变量和静态字段、枚举形状、泛型签名、原生代码，这次更新换不掉。

热重启会重新执行 main，State 重新创建，但不会把原生工程重新装一遍。

改了插件、资源或原生代码，要完全重新启动进程。

profile 和 release 是 AOT，没有热重载。

21. InheritedWidget 是干什么的

判断框架：数据放在比较靠上的位置之后，谁登记了依赖，谁才会因为这次通知而重建。没登记的人，只是当时读到了值。

画面：InheritedWidget 是挂在树上的公告板。子节点用 of 去看的时候，会在公告板上写下自己的名字。公告更新时只叫这些名字，不是把楼下所有房间都拆掉重建。

做法当时能不能读到之后变了会不会重建你
dependOnInheritedWidgetOfExactType、Theme.of、MediaQuery.of、Provider 的 watch能，找到最近的那一个会，但要 updateShouldNotify 返回 true
只向上找、不登记；Provider 的 read能不会
updateShouldNotify 返回 false新配置会换上不通知已经登记的人

决策清单：

  • 子组件要跟着这份数据变 → 用会登记依赖的 of 或 watch。
  • 回调里只取当前值，不希望订阅 → read 这种不登记的读法。
  • initState 里不能查找并登记 → 放到 didChangeDependencies。
  • Provider 抛出找不到 → 先看读取的位置是不是在 Provider 的下面。沿树向上找不到，就不是「数据没刷新」。

哪些是保证，哪些是优化

  • 框架保证：依赖登记之后，updateShouldNotify 为 true 时，框架通知这些依赖者重建。通知本身不是把 InheritedWidget 下面的所有节点一律标脏。
  • InheritedWidget 自己的 child 如果在父级重建时还是同一个 Widget 实例，子树可以走普通的 identical 跳过。如果父级每次都 new 一个新的 child，那是普通的父级重建，和「通知依赖者」不是同一条路径。
  • Provider 是 InheritedWidget 外面的写法。数据怎么顺着树传下去，根子还是 InheritedWidget。这是封装，不是另一套渲染机制。

常见误区

  • InheritedWidget 不是「子树全部重建」。
  • 没登记就只是当时读到，不会订阅。
  • initState 里调用 of 是时机错了，不是 InheritedWidget 不能在第一帧读。

口述版

InheritedWidget 把数据放在祖先节点上。子组件调用 dependOnInheritedWidgetOfExactType，或 Theme、MediaQuery 的 of，或 Provider 的 watch，会找到最近的那一个，并把当前 Element 登记成那个 InheritedElement 的依赖者。

祖先换成新的 InheritedWidget 之后，只有 updateShouldNotify 返回 true，框架才通知这些依赖者重建，不是把下面所有节点标脏。返回 false 时新配置会换上，已经登记的依赖者也不通知。

只向上找、不登记的读法，例如 Provider 的 read，当时能读到，之后变了不重建。这种登记不能写在 initState，要放在 didChangeDependencies。

22. 状态管理怎么选

判断框架：状态变了，谁负责通知、通知谁、谁重建、重建多大、这份状态要活多久。先把地图画出来，再按场景选，不要先报一个库名。

画面：setState 是在自己的工位上贴「待 build」。InheritedWidget 是树上的公告板，只有登记过的人会被叫到。Riverpod 把状态放进独立容器，读取时不用拿着 BuildContext 往上爬。Bloc 是界面把「发生了什么」交出去，业务算出新状态再交回来。

方案状态放哪谁通知、重建谁适合
setState这个 State 的字段你标记当前 Element，这棵子树 build局部、短命、逻辑和界面写在一起
ValueNotifier + ValueListenableBuilder一个可监听的值只有包着的 builder还是局部，但要缩小重建
InheritedWidget上层组件里updateShouldNotify 为 true 时，只重建登记过的顺着树向下共享
ProviderInheritedWidget 的常用封装watch 登记，read 不登记；select / Selector 可以更细树内共享。读的位置必须在它下面
Riverpod独立的 Provider 容器，不靠 BuildContext 向上找ref.watch，可以只监听一个字段；没人听时可以释放跨页面、要测试、要离开这棵组件树
Cubit / Bloc业务对象里。Cubit 直接调用方法交出新状态；Bloc 多一层事件BlocBuilder 的 buildWhen 决定重建不重建界面和业务要分开测。事件多就用 Bloc，简单状态用 Cubit
GetX常把状态、路由和依赖放在一起调用直接，刷新从哪来不如上面好追能说清代价再选，不要只报库名

决策清单：

  • 只是这个组件里的字段？ → setState。
  • 还是局部，但父级 build 太重？ → 把 State 拆小，或用 ValueListenableBuilder。
  • 要沿树给下面用？ → InheritedWidget 或 Provider。
  • 要精细控制重建范围？ → Selector、context.select、Riverpod 的 select、BlocBuilder 的 buildWhen。
  • 跨页面，而且不希望绑着 BuildContext、逻辑要单测？ → Riverpod 或 Bloc。
  • 事件要按类型展开？ → Bloc。只是几个方法改状态？ → Cubit 就够。
  • 团队已经统一某个库 → 先服从团队，再讲你知道的边界。

哪些是保证，哪些是优化

  • 框架保证：setState 只标记当前 Element。InheritedWidget 只通知依赖者。这些重建范围是机制，不是换一个库就会自动变小。
  • Provider 仍然从当前位置顺着父组件往上找。Riverpod 把状态放在独立容器里，就是为了不用在这棵组件树上找。这是库的设计差异。
  • 「select 能少重建」依赖你真的只订阅了那个字段。父级如果整页 setState，下面的优化可能根本走不到。

常见误区

  • Provider 找不到，通常是读取的位置不在它下面。read 能拿到当前值，但之后变了也不会刷新。
  • 简单页面套一整套 Bloc，和复杂业务只靠一层层 setState，都是边界选错，不是框架做不到。
  • 性能问题先看是谁在重建，不要先换状态管理库。

口述版

先看状态放在哪、谁被通知、重建哪一段、要活多久。只在这个 State 的字段里，用 setState，它只把当前 Element 标成需要 build。还想把重建缩到一个值，用 ValueNotifier 和 ValueListenableBuilder，重建的是包着的那个 builder。

要沿 Element 树向下共享，用 InheritedWidget 或 Provider：watch 会 depend，read 不登记，所以当时能读到、之后变了不刷新；读的位置必须在 Provider 下面。

Riverpod 把状态放在独立的 Provider 容器里，不从 BuildContext 向上找；ref.watch 可以只订阅一个字段，没有监听者时可以释放。

Cubit 在业务对象里用方法交出新状态；Bloc 再多一层事件，界面把事件送进 Bloc，BlocBuilder 用 buildWhen 决定要不要重建，业务对象可以离开 Widget 测。

GetX 常把状态、路由和依赖放在一起，调用处直接改状态，但这次重建是哪个响应式对象触发的，不如 markNeedsBuild 或 buildWhen 从调用点看得清。

选型看这些边界，不是先报一个库名。

23. Navigator 和 MaterialApp 做了什么

判断框架：先问页面栈谁管，再问被盖住的那一页还在不在树上。打开新页面，默认不是把旧页面卸载掉。

画面：Navigator 是一叠页面。push 是往上再放一张，下面那张通常还在，只是被挡住。pop 才从栈上拿走，拿走的那张才会 dispose。

东西作用关键记忆
Navigator打开、返回、替换，以及页面之间的动画管的是路由栈，不是单个 Widget 的 State
MaterialApp放好主题、本地化等，并创建一个 Navigator不只是套一层视觉风格
Navigator.of(context)从当前位置向上找最近的那个嵌套导航器时，最近的不一定是根上那个
push匿名路由，直接给出页面不需要先起名字
pushNamed用名字找页面对应关系写在 routes 或 onGenerateRoute
go_router一份路由表对应地址适合深链、Web 地址、登录拦截。栈不复杂时不必上

决策清单：

  • 页面里直接打开下一页 → push。要统一路径、深链 → 命名路由或 go_router。
  • 下一页要把结果交回来 → final result = await Navigator.push(...)，下一页 pop(result)。
  • 跳转放点击回调，或者放在导航条件已经确定之后。不要放在 build 里，否则每次重建都会再打开一页。
  • 页面 A 打开页面 B：A 的 State 通常还在，也还挂在树上，只是被盖住，不会重新走 initState。只有 A 被从栈里拿掉，才会 dispose。这个开关是 maintainState，默认 true。

哪些是保证，哪些是优化

  • 框架行为：maintainState 默认 true，被盖住的路由子树留在内存里。这不是编译器顺便做的缓存，而是路由的默认策略。
  • 路由动画、以及被盖住的页面是否还在继续 build，依具体 Route 和 TickerMode 而定。不要说成「被盖住就完全没有代码在跑」或「一定每帧都在 build」。
  • go_router 是路由库，不是 Navigator 的替代运行时。它底下仍然要落到页面栈上。

常见误区

  • 打开新页面时，旧页面默认没有离开树。老说法「push 会 deactivate 旧页面」是错的。
  • MaterialApp 不只是主题，它会把 Navigator 放好。
  • 在 build 里 push，每次重建都会再开一页。

口述版

Navigator 管的是路由栈：打开、返回、替换，以及路由之间的转场，不是单个 Widget 的 State。MaterialApp 会放好主题和本地化，并创建一个 Navigator。Navigator.of(context) 从当前 Element 向上找最近的那个，嵌套时不一定是根上那个。

直接 push 是匿名路由，不需要先起名字；pushNamed 用 routes 或 onGenerateRoute 按名字找页面。await push 的结果就是下一页 pop 时交回的值。

A push B 时，A 默认 maintainState 为 true，这条路由的子树仍挂在树上，不会因此 deactivate 或 dispose，也不会重新走 initState。只有 A 被从栈里移出才会 dispose。上面还有别的路由时，旧路由是否还在 build，看具体 Route 和 TickerMode，不是上面多了一页就完全没有代码在跑，也不是一定每帧都在 build。

深链和 Web 地址再用 go_router，它底下仍然落到页面栈上。不要在 build 里 push，否则每次重建都会再打开一页。

24. 动画怎么做，vsync 是什么

判断框架：先问进度谁拿着：是框架帮你从旧值过渡到新值，还是你自己拿着一个控制器。vsync 问的是这个进度跟谁的节拍走。

画面：隐式动画是你只改终点和时长，框架开车。显式动画是你拿着方向盘：一个 0 到 1 的进度，再映射成宽度或透明度。vsync 是屏幕每次刷新时的节拍器，动画跟节拍走，不在两次刷新之间空转。

隐式动画显式动画
你提供什么目标值和 durationAnimationController 产生 0 到 1，Tween 映射成实际值
例子AnimatedContainer、AnimatedOpacity、AnimatedPaddingAnimatedBuilder、FadeTransition
能不能中途停、重复、跟手不好停，也不好把几段接起来可以。需要这些控制时再上控制器
节拍框架内部也跟帧走你要把 vsync 交给控制器

细节：跟这个信号走的计时器叫 Ticker。一个 State 只有一个动画，用 SingleTickerProviderStateMixin。要同时跑好几个，用 TickerProviderStateMixin。页面不在屏幕上、或 TickerMode 关掉时，Ticker 会停。AnimationController 要在 dispose 里释放，否则 Ticker 还挂着。

决策清单：

  • 只是某个属性要从现在的值变到新的值 → 隐式动画。
  • 要开始、暂停、重复，或者跟着手势走 → 显式动画。
  • 两个页面上 tag 相同的 Hero → 跳转时同一块元素从旧位置移到新位置，不用自己算两边的坐标。
  • Controller 创建了 → dispose 里一定释放。

哪些是保证，哪些是优化

  • 框架机制：vsync 绑的是调度器的帧回调，不是你自己用 Timer 在两次刷新之间空转。Ticker 由 TickerProvider 提供。
  • 页面不可见时 Ticker 停，是 mixin 配合 TickerMode 的行为。不要把它说成「操作系统保证动画一定暂停」。
  • 屏幕是 120Hz 时节拍更密，前提是设备真的在用这个刷新率。刷新率是否生效，依设备和平台配置而定。

常见误区

  • vsync 不是一个抽象口号。落到代码上就是 TickerProvider，一般由 State 的 mixin 提供。
  • 隐式动画省事，但做不了手势驱动和复杂编排。
  • 不 dispose Controller，Ticker 会漏掉。这和 Widget 能不能 const 无关。

口述版

某个属性只要从当前值过渡到新的目标值，用隐式动画，给出目标值和 duration，例如 AnimatedContainer。

要开始、暂停、重复，或者跟着手势走，就自己持有 AnimationController。它默认的下限是 0、上限是 1，Tween 把这个进度映射成宽度或透明度，界面用 AnimatedBuilder 或 FadeTransition 订阅这个动画。

vsync 的类型是 TickerProvider，一般由 State 的 mixin 提供。Ticker 注册的是调度器的帧回调，一帧回调一次，不是用 Timer 在两次刷新之间自己计时。一个动画用 SingleTickerProviderStateMixin，同时多个用 TickerProviderStateMixin。页面不可见，或者 TickerMode 关掉时，mixin 会让 Ticker 停。这是 mixin 和 TickerMode 的行为，不是操作系统保证动画一定暂停。

AnimationController 要在 dispose 里释放，否则 Ticker 还挂着。

两个页面上 tag 相同的 Hero，跳转时由框架把同一块元素从旧位置移到新位置。

25. 布局时，约束和尺寸怎么传

判断框架：布局只有三句：父组件把允许范围传下去，子组件在范围里报自己的大小，父组件再决定子组件放在哪。尺寸不是子组件单方面宣布的，位置也不是子组件自己定的。

画面：父组件递下去一个盒子，盒子有最小宽度、最大宽度、最小高度、最大高度。子组件不能把盒子撑破，也不能自己决定钉在父组件的哪个角。英文就是：Constraints go down, sizes go up, parent sets position。

概念是什么关键记忆
BoxConstraintsminWidth、maxWidth、minHeight、maxHeight子组件交回去的尺寸必须落在里面
紧约束最小等于最大子组件的这一维尺寸被定死
无界某一维的最大是无限滚动方向上常见。孩子若还要一个有限的最大尺寸，就会报错
Expanded把 Flex 分到的那段主轴空间占满必须放在 Row、Column 或 Flex 里，主轴最大尺寸得有限
Flexible最多用这么多，子组件可以更小同样必须在 Flex 里
shrinkWrap让滚动组件按孩子把自己的尺寸量出来项很多时会一次布局很多孩子，不要拿它当默认解法

决策清单：

  • Column 里放纵向 ListView，报无界高度 → 给列表一个有限高度，例如外包 Expanded，而且外层 Column 自己的高度也得有限。
  • 纵向滚动组件里面再放 Expanded，或者再放一个自己也要无限高的 ListView → 同样是无界：里面要一个有限的最大高度，外面沿滚动方向给不出这个上限。
  • 文字在 Row 里横向溢出 → 这段文字没有有限的最大宽度。用 Expanded 或 Flexible 把宽度限制住。
  • 子组件想自己决定在父组件里的位置 → 做不到。用 Align、Center、Positioned 这种父布局。

哪些是保证，哪些是优化

  • 渲染协议：约束向下、尺寸向上、父定位置。违反就会在布局阶段失败。这不是一项可以关掉的优化。
  • 能跳过子树布局，是因为约束和尺寸没有变，RenderObject 可以标记为不必重来。那是框架优化。协议本身不变。
  • 滚动组件沿滚动方向给无限约束，是它的布局协议，不是 ListView 的 bug。

常见误区

  • 子组件不能返回超出 constraints 的尺寸，也不能自己设置自己在父组件里的位置。
  • Expanded 不是哪里都能用，必须在 Flex 里，而且主轴不能是无界的。
  • 项很多时用 shrinkWrap 把列表撑开，会一次布局很多子组件。

口述版

父组件把宽高的允许范围传给子组件，子组件在这个范围里决定自己的大小并交回去，父组件再决定子组件放在哪。这个范围是 BoxConstraints，最小和最大都有。

Expanded 是把分到的主轴占满，Flexible 是最多用这么多、可以更小，两者都必须放在 Row、Column 或 Flex 里，而且主轴最大尺寸得有限。

纵向 ListView 沿着滚动方向给的是无限高，里面再放 Expanded 或另一个 ListView 就会报无界高度。列表套在 Column 里，要给一个有限高度；项很多不要靠 shrinkWrap。

文字在 Row 里溢出，是缺少有限的最大宽度。

26. Widget、Element、RenderObject、Layer 和一帧渲染

判断框架：先把四个角色分开：配置、活着的树节点、布局绘制、交给合成的层。然后再讲一帧按什么顺序走。不要说 Element 永远不会重建。

画面：Widget 是一张不能改的施工单。Element 是树上的工位，拿着当前这张施工单；有状态时，口袋里还放着 State。RenderObject 是真正量尺寸、画图、判断点到了谁的人。Layer 是画完后交给画像素线程去合并的一层结果。

对象像什么变不变负责
Widget配置不可变，build 时频繁新建描述这一帧应该长什么样
Element树上的节点可变，能复用就复用拿着当前 Widget；创建并保存 State；更新孩子
RenderObject渲染对象可变，配置没变可以不重来布局、绘制、命中测试
Layer合成层按需更新交给 Raster 线程合成、变成像素

一帧怎么走：

  • build：写出新的 Widget 配置。
  • layout：父组件把约束传下去，子组件把尺寸交回去，父组件再摆位置。
  • paint：画出或更新 Layer。
  • 合成之后，画像素线程把这些层变成像素。RepaintBoundary 让一块区域单独重画，不要带着整页一起重画。

决策清单：

  • 父 Element 更新孩子：运行时类型和 key 都相同 → 沿用原来的 Element，只更新配置。有一个不同 → 卸掉旧的，再建新的。
  • 没有 Key 的列表只是换了顺序 → 同一层按位置和类型对上号，State 可能留在原来的格子上。
  • 某一小块经常重画 → 给它 RepaintBoundary。每一块都单独成层会多占内存，合成也更贵，不要到处包。

哪些是保证，哪些是优化

  • 框架模型：Widget 不直接画。Element 持有配置和 State。RenderObject 负责布局、绘制和命中。这是三棵树的分工，不是编译优化。
  • 可以跳过的部分：配置没变的 RenderObject 可以跳过重新布局或重新绘制。build 调用得很频繁，不等于整棵绘制树都重建。
  • 「Element 不会被重建，只会被更新」说绝对了。类型或 key 变了就会换新的。能复用是更新规则，不是永远不重建。

常见误区

  • Widget 不是树上的活节点，BuildContext 也不是 Widget。
  • build 次数多，不表示 Layer 和像素每次都全量重来。
  • 没有 Key 时不要以为框架能按业务 id 认出列表项。它只看位置和类型。

口述版

Widget 是不可变配置，build 时会新建，它不直接画。Element 拿着当前 Widget，有状态时保存 State；能复用就复用，runtimeType 或 key 变了就会换成新的。RenderObject 做布局、绘制和命中测试。Layer 是合成层，paint 时画出或更新，再交给 Raster 线程合成成像素。

父 Element 更新孩子时，runtimeType 和 key 都相同就沿用原来的 Element，只更新配置；有一个不同就卸掉旧的，再建新的。

一帧的顺序是 build、layout、paint，然后合成、光栅化。build 调用得多，不等于绘制树全量重建：配置没变的 RenderObject 可以跳过重新布局或重新绘制。RepaintBoundary 让一块区域单独成层重画；每一块都成层会多占内存，合成也更贵。

27. 线程模型，以及高刷新率上怎么看掉帧

判断框架：先分清四条引擎线程各自干什么，再看这一帧的时间花在 UI 还是花在光栅。最后才谈刷新率预算。不要把 isolate 和这四条线程说成同一套东西。

画面：Embedder 准备了四条长期稳定的任务通道。Dart 的 build、layout、paint 在界面线程上，主 isolate 也在这条线程。画成像素在 Raster 线程。系统消息在平台线程。图片解码在文件线程。

线程现在怎么叫干什么超时了像什么
平台线程Platform系统消息和插件调用原生侧卡住，Dart 在等平台结果
界面线程UI。主 isolate 跑在这里build、layout、paint，产出这一帧的图层Dart 太重，构建或布局超时
画像素线程Raster。旧文章里的 GPU 线程就是这一条把图层合成，再画成像素交给 GPU图层太多、大图、着色器编译。GPU 是硬件，不是这条线程本身
文件线程IO解码图片、读资源解码堵住时，不要把这件事做回 UI 线程

决策清单：

  • 屏幕发出「该画下一帧了」之后，界面线程做完构建，把图层交给画像素线程。哪一条超时，卡顿就出在它负责的步骤。
  • 用 DevTools 的帧图区分是 build、layout 慢，还是画成像素这一步慢。测量用 profile。debug 本身更慢，不能当成正式包的帧时间。
  • 第一次用到某种绘制效果，GPU 可能要临时编译着色器，卡在画像素这一步。Impeller 提前准备这些绘制程序，就是为了少做这种临时编译。它是不是默认，依版本和平台而定。
  • 120Hz 时一帧大约 8.3 毫秒，60Hz 大约 16.7 毫秒。系统是否真的给到这个刷新率，依设备和平台配置而定。Flutter 能跟上的前提是这一帧做完了，而且系统允许这个刷新率。

哪些是保证，哪些是优化

  • 架构约束：这四条线程由 Embedder 创建，引擎活着的时候保持稳定。Engine 自己不创建它们。
  • 和 isolate 的分界：主 isolate 跑在界面线程上。再用 spawn 开出来的 isolate，不归这四条线程编制，框架也不替你统一管理。
  • 着色器预编译、Impeller、光栅缓存，是引擎为了减少卡顿做的实现。它们不是「Dart 单线程所以不会掉帧」。

常见误区

  • 把 Raster 线程直接叫 GPU，容易让人以为卡在显卡上。旧称 GPU Thread 指的是这条光栅线程。
  • 掉帧不一定是 Dart 慢。也可能是光栅、着色器或图片解码。
  • debug 不掉帧不能说明 release 没问题，反过来也一样。

口述版

这四条线程由 Embedder 创建，引擎活着的时候保持这几条，Engine 自己不创建它们。平台线程处理系统消息和插件调用。主 isolate 跑在界面线程上，做 build、layout、paint，产出这一帧的图层。画像素线程，也就是 Raster，把图层合成再画成像素交给 GPU；旧文章里的 GPU 线程指的是这一条光栅线程，不是显卡本身。图片解码和读资源在文件线程上，不要把解码做回界面线程。

120Hz 时一帧预算大约 8.3 毫秒，系统是否真的给到这个刷新率，看设备和平台。掉帧用 profile 的帧图分清时间在界面线程还是画像素线程，debug 的帧时间不能当成正式包。

第一次用到某种绘制效果，可能要临时编译着色器，卡顿出在画像素这一步。Impeller 提前准备这些绘制程序，用来少做这种临时编译；它是不是默认，看版本和平台。

spawn 出来的 isolate 不归这四条线程编制。

28. 什么时候自定义布局

判断框架：先问现有的布局和绘制够不够。够就组合。只是样子特殊，就自己画。排列规则本身变了，才自己写 RenderObject。

画面：组合是用现成的积木搭。CustomPaint 是在一块已经布好局的区域上画画。自定义 RenderObject 是连「怎么量、怎么摆」都自己定，但仍然要服从父组件递下来的约束。

层级什么时候用你改什么
组合间距、点击、状态用现有 Widget 能做包一层。这是默认选择
CustomPaint / CustomPainter图表、特殊形状。Row、Stack 摆得开，只是画不出来只画。位置和大小仍交给现有布局
RenderObjectWidget + RenderBox排列规则，现有布局表达不了重写怎么算大小、怎么画、怎么判断点到了谁

决策清单：

  • 能用 Row、Column、Stack、Padding、CustomPaint 拼出来 → 不要写 RenderObject。
  • 真的要自定义布局 → Widget 对外是配置，Element 负责更新和挂到树上，RenderObject 真正布局和绘制。三件套各管一段。
  • 算大小必须落在父组件给的范围内，再把尺寸交回去。自己在父组件里的位置，由父组件决定。
  • 同时要想无障碍信息 semantics、要传给父布局的 parentData，以及这块区域要不要单独重画 isRepaintBoundary。

哪些是保证，哪些是优化

  • 渲染协议：自定义 RenderBox 也不能违反约束向下、尺寸向上、父定位置。这不是可选优化。
  • isRepaintBoundary 决定这块会不会单独成层。成层能少带动别人重画，也会增加内存和合成成本。它是取舍，不是写上就更快。

常见误区

  • 继承一个 Widget 再重写 build，那是组合，不是自定义布局协议。
  • 不要在 paint 里偷偷改布局。下一轮约束会对不上。
  • 一上来写 RenderObject，通常是把能组合的东西复杂化了。

口述版

先用现有 Widget 拼。只有要画的形状特殊，用 CustomPaint，位置和大小仍然交给现有布局。

排列规则用 Row、Column、Stack 都做不到，才实现 RenderObjectWidget 和 RenderBox，重写算大小、绘制和命中。三件套里，Widget 是配置，Element 负责挂到树上并更新，RenderObject 真正布局和绘制。

算大小必须落在父组件给的约束里，再把尺寸交回去；自己在父组件里的位置由父组件决定。还要提供 semantics，把交给父布局的数据放进 parentData，并用 isRepaintBoundary 决定这块会不会单独成层。成层能少带动旁边重画，也会多占内存、让合成更贵。

29. 一次点击为什么只有一个组件响应

判断框架：一次点击先做命中测试，再进手势竞技场。最后只有一个胜者，所以不是「事件丢了」，而是竞争分出了胜负。

画面：手指按下，先找出这个点落在哪些组件里，得到一条从最里面的子组件到外层父组件的路径。路径上通过 GestureDetector 注册的识别器进入同一个竞技场。手指移动或抬起时分出胜负，胜者才收到这次手势。

角色进不进竞技场结果
GestureDetector 的 onTap、拖动等进 Gesture Arena和别的识别器互斥，最后通常只留一个胜者
列表的滑动进手指移动超过一小段距离，滑动获胜，按钮的点击取消
Listener不进直接收按下、移动、抬起。父组件只想观察，用这个，不要再叠一个会互抢的 onTap
HitTestBehavior决定空白算不算点中自己默认只认点中了子组件。设成 opaque，整块区域都算点中

决策清单：

  • 父子都写了 onTap → 通常只有子组件收到。抬起时如果还剩多个，先加入竞技场的那个赢。命中路径从里向外加入，所以一般是更靠里的子组件。
  • 父组件只是想知道手指在自己范围内动过 → 用 Listener，不要再加一个 onTap 去和子组件抢。
  • 列表里的按钮和滑动抢 → 这是竞技场分出了胜负。超过触摸阈值后滑动赢，点击被取消。
  • 透明区域也要点中自己 → behavior: HitTestBehavior.opaque。

哪些是保证，哪些是优化

  • 框架机制：命中测试产出一条路径，手势识别器在竞技场里竞争。这不是事件系统随机丢事件，也不是编译器优化。
  • 「先加入的获胜」是抬起时仍未分出胜负的规则。如果某个识别器更早宣布自己胜出或失败，例如滑动超过 slop，就按那个结果，不必等到抬起。
  • 手势阈值的具体像素依设备和手势设置而定，面试说出「超过一小段移动，拖动赢、点击取消」即可，不要背死一个魔法数字。

常见误区

  • 不是父组件收不到指针，而是 onTap 这种识别器在竞技场里输了。
  • Listener 可以观察指针，同时不把子组件的 tap 挤掉。
  • 列表滑动把按钮点击取消，是竞争结果，不是点击事件丢失。

口述版

手指按下后，先找出点中了哪些组件，得到从最里层到外层的一条路径。GestureDetector 注册的识别器进入手势竞技场，最后只有一个获胜，所以父子都写了 onTap 时，通常只有子组件收到。

抬起时如果还剩多个，先加入的那个赢，一般就是更靠里的子组件。列表里的按钮和滑动会抢，移动超过一小段距离，滑动获胜，点击取消。

父组件只想观察指针，用 Listener，不要再叠一个 onTap。behavior 设成 opaque 时，空白处也算点中自己。

30. Flutter 如何和 Android / iOS 通信

判断框架：先看这次是「把消息编好异步送去原生」，还是「按 C 的调用方式直接调函数」。系统界面和权限对象走消息；已经有的 C 库或极频繁的调用，再考虑 FFI。

画面：Platform Channel 是两边约好编码的异步信箱。参数先装进标准信封，送到原生，再把结果拆回来。FFI 是直接拨 C 函数，少一次装拆，但内存里字段怎么排列要自己管。

方式形状适合
MethodChannel调用一次方法，带回一个结果或一个错误要「调用一次、拿一个结果」
EventChannel原生不停把事件推过来，Dart 这边是 Stream传感器、扫码这种连续回调
BasicMessageChannel按约定编码双向传消息不限定成一次请求、一次返回
dart:ffi按 C ABI 直接调函数已有 C 或 C++ 库，或者调用非常频繁、不想每次都走消息

决策清单：

  • 一次请求一个结果 → MethodChannel。原生要连续上报 → EventChannel。不要在原生那边用一个死循环占住这条通道。
  • 参数和返回值要能按 StandardMessageCodec 装进去：空、布尔、整数、小数、字符串、几种定长字节和数值数组，以及 List 和 Map。自定义对象先拆成这些。
  • 系统界面、Activity、权限这类平台对象 → 仍然用 Channel，不要用 FFI 硬拿。
  • 热路径上的 C 库 → FFI，并自己管内存。少了一次编解码，不代表更简单。

哪些是保证，哪些是优化

  • 框架行为：通道不会自动帮你切到正确的线程。Dart 这边在主 isolate、也就是界面线程上收发。原生那边要把调用切到它自己要求的线程，例如要碰 UI 时切到平台主线程。
  • 消息会按 codec 编解码，这是通道的成本，不是编译器可有可无的一步。FFI 省掉的是这次装拆，换来的是你自己保证调用约定和对象生命周期。
  • 具体插件内部用 Channel 还是 FFI，依实现而定。不要说每个插件都只用 MethodChannel。

常见误区

  • Platform Channel 不是线程安全的自动切换。原生线程要自己切。
  • EventChannel 在 Dart 侧是 Stream，不是再包一个 MethodChannel 死循环。
  • FFI 适合 C ABI，不适合拿来随便操作 Android 的 Activity 或 iOS 的 UI 对象。

口述版

Platform Channel 是异步消息：参数和返回值按 codec 编解码，不是共享原生对象。一次方法、一个结果或一个错误，用 MethodChannel。原生连续上报、Dart 侧拿到 Stream，用 EventChannel，不要在原生那边用死循环占住通道。不限定成一次请求一次返回，用 BasicMessageChannel。

StandardMessageCodec 能直接装的是 null、布尔、整数、小数、字符串、定长的字节和数值数组，以及 List 和 Map；自定义对象先拆成这些。

通道不会自动切线程：Dart 这边在主 isolate、也就是界面线程上收发，原生要把调用切到它自己要求的线程，例如碰 UI 时切到平台主线程。

已经有 C 或 C++ 库，或者调用非常频繁、不想每次都走消息，用 dart:ffi，自己保证调用约定和对象生命周期。Activity、权限这类平台对象仍然走 Channel，不用 FFI 去拿。

31. 包和插件有什么区别

判断框架：先问这份依赖里有没有各端实现。纯 Dart 是包。包再加上 Android、iOS 或其他平台实现，才是插件。通道是通信办法，插件是把办法和实现打包给别人用的形式。

画面：package 是一个可以写进 pubspec 的代码包。plugin 也是这样一个包，只是口袋里还有平台工程，用来碰系统能力。业务侧只依赖它的 Dart 接口。

包 package插件 plugin
里面有什么Dart 代码、Widget、工具也是一个包，另外带 Android、iOS 或其他平台实现
碰不碰系统不碰通常要碰
怎么调到原生不需要一般通过 Platform Channel 或 FFI。不是每个插件都只用 MethodChannel

决策清单：

  • 纯 Dart 的工具和 Widget → 做成包就行。
  • 只在这一个应用里用的原生调用 → 写在应用自己的 Android、iOS 工程里。
  • 同一套原生能力要给多个应用用 → 再做成插件，业务只依赖 Dart 接口。

哪些是保证，哪些是优化

  • 工程结构：插件是带平台实现的包，不是和包并列的另一种语言。pub 如何发现平台实现，是工具链的约定。
  • 通道或 FFI 是插件内部的通信手段。选哪一种依插件作者而定，不是「插件」这三个字保证了只用某一种通道。

常见误区

  • 有 Channel 代码，不等于已经做成了可复用插件。它可能只是写在当前应用工程里。
  • 插件不是必须只用 MethodChannel。
  • 包和插件不是二选一的运行时。插件首先是一个包。

口述版

包是一份可以依赖的代码，纯 Dart 的工具和 Widget 做成包就行。

插件也是一个包，但另外带了 Android、iOS 或其他平台实现，这些实现才会去调用系统能力。业务侧只依赖它的 Dart 接口，里面一般通过 Platform Channel 或 FFI 调到原生。通道是通信办法，插件是把这个办法和各端实现打包给别人用的形式。

只在一个应用里用的原生调用，写在应用自己的工程里就行；要给多个应用用，再做成插件。

32. 混合栈怎么组织

判断框架：先问导航栈是 Flutter 自己一张，还是原生一张、Flutter 一张。全屏都是 Flutter 时，不需要混合栈。已经有原生 App、要一页一页嵌进去，才要让两张栈对上，并决定用一个引擎还是多个引擎。

画面：混合栈里，原生页面是外层容器，Flutter 页面画在容器里。两边要同时知道谁在栈顶、谁该接收触摸、谁被盖住之后还要不要继续画、定时器还要不要跑。

方案好处代价
整个应用都是 Flutter只用自己的 Navigator 或路由库不需要 flutter_boost
一个引擎，多个原生页共用内存更省要处理哪一页正在显示、触摸给谁、谁在栈顶
多个引擎，一个容器一个彼此隔开启动更慢、内存更大，插件也要各注册一次
flutter_boost原生当容器，路由表和消息让两边的栈、生命周期对上。能继续用原生导航，旧页面可以慢慢换容器怎么复用、内存、插件初始化和两边栈的同步，都要额外维护

决策清单：

  • 新项目 Android 和 iOS 都用 Flutter 写 → 用 Navigator，不引入 flutter_boost。
  • 已有原生壳，逐页替换 → 才做混合栈。先定一个引擎还是多个引擎。
  • 最容易错的是生命周期：原生页面盖住 Flutter 页面时，Flutter 还在不在画，引擎里的定时器还在不在跑。这两件事要有明确策略。

哪些是保证，哪些是优化

  • 没有「混合栈自动正确」这层保证。引擎复用能省内存，但可见性和触摸要自己对齐。多引擎是隔离，不是免费。
  • flutter_boost 是这种嵌进原生导航的一种做法，不是 Flutter 官方唯一方案。官方 add-to-app 怎么复用引擎，依 Flutter 版本而定，不要把某个第三方库的内部实现说成框架保证。

常见误区

  • 全 Flutter 项目不需要 flutter_boost。
  • 一个引擎被多个原生页共用，不是天然安全。
  • 混合栈最难的通常不是把页面打开，而是盖住之后绘制和定时器有没有停。

口述版

整个应用都是 Flutter 时，用自己的 Navigator 就够，不需要 flutter_boost。已有原生壳、要逐页嵌进 Flutter，才要同时维护原生导航和 Flutter 导航。要明确的是：哪一页正在显示、触摸交给谁、原生页在 Flutter 页上面时 Flutter 还画不画、引擎里的定时器还跑不跑。这些没有自动对齐的框架保证。

一个引擎被多个原生页共用更省内存，但可见性和触摸要自己对齐。一个容器一个引擎，彼此隔开，启动更慢、内存更大，插件也要各注册一次。

flutter_boost 是原生当容器，用路由表和消息让两边的栈和生命周期对齐的一种做法，不是官方唯一方案；能沿用原生导航、旧页面可以逐页换，容器怎么复用、内存、插件初始化和两边栈是否一致，都要自己维护。新项目不引入它。

33. 构建模式和多端产物

判断框架：先分三种构建模式：开发、量速度、上架。模式决定有没有 assert、是 JIT 还是 AOT、能不能热重载。打成哪个平台是后面的打包步骤。

画面：debug 是边跑边编译的开发车间，检查和热重载都还在。profile 是已经编成机器码、但还带着秒表。release 是拿掉秒表和 assert、再把确定走不到的代码删掉的上架包。

模式编译assert 和调试能不能当性能结论
debug手机和桌面是 JIT，边运行边编译assert 还在，可以热重载不能。帧时间和包体积都不能当成正式包
profile和 release 一样是 AOTassert 关掉，但留着性能记录，给 DevTools用来看卡顿
releaseAOT，并做 tree shaking去掉 assert。混淆要单独打开上架用这个。着色器和启动时间也要在 profile 或真机 release 上看

决策清单：

  • 写界面 → debug。看卡顿 → profile。上架 → release。
  • debug 流畅，不能说明 release 没问题，反过来也一样。
  • 产物只是最后交给谁：Web 是 flutter build web 的静态文件；Android 是 apk 或 appbundle；iOS 走 flutter build ios 和 Xcode 归档；桌面是 macos、windows、linux。签名是上架打包时按平台做的，不是编译模式本身。

哪些是保证，哪些是优化

  • 工具链：JIT 才能热重载。AOT 是发布构建，没有热重载。这不是语言语法，是编译模式。
  • 编译器优化：tree shaking 是提前编译时从 main 看出哪些 Dart 代码走不到，再删掉。debug 是边运行边编译，不会做同样的删除，所以 debug 包的大小不能用来估计上架体积。
  • 混淆 --obfuscate 要单独打开，不是 release 自动等于已经混淆。
  • 上面说的 JIT / AOT 指手机和桌面这套 Dart 编译。Web 的 release 是编译成 JavaScript 或 Wasm，同样不能热重载。不要说成机器码 AOT。

常见误区

  • profile 不是「debug 少打一点日志」。它是 AOT。
  • release 不等于已经混淆、已经签名。签名和混淆是另外的打包选项。
  • 用 debug 包的体积估计商店包，会估错，因为 debug 不做同样的 tree shaking。

口述版

写界面用 debug。手机和桌面上它是 JIT，assert 还在，可以热重载；这时的帧时间和包体积不能当成正式包，因为 debug 不会做和 release 一样的 tree shaking。

看卡顿用 profile：它和 release 一样是 AOT，assert 关掉，但留着给 DevTools 的性能记录。

上架用 release：AOT，去掉 assert，并从 main 出发删掉确定走不到的 Dart 代码，这就是 tree shaking。混淆要单独加 --obfuscate，不是 release 就自动混淆；签名是按平台在打包时做的，不是编译模式本身。

Web 是 flutter build web 的静态文件，Android 是 apk 或 appbundle，iOS 走 flutter build ios 和 Xcode 归档，桌面是 macos、windows、linux。

手机和桌面的 release 是机器码 AOT；Web 的 release 是 JavaScript 或 Wasm，同样不能热重载，不要说成机器码 AOT。

七、性能

34. 怎样减少重建、长列表卡顿和大图开销

判断框架：先分清慢在哪一步：重新 build，算布局，还是画成像素。三件事的药不一样。最常见的是重建范围太大、一次创建的子组件太多、图片按原图尺寸解码。

画面：build 慢，是施工单写得太多。layout 慢，是一次量了太多孩子。raster 慢，是图层、模糊和像素太大。profile 的帧图先告诉你时间花在哪，再动手。

慢在哪常见原因先做什么
界面线程的 build在页面根上 setState把会变的 State 放到真正会变的小组件里。不变的子树做成 const
layoutListView(children:) 一次创建全部孩子，或大列表 shrinkWrapListView.builder，滑到附近才创建。高度固定就告诉列表，省掉反复测量
画像素整页跟着小动画重画、模糊和裁剪、图按原图解码只把经常重画的小块放进 RepaintBoundary。图片用 cacheWidth / cacheHeight 按显示像素解码
内存涨Controller、订阅、Timer 没释放，或图片缓存先看 dispose 里有没有放开，再怀疑图片缓存

决策清单：

  • 父组件重新 build 时，子组件还是同一个对象 → 框架不再向下更新它。构造参数里每次都 new 一个对象，就写不成 const，这条捷径也不会发生。
  • 每一项的 Key 用业务 id，不要在 build 里创建 UniqueKey。
  • RepaintBoundary 能让滚动条、动画图标单独重画。每一块都是单独的一层，划得太多会多占内存，合并图层也更贵。
  • 不要在 build 里把整张原图读进内存。上传前先压缩、缩小；大文件分段传，并带上进度、取消和重试。压缩和算哈希放到另一条 isolate，进度再用 Stream 或状态管理送回界面那条。
  • profile 里界面线程的 build 很长 → 先拆 Widget，并把 setState 下放到更小的组件。画像素那条很长 → 再看图层、模糊、裁剪和图片。先不要换状态管理库。

哪些是保证，哪些是优化

  • 框架优化，不是语言保证：const 子 Widget 还是同一个对象时，Element 不再向下比较。这是更新规则带来的跳过，不是 const 让 build 方法不会被调用到。
  • ListView.builder 的懒创建、光栅缓存、图片按目标尺寸解码，都是框架和引擎的优化。用不用得上，取决于你有没有一次把所有孩子建出来、有没有按原图像素解码。
  • 测量本身要用 profile。debug 的帧时间不是正式包的结果，这是构建模式的差别，不是优化建议。

常见误区

  • 先换状态管理库，通常解决不了根上 setState 或大图解码。
  • RepaintBoundary 不是包得越多越快。
  • 在 build 里写 UniqueKey()，会让项的 State 每次都被丢掉，列表更抖，不是更稳。

口述版

先用 profile 的帧图分清时间在 build、layout 还是光栅，不要用 debug 的帧时间下结论。

build 长，是 setState 标在了过大的 Element 上：把它放到真正变化的 State 上，不变的子 Widget 写成 const。父组件重新 build 时，子 Widget 若还是同一个对象，Element.updateChild 不再向下更新它；这是跳过子树更新，不是 const 让 build 方法不会被调用到。

长列表不要用 ListView(children:) 一次创建全部孩子，用 ListView.builder，滑到附近才创建；高度固定就告诉列表，省掉反复测量。项很多时不要靠 shrinkWrap。每一项的 Key 用业务 id，不要在 build 里 UniqueKey()，否则每次都会丢掉旧 Element。

RepaintBoundary 只包经常单独重画的小块；每一块都是单独的一层，划得太多会多占内存，合成也更贵。

大图用 cacheWidth 和 cacheHeight 按显示像素解码，不要按原图像素解码。压缩和算哈希放到另一个 isolate。

内存先看 dispose 里有没有放开 Controller、订阅和 Timer，再怀疑图片缓存。

附录：初级语法

下面几题在老题库里出现过，现在很少单独成题。空安全的 ?? 可以当作第 1 题的补充。

A1. ?? 和 ??=

判断框架：两个都看左边是不是 null。一个只决定表达式的结果，一个会在为空时把右边赋给左边。

画面：?? 是「左边没有就用右边顶上，左边那个变量本身不动」。??= 是「左边如果还空着，就把右边放进去」，整个表达式的结果是放完之后的值。

写法左边是 null左边不是 null左边的变量变不变
a ?? b结果是 b结果是 a不变
a ??= b把 b 赋给 a，结果是赋完的值不赋值，结果是原来的 a只有原来是 null 才变

哪些是保证，哪些是优化

  • 语言保证：判断的是 null。这是空安全里的运算符，不是运行时偶然的短路优化。
  • 右边在左边已经非空时不会被求值。这是这两个运算符的语义，面试可以当成语言规则来说。

常见误区

  • ?? 不会给左边赋值。??= 才会。
  • 它们只处理 null，不处理空字符串、0 或 false。

口述版

a ?? b 在 a 为 null 时结果是 b，否则结果是 a，不会给 a 赋值。

a ??= b 只在 a 为 null 时把 b 赋给 a，表达式的结果是赋值之后的值；a 已经非空就不赋值，结果仍是原来的 a。

左边已经非空时，右边不会被求值。两者都只判断 null，不把空字符串、0 或 false 当成空。

A2. 默认是强引用还是弱引用

判断框架：先问普通变量会不会让对象活着。会，就是强引用。弱引用是另外显式造出来的，不是默认行为。

画面：强引用是手里一直抓着对象，垃圾回收不能把它拿走。弱引用是一张可以失效的便条：对象若没有别的强引用了，就可以被回收，便条之后拿出来可能是空的。

强引用弱引用
默认吗普通变量默认就是强引用不是默认。要用 WeakReference
对象能不能回收还有强引用就不会只剩弱引用时可以回收
典型用途日常持有缓存，或者对象被回收时用 Finalizer 做清理

决策清单：

  • 普通字段、局部变量、集合里的元素 → 强引用。不要假设 Dart 默认是弱的。
  • 缓存不想挡住回收 → 把那一个引用放进 WeakReference。其他普通变量不变，仍然是强的。
  • 对象回收时要顺便清理原生资源 → 看 Finalizer。不要在析构时机上假设和 Java 的 finalize 一样，具体时机依运行时而定。

哪些是保证，哪些是优化

  • 语言和运行时：可达的强引用会保住对象。只有放进 WeakReference 的那一个引用是弱的。
  • 垃圾回收什么时候跑，是运行时的事，不是你把变量写成局部变量就会立刻回收。

常见误区

  • Dart 默认不是弱引用。闭包抓着 State，State 就还在，这就是强引用。
  • 一个对象上只要还有别的普通变量指着它，WeakReference 不会让它消失。

口述版

普通变量、字段和集合里的元素默认是强引用。对象还有可达的强引用时，垃圾回收不会收走它。

弱引用不是默认，要显式放进 WeakReference；只剩弱引用时对象可以被回收，之后再取可能是 null。同一个对象上只要还有别的普通变量指着它，WeakReference 不会让它消失。

对象被回收时要清理原生资源，用 Finalizer，时机由运行时决定，不要假设和 Java 的 finalize 一样。变量离开作用域，也不表示对象会立刻被回收。

A3. getter 和 setter

判断框架：getter 和 setter 是方法打扮成字段。读的时候走 getter，赋值的时候走 setter。外面用起来像字段，里面可以检查、可以换算。

画面：真正存着的是 _celsius。外面读 celsius 像读字段，其实进了 getter。外面赋值像写字段，其实进了 setter，可以在这里拒绝绝对零度以下的值。fahrenheit 只有 getter，没有自己的存储，每次按摄氏度算出来。

class Temperature {
  double _celsius = 0;

  double get celsius => _celsius;
  set celsius(double value) {
    if (value < -273.15) {
      throw ArgumentError('below absolute zero');
    }
    _celsius = value;
  }

  double get fahrenheit => _celsius * 9 / 5 + 32;
}

决策清单：

  • 赋值时要校验、要通知 → 用 setter，不要让外面直接改字段。
  • 值可以由别的字段算出来 → 只提供 getter，不必再存一份。
  • 库外不能碰的存储 → 字段名以下划线开头，再配公开的 getter / setter。

哪些是保证，哪些是优化

  • 语言保证：读访问调用 getter，赋值调用 setter。调用处的写法可以和字段一样。
  • getter 可能被内联。那是编译器优化，不改变「中间可以做校验和计算」这个语义。

常见误区

  • getter 不是必须有一块同名存储。它可以是计算出来的。
  • setter 可以抛错，拒绝不合法的值。它不是一次必定成功的赋值。

口述版

getter 和 setter 让外面像读写字段，实际走的是方法。

setter 里可以校验，比如温度不能低于绝对零度。getter 可以没有自己的存储，例如华氏度每次由摄氏度算出来。

真正的数据可以放在下划线字段里，库外只能通过公开的 getter 和 setter 碰到它。

A4. 库的可见性

判断框架：Dart 的可见性按库，不按类，也没有 public、protected、private 关键字。先问这个名字是不是以下划线开头，再问调用方是不是同一个库。

画面：一个库是一组一起编译的文件。下划线名字像库内部的抽屉，库外看不到。没有下划线的名字默认就能被库外使用。export 是把别的库里那些公开名字再转手递出去。

名字谁能用关键记忆
不以 _ 开头库外可以直接用没有 public 关键字，这就是公开
以 _ 开头只有当前这个库私有的是库，不是类。同一个库里的其他类也能用
export把别的库的公开声明再导出导出不了别人的下划线名字

决策清单：

  • 只想给本库用 → 名字以下划线开头。
  • 要给调用方用 → 不要加下划线。想少暴露，就把实现细节留在下划线名字里。
  • 想让调用方从一个库导入到另一库的公开 API → export。

哪些是保证，哪些是优化

  • 语言保证：下划线可见性在库边界上检查。这不是分析器可关的风格，库外访问私有名字会编译失败。
  • tree shaking 可以删掉确定用不到的公开代码，那是发布构建的编译优化。它不改变「没有下划线就可以被库外引用」这条规则。

常见误区

  • 下划线不是「这个类外面不能用」。同一个库里的其他文件、其他类也能用。
  • Dart 没有 protected。想限制继承和实现，用 Dart 3 的类修饰符，那是另一题，不是下划线。

口述版

Dart 没有 public、protected、private 这些关键字，可见性按库，不按类。

名字以下划线开头，库外访问会编译失败；同一个库里的其他文件、其他类仍能用。没有下划线的名字，库外可以直接引用。

export 把别的库的公开声明再导出到当前库的公开 API，导不出别人的下划线名字。

tree shaking 可以在发布构建里删掉确定用不到的公开代码，那不改变「没有下划线就可以被库外引用」这条规则。

A5. 级联操作符 ..

判断框架：先看整个表达式的结果是「原来那个对象」，还是「最后一次调用的返回值」。级联要的是前者。

画面：.. 是对着同一个对象连续做几件事，中间不用反复写出对象名字。做完之后，表达式交回来的还是这个对象，不是最后那个方法的返回值。对象可能是 null 时，用 ?..，左边是 null 就整段跳过。

写法对着谁调用表达式结果
.前一个表达式的结果这次调用的返回值
..一开始那个对象还是那个对象
?..左边非空才调用左边是 null 时结果是 null，否则还是那个对象

决策清单：

  • 连续配置同一个对象，例如建好之后设几个字段 → ..。
  • 下一步要用上一次方法的返回值 → 用普通的 .，不要用级联。
  • 接收者可能是 null → ?..。

哪些是保证，哪些是优化

  • 语言保证：级联的结果是接收者本身。这不是格式化工具随便改写的语法糖以外的运行时优化；它的语义就是返回接收者。
  • 编译器当然可以把它展开成几次调用。展开之后，结果仍然是原对象，这个不能被优化掉。

常见误区

  • .. 的结果不是最后一次调用的返回值。最后那次如果返回 void 或其他类型，外面拿到的仍是原对象。
  • ?.. 不是把对象变成非空，只是左边为 null 时不要继续调用。

口述版

.. 的每次调用都作用在最初那个接收者上，整个表达式的值也是这个接收者，不是最后一次调用的返回值。最后一次即使返回 void 或其他类型，外面拿到的仍是原对象。

普通的 . 才把这次的返回值交给下一次调用。

?.. 是接收者非空才调用；左边是 null 时整段不调用，结果是 null，不会把对象变成非空。
