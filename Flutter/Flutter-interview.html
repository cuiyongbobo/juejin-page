一、Dart

1. var、Object、dynamic，以及空安全

口述版

  • var x = 1 推断完成后，静态类型就是 int。之后还可以再赋另一个 int，变的是值，类型已经确定。它不是常量。
  • Object 是非空的公共父类型。静态类型上只能直接调用 Object 的成员。要表示可以是 null，写成 Object?。
  • dynamic 把成员检查推迟到运行时，值也可以是 null。调用了不存在的成员，运行时才抛。类型能确定就不要用它。
  • T? 表示这个值可以是 null。! 是断言当前值不是 null，实际是 null 就抛。它不是把对象改成非空类型。
  • ?. 在接收者为 null 时短路，?? 在左边为 null 时取右边，??= 只在左边为 null 时赋值，...? 是空安全的集合展开。它们都不改变静态类型，只是读写时的简写。
  • 不带初始化表达式的 late，读取前必须先赋值，否则抛 LateInitializationError。初始化表达式留到第一次读取才执行。只能赋值一次时写成 late final，例如 late final x = compute()。
  • 本地变量判空之后，如果闭包里没有给它赋值，流分析会把它提升成非空。这是类型系统的分析，不是运行时把对象改了。闭包里只要出现赋值，整段提升都会取消。类的字段多数时候不会因为判空被提升。Dart 3.2 起，一部分私有、非外部字段可以提升，范围依版本而定。

解析

这道题问的是编译器在这个名字上知道多少，以及 null 能不能混进来。推断完成后类型就锁住了，锁的是类型，不是这一次的值。

var x = 1;          // 静态类型是 int，之后只能再赋 int
Object obj = x;     // 只能直接调 Object 的成员
dynamic raw = json; // 成员检查推迟到运行时，也可以是 null
String? name;
final text = name!; // 是 null 就抛，不是把对象改成非空类型

?.、??、??=、...? 是空安全里的读写简写：前者在接收者为 null 时短路，中者给默认值，??= 只在为空时赋值，最后者用于集合展开。它们不改变静态类型，也不做运行时转换。把 ?? 和 || 混用是常见错误：|| 只看真假，?? 只看是不是 null。

本地变量写过 if (value != null) 之后，花括号里的 value 会被提升成非空，一般不必再写 !。这是类型系统的流分析，不是运行时把对象变了。这个局部变量只要在闭包里被赋值，提升会整段关掉，判空之后仍按可空使用。类的字段很多时候不会自动提升。Dart 3.2 起，一部分私有、非外部字段可以提升，依版本而定，不要说成所有字段都会提升。

late 用在字段要等一会儿才有、但读取前一定赋过的地方。没有初始化表达式时，读在写之前会抛 LateInitializationError。初始化表达式留到第一次读取才执行。只能赋一次再写成 late final。分析器警告是开发工具，不是另一套语言规则。dynamic 也不会让程序跑得更快。

2. const 和 final 的区别

口述版

  • final 在运行时赋值一次，之后这个名字不能再指向别的对象。对象如果可变，内容仍然可以修改，例如 final list = <int>[] 之后还可以 add。
  • const 必须在编译期算出来。用 const 造出的对象深度不可变，相同常量在同一个 isolate 里是同一个对象。
  • 实例字段不能写 const，类常量写成 static const。const 构造要求字段都是 final，参数也必须是编译期常量。
  • 类有 const 构造时，普通调用不写 const，得到的是新实例。已经处在 const 上下文里，可以不写关键字，仍然按常量求值。
  • 父组件重新 build 时，子 Widget 如果还是同一个对象，Element.updateChild 不再向下更新这棵子树。依据是 Widget 实例相同，不是 const 跳过了 build。

解析

final 锁的是绑定：这个名字不能再指向别处。房间里的东西仍可能搬动。const 做的是编译期常量，真正用 const 造出来的对象深度不可变，而且会规范化。

final list = <int>[];
list.add(1);                 // 可以。锁的是绑定，不是列表内容
const a = [1];
const b = [1];               // 同一个 isolate 里 a 和 b 是同一个对象
// a.add(2);                 // 运行时失败，常量深度不可变

class Box {
  static const zero = 0;     // 实例字段不能写 const
  final int n;
  const Box(this.n);
}
final box = Box(1);          // 普通调用，每次是新实例
const box2 = Box(1);         // 显式 const 上下文
const boxes = [Box(1)];      // 隐式 const 上下文，Box(1) 同样规范化

const 构造函数要求字段都是 final，调用时传入的参数也必须是编译期常量。不写 const 关键字，只在调用处不处于 const 上下文时才是新实例。带函数体的工厂不能是编译期常量构造，那是另一题。跨 isolate 发消息时对象通常会被拷贝，不能把 const 身份当成进程里全局唯一。

Flutter 里父组件重新 build 时，子 Widget 若仍是同一个对象，框架就不再向下更新这棵子树。这是 Element.updateChild 的行为，不是 const 有魔法跳过 build。构造参数里每次都 new 一个新对象，就写不成 const，这条捷径也不会发生。

3. Dart 是值传递还是引用传递

口述版

  • Dart 的参数按值传递。传进去的是对象引用的一份拷贝，参数不是调用方那个变量的别名。
  • 通过这份引用修改对象的字段，调用方能看到，因为两份引用指向同一个对象。给参数重新赋值，只改变函数里的这个局部变量。
  • 所以 list.add(1) 调用方能看到，list = [] 调用方看不到。要让调用方改指向另一个对象，把新对象 return 出去。

解析

参数是函数自己的一个新变量，里面拷了一份地址。你拿这个地址去改房间里的东西，外面看得到；你让这个新变量改去指另一间房，外面那个变量不动。

void grow(List<int> list) { list.add(1); }   // 调用方看得到
void reset(List<int> list) { list = []; }    // 调用方看不到

这是语言保证：没有 C++ 那种「外面那个变量的别名」。编译器可能内联、可能省略一些拷贝，但不会把「给参数重新赋值」变成修改调用方的变量。想避免被外面改到，传不可变对象，或者在边界上拷一份。

4. extends、implements 和 mixin

口述版

  • extends 是单继承。子类复用父类的实现，并且是父类的子类型，构造时还要调用父类构造。
  • implements 不复用实现，接口上的成员要自己全部实现。一个类可以同时实现多个。
  • mixin 用 with 把一份现成实现混入类中，可以有字段和方法，不能声明生成构造函数，但可以声明 factory 构造函数。on 限制只有指定类型的子类才能混入，mixin 里可以调用宿主类型的成员。
  • 多个 mixin 同名时，由线性化决定谁先被调用：with 里靠后的覆盖靠前的。靠后的实现没有调用 super，前面的同名方法不会执行。调用了 super，才沿着线性化链继续调用前一个。
  • Dart 3 的类修饰符是语言规则，不是 lint。interface 表示库外只能实现、不能继承。base 表示只能继承、不能实现，子类自己也必须是 base、final 或 sealed。final 表示库外既不能继承也不能实现。sealed 表示子类必须写在同一个库里。
  • 既要父类的实现、又要子类型关系，用 extends。只要契约，用 implements。要复用一段行为，用 mixin。不需要类型关系，优先用组合。

解析

Dart 仍然只能 extends 一个类。要复用的是「实现加上是一个什么类型」，用继承；只是一份契约，用 implements；一段可以拼上去的行为，用 mixin。

class Animal { void breathe() {} }
class Dog extends Animal implements Runnable {}
mixin Walk on Animal { void go() => breathe(); }
class Cat extends Animal with Walk {}

mixin 不能声明生成构造函数，但可以声明 factory 构造函数，所以不会出现多个父类构造对不上。on 限制宿主，mixin 里面可以调用这个宿主类型的成员。同名方法由线性化决定谁先被调用：靠后的盖住靠前的。靠后的方法调用 super 时，前面那一份会接着执行。这不是编译器随便挑一个更快的版本，也不是没写 super 就会自动叠着跑。

Dart 3 还可以限制库外的人怎么用这个类，这是语言规则，不是 lint。mixin class 既能当类，也能当 mixin。只是复用代码、不需要类型关系时，优先考虑组合。

5. extension 是干什么的

口述版

  • extension 给已有类型增加方法或 getter，不用修改原类，也不用继承。
  • 选中哪一个扩展，编译期就按变量声明出来的静态类型确定，所以在 dynamic 上调用不到。运行时对象即使是子类，也不会因此改选另一个扩展。
  • 类型自己已有的同名成员优先。扩展不能增加实例字段，也就不能保存状态。扩展所在的库要 import 之后才能使用。
  • 适合不保存状态的工具方法。要保存数据，或者希望子类改写，用类或 mixin。

解析

扩展像贴在静态类型上的一层便利贴。编译器看变量写出来的类型，决定用哪一张。运行时对象实际是子类，也不会因此改选另一张。

extension StringX on String {
  bool get isBlank => trim().isEmpty;
}
String name = '  ';
name.isBlank;              // 编译期按 String 选定
dynamic raw = name;
// raw.isBlank;            // 静态类型是 dynamic，看不见扩展

扩展不能覆盖类型已有的成员，也不能加实例字段。两个扩展撞名时，可以 hide 其中一个，或写成 扩展名(对象).方法()。没导入就当没有。

编译器可能把这次调用内联掉。那是优化，不改变「按写出来的类型选定」这个规则。调用看起来像实例方法，其实不是运行时按对象的真实类型分发。

6. 工厂构造函数和普通构造函数

口述版

  • 生成构造的函数体不能返回另一个对象。不在 const 上下文里的普通调用，每次创建当前这个类的新实例。
  • const 上下文里的 const 生成构造，返回规范化后的那一个实例。同值常量是同一个对象。
  • factory 的函数体必须 return 一个这个类型能接受的对象，所以可以返回已有实例，也可以返回子类型。
  • 带函数体的 factory 不能是编译期常量构造。重定向形式的 const factory 可以。
  • 构造函数名叫 fromJson，并不表示它是 factory。只是把字段填进一个新对象，用命名生成构造。要返回已有实例或子类型，才用工厂。

解析

普通构造函数是车间：普通调用每次出一台当前型号的新机器，函数体不能换成另一台。const 生成构造在 const 上下文里不另造一台，返回规范化后的那一台。工厂构造函数是前台：可以给你仓库里那一台，也可以给你一台子型号。调用方的静态类型仍然可以是父类。

class User {
  User(this.name);
  User.fromJson(Map<String, Object?> json) : name = json['name'] as String;
  factory User.cached(String name) => _cache.putIfAbsent(name, () => User(name));
  final String name;
}

生成构造函数用初始化列表和函数体，不能返回另一个实例。const 生成构造在 const 上下文里返回规范化实例，这和工厂返回一个已有对象不是同一件事。factory 必须返回一个这个类型能接受的对象。工厂不是一项性能优化，也不是「更快的 new」。它只是放宽「必须新造当前类」。

对象在编译期就要定死，用 const 生成构造。不能 const 的是带函数体的工厂；重定向的 const factory 是语言允许的，不要说成所有 factory 都不能 const。

二、异步和并发

7. Future 和 async / await

口述版

  • Future 表示稍后会完成一次，结果是一个值，或者一个错误。
  • async 函数被调用后，先在当前 isolate 上同步执行到第一个 await，然后才把 Future 交给调用方。这一步不会并行。
  • await 挂起的是这个异步函数剩下的代码。等的 Future 完成后，续体以微任务继续，比定时器和点击更优先。这次等待不会阻塞事件循环。
  • Future(() {}) 的函数体进入事件队列。耗时计算即使用 Future 包起来，仍然在当前 isolate 上执行，要放到另一个 isolate。
  • 要等多个 Future 一起完成，用 Future.wait；要手动控制一个 Future 何时完成，用 Completer。

解析

Future 是一张回执，成功或失败只会来一次。async 函数被调用后，先在当前调用栈上把第一个 await 之前的代码跑完，再把 Future 交给调用方。await 是把这个函数剩下的活挂起来，回执到了再继续。一个 async 函数里可以没有 await，也可以有多个。

Future<int> load() async {
  try {
    return await fetch();     // 错误发生在 await 上，try/catch 接得住
  } catch (e) {
    return 0;
  }
}
final pending = fetch();     // 没 await，旁边的 try/catch 接不住

Future 完成后的续体进微任务，比点击、定时器这些事件更优先。scheduleMicrotask 和 Future.microtask 也进微任务。网络和文件回调进事件队列。这是运行时的事件循环规则，不是编译器把异步优化成同步。Future 不会因为你多包一层就变成并行。

多个 Future 用 Future.wait 汇总：默认会等所有 Future 都结束，再带着第一个错误完成；eagerError: true 时第一个错误就立即返回。要把回调式 API 包成 Future，或者手动决定何时完成，用 Completer；completer.complete(value) 和 completeError 只能调一次。

8. Future 和 Stream 有什么不一样

口述版

  • Future 完成后只有一个结果，完成之后再 await 仍能拿到它。
  • Stream 是一串事件，可以有多次数据和多次错误，最后有一次结束。
  • 单订阅流只能 listen 一次，再次监听会报错。广播流可以同时有多个监听者。
  • dart:async 里普通的广播流不缓冲，后订阅的收不到订阅之前已经发出的事件。单订阅流在有人 listen 之前会先把事件缓冲起来。自己实现的流如果保留了最新值，订阅时可以拿到那一份。
  • 界面里接流常用 StreamBuilder，它负责订阅、取消订阅，并在快照变化时重建。
  • async* 里 yield 一次发出一个事件。await for 挂起的是当前这个异步函数，每到一个事件执行一次循环体，不会阻塞这条 isolate。
  • 页面 dispose 时要取消 StreamSubscription，否则容易出现 setState() called after dispose()。

解析

Future 是一封信，拆开一次就结束。Stream 是一条水管，可以多次出水、多次报错，最后有一个结束信号。两者都在当前 isolate 上调度，都不是并行。

await for (final event in stream) {
  print(event);
  if (event == 'stop') break;   // 离开时取消这次订阅
}

async* 每 yield 一次就往外发一个事件。yield* 是把另一条流里的事件接着转出去。单订阅不能听第二次，但它在还没有监听者时会缓冲事件，等 listen 之后按顺序补发；广播流不保留，没人在听就丢掉。这是单订阅和广播最容易混淆的地方。dart:async 的普通广播流不补发过去的事件；保留最新值的实现会在订阅时交出那一份。await for 挂起的是当前这个异步函数，不会把整条 isolate 卡住。「await for 会把线程堵死」是老说法。

界面里用 StreamBuilder，它会在订阅、收到事件和出错时用新的快照重建；不要在 build 里自己 listen，那会每次重建都多一个订阅。需要把流拆开、合并、去重，用 StreamTransformer 或 stream.map / where / expand。

广播流上不要随便 await for。流不结束，这个函数就会一直停在循环里。广播流的缓冲策略、暂停时还丢不丢事件，依具体 Stream 实现而定，不要说成所有广播流行为完全一样。页面 dispose 之后订阅还在，是常见的 setState() called after dispose() 来源。

9. Dart 是不是单线程？事件循环怎么跑

口述版

  • 同一个 isolate 上不会有两段 Dart 代码同时执行。整个进程可以有多个 isolate，VM 可以把它们安排到不同的系统线程上。没有的是多个线程共享同一块内存。
  • 当前这段同步代码跑完之后，先清空微任务队列，再从事件队列取一个事件。这个事件做完，再清空期间新来的微任务。
  • scheduleMicrotask、Future.microtask 和 Future 完成后的续体进微任务。Future(() {})、Timer、手势、网络和文件完成进事件队列。
  • await 只挂起当前这个 async 函数，事件循环继续处理其他任务。同步代码还没返回时，微任务也不会开始执行。
  • 微任务里如果不停再安排微任务，事件队列里的点击和下一帧就一直不会执行。

解析

一个 isolate 是一条执行线加两个队列。微任务是插队的小纸条，事件队列是正常排队的点击、定时器和 I/O。

同一个 isolate 上不会有两段 Dart 代码同时执行。一个应用可以有多个 isolate，Dart VM 可以把它们安排到不同的系统线程上。没有的是「多个线程一起改同一块内存」。

想排在点击和定时器前面、又不能太重，用微任务。普通的稍后执行用 Future(() {}) 或 Timer，进事件队列。await 停住的是当前这个 async 函数，不是这条 isolate。

10. Isolate 是什么，和 Future 有什么区别

口述版

  • 每个 isolate 有自己的堆和事件循环。彼此不共享堆，所以不能直接修改另一个 isolate 里的对象。
  • Future 只是当前 isolate 上稍后才有的一个结果，不会因此并行。
  • 通信用 SendPort 发送、ReceivePort 接收。消息默认拷贝一份。TransferableTypedData 是把那块内存的所有权转移过去，转移之后原来的 isolate 不能再使用。
  • 一次计算完成后拿回结果，用 compute 或 Isolate.run。需要长期在后台接收消息，用 Isolate.spawn。Isolate.exit 可以把结果直接交给等待方，省掉一次拷贝。
  • ReceivePort 用完要 close，否则对应的 isolate 可能一直不退出。
  • 引擎的界面、画像素、平台、文件线程不是 isolate。只是等待 I/O 时用 Future。再放进 isolate，多出来的是启动和拷贝，不是并行。Web 上 isolate 通常接近 Worker。

解析

Isolate 是一间自己带桌子和信箱的房间。每间房有自己的内存和事件循环，不能伸手改另一间房的对象，只能寄信。这是 actor 模型，不是编译器可选的优化。

VM 上 isolate 可以被安排到不同系统线程。Web 上通常接近 Worker。Flutter 引擎另外有界面、画像素、平台、文件这几条线程，它们不是 isolate。主 isolate 跑在界面线程上；你 spawn 出来的 isolate 不归这套线程编制。

消息能发的类型有限：基本类型、List/Map、SendPort、TransferableTypedData 等；同一个 isolate group 里多数对象可以发，但仍然会拷贝。一次计算结束用 Isolate.exit 返回结果，可以避免把结果再拷一遍。ReceivePort 用完要 close，否则对应的 isolate 可能一直不退出。

只是等 I/O，再包进 isolate 多的是启动和拷贝，不是并行收益。全局变量也是各有一份，不是加锁就能一起改。「Dart 没有多线程」不准确。没有的是多个线程共享同一块内存这种写法。

三、框架入门

11. Flutter 和原生开发的差别

口述版

  • 普通界面是自绘：不创建系统控件，由引擎里的 Skia 或 Impeller 画成像素。具体用哪一个，取决于 Flutter 版本和目标平台。
  • 写法是声明式：业务代码描述这份数据下界面长什么样，框架用新的 Widget 去更新已有的 Element 和 RenderObject。
  • 手机和桌面的 debug 是 JIT，热重载依赖 JIT。这两端的 release 是 AOT，没有热重载。Web 的热重载见第 20 题。
  • 系统能力通过插件和 Platform Channel 调用。地图、网页可以用 PlatformView 嵌入一块原生视图，那一块就不是自绘。
  • 安装包通常更大。能否流畅，取决于 AOT、这条自绘管线，以及没有把重活放在界面线程上。这不是语言保证。

解析

先看界面是自己画出来的，还是把系统控件拼起来的。Flutter 交出去的是「这一帧界面应该长什么样」。自绘和声明式更新是架构，不是某次编译碰巧这么做。

对照着看：原生直接用系统控件；React Native 把组件映射成系统控件，新架构用 JSI / Fabric / TurboModules 直接调用原生，不再依赖旧桥，各端仍然更容易长得不一样。Flutter 的系统能力靠插件和 Platform Channel，必要时用 PlatformView 嵌一块原生视图。桌面小组件、很深的系统接口仍然要原生配合。

手机和桌面的热重载在 debug 的 JIT 里，是开发期工具，不是它比原生快的原因。Web debug 另有热重载，见第 20 题。release 没有热重载；手机和桌面的 release 是 AOT。画像素的库是 Skia 或 Impeller，较新稳定版在 iOS 和 Android 上 Impeller 常常是默认，其他平台可能仍是 Skia，不要说死成某一个。「流畅程度通常接近原生」依赖 AOT、自绘管线，以及没有在界面线程上做重活，不是语言保证。

12. Flutter 的整体架构

口述版

  • 自下而上是 Embedder、Engine、Framework。
  • Embedder 对接窗口、线程、系统事件和插件。
  • Engine 主要是 C++，包含 Dart 运行时和图形，通过 dart:ui 交给上层，画像素用 Skia 或 Impeller。
  • Framework 用 Dart 写绘制、手势、渲染、Widget、Material 和 Cupertino。业务代码导入的是 material 或 cupertino，不直接对 Engine 编程。dart:ui 是 Framework 和 Engine 的交界，不是整套 SDK。
  • UI、Raster、IO、Platform 这四条 Task Runner 由 Embedder 创建，引擎活着的时候不能换。Dart VM 仍会为 GC、后台编译和 spawn 出来的 isolate 使用别的系统线程。

解析

从贴着操作系统的一层，问到贴着业务代码的一层。

UI、Raster、IO、Platform 这四条由 Embedder 创建，引擎活着的这段时间里不能换掉。这句话不覆盖 Dart VM 自己用到的辅助线程，也不覆盖 spawn 出去的 isolate。dart:ui 不是整个 Flutter SDK，不要说「写 App 时直接导入 dart:ui 就等于用了整套框架」。业务代码一般不直接对着 Engine 写。

13. main 和 runApp 分别做什么

口述版

  • main 是 Dart 程序的入口。
  • runApp 先确保 WidgetsFlutterBinding 已经初始化，再把传入的 Widget 挂成根，并调度第一帧。这次调用返回时，界面还没有画完。根通常是 MaterialApp 或 CupertinoApp。
  • 在 runApp 之前就要调用插件时，先调用 WidgetsFlutterBinding.ensureInitialized()。
  • 热重载不会重新执行已经跑过的 main。改了启动逻辑要热重启。

解析

main 是开门，可以先做初始化，再调用 runApp。runApp 是把根 Widget 交给绑定层，Widget、Element、RenderObject 这三棵树和第一帧从这里排上日程。挂上不等于这一调用返回时像素已经画完。

void main() {
  WidgetsFlutterBinding.ensureInitialized(); // runApp 之前就要用插件时才需要
  runApp(const MyApp());
}

热重载不重跑已经执行过的 main，热重启会。这是开发期工具。release 没有热重载，不是框架在正式包里的行为。改了启动代码却看不到效果，不是 runApp 没执行过，而是热重载没有重跑 main。在绑定还没准备好时就用插件，会在 runApp 之前失败。

14. Widget 有哪几类，为什么不能改

口述版

  • Widget 是不可变配置，框架拿新旧两份来比较。build 会不断新建它，所以配置要保持轻量。真正留在树上的是 Element。
  • StatelessWidget 没有单独的 State，界面由构造参数和它依赖的上层数据决定。
  • StatefulWidget 通过 createState 创建 State，State 由 StatefulElement 保存。runtimeType 和 key 都没变、Element 被复用时，State 还在。
  • 只修改自己的字段不会自动重建，要调用 setState。父组件传入新配置，或者已经登记依赖的 InheritedWidget 发出通知，也会重建。
  • InheritedWidget 让子孙登记依赖。RenderObjectWidget 配置 RenderObject。布局和绘制在 RenderObject 上。
  • 按基类还能再分：ProxyWidget 下面是 InheritedWidget 和 ParentDataWidget；RenderObjectWidget 下面分 Leaf、SingleChild、MultiChild 三种。

解析

Widget 是一张不能改的施工单，build 时会不断新开一张。Element 是树上的工位。StatefulWidget 把 State 交给 Element 保管，施工单换了，只要工位还在，State 就还在。

字段用 final 是语言层面锁住绑定。@immutable 是框架和分析器的约定。Widget 会被频繁新建，所以要轻，这是设计，不是某次渲染优化碰巧复用了 Widget。如果配置本身还能被改掉，框架就分不清这次 build 到底变了什么。不可变是为了比较。你仍然不该去改它。不可变的是配置，Element 和 State 是可变的。

按基类看，Widget 先分成 StatelessWidget、StatefulWidget、ProxyWidget 和 RenderObjectWidget。ProxyWidget 自己不创建 RenderObject，只把数据往下传，InheritedWidget 和 ParentDataWidget 都属于它；RenderObjectWidget 再按孩子数量分成 Leaf、SingleChild、MultiChild 三种。

StatelessWidget 没有自己的 State，也就没有 initState 和 dispose。它在 build 里调用 Theme.of 这类会 depend 的方法时，StatelessElement 会登记依赖，上层数据通知后一样会重建。父组件传入新配置也会重建。数据变了却没刷新，不是 StatefulWidget 坏了，是没有 setState，也没有依赖通知。Widget 不只是控件，间距、主题、继承数据的包装也是 Widget。

15. State 的生命周期

口述版

  • 顺序是 createState、initState、didChangeDependencies、build。
  • initState 只在第一次挂到树上时调用一次，开头调用 super.initState()。这里不能 Theme.of、MediaQuery.of，那些放 didChangeDependencies。
  • 父组件传入新 Widget、运行时类型和 key 都没变，走 didUpdateWidget。自己 setState 不走这里。
  • 暂时从树上卸下时走 deactivate，super 放在方法末尾。GlobalKey 换父节点时，State 可能再次挂上，不要在这里释放资源。
  • 确定不会再挂回去才 dispose：先释放 Controller、Timer 和订阅，再调用 super.dispose()。dispose 返回、和 Element 断开之后，mounted 才变成 false。写在 dispose 里面时还能读到 true，但已经不能 setState。
  • 打开新页面时，旧路由默认 maintainState 为 true，旧的 State 还挂在树上。应用进后台走 WidgetsBindingObserver。

解析

State 比单次 Widget 活得长。口袋还在，State 就在；口袋确定拆掉，才是 dispose。上面的调用顺序是框架保证，不是编译器优化。

build 里不改数据、不发请求、不订阅。didUpdateWidget 里比较 oldWidget 和 widget，换订阅、重启动画。父组件把 userId 换成另一个，只写在 initState 里，页面会继续显示旧用户。

异步回调回来先看 mounted。dispose 返回、State 和 Element 断开之后，mounted 才变成 false。写在 dispose 里面的代码当时还能读到 true，不代表还能 setState。super.initState() 写在方法末尾是错的。末尾调用 super 的是 deactivate 和 dispose。

setState() called after dispose() 这类检查包在 assert 里，profile 和 release 会去掉 assert。State 已经和 Element 断开后再调用，常见版本会因为 element 已经是空而抛错。检查被拿掉，不表示这次调用变得合法。reassemble 是热重载这条开发期路径，正式包不会走它来更新你的 initState。热重载不会重跑 initState。

16. setState 做了什么

口述版

  • setState 是 Flutter 框架的方法，不是 Dart 语言特性。它先同步执行回调，再对当前 Element 调用 markNeedsBuild。
  • 这次调用返回前不会把界面重画完。build 发生在这一帧的构建阶段，或排到下一帧。同一次事件循环里的多次标记合并成一次 build。
  • 重建从被标记的 Element 开始，不是整个应用。子节点里 runtimeType 和 key 都相同的 Element，会更新原来的节点，不会新建。
  • 调用要写在真正发生变化的那个 State 上，而且不能写在 build 里。build 里要 setState、发请求或订阅，是副作用放错了地方。
  • 回调不要写成 async，也不要 return 一个 Future。异步工作先做完，再在需要刷新时调用 setState。dispose 之后再调用会抛错。

解析

setState 是 Flutter 框架的方法，不是 Dart 语言特性。回调同步执行，然后标记需要 build。

只有一小块在变，setState 写在那一块自己的 State 上。同一段点击处理里要改好几个字段，可以多次 setState，框架会合成一次 build，更好的写法是一次回调里改完。想让更小的区域听一个值，用 ValueListenableBuilder、Selector 或 Bloc 的 buildWhen。

新 Widget 和旧子节点按类型和 key 比较，对得上就更新原 Element。这是框架的复用，不是语言保证。build 里发现自己想 setState、发请求或订阅，是副作用放错地方了。build 一帧里可能走很多次。

setState 的回调要同步完成。写成 async 时，await 之后的代码不在这次标记的范围内，debug 下框架还会直接报「回调返回了 Future」。正确做法是先把异步结果拿回来，再调用一次 setState。State 已经 dispose 之后再调用，debug 下会被 assert 拦住，release 下也可能因为 Element 为空而抛错。

17. BuildContext 是什么

口述版

  • BuildContext 由 Element 实现，每个 Element 一份，表示这个节点在树上的位置。它不是 Widget，也不是全局单例。
  • Theme.of、MediaQuery.of，以及默认会监听的 Provider.of，都从当前 Element 向祖先查找最近的那个，并把当前 Element 登记为依赖者。updateShouldNotify 返回 true 时，重建的是这些依赖者。
  • Navigator.of、context.read、findAncestor* 只向上查找，不登记依赖，当时能读到当前值，之后变化不会通知。
  • initState 里 context 已经有了，但还不能做这种查找并登记，要放到 didChangeDependencies 或 build。发请求和跳转不要放进 build。

解析

BuildContext 是 Element 对外露出的接口，一张位置凭证。查找走的是 Element 树，不是在 Widget 配置对象上递归。

要跟着主题、MediaQuery、Provider 变，在 didChangeDependencies 或 build 里用 of。只取一次当前值，用不登记的读法，并接受它不会再通知你。跳转、发请求、订阅放生命周期或点击回调。异步回来再用 context，先看 context.mounted（State 里用 mounted）；跨 await 使用 context 的 lint 就是 use_build_context_synchronously。State 和 Element 断开之后，这张位置凭证不能再当树上的位置用。

initState 里禁止 depend 的检查，在 debug 下会用 assert 拦住。这是框架约束。release 拿掉 assert，不表示这个时机突然变得正确。State 通过 context 找到自己的 Element，context 不是 State 的别名。

18. Key 有什么用

口述版

  • 同一个父节点下，runtimeType 和 key 都相同，才复用原来的 Element。没有 Key 时按位置和运行时类型匹配。列表只是换了顺序，State 留在原来的下标上。
  • 列表项用 ValueKey，相等比较走 ==。ObjectKey 用 identical，内容相同的两个新对象比较不成立。UniqueKey 每次都是新对象，写在 build 里，旧 Element 不会被复用，旧 State 每次都被丢掉。
  • 本地 Key 只在同一个父节点的孩子之间比较。
  • GlobalKey 登记在全局表里，同一个 key 整棵树只能挂一处。换父节点时可以把原来的 State 挪过去，也能拿到 currentState。不适合当日常状态管理。

解析

Key 解决的是同一次更新里，「这个父节点下面，哪个孩子还是上次那个孩子」。它不解决滑出屏幕后保不保活。

ObjectKey 用 identical，ValueKey 用 ==。这是这两个类自己的相等实现，不要记反。两个内容一样、但是新创建的对象，ObjectKey 对不上。UniqueKey 每次都是一个新身份，用来故意丢掉旧 State。写在 build 里，旧 State 每次都被丢掉。

列表每一项的 State 串了，给每一项加 ValueKey(item.id)，不是给整个 ListView 加一个 Key。本地 Key 只在同一个父组件的子组件之间比较。换了父组件还要留 State，才考虑 GlobalKey。GlobalKey 能在换父节点时把 State 挪过去，也能拿 currentState、currentContext、currentWidget，代价是全局登记。复用 Element 能少做销毁和创建，但 Key 本身不是一项渲染加速开关。

19. 滑出屏幕后，状态怎么留住

口述版

  • ListView、TabBarView、PageView 这类会懒构建的组件，子项离开缓存范围后会从树上卸掉，State 跟着 dispose。
  • 要留住 State，就混入 AutomaticKeepAliveClientMixin，wantKeepAlive 返回 true，并在 build 里先调用 super.build(context)。不调用这一步，就不会向祖先登记保活。
  • 登记之后，子节点离开缓存范围仍然留在树上，只是不再绘制。这是用内存换保留 State，不是让它继续显示在屏幕上。
  • 只需要保留滚动位置时，用 PageStorageKey。wantKeepAlive 后来变成 false，要调用 updateKeepAlive()。普通 Column 里的孩子本来就不会因为懒构建被卸掉。

解析

Key 管同一次更新里的身份，保活管滑出缓存范围之后还拆不拆工位。

class _TabState extends State<TabPage> with AutomaticKeepAliveClientMixin {
  @override
  bool get wantKeepAlive => true;

  @override
  Widget build(BuildContext context) {
    super.build(context);          // 不调用就不会登记
    return const Text('kept');
  }
}

保活是 AutomaticKeepAlive 和可滚动组件之间的约定。忘了 super.build(context)，wantKeepAlive 不会生效。列表的缓存范围、Tab 是否预加载相邻页，依组件和参数而定，不要说成「滑出一像素就一定 dispose」。保活不是让它继续画在屏幕上，只是离开缓存范围后仍留在树上。它用内存换「不要销毁」，包太多会更占内存，不是渲染优化开关。只需要滚动偏移时，用 PageStorageKey 就够。

20. 热重载和热重启

口述版

  • 热重载在 debug 里有。手机和桌面把改过的库送进正在运行的 isolate，靠的是 JIT。Web debug 从 Flutter 3.35 起默认也有，走浏览器里的开发编译器。
  • 两边都不重跑已经执行过的 main 和 initState，原来的 State 还在，然后走 reassemble 再 build。
  • 已经初始化的全局变量和静态字段、枚举的形状、泛型签名、原生代码，这次热重载替换不了。
  • 热重启会重新执行 main，State 重新创建，但不会把原生工程重新装一遍。改了插件、资源或原生代码，要完全重新启动进程。
  • 手机和桌面的 profile、release 是 AOT，没有热重载。Web 的 release 是 JavaScript 或 Wasm，同样不能热重载。

解析

热重载是在还活着的进程上打补丁，然后重新 build，口袋里的 State 尽量留着。热重启是把 main 再走一遍，口袋清空，但原生工程不重装。

手机和桌面的 debug 是 JIT，边运行边编译。profile 和 release 是 AOT，提前编译成机器码。这是工具链，不是 Dart 语法。热重载会找出改过的部分、送进正在运行的程序、再重建 Widget。它不是只把画面重画一遍，也不是把应用关掉再打开。改了 initState 没效果，是因为旧 State 还在，不是热重载失败。debug 能热重载，不能用来证明 release 的性能。

Web debug 从 Flutter 3.35 起默认也有有状态热重载，实现是浏览器里的开发编译器，不是上面这套 VM JIT，同样不重跑 main 和 initState。Web 的 release 是编译成 JavaScript 或 Wasm，不要把手机上的 JIT / AOT 原句套过去。Web 的 release 同样不能热重载。

21. InheritedWidget 是干什么的

口述版

  • InheritedWidget 把数据放在祖先节点上。
  • 子组件用 dependOnInheritedWidgetOfExactType，或 Theme、MediaQuery 的 of，或 Provider 的 watch，会找到最近的那一个，并把当前 Element 登记成依赖者。
  • 祖先换成新的 InheritedWidget 之后，只有 updateShouldNotify 返回 true，才通知这些依赖者重建。返回 false 时，新配置会换上，已经登记的依赖者也不通知。
  • 只向上查找、不登记依赖的读法，例如 Provider 的 read，当时能读到当前值，之后变化不会触发重建。这种登记不能写在 initState，要放在 didChangeDependencies。
  • 只想按某个字段通知，用 InheritedModel 和 aspect；想直接监听一个 Listenable，用 InheritedNotifier。

解析

数据放在比较靠上的位置之后，谁登记了依赖，谁才会因为这次通知而重建。没登记的人，只是当时读到了值。

通知本身不是把 InheritedWidget 下面的所有节点一律标脏。InheritedWidget 自己的 child 如果在父级重建时还是同一个 Widget 实例，子树可以走普通的 identical 跳过。如果父级每次都 new 一个新的 child，那是普通的父级重建，和「通知依赖者」不是同一条路径。

依赖粒度可以更细：InheritedModel 用 aspect 区分同一个模型里的不同字段，只有 updateShouldNotifyDependent 认为相关的依赖者才重建；InheritedNotifier 把 Listenable 和 InheritedWidget 合在一起，notifyListeners 时通知依赖者。

Provider 是 InheritedWidget 外面的写法。数据怎么顺着树传下去，根子还是 InheritedWidget。这是封装，不是另一套渲染机制。读的位置必须在 Provider 下面。沿树向上找不到，就不是「数据没刷新」。initState 里调用 of 是时机错了，不是 InheritedWidget 不能在第一帧读。

22. 状态管理怎么选

口述版

  • 先看状态放在哪、谁会被通知、重建的是哪一段、状态要保留多久。
  • 只在这个 State 的字段里，用 setState，它只把当前 Element 标成需要 build。还想把重建缩到一个值，用 ValueNotifier 和 ValueListenableBuilder。
  • 沿 Element 树向下共享，用 InheritedWidget 或 Provider。watch 会 depend，read 不登记。读的位置必须在 Provider 下面。
  • Provider 底下通常是 ChangeNotifier：状态变化后 notifyListeners，Consumer / watch 的界面重建；只想听一个字段用 Selector。
  • Riverpod 把状态放在独立的 Provider 容器里，不从 BuildContext 向上找。ref.watch 配 select 可以只订阅一个字段。代码生成的 @riverpod 默认 autoDispose，手写的普通 Provider(...) 默认不会，要写成 Provider.autoDispose。
  • Cubit 在业务对象里用方法交出新状态。Bloc 再多一层事件，BlocBuilder 用 buildWhen 决定要不要重建。
  • GetX 常把状态、路由和依赖放在一起。这次重建是哪个对象触发的，不能像 markNeedsBuild 或 buildWhen 那样直接指出来。选型就看状态放在哪、通知了谁、重建范围能不能说清。

解析

setState 只标记当前 Element。InheritedWidget 只通知依赖者。这些重建范围是机制，不是换一个库就会自动变小。

「select 能少重建」依赖你真的只订阅了那个字段。父级如果整页 setState，下面的优化可能根本走不到。事件要按类型展开用 Bloc，只是几个方法改状态用 Cubit 就够。跨页面、不希望绑着 BuildContext、逻辑要单测，用 Riverpod 或 Bloc。团队已经统一某个库，先服从团队，再讲你知道的边界。

Provider 的常见实现是 InheritedWidget 包一个 ChangeNotifier。notifyListeners 触发后，Consumer、context.watch 和 context.select 的订阅者重建；context.read 不订阅。Selector 用 shouldRebuild 控制只在选中的值变化时重建。

Provider 找不到，通常是读取的位置不在它下面。read 能拿到当前值，但之后变了也不会刷新。简单页面套一整套 Bloc，和复杂业务只靠一层层 setState，都是边界选错。性能问题先看是谁在重建，不要先换状态管理库。

23. Navigator 和 MaterialApp 做了什么

口述版

  • Navigator 管理的是路由栈：打开、返回、替换，以及转场。MaterialApp 会配置主题和本地化，并创建一个 Navigator。
  • Navigator.of(context) 从当前 Element 向上找最近的那个，嵌套时不一定是根上那个。
  • 直接 push 得到的是匿名路由。pushNamed 用 routes 或 onGenerateRoute 按名字生成页面。await push 等到的结果，就是下一页 pop 时交回来的值。
  • A push B 时，A 默认 maintainState 为 true，这条路由的子树仍挂在树上，不会因此 deactivate 或 dispose。只有 A 被从栈里移出才会 dispose。
  • 需要深链和 Web 地址时再用 go_router。它是路由库，不是 Navigator 的替代运行时。不要在 build 里 push，每次重建都会再打开一页。
  • 替换当前页用 pushReplacement，清掉中间页用 pushAndRemoveUntil。要拦截返回，用 PopScope（WillPopScope 已废弃）。
  • 需要声明式路由、深链和 Web 地址，用 Navigator 2.0 的 Router / RouteInformationParser，或者直接用 go_router。

解析

Navigator 是一叠页面。push 是往上再放一张，下面那张通常还在，只是被挡住。pop 才从栈上拿走，拿走的那张才会 dispose。

final result = await Navigator.of(context).push(...);
Navigator.of(context).pop(result);

页面里直接打开下一页用 push。要统一路径、深链，用命名路由或 go_router。跳转放点击回调，或者放在导航条件已经确定之后。在 build 里 push，每次重建都会再打开一页。

Navigator 1.0 是命令式 push/pop，适合页面不多的应用；Navigator 2.0 把路由栈交给 RouterDelegate 和 RouteInformationParser，适合深链和 Web。实际项目里常用 go_router 包一层。返回拦截用 PopScope 的 canPop 和 onPopInvokedWithResult，不要再写 WillPopScope。

路由动画、以及被盖住的页面是否还在继续 build，依具体 Route 和 TickerMode 而定。不要说成「被盖住就完全没有代码在跑」或「一定每帧都在 build」。go_router 是路由库，不是 Navigator 的替代运行时。栈不复杂时不必上。MaterialApp 不只是套一层视觉风格，它会把 Navigator 放好。

24. 动画怎么做，vsync 是什么

口述版

  • 某个属性只要从当前值过渡到新的目标值，用隐式动画，例如 AnimatedContainer，给出目标值和 duration。
  • 要控制开始、暂停、重复，或者由手势驱动，就自己持有 AnimationController。默认范围是 0 到 1，Tween 把进度映射成宽度或透明度。
  • vsync 的类型是 TickerProvider，一般由 State 的 mixin 提供。一个动画用 SingleTickerProviderStateMixin，同时多个用 TickerProviderStateMixin。
  • Ticker 注册的是调度器的帧回调，一帧回调一次，不是用 Timer 自己计时。路由被盖住时，框架会把这条子树的 TickerMode 关掉，动画会停。只是滚出屏幕，或者透明度变成 0，只要 TickerMode 仍然开启，Ticker 就会继续回调。
  • AnimationController 要在 dispose 里释放，否则 Ticker 会泄漏。两个页面上 tag 相同的 Hero，跳转时在 Overlay 里放一个 shuttle 做飞行。要把同一个 Element 移到新的父节点，用 GlobalKey。Hero 做的不是这件事。
  • 把 Animation 映射成界面，用 AnimatedBuilder；它只重建 builder 里的那一段。曲线用 CurvedAnimation，区间映射用 Tween.animate。

解析

隐式动画是你只改终点和时长，框架开车。显式动画是你拿着一个 0 到 1 的进度，再映射成宽度或透明度。vsync 是屏幕每次刷新时的节拍，动画跟节拍走，不在两次刷新之间空转。

class _BoxState extends State<Box> with SingleTickerProviderStateMixin {
  late final AnimationController _controller = AnimationController(
    vsync: this,
    duration: const Duration(milliseconds: 300),
  );
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }
}

跟这个信号走的计时器叫 Ticker。一个 State 只有一个动画，用 SingleTickerProviderStateMixin。要同时跑好几个，用 TickerProviderStateMixin。Ticker 停不停，看的是 TickerMode.of(context)。路由被盖住时框架会关掉 TickerMode，所以被盖住的页面上的动画会停。列表里滚出屏幕、子树里没有 TickerMode(enabled: false) 的 Controller 会继续 tick。这是 mixin 配合 TickerMode 的行为，不要把它说成「页面不可见操作系统就会让动画暂停」。不 dispose Controller，Ticker 会漏掉。这和 Widget 能不能 const 无关。

AnimatedBuilder 的 child 参数可以放不随动画变化的部分，避免每次 tick 都重建整棵子树。曲线用 CurvedAnimation 包一层，区间映射用 Tween.animate，多个动画可以用 Interval 编排。AnimationStatus 用来在 completed / dismissed 时做下一步。

隐式动画省事，但做不了手势驱动和复杂编排，也不好把几段接起来。tag 相同的两个 Hero，飞行发生在 Overlay 的 shuttle 上，不用自己算两边的坐标。这不是把原来的 Element 重新挂到新页面上；要挪同一个 Element，用 GlobalKey。屏幕是 120Hz 时节拍更密，前提是设备真的在用这个刷新率。刷新率是否生效，依设备和平台配置而定。

25. 布局时，约束和尺寸怎么传

口述版

  • 父组件把宽高的允许范围传给子组件。子组件在这个范围里决定自己的大小并交回去。子组件不能自己决定位置，位置由父组件设置。
  • 子组件报出的尺寸超出范围时，debug 里 assert 会在布局阶段失败。profile 和 release 会去掉这段 assert，但协议上仍然不允许。viewport 和 Flex 遇到无界约束，抛的是 FlutterError，release 里也会抛。
  • 这个范围的类型是 BoxConstraints。某一维最小等于最大，就是紧约束，这一维的尺寸由父组件确定。
  • Expanded 会把分到的主轴空间占满。Flexible 默认 fit 是 loose，分到的空间只是上限，子组件可以更小。两者都必须放在 Row、Column 或 Flex 里。Flexible 把 fit 设成 tight 时，和 Expanded 一样要把分到的空间占满。
  • 纵向 ListView 沿滚动方向给孩子的最大高度是无限。Column 里直接放这个 ListView，会因为高度无界而失败。Expanded 直接作为 ListView 的孩子，先抛出的错误是父组件必须是 Flex。
  • 列表放进 Column 时，要先给它一个有限高度，而且外层 Column 自己的高度也得有限。子项很多时不要用 shrinkWrap，它会为了算出自己的尺寸一次布局很多孩子。文字在 Row 里溢出，是这一维没有有限的最大宽度。
  • 要根据父级给的实际尺寸决定布局，用 LayoutBuilder。想按孩子的固有尺寸来，用 IntrinsicHeight / IntrinsicWidth，它们会多量一遍，代价高。
  • 固定宽高比用 AspectRatio，按比例缩放用 FittedBox，给子组件加额外约束用 ConstrainedBox。

解析

尺寸不是子组件单方面宣布的，位置也不是子组件自己定的。子组件尺寸超出 constraints 的检查在 assert 里，debug 会失败，profile 和 release 拿掉 assert 后不会因此抛错。viewport 和 Flex 的无界约束是 throw FlutterError，release 里仍然会抛。这不是一项可以关掉的优化。

Column(
  children: [
    Expanded(child: ListView.builder(...)), // 外层高度有限，列表才有上限
  ],
)

Column 里放纵向 ListView，报无界高度，是因为列表还要一个有限的最大高度，外面沿滚动方向给不出这个上限。给列表一个有限高度，例如外包 Expanded，而且外层 Column 自己的高度也得有限。纵向滚动组件里面再放一个自己也要无限高的 ListView，是同一类无界。Expanded 必须放在 Flex 里；Flex 的主轴最大尺寸无限时，Expanded 报的才是无界约束。把它直接放进 ListView，先遇到的是父组件必须是 Flex。

LayoutBuilder 拿到的是父级传下来的 BoxConstraints，适合按可用宽度切换布局。IntrinsicHeight / IntrinsicWidth 会先问孩子「你最小能多高/多宽」，再按这个值布局，孩子多或嵌套深时开销明显。AspectRatio、FittedBox、ConstrainedBox 都是在现有约束上再做一层换算，不改变「约束向下、尺寸向上」的协议。

子组件想自己决定在父组件里的位置，做不到。用 Align、Center、Positioned 这种父布局。能跳过子树布局，是因为约束和尺寸没有变，RenderObject 可以标记为不必重来。那是框架优化，协议本身不变。shrinkWrap 让滚动组件按孩子把自己的尺寸量出来，项很多时会一次布局很多孩子，不要拿它当默认解法。

26. Widget、Element、RenderObject、Layer 和一帧渲染

口述版

  • Widget 是不可变配置，build 时会新建，Widget 自己不绘制。
  • Element 持有当前 Widget，有状态时保存 State。runtimeType 和 key 都相同，就更新原来的 Element；有一个不同，就换成新的。
  • RenderObject 做布局、绘制和命中测试。Layer 是合成层。大多数 RenderObject 画进当前层。RepaintBoundary 会单独成层；Opacity 在非全透明时推 OpacityLayer；Transform / Clip 只有在需要合成时才成层；PlatformView、BackdropFilter、ShaderMask 等也有自己的层。
  • 一帧里如果这些阶段都要走，顺序是 build、layout、paint，然后合成、光栅化。没有人调用 markNeedsBuild，这一帧可以不 build。某一帧也可以只有 layout，或者只有 paint。
  • build 调用得多，不等于绘制树全量重建。RepaintBoundary 让一块区域单独成层重画。每一块都成层会多占内存，合成也更贵。

解析

四个角色分开：配置、活着的树节点、布局绘制、交给合成的层。不要说 Element 永远不会重建。

这是三棵树的分工，不是编译优化。某一帧只做被标脏的阶段：没有人 markNeedsBuild，这一帧可以不 build；只有 markNeedsPaint，就只重画。配置没变的 RenderObject 在布局或绘制阶段里还可以再跳过自己。build 调用得很频繁，不等于整棵绘制树都重建，也不表示 Layer 和像素每次都全量重来。没有 Key 的列表只是换了顺序，同一层按位置和类型对上号，State 可能留在原来的格子上。框架不会按业务 id 认出列表项。

层不是按 Widget 类型一刀切的：RepaintBoundary 的 isRepaintBoundary 为 true，会单独成层；RenderOpacity 只在 0 到 255 之间推 OpacityLayer；RenderTransform 和 RenderClip* 只有在 needsCompositing 为 true 时才创建对应的层，否则只是在 canvas 上做变换或裁剪。PlatformView 的 TextureLayer、BackdropFilter、ShaderMask 也各自成层。不要把「成层」说成只有某几个 Widget 才会发生。

某一小块经常重画，给它 RepaintBoundary。每一块都单独成层会多占内存，合成也更贵，不要到处包。BuildContext 也不是 Widget。

27. 线程模型，以及高刷新率上怎么看掉帧

口述版

  • 手机和桌面上，平台线程、界面线程、Raster、文件线程这四条由 Embedder 创建。主 isolate 跑在界面线程上，做 build、layout、paint。
  • Raster 把图层合成再画成像素交给 GPU。旧文章里的 GPU 线程指的是这一条，不是显卡本身。图片解码在文件线程上。
  • Web 没有同一套四条线程。
  • 120Hz 时一帧预算大约 8.3 毫秒。掉帧用 profile 的帧图分清时间在界面线程还是画像素线程。debug 的帧时间不能当成正式包。
  • 第一次用到某种绘制效果，可能要临时编译着色器，时间花在画像素这一步。Impeller 提前准备这些绘制程序，就是为了减少这种临时编译。spawn 出来的 isolate 不属于这四条线程。

解析

下面这四条是移动端和桌面 Embedder 的线程。Web 不按 Platform、UI、Raster、IO 来分。先分清各自干什么，再看这一帧的时间花在 UI 还是花在光栅。不要把 isolate 和这四条线程说成同一套东西。

用 DevTools 的帧图区分是 build、layout 慢，还是画成像素这一步慢。测量用 profile。debug 本身更慢，不能当成正式包的帧时间。debug 不掉帧不能说明 release 没问题，反过来也一样。

第一次用到某种绘制效果，GPU 可能要临时编译着色器，卡在画像素这一步。Impeller 提前准备这些绘制程序，就是为了少做这种临时编译。着色器预编译、Impeller、光栅缓存，是引擎为了减少卡顿做的实现。它们不是「Dart 单线程所以不会掉帧」。60Hz 大约 16.7 毫秒一帧。Flutter 能跟上的前提是这一帧做完了，而且系统允许这个刷新率。

主 isolate 跑在界面线程上。再用 spawn 开出来的 isolate，不归这四条线程编制，框架也不替你统一管理。把 Raster 线程直接叫 GPU，容易让人以为卡在显卡上。掉帧不一定是 Dart 慢，也可能是光栅、着色器或图片解码。

28. 什么时候自定义布局

口述版

  • 先用现有 Widget 组合。只有绘制的形状特殊，才用 CustomPaint。位置和大小仍然交给现有布局。
  • 排列规则用 Row、Column、Stack 都表达不了，才实现 RenderObjectWidget 和 RenderBox，重写测量、绘制和命中测试。
  • Widget 是配置，Element 负责挂到树上并更新，RenderObject 真正做布局和绘制。测量结果必须落在父组件给出的约束里。自己在父组件中的位置由父组件决定。不要在 paint 里修改布局。
  • 还要提供 semantics。交给父布局的数据放进 parentData。isRepaintBoundary 决定这块会不会单独成层。单独成层可以减少相邻区域一起重画，同时会增加内存和合成成本。

解析

组合是用现成的积木搭。CustomPaint 是在一块已经布好局的区域上画画。自定义 RenderObject 是连「怎么量、怎么摆」都自己定，但仍然要服从父组件递下来的约束。自定义 RenderBox 也不能违反约束向下、尺寸向上、父定位置。

能用 Row、Column、Stack、Padding、CustomPaint 拼出来，不要写 RenderObject。继承一个 Widget 再重写 build，那是组合，不是自定义布局协议。不要在 paint 里偷偷改布局，下一轮约束会对不上。一上来写 RenderObject，通常是把能组合的东西复杂化了。

isRepaintBoundary 决定这块会不会单独成层。成层能少带动别人重画，也会增加内存和合成成本。它是取舍，不是写上就更快。

29. 一次点击为什么只有一个组件响应

口述版

  • 手指按下后，先做命中测试，得到从最里层到外层的一条路径。
  • 这条路径上，GestureDetector 注册的识别器进入手势竞技场，最后只有一个胜出。父子都写了 onTap 时，通常只有子组件的识别器胜出。
  • 手指抬起时如果还没分出胜负，先加入竞技场的那个胜出。命中路径从里向外加入，所以一般是更靠里的子组件。列表里的按钮和滑动会竞争：移动超过 slop 之后，滑动胜出，点击被取消。具体像素随设备和手势设置变化。
  • 父组件只观察指针、不参与竞争时，用 Listener，它不进入竞技场。behavior 设成 HitTestBehavior.opaque 时，空白区域也算命中自己。

解析

一次点击先做命中测试，再进手势竞技场。最后只有一个胜者，所以不是「事件丢了」，而是竞争分出了胜负。这不是事件系统随机丢事件，也不是编译器优化。

「先加入的获胜」是抬起时仍未分出胜负的规则。命中路径从里向外加入，所以一般是更靠里的子组件。如果某个识别器更早宣布自己胜出或失败，例如滑动超过 slop，就按那个结果，不必等到抬起。手势阈值的具体像素依设备和手势设置而定，说出「超过一小段移动，拖动赢、点击取消」即可，不要背死一个魔法数字。

父组件只是想知道手指在自己范围内动过，用 Listener，不要再加一个 onTap 去和子组件抢。透明区域也要点中自己，用 behavior: HitTestBehavior.opaque。不是父组件收不到指针，而是 onTap 这种识别器在竞技场里输了。列表滑动把按钮点击取消，是竞争结果，不是点击事件丢失。

六、混合与构建

30. Flutter 如何和 Android / iOS 通信

口述版

  • Platform Channel 传的是异步消息。参数和返回值按 codec 编解码，两边不共享原生对象。
  • 一次方法调用对应一个结果，用 MethodChannel。原生侧连续上报、Dart 侧得到 Stream，用 EventChannel。消息不限定成一次请求一次返回，用 BasicMessageChannel。
  • StandardMessageCodec 可以直接编码的是 null、布尔、数字、字符串、字节数组，以及 List 和 Map。自定义对象要先拆成这些类型。
  • Dart 这边在主 isolate，也就是界面线程上收发。原生回调默认在平台主线程上执行，Android 是主线程，iOS 是 main。耗时工作要自己移到别的线程，通道不会把这次调用自动放到后台。
  • 使用 background TaskQueue 之后，回调不在平台主线程上。这时再访问 UI，要切回平台主线程。已经有 C 或 C++ 库，或者调用非常频繁，用 dart:ffi，少一次编解码，内存布局和对象生命周期要自己保证。Activity 和权限仍然走 Channel。
  • 通道多、参数复杂时，用 Pigeon 生成类型安全的接口，少手写字符串方法名。要嵌原生视图用 PlatformView，它有自己的生命周期和合成成本。

解析

先看这次是「把消息编好异步送去原生」，还是「按 C 的调用方式直接调函数」。Platform Channel 是两边约好编码的异步信箱。FFI 是直接拨 C 函数，少一次装拆，但内存里字段怎么排列要自己管。

const channel = MethodChannel('app/settings');
final value = await channel.invokeMethod<String>('getName');

消息会按 codec 编解码，这是通道的成本，不是编译器可有可无的一步。FFI 省掉的是这次装拆，换来的是你自己保证调用约定和对象生命周期。系统界面、Activity、权限这类平台对象仍然用 Channel，不要用 FFI 硬拿。热路径上的 C 库用 FFI，并自己管内存。少了一次编解码，不代表更简单。

Pigeon 根据 Dart 定义生成两端代码，方法名和参数类型在编译期就能对上，适合通道多、团队协作的场景；它底层仍然是 Platform Channel。PlatformView 把原生视图嵌进 Flutter 的层树，性能取决于平台实现和混合模式，页面销毁时要确认原生视图也释放。

默认 MethodChannel 的原生 handler 在平台主线程上执行。通道不会把一次耗时调用自动挪到后台。要在后台处理，创建 TaskQueue 再交给 MethodChannel；从那条线程碰 UI，再切回平台主线程。Result 可以异步提交，也可以在别的线程提交。具体插件内部用 Channel 还是 FFI，依实现而定，不要说每个插件都只用 MethodChannel。EventChannel 在 Dart 侧是 Stream，不是再包一个 MethodChannel 死循环。

31. 包和插件有什么区别

口述版

  • 包是一份可以被依赖的代码。纯 Dart 的工具和 Widget，做成包即可。
  • 插件首先也是一个包，另外带有 Android、iOS 或其他平台的实现。系统能力由这些平台实现去调用。
  • 业务侧只依赖它的 Dart 接口。插件内部通过 Platform Channel 或 FFI 调用原生，用哪一种由实现决定。
  • 只给一个应用用的原生调用，写在应用自己的工程里即可。代码里有 Channel，还不等于已经做成可复用插件。要给多个应用复用，再做成插件。
  • 要给多个平台分别实现、又保持同一个 Dart 接口，用 federated plugin：一个 platform interface 包，加各平台的实现包。

解析

先问这份依赖里有没有各端实现。纯 Dart 是包。包再加上 Android、iOS 或其他平台实现，才是插件。插件首先是一个包，不是和包并列的另一种语言。pub 如何发现平台实现，是工具链的约定。

有 Channel 代码，不等于已经做成了可复用插件。它可能只是写在当前应用工程里。通道或 FFI 是插件内部的通信手段。选哪一种依插件作者而定，不是「插件」这三个字保证了只用某一种通道。业务侧只依赖它的 Dart 接口。

federated plugin 把接口和实现拆开：plugin_platform_interface 定义抽象接口，各平台包实现它，应用只依赖接口。默认实现和 endorsed 实现由 pubspec.yaml 的 plugin 配置声明，具体发现方式依 Flutter 版本和工具链而定。

32. 混合栈怎么组织

口述版

  • 整个应用都是 Flutter 时，用自己的 Navigator 即可，不需要 flutter_boost。
  • 已有原生壳、Flutter 要逐页嵌进去，才需要同时维护原生导航和 Flutter 导航。框架不会自动把两边的栈、触摸和绘制对齐。
  • 必须对齐的是：当前显示的是哪一页、触摸事件交给谁、原生页盖住 Flutter 之后绘制是否继续、引擎里的定时器是否继续运行。
  • 多个原生页共用一个引擎更省内存，但可见性和触摸要自己对齐。一个容器配一个引擎，状态彼此隔离，启动更慢，内存也更大，插件也要各注册一次。
  • flutter_boost 的做法是原生当容器，再用路由表和消息把两边对齐。新项目如果 Android 和 iOS 都用 Flutter 写，不引入它。
  • 要复用引擎，iOS 用 FlutterEngineGroup，Android 用 FlutterEngineCache 加已启动的 FlutterEngine。复用能省启动时间，但页面之间的状态隔离要自己保证。

解析

混合栈里，原生页面是外层容器，Flutter 页面画在容器里。两边要同时知道谁在栈顶、谁该接收触摸、谁被盖住之后还要不要继续画、定时器还要不要跑。没有「混合栈自动正确」这层保证。

新项目 Android 和 iOS 都用 Flutter 写，用 Navigator，不引入 flutter_boost。已有原生壳、逐页替换，才做混合栈。最容易错的是生命周期：原生页面盖住 Flutter 页面时，Flutter 还在不在画，引擎里的定时器还在不在跑。混合栈最难的通常不是把页面打开，而是盖住之后绘制和定时器有没有停。

flutter_boost 能继续用原生导航，旧页面可以慢慢换。容器怎么复用、内存、插件初始化和两边栈的同步，都要额外维护。官方 add-to-app 怎么复用引擎，依 Flutter 版本而定，不要把某个第三方库的内部实现说成框架保证。一个引擎被多个原生页共用，不是天然安全。

iOS 上 FlutterEngineGroup 让多个引擎共享已加载的 Dart 代码和字体等资源，比各自冷启动快，内存也更省；每个引擎仍然是独立的 isolate 和 Navigator。FlutterEngineCache 在 Android 上按 id 缓存已经启动的引擎，新页面直接进入预热好的引擎。复用的代价是状态：上一个页面的 Navigator 栈、全局变量和订阅还在，要么明确重置，要么按页面划分引擎。

33. 构建模式和多端产物

口述版

  • debug 用来开发界面。手机和桌面上是 JIT，assert 还在，可以热重载。这时的帧时间和包体积都不能当成正式包的结果。
  • profile 用来测量卡顿。手机和桌面上和 release 一样是 AOT，assert 关掉，但保留给 DevTools 的性能记录。Web 的 profile 是 dart2js，不是机器码 AOT。
  • release 用来上架。手机和桌面是 AOT，去掉 assert，并从 main 出发做 tree shaking，删掉确定执行不到的 Dart 代码。混淆要单独打开 --obfuscate。release 本身不包含混淆和签名。
  • Web 的产物是静态文件，Android 是 apk 或 appbundle，iOS 走 Xcode 归档，桌面是 macos、windows、linux。Web 的 release 编译成 JavaScript 或 Wasm，不能热重载，也不要把它说成机器码 AOT。

解析

模式决定有没有 assert、手机和桌面是 JIT 还是 AOT、能不能热重载。打成哪个平台是后面的打包步骤。手机和桌面的 debug 是 JIT，这两端的热重载靠它。Web debug 的热重载不靠这套 JIT / AOT。手机和桌面的 AOT 是发布构建，没有热重载。这不是语言语法，是编译模式。

tree shaking 是提前编译时从 main 看出哪些 Dart 代码走不到，再删掉，影响的是产物体积。debug 是边运行边编译，不会做同样的删除。debug 帧时间不能当成正式包，是因为 JIT、assert 还在，以及额外检查，不是因为少做了 tree shaking。混淆 --obfuscate 要单独打开。release 不等于已经混淆、已经签名。签名和混淆是另外的打包选项。着色器和启动时间也要在 profile 或真机 release 上看。debug 流畅，不能说明 release 没问题，反过来也一样。

上面说的 JIT / AOT 指手机和桌面这套 Dart 编译。Web 的 release 是编译成 JavaScript 或 Wasm，同样不能热重载，不要说成机器码 AOT。

七、性能

34. 怎样减少重建、长列表卡顿和大图开销

口述版

  • 先用 profile 的帧图分清时间在 build、layout 还是光栅。不要用 debug 的帧时间下结论。
  • build 偏长，通常是 setState 标在了过大的 Element 上。把它放到真正发生变化的那个 State 上，不变的子 Widget 写成 const。子 Widget 如果还是同一个对象，Element.updateChild 不再向下更新它。构造参数里每次都新建对象，就写不成 const，也就不会因为实例相同而跳过子树更新。
  • 长列表用 ListView.builder，滑到缓存范围附近再创建那一项的 Widget。不要用 ListView(children:)，父组件 build 时就会把整份 Widget 列表创建出来。子项高度固定时，把固定高度交给列表，避免逐项测量。子项很多时不要用 shrinkWrap。
  • 每一项的 Key 用业务 id，不要在 build 里 UniqueKey()。
  • RepaintBoundary 只包经常单独重画的小块。大图用 cacheWidth 和 cacheHeight 按物理像素解码，逻辑尺寸要乘 devicePixelRatio。
  • 压缩和算哈希放到另一个 isolate。内存先看 dispose 里有没有放开 Controller、订阅和 Timer。
  • 长列表定高时给 itemExtent，或按固定类型给 prototypeItem，估算滚动范围就不用逐项测量。复杂滚动结构用 Sliver 和 CustomScrollView，别把整页塞进一个 ListView。图片可以用 precacheImage 提前解码。

解析

先分清慢在哪一步。build 慢，是施工单写得太多。layout 慢，是一次量了太多孩子。raster 慢，是图层、模糊和像素太大。三件事的药不一样。

父组件重新 build 时，子组件还是同一个对象，框架不再向下更新它。构造参数里每次都 new 一个对象，就写不成 const，这条捷径也不会发生。在 build 里写 UniqueKey()，会让项的 State 每次都被丢掉，列表更抖。

ListView(children:) 在父组件 build 时就把子 Widget 都放进列表，项一多，这份列表本身就占内存。Element 和 RenderObject 仍然是滑到缓存范围才挂上。ListView.builder 连 Widget 也留到要显示时再造。shrinkWrap 才会为了算出自己的尺寸，一次布局很多孩子。

RepaintBoundary 能让滚动条、动画图标单独重画。每一块都是单独的一层，划得太多会多占内存，合并图层也更贵。不要在 build 里把整张原图读进内存。cacheWidth 和 cacheHeight 的单位是物理像素。按逻辑像素传入，解码尺寸会小一个 devicePixelRatio。上传前先压缩、缩小；大文件分段传，并带上进度、取消和重试。压缩和算哈希放到另一条 isolate，进度再用 Stream 或状态管理送回界面那条。

itemExtent 告诉列表每一项多高，滚动条和跳转就不用逐项测量，代价是高度必须真的固定。prototypeItem 用一项代表同类项的高度。Sliver 让头部、列表、吸顶和嵌套滚动各自管理布局，CustomScrollView 再组合它们，比在 ListView 里套 SingleChildScrollView 更容易控制。预加载要分批，别一次预加载太多。

先换状态管理库，通常解决不了根上 setState 或大图解码。测量本身要用 profile。debug 的帧时间不是正式包的结果，这是构建模式的差别。
