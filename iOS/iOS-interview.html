一、硬技术篇

1.对象方法和类方法的区别？

  • 对象方法能够访问成员变量。
  • 类方法中不能直接调用对象方法，想要调用对象方法，必须创建或者传入对象。
  • 类方法可以和对象方法重名。
  • 再深入一点说：对象方法保存在类对象的方法列表中，类方法保存在元类的方法列表中。

引伸1. 如果在类方法中调用self 会有什么问题？

  • 在实例方法中，self 指向实例对象，不能直接用它调用类方法；应通过类名调用。
  • 在类方法中self可以调用其他类方法。
  • 在类方法中self不可以调用实例方法。
  • 总结：类方法中的 self 是 Class 对象；实例方法中的 self 是指向实例对象的指针。

引申2. 讲一下对象，类对象，元类，跟元类结构体的组成以及他们是如何相关联的？

  • 对象的结构体当中存放着isa指针和成员变量，isa指针指向类对象
  • 类对象的isa指针指向元类，元类的isa指针指向NSObject的元类
  • 类对象和元类的结构体有isa，superClass，cache等等

引申3. 为什么对象方法中没有保存对象结构体里面，而是保存在类对象的结构体里面？

  • 方法是每个对象相互可以共用的，如果每个对象都存储一份方法列表太浪费内存，由于对象的isa是指向类对象的，当调用的时候， 直接去类对象中去查找就可以了，节约了很多内存空间。

引申4. 类方法存在哪里？ 为什么要有元类的存在？

  • 所有的类自身也是一个对象，我们可以向这个对象发送消息(即调用类方法)。 为了调用类方法，这个类对象的isa指针需要指向一个objc_class结构体，而这个结构体的方法列表中保存的是类方法。这个被类对象isa指向的结构体就是meta-class（元类）。因此，类方法实际保存在元类的方法列表中；元类的存在主要是为了让“类对象”和普通对象使用同一套isa消息查找机制，从而统一对象方法和类方法的查找路径。

引申5. 什么是野指针？

  • 野指针就是指向一个被释放或者被收回的对象，但是对指向该对象的指针没有做任何修改，该指针仍指向已经回收的内存地址。
  • 勘误：野指针指向的内存可能已被回收，任何解引用、成员访问、消息发送或 %@ 打印都可能崩溃；只有打印指针变量本身（如 %p）不一定解引用对象内存。样例如下

3.深拷贝和浅拷贝

  • 深浅拷贝的区别不能简化为“是否创建新对象”：浅拷贝可能创建新容器，但元素仍是引用；深拷贝会递归复制元素。
  • copy 通常得到不可变对象，mutableCopy 得到可变对象；但对集合来说，二者默认通常只复制容器本身，是否深拷贝要看元素是否被复制。
  • 勘误：mutableCopy 对集合类通常只复制容器本身，元素仍为引用复制；真正深拷贝需要按元素复制（如 initWithArray:copyItems: 或归档解档）。
  • copy 对不可变对象通常可复用原对象，对可变对象会产生新的不可变容器；是否“深”要看元素是否也被复制。

4.NSString类型为什么要用copy修饰 ？

  • 勘误：NSString 本身不可变；使用 copy 是为了隔离外部传入的 NSMutableString，避免外部后续修改影响属性值。
  • 当NSString的赋值来源是NSString时，strong和copy作用相同。
  • 当赋值来源是 NSMutableString 时，copy 会生成新的不可变副本，修改来源字符串不会影响属性值；对集合属性仍需注意元素层级是否深拷贝。

5.iOS中block 捕获外部局部变量实际上发生了什么？__block 中又做了什么？

Block 捕获外部局部变量，本质是值拷贝。编译器会把 Block 用到的外部局部变量作为成员变量追加到 Block 结构体里，初始化时传入的是变量当时的值，并且这个成员变量被 const 限定。所以：

  • Block 内部拿到的是捕获那一刻的快照，外部变量之后再变，Block 里仍是旧值；
  • 因为成员是 const，在 Block 内部不能直接给它赋值，否则编译报错。

对于对象类型，捕获的是指针的值，也就是对象地址。这个指针成员同样被 const 限定，所以可以通过它修改对象内部属性（对象在堆上），但不能给这个指针重新赋值指向别的对象。原理和基本类型一致：值拷贝 + const 限定。

加上 __block 后，编译器不再直接拷贝值，而是生成一个 __block_byref_xxx 结构体来包装原变量，Block 里存的是指向这个结构体的指针。关键在 __forwarding：Block 在栈上时访问栈上的结构体；当 Block 被拷贝到堆时，这个结构体也会被拷到堆，__forwarding 会指向堆上的新地址，栈上旧结构体的 __forwarding 也被调整为指向堆上那份。这样无论从哪边访问，最终都落到堆上同一份变量，修改才能生效。

一句话总结：普通捕获是值拷贝，成员被 const 限定，所以只读、是快照；__block 是把变量包装成结构体，让变量生命周期和 Block 绑定，Block 上堆时变量跟着上堆，并通过 __forwarding 保证访问指向正确的那一份，从而实现可修改。

如果面试官追问，可补一句：ARC 下 __block 对对象类型还涉及 retain/release 管理，以及循环引用问题，这是另一个考点。

6.iOS Block为什么用copy修饰？

  • block 是一个对象
  • 在 MRC 中，局部字面量 Block 常位于栈上。如果让它逃逸出定义作用域而没有复制到堆上，原栈帧销毁后继续调用就可能出现悬垂指针。
  • copy 会把栈 Block 复制到堆并返回可长期持有的对象。全局 Block 和静态 Block 位于全局/静态存储区，不是所有 Block 都在栈上。
  • ARC 下 block 仍可能最初位于栈上；使用 strong 属性持有时，retain/copy 机制通常会把栈 block 复制到堆，因此效果常等价。copy 能显式表达“我要把 block 移到堆上”的意图，推荐继续使用。

7. 为什么分类中不能创建完整的属性 Property（runtime 关联对象除外）？

  • 分类的实现原理是将category中的方法，属性，协议数据放在category_t结构体中，然后将结构体内的方法列表拷贝到类对象的方法列表中。 Category可以添加属性，但是并不会自动生成成员变量及set/get方法。因为category_t结构体中并不存在成员变量。通过之前对对象的分析我们知道成员变量是存放在实例对象中的，并且编译的那一刻就已经决定好了。而分类是在运行时才去加载的。那么我们就无法在程序运行时将分类的成员变量添加到实例对象的结构体中。因此分类中不可以添加成员变量。

  • 再深入一点回答：类在内存中的布局在编译/注册后已经确定， 之后再修改代码也不会改变内存中的位置，class_ro_t 的属性在运行期间就不能再改变了， 再添加方法是会修改class_rw_t 的methods 而不是class_ro_t 中的 baseMethods

引伸：关联对象的原理？
  • 关联对象并不是存储在关联对象本身内存中，而是存储在全局统一的一个容器中；
  • 由 AssociationsManager 管理并在它维护的一个单例 Hash 表 AssociationsHashMap 中存储；
  • 使用 AssociationsManagerLock 自旋锁保证了线程安全
引伸：分类可以添加那些内容？
  • 实例方法，类方法，协议，属性
引伸：Category 的实现原理？
  • Category 在刚刚编译完成的时候， 和原来的类是分开的，只有在程序运行起来的时候， 通过runtime合并在一起。

引申 能否向编译后得到的类增加实例变量？能否向运行时创建的类添加实例变量？
简要总结
  • 结论：不能向已注册到 runtime 的类添加实例变量。class_addIvar 仅对 objc_allocateClassPair 创建、尚未 objc_registerClassPair 的类有效。
  • 原因：注册后 runtime 已固定 objc_ivar_list 和 instanceSize，可能有实例分配、KVO 等依赖该布局，再加 ivar 会破坏内存布局。
  • 编译 vs 注册：编译只生成文件里的类结构数据；注册才让 runtime 接管并固定布局。分界线是注册，不是编译。编译进 App 的类随加载即注册，所以不能加；但“已创建未注册”的动态类可以加。
  • 记忆：编译决定类长什么样，注册决定布局被固定；加 ivar 的截止线是注册。
  • 替代方案：加方法用 class_addMethod；加属性用关联对象 objc_setAssociatedObject；真要加 ivar 只能动态建新类，加完再注册。
引申 主类和分类实现同名 foo 方法，主类方法会被覆盖吗？如果想只执行主类方法，如何处理？
  • 分类并不会物理覆盖主类方法。运行时按方法列表顺序查找，分类方法通常排在主类方法之前，所以同名 selector 会优先命中分类实现。
  • 如果想要明确执行不同实现，应避免同名冲突：拆分 Category、改方法名，或设计显式派发方法。不要依赖 class_copyMethodList 的返回顺序判断哪个是“原方法”。
- (void)foo{
  [类 invokeOriginalMethod:self selector:_cmd];
}

+ (void)invokeOriginalMethod:(id)target selector:(SEL)selector {
    uint count;
    Method *list = class_copyMethodList([target class], &count);
    for ( int i = count - 1 ; i >= 0; i--) {
        Method method = list[i];
        SEL name = method_getName(method);
        IMP imp = method_getImplementation(method);
        if (name == selector) {
            ((void (*)(id, SEL))imp)(target, name);
            break;
        }
    }
    free(list);
}

8. load 和 initialize 的调用情况，以及子类的调用顺序问题？

① 调用时刻：+load方法会在Runtime加载类、分类时调用（不管有没有用到这些类，在程序运行起来的时候都会加载进内存，并调用+load方法）； 运行时对每个类/分类自动调用一次 +load；开发者手动调用只是额外调用，不改变运行时的调用规则。

② 调用方式： 系统自动调用 +load 时通常直接按函数地址调用；开发者手动调用才走 objc_msgSend。

③ 调用顺序： 先调用类的+load，按照编译先后顺序调用（先编译，先调用），调用子类的+load之前会先调用父类的+load； 再调用分类的+load，按照编译先后顺序调用（先编译，先调用）（注意：分类的其它方法是：后编译，优先调用）。

① 调用时刻：+initialize方法会在类第一次接收到消息时调用。 如果子类没有实现+initialize方法，会调用父类的+initialize，所以父类的+initialize方法可能会被调用多次，但不代表父类初始化多次，每个类只会初始化一次。

② 调用方式： 消息机制objc_msgSend函数调用。

③ 调用顺序： 先调用父类的+initialize，再调用子类的+initialize （先初始化父类，再初始化子类）

  • +initialize方法的调用方式为消息机制，而非像+load那样直接通过函数地址调用。

OC在定义属性时有nonatomic和atomic两种选择
atomic：保证单个 getter/setter 的原子访问；具体实现不一定等价于 @synchronized。
nonatomic：非原子属性。

    @synchronized(self) {
       _age = age;
    }

		age1 = _age;
	}

原子和非原子属性的选择
nonatomic和atomic对比
atomic 只保证单个 getter/setter 的内存访问原子性，不保证复合业务操作线程安全。
nonatomic：非线程安全，适合内存小的移动设备

iOS开发的建议
所有属性都声明为nonatomic
尽量避免多线程抢夺同一块资源
尽量将加锁、资源抢夺的业务逻辑交给服务器端处理，减小移动客户端的压力

atomic就一定能保证线程安全么？
不能。atomic 只保证单个存取操作的原子性，不保证复合业务操作线程安全。例如一个线程在连续多次读取某条属性值时，与此同时别的线程也在改写值，这样还是会读取到不同的属性值！  或者 一个线程在获取当前属性的值， 另外一个线程把这个属性释放掉， 有可能造成崩溃

14. RunLoop的基础知识

RunLoop 的作用是什么？内部工作机制了解么？

一句话概括：RunLoop 是 iOS/OSX 里的 Event Loop 实现。它让线程在处理完当前任务后不直接退出，而是进入休眠，等待事件到来再被唤醒；同时把定时器、输入源、UI 刷新、手势、AutoreleasePool 等事件统一调度在合适的 Mode 中执行。

RunLoop 的主要作用：

  • 保持程序持续运行：主线程在应用启动时会创建并运行 RunLoop，使主线程可以一直接收事件而不是执行完启动流程就退出。
  • 调度事件：处理触摸、手势识别、Timer、performSelector、网络回调、Source 等事件。
  • 降低资源占用：没有事件时休眠线程，有事件时被唤醒，避免忙等。
  • 驱动 UI 刷新：系统在主线程 RunLoop 中处理界面刷新和布局相关任务。
  • 管理 AutoreleasePool：主线程 RunLoop 通过 Observer 在进入前创建 autorelease pool，并在即将休眠或退出时释放并重建。
  • 线程保活与卡顿监控：常驻线程依赖 RunLoop；监控主线程 RunLoop 状态也可用于卡顿检测。

结合线程与内存管理看内部机制：

  • RunLoop 和线程是一一对应的；这种关系保存在全局字典中。主线程的 RunLoop 在程序启动时默认创建，子线程的 RunLoop 是懒加载，第一次获取时创建，线程结束时销毁。
  • RunLoop 每次循环会通知 Observer 即将进入，然后按当前 Mode 找到可处理的 Timer、Source 或 Observer 回调；处理完成后进入休眠，被 mach port 或 timer 唤醒后继续下一轮。
  • RunLoop Mode 决定同一时刻哪些 Source/Timer 可以被处理。因此滚动过程中 default mode 的 Timer 可能暂停，这也是 NSTimer 常见问题的根源。
  • 主线程 RunLoop 会注册两个 autorelease pool Observer：一个在即将进入 RunLoop 时 push，另一个在即将休眠和即将退出时 pop，随后再重新 push。这解释了 autorelease 对象的生命周期和 RunLoop 的关系。

17. @synthesize 和 @dynamic 分别有什么作用

- @property有两个对应的词，一个是 @synthesize，一个是 @dynamic。如果 @synthesize和 @dynamic都没写，那么默认的就是@synthesize var = _var;
- @synthesize 的语义是如果你没有手动实现 setter 方法和 getter 方法，那么编译器会自动为你加上这两个方法。

- @dynamic 告诉编译器：属性的 setter 与 getter 方法由用户自己实现，不自动生成。（当然对于 readonly 的属性只需提供 getter 即可）。假如一个属性被声明为 @dynamic var，然后你没有提供 setter 方法和 getter 方法，编译的时候没问题，但是当程序运行到 instance.var = someVar，由于缺 setter 方法会导致程序崩溃；或者当运行到 id someVar = instance.var 时，由于缺 getter 方法同样会导致崩溃。编译时没问题，运行时才执行相应的方法，这就是所谓的动态绑定。

18. static 有什么作用?

static 主要有三个作用。

① 隐藏（内部链接）：文件作用域用 static 修饰变量或函数，就变成内部链接，只能本文件访问，其他文件引不到，常用来做私有函数和常量。

② 静态存储期：函数内的 static 局部变量只初始化一次，函数返回不销毁，所以能记录旧值，比如计数器；未初始化时默认是 0。

③ Objective-C 模拟类变量：因为 OC 不能定义类变量，常用文件作用域的 static 全局变量模拟类变量，单例里的 static id _instance 配 dispatch_once 就是典型用法。

19. objc 在向一个对象发送消息时，发生了什么？

向一个 Objective-C 对象发送消息，编译器会把它转换成对 objc_msgSend 的调用，整个过程是运行时动态查找的。

首先判断 receiver 是否为 nil，如果是 nil 就直接返回，不会崩溃。然后系统会先去接收者所属类的方法缓存里找对应的 selector，这是为了性能，因为调用过的方法很可能再次被调用。如果缓存没命中，就去类的方法列表里找，当前类没有就沿着 super_class 指针逐级往上，一直找到根类。一旦找到对应的 IMP，就跳转执行，同时把这个映射写入缓存，加速下次查找。

如果整条继承链都找不到实现，系统不会立刻崩溃，而是给你三次补救机会。第一次是动态方法解析，调用 resolveInstanceMethod 或 resolveClassMethod，你可以用 class_addMethod 动态添加一个实现。第二次是快速转发，实现 forwardingTargetForSelector，返回一个能处理这个消息的其他对象，系统直接把消息转给它，这是最轻量的方式。第三次是完整转发，先通过 methodSignatureForSelector 拿到方法签名，再创建 NSInvocation 对象，在 forwardInvocation 里你可以修改参数、目标，或者转发给别的对象。

如果这三步都没有被正确处理，系统才会调用 doesNotRecognizeSelector，抛出 unrecognized selector 异常，程序崩溃。

23. 网络协议

  • TCP三次握手和四次挥手？

三次握手（面试口述版）

三次握手是 TCP 建立连接的过程。

第一次，客户端向服务端发送 SYN 报文，带上自己的初始序列号 x，然后进入 SYN_SENT 状态，相当于告诉服务端：“我想和你建立连接。”

第二次，服务端收到后回复 SYN + ACK，确认号是 x+1，表示“你的请求我收到了”；同时带上自己的初始序列号 y，然后进入 SYN_RCVD 状态，相当于告诉客户端：“我也准备好了。”

第三次，客户端再回一个 ACK，确认号是 y+1。这时客户端进入 ESTABLISHED，服务端收到这个确认后也进入 ESTABLISHED，连接就正式建立完成了。

之所以必须是三次，主要有两个原因：一是让双方都确认自己和对方的发送、接收能力是正常的；二是防止网络中早已失效的旧 SYN 报文又到达服务端，让服务端误以为客户端要新建连接，从而白白占用资源。所以最后的 ACK 是必不可少的。

四次挥手（面试口述版）

四次挥手是 TCP 断开连接的过程。

第一次，客户端向服务端发送 FIN 报文，表示“我没有数据要发了，想关闭连接”，然后进入 FIN_WAIT_1 状态。

第二次，服务端收到后先回一个 ACK，表示“我知道你要关了”，此时客户端进入 FIN_WAIT_2，服务端进入 CLOSE_WAIT。但这时服务端可能还有数据没发完，所以它不会立刻关闭，而是先把剩下的数据继续发给客户端。

第三次，等服务端数据发送完了，它再向客户端发送 FIN，表示“我这边也没有数据要发了，可以关闭了”，然后进入 LAST_ACK 状态。

第四次，客户端收到 FIN 后再回一个 ACK，并进入 TIME_WAIT，等待一段时间后才真正关闭；服务端收到这个 ACK 后就关闭连接。

之所以需要四次，是因为 TCP 是全双工通信，客户端不再发送数据，不代表服务端也没有数据要发。所以服务端收到 FIN 后，要先把 ACK 发回去，等自己数据发完后再单独发 FIN。因此中间的 ACK 和 FIN 通常会分成两次发送，这就形成了四次挥手。

HTTP

  • 客户端接收并解析响应，然后展示给用户

HTTPS

  • 客户端向服务器发送请求。
  • 服务端将包含公钥的证书返回给客户端（公钥在证书里，并非单独返回一把公钥）。

NSTimer 循环引用 — 面试精简话术

一句话点题：scheduledTimerWithTimeInterval:target: 会强引用 target；如果 self 又强引用 timer，就形成 self ↔ timer 的 retain cycle，两边都释放不掉。

关键误区（面试加分点）：把 timer 属性改成 weak 不能解决。因为 RunLoop → timer → target(self) 这条强引用链还在，self 引用计数始终 ≥ 1，dealloc 永远不执行，也就没机会 invalidate，形成死锁。

三种解法：

  1. NSProxy 弱代理（经典方案）：继承 NSProxy 做中间人，弱引用 self，把 timer 的 target 换成代理。引用链变成 RunLoop → timer → proxy ⇢(weak) self，循环被打断。NSProxy 是专门做消息转发的根类，比 NSObject 代理走转发路径更直接高效。
  2. Block 版 API（iOS 10+，现代方案）：scheduledTimerWithTimeInterval:repeats:block:，block 内用 __weak self 弱捕获。
  3. 主动 invalidate：在合适的生命周期（如 viewWillDisappear）调用 [timer invalidate]; timer = nil;，让 RunLoop 释放 timer，进而释放 self。

收尾一句：本质是打破 timer 对 self 的强引用——要么换弱代理/弱捕获，要么主动 invalidate；只改属性 weak 是无效的。

25. 为什么 AFN3.0 中需要设置 operationQueue.maxConcurrentOperationCount = 1？AFN2.0 为什么不需要？

  • 功能不一样， 2.x是基于NSURLConnection的，其内部通过常驻线程处理异步回调。 3.0 是基于NSURLSession其内部是需要串行的鉴于一些多线程数据访问的安全性考虑， 设置这个达到串行回调的效果。
面试口述精简版

AFN 3.0 里设置 operationQueue.maxConcurrentOperationCount = 1，不是让网络请求串行，而是把这个 queue 作为 NSURLSession 的 delegateQueue，让 session delegate 回调和 completion 处理串行执行。请求本身仍然是并发的。这样做主要是为了数据安全和回调顺序：AFN 内部维护 task 和 delegate 的映射字典，本身有锁保护；并发回调会争锁、切换线程，还可能让同一个 task 的 didReceiveData 和 didComplete 乱序，所以干脆串行化回调通道，更安全也更高效。

AFN 2.0 不需要这个设置，是因为 2.0 的 operationQueue 是用来管理和发起并发请求的，不能设为 1；它的回调靠的是常驻线程 + RunLoop。NSURLConnection 的回调依赖发起请求线程的 RunLoop，所以 AFN 用 dispatch_once 创建一条全局单例线程，并往 RunLoop 里加一个 NSMachPort 防止 RunLoop 退出，从而保活线程，让所有请求回调都在这条线程上排队处理。

这条常驻线程 AFN 自己不会主动退出，生命周期基本跟 App 进程一致，App 被杀才结束。理论上可以通过 CFRunLoopStop 或 [thread cancel] 让它退出，但 AFN 正常流程不会调用；一旦停了，后续网络回调就没地方投递了。

一句话总结：2.0 是“保活一条线程，用 RunLoop 串行回调”；3.0 是“指定一个串行 delegateQueue，用队列串行回调”，用队列机制替代了常驻线程。

AFNetworking 2.0 和3.0 的区别？

  • AFN3.0 移除了所有 NSURLConnection 请求 API
  • AFN3.0使用NSOperationQueue代替AFN2.0的常驻线程

2.x版本常驻线程的分析

  • 在请求完成后我们需要对数据进行一些序列化处理，或者错误处理。如果我们在主线程中处理这些事情很明显是不合理的。不仅会导致UI的卡顿，甚至受到默认 RunLoop Mode 的影响，我们在滑动tableview的时候，会导致事件处理暂停。

  • 这里时候我们就需要一个子线程来处理事件和网络请求的回调了。但是，子线程在处理完事件后就会自动结束生命周期，这个时候后面的一些网络请求的回调我们就无法接收了。所以我们就需要开启子线程的 RunLoop 来保持线程常驻。

  • 当然我们可以每次发起一个请求就开启一条子线程，但是这个想一下就知道开销有多大了。所以这个时候保活一条线程来对请求的回调处理是比较好的一个方案。

3.x 版本不再常驻线程的分析？

  • 在3.x的AFN版本中使用的是NSURLSession进行封装。对比于NSURLConnection，NSURLSession不需要在当前的线程等待网络回调，而是可以让开发者自己设定需要回调的队列。

  • 勘误：AFN 3.0 中该 queue 是传给 NSURLSession 的 delegateQueue，串行化的是 session delegate 回调和 completion 处理，不是让网络请求本身串行下载或发送；多个 task 可以并发。

    AutoreleasePoolPage * const parent; // 父节点

27. iOS 界面渲染机制？

  • 先简单解释一下渲染机制

首先iOS渲染视图的核心是Core Animation，其渲染层次通常描述为：模型树 -> 呈现树 -> 渲染树

  • 一共三个阶段

  • CPU阶段（进行Frame布局，准备视图和图层之间的层级关系）

  • GPU/渲染服务阶段（OpenGL ES 或 Metal）， （渲染服务把上面提供的图层上色，生成各种帧）

  • GPU 阶段（合成帧缓冲并输出到屏幕）

  • 稍微详细说明

  • 首先一个视图由CPU进行Frame布局，准备视图和图层的层级关系。

  • CPU 会将处理视图和图层的层级关系打包，通过IPC（进程间的通信）通道提交给渲染服务（OpenGL和GPU）

  • 渲染服务首先将图层交给OpenGL进行纹理生成和着色，生成前后帧缓存，再根据硬件的刷新帧率，一般以设备的VSync信号和CADisplayLink（类似一个刷新UI专用的定时器）为标准，进行前后帧缓存的切换

  • 最后，将最终 要显示在画面上的后帧缓存交给GPU，进行采集图片和形状，运行变换， 应用纹理混合，最终显示在屏幕上。

程序卡顿的原因？

  • 正常渲染流程
  • CPU 计算完成后交给 GPU，在 VSync 到来时将内容渲染到屏幕上
  • 非正常（卡顿/掉帧）的流程
  • CPU计算时间正常或者慢，GPU 渲染时间过长。VSync 到来时由于没有绘制完成，CPU 开始计算下一帧，当下一帧正常绘制完成后，把当前没有绘制完成的帧丢弃， 显示了下一帧，于是这样就造成了卡顿。 需要注意的是：Vsync时间间隔是固定的， 比如 60Hz 屏幕约每 16.67ms 触发一次 VSync，类似定时器

在科普一下 1.Core Animation Core Animation 在 RunLoop 中注册了一个 Observer，监听了 BeforeWaiting 和 Exit 事件。这个 Observer 的优先级是 2000000，低于常见的其他 Observer。当一个触摸事件到来时，RunLoop 被唤醒，App 中的代码会执行一些操作，比如创建和调整视图层级、设置 UIView 的 frame、修改 CALayer 的透明度、为视图添加一个动画；这些操作最终都会被 CALayer 捕获，并通过 CATransaction 提交到一个中间状态去（CATransaction 的文档略有提到这些内容，但并不完整）。当上面所有操作结束后，RunLoop 即将进入休眠（或者退出）时，关注该事件的 Observer 都会得到通知。这时 CA 注册的那个 Observer 就会在回调中，把所有的中间状态合并提交到 GPU 去显示；如果此处有动画，CA 会通过 DisplayLink 等机制多次触发相关流程。

2.CPU渲染职能

  • 布局计算：如果视图层级过于复杂，当试图呈现或者修改的时候，计算图层帧率就会消耗一部分时间，
  • 视图懒加载： iOS只会当视图控制器的视图显示到屏幕上才会加载它，这对内存使用和程序启动时间很有好处，但是当呈现到屏幕之前，按下按钮导致的许多工作都不会被及时响应。比如，控制器从数据库中获取数据， 或者视图从一个xib加载，或者涉及 I/O 图片加载都会比 CPU 正常操作慢得多。
  • 解压图片：PNG或者JPEG压缩之后的图片文件会比同质量的位图小得多。但是在图片绘制到屏幕上之前，必须把它解码成完整的位图尺寸(通常等同于图片宽 x 长 x 4个字节)。为了节省内存，iOS通常直到真正绘制的时候才去解码图片。根据你加载图片的方式，第一次对 图层内容赋值的时候(直接或者间接使用 UIImageView )或者把它绘制到 Core Graphics中，都需要对它解压，这样的话，对于一个较大的图片，都会占用一定的时间。
  • Core Graphics绘制：如果对视图实现了drawRect:或drawLayer:inContext:方法，或者 CALayerDelegate 的 方法，那么在绘制任何内容之前都会产生一个巨大的性能开销。为了支持对图层内容的任意绘制，Core Animation必须创建一个内存中等大小的寄宿图片。然后一旦绘制结束之后， 必须把图片数据通过IPC传到渲染服务器。在此基础上，Core Graphics绘制就会变得十分缓慢，所以在一个对性能十分挑剔的场景下这样做十分不好。
  • 图层打包：当图层被成功打包，发送到渲染服务器之后，CPU仍然要做如下工作:为了显示 屏幕上的图层，Core Animation必须对渲染树中的每个可见图层通过 OpenGL/Metal 循环转换成纹理或三角形数据。由于GPU并不知晓Core Animation图层的任何结构，所以必须 要由CPU做这些事情。这里CPU涉及的工作和图层个数成正比，所以如果在你的层 级关系中有太多的图层，就会导致 CPU 每一帧的渲染，即使这些事情不是你的应用 程序可控的。

3.GPU渲染职能 GPU会根据生成的前后帧缓存数据，根据实际情况进行合成，其中造成GPU渲染负担的一般是：离屏渲染，图层混合，延迟加载。

这里又会出现一个面试题！！！ 一个UIImageView添加到视图上以后，内部如何渲染到手机上的？

图片显示分为三个步骤： 加载、解码、渲染、 通常，我们程序员的操作只是加载，至于解码和渲染是由UIKit内部进行的。 例如：UIImageView显示在屏幕上的时候需要UIImage对象进行数据源的赋值。而UIImage持有的数据是未解码的压缩数据，当赋值的时候，图像数据会被解码变成RGB颜色数据，最终渲染到屏幕上。

传统的问法来了：UIView和CALayer的区别？ 通常我们这样回答：UIView可以响应用户事件，而CALayer不能处理事件

回答这个之前， 先回顾一下另外一个经典面试题：事件响应链和事件传递？

基本概念：

  • 响应链由多个 UIResponder 对象组成，通常从第一响应者一直到 UIApplication。

  • 事件传递是获取响应链后，将事件由第一响应者向 UIApplication 传递的过程。

  • 事件的分发和传递

  • 当程序中发生触摸事件之后，系统会将事件添加到UIApplication管理的一个队列当中

  • UIApplication将处于任务队列最前端的事件向下分发 即UIWindow

  • UIWindow将事件向下分发，即UIView或者UIViewController

  • UIView首先看自己能否处理这个事件，触摸点是否在自己身上，alpha 是否大于 0.01，userInteractionEnabled 是否为 YES，hidden 是否为 NO，如果这些都满足，那么继续寻找其子视图

  • 遍历子控件，重复上面步骤

  • 如果没有找到，那么自己就是该事件的处理者

  • 如果自己不能处理，那么就不做任何处理 即视为没有合适的View能接收处理当前事件，则该事件会被废弃。

  • *** 怎么寻找当前触摸的是哪一个View?*** 下面是两个方法

// 此方法返回的View是本次点击事件需要的最佳View
- (UIView *)hitTest:(CGPoint)point withEvent:(UIEvent *)event

// 判断一个点是否落在范围内
- (BOOL)pointInside:(CGPoint)point withEvent:(UIEvent *)event

事件传递给控件之后， 就会调用hitTest:withEvent方法去寻找更合适的View，如果当前View存在子控件，则在子控件继续调用hitTest:withEvent方法判断是否是合适的View， 如果还不是就一直遍历寻找， 如果子视图均未命中，则返回自身；如果当前视图不能接收事件，则返回 nil。

// 示例：自定义 BaseView 可以重写 hitTest:withEvent:
- (UIView *)hitTest:(CGPoint)point withEvent:(UIEvent *)event {
   // 1.判断当前控件能否接收事件
   if (self.userInteractionEnabled == NO || self.hidden == YES || self.alpha <= 0.01) return nil;
   // 2. 判断点在不在当前控件
   if ([self pointInside:point withEvent:event] == NO) return nil;
   // 3.从后往前遍历自己的子控件
   NSInteger count = self.subviews.count;
   for (NSInteger i = count - 1; i >= 0; i--) {
      UIView *childView = self.subviews[i];
       // 把当前控件上的坐标系转换成子控件上的坐标系
	  CGPoint childP = [self convertPoint:point toView:childView];
      UIView *fitView = [childView hitTest:childP withEvent:event];
       if (fitView) { // 寻找到最合适的view
           return fitView;
       }
   }
   // 循环结束,表示没有比自己更合适的view
   return self;

}
